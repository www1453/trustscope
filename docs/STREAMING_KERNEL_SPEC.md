# 流式 CNN 核心 · 施工规格（文献路线）

> 2026-09-24 定。**目的**：按 Sensors 2026 那篇 Zynq-7020 设计的路线（"fully streaming,
> hand-written RTL"）把卷积核心重写成**流式结构**，而不是继续调单体循环的 pragma。
>
> **为什么必须换结构**：六次实测（见 `STATUS.md` 第八节 / `RESULTS_W1W2.md`）
> 全部停在 56–80 ms、LUT 111–121%，其中两个假设被实测否定：
> ① "权重访存是瓶颈" —— 把权重重排成 72 字节连续突发后，HLS **确实推出了突发**
> （日志 `Multiple burst reads of length 72`），**延迟只差 64 个周期**；
> ② "9 级加法链是瓶颈" —— 改成加法树后**综合结果逐位相同**。
> 剩下的唯一嫌疑：**288 个寄存器构成的完全分区窗口阵列**（LUT 115% 的来源，
> 且每周期要按 9 个不同索引取值 → 多路选择器又大又长）。

---

## 一、与前六次的**结构**差别（这才是重点）

| 维度 | 前六次 | 本次 |
|---|---|---|
| 窗口存放 | `win[3][3][32]` **完全分区 = 288 个寄存器** | **每个输入通道只保留 3×3=9 个寄存器**，滑动；行数据在 **BRAM 行缓存**里 |
| 输入通道循环 | 在窗口内部（每像素读 9 个 tap × cin） | **通道在最外层**，每次只处理**一个**输入通道，输出在 BRAM 里累加 |
| 权重 | 每 MAC 从 `m_axi` 取（或整层 9216B 全展开 → 崩） | **每个输出通道组一份小缓冲**（`OC_PAR×9` ≤ 72 字节），显式 `ram_1p` |
| 阶段间 | 全在一个函数里顺序执行 | **`#pragma HLS DATAFLOW`**：行缓存加载 / 卷积 / 池化 作为独立阶段用 FIFO 相连 |

**一句话**：前六次都在让"一个巨大的组合块"跑得快；这次是让**数据流经一串小阶段**，
每个阶段的寄存器/LUT 需求都是常数。

---

## 二、代码骨架（HLS 风格，供施工参考）

```cpp
// ---------------------------------------------------------------- 行缓存
// 3 行 x MAXW，放 BRAM，不做完全分区
static void load_rows(const uint8_t *in, int ic, int H, int W, int y, uint8_t lb[3][MAXW])
{
#pragma HLS INLINE off
    // 只加载 3 行：y-1, y, y+1（越界补 0）
}

// ---------------------------------------------------------------- 卷积阶段
// 通道在最外层：每次一个输入通道，输出在 out_acc (BRAM) 上累加
static void conv_stage(const uint8_t lb[3][MAXW], int W,
                       const int8_t wq[OC_PAR][9], const int32_t bias[OC_PAR],
                       int32_t out_acc[OC_PAR][MAXW])   // 一行的累加器
{
#pragma HLS INLINE off
    for (int x = 0; x < W; ++x) {
#pragma HLS PIPELINE II=1          // 每周期一个输出像素
        int32_t acc[OC_PAR];
#pragma HLS ARRAY_PARTITION variable=acc complete dim=1
        for (int o = 0; o < OC_PAR; ++o) { acc[o] = out_acc[o][x]; }   // 读回上次的累加
#pragma HLS UNROLL
        for (int ky = 0; ky < 3; ++ky)
#pragma HLS UNROLL
        for (int kx = 0; kx < 3; ++kx) {
            uint8_t v = lb[ky][x + kx];          // 行缓存里的一个字节
            for (int o = 0; o < OC_PAR; ++o)
#pragma HLS UNROLL
                acc[o] += (int32_t)v * (int32_t)wq[o][ky * 3 + kx];
        }
#pragma HLS UNROLL
        for (int o = 0; o < OC_PAR; ++o) { out_acc[o][x] = acc[o]; }
    }
}
```

**关键点（每一处都对应一次实测失败）**
1. `wq[OC_PAR][9]` 只有 **72 字节**，显式 `#pragma HLS ARRAY_PARTITION variable=wq complete dim=0`
   → 72 个乘法器能同时取到操作数，**但总共只有 72 个寄存器**，不是 288。
2. `acc[OC_PAR]` 只 8 个寄存器，**没有任何跨像素的窗口寄存器**。
3. `lb[3][MAXW]` 留在 **BRAM**，不要分区 —— 它的访问是顺序的。
4. 输出**逐行**累加（`out_acc`），所以通道循环可以在最外层，**但不需要重建窗口**
   （这正是前六次里"通道在外就得重建窗口"那个死结的解法：窗口是按行加载的）。
5. `#pragma HLS DATAFLOW` 放在包一层的函数上，把"加载行 / 卷积 / 池化"变成流水阶段。

## 三、必须一次只改一处（这是纪律，不是建议）

前六次里最贵的两次错误都是"一次改两处"：
- v5（整层权重 + 完全分区窗口 + 72 路展开一起上）→ **综合卡死 29 分钟**
- v2（展开 + HLS 自动展开 ic）→ **LUT 111%**

**施工顺序（每步之间必须全量综合）**
```
第 1 步  只把窗口从 288 寄存器改成"行缓存 BRAM + 每通道 9 个滑动寄存器"
         其它一律不动（不动通道顺序、不动权重、不动 tiling）
第 2 步  通道循环移到最外层 + 输出行累加   → 引入 out_acc
第 3 步  权重改成 OC_PAR×9 的小缓冲（显式 ram_1p / 完全分区）
第 4 步  加 #pragma HLS DATAFLOW
```

**每一轮必须做的事**
```
1. 主机先验：g++ 编译 tb_cnn.exe，必须仍然 200/200 bit-exact
2. 删 hls_proj 全量综合（T14：增量缓存会骗人，让你"验证"一个没生效的改动）
3. 只读三个数：延迟 / LUT / DSP
4. 不达标 → 回退到上一步的可用状态，再改一处
```

## 四、停止判据（事先写死，避免沉没成本）

| 情况 | 动作 |
|---|---|
| 第 1 步综合**卡死超过 20 分钟** | 立刻放弃该步，回到上一步；写进案例集 |
| 第 2 步后 **LUT 仍 > 100%** | 把 `OC_PAR` 从 8 降到 4 再试**一次**，仍不过则停止 |
| 第 4 步后延迟 **仍 > 10 ms** | **停止**，判定"HLS 在这颗芯片上做不了这个规模的卷积核心"，写进报告 |
| 任意一步综合结果**与上一步逐位相同** | 按 T14 处理：**先删工程全量重跑确认**，再下结论 |

**达标线**：延迟 ≤ 10 ms（宽松版：能装下且 ≤ 20 ms，就有 PS/PL 对比价值）。
**参考**：文献同芯片 4.45 GMAC/s；我们 7.8M MAC → 1.75 ms 是上限参考值。

不是"我们没做出来"，而是：
