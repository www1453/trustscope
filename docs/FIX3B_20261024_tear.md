# Fix 3b (2026-10-24) — the WIP store index was built on a wrong bit; replaced, and measured

**Result in one line: the c1066f4 approach is NOT right — CAP_FRPTR bit 4 is the LSB of a
GRAY-coded counter, not a binary one — and it is replaced by an edge-synchronised
selection. On a static scene the index-independent row detector now counts a rewrite
during the render in 2.9% of renders, against 81.6% with the positive control
(deliberately reading the store that is being written). The cost is real: the edge wait
stretches the loop from ~82 ms to ~136 ms (12.5 -> 7.3 fps). The proper fix is one line
in the block design (route `s2mm_frame_ptr_out[1]`), which needs a bitstream this session
may not program.**

## What was measured first (known-answer, not a statistic)

`MB_CMD = 6` runs `cap_order_probe()`: it writes a different canary to ROW 0 of all four
capture stores and polls all four canaries plus the parity bit from the CPU at ~370 kHz,
recording store index, parity and time of each death (`ps_fft_dual/cap_order_host_20261024.tcl`).
Three runs, same answer:

| event | store written | parity at its start | time from injection (µs) |
|---|---|---|---|
| 1 | 0 | 0 | 14,447 / 16,607 / 19,860 |
| 2 | 1 | 1 | 41,656 / 43,817 / 47,070 |
| 3 | 2 | 1 | 68,865 / 71,026 / 74,278 |
| 4 | 3 | 0 | 96,074 / 98,235 / 101,487 |

The store is written every **27.2 ms** (a ~37 fps capture), in address order 0,1,2,3. The
parity at the four stores' starts is **0,1,1,0** — the LSB sequence of a 2-bit GRAY
counter. (An earlier run of the same probe had the µs conversion off by 10x and read the
parity once per poll iteration instead of once per death; both were fixed before these
numbers. The raw log is reproducible with the script named above.)

This was cross-checked from the host without the firmware: sampling one store's row-0
word at ~16 ms intervals (`ps_fft_dual/store0_row0_20261024.tcl`) shows that store
changing every ~107 ms, and all four stores show the same period — four stores x 27 ms.
The VDMA's own registers confirm the four start addresses and CR = 0x00010003
(`ps_fft_dual/cap_regs_20261024.tcl`).

## Why the WIP index could not work

`cap_ho_sample()` counted **bit-4 edges** as if they were store handovers. Bit 4 toggles
every TWO stores, so `g_cap_wr_idx` advanced at half the store rate and had no fixed
relation to a store. Its "parity correction" compared that counter's own LSB with the
hardware bit, so it agreed by construction: measured `cap_fix = 0` for a whole boot while
the selection was wrong. The boot canary calibration sets bit 1 once from a first-death
observation, but the thing it counts (bit-4 edges) is not the thing it thinks.

The row detector (index-independent, compares 8 row sums of the store before and after
the render) said so: with the old selection, ~53% of renders saw a row change, and the
two possible selections (`index+1` and `index+3`) gave the SAME rate — logically
impossible if the index tracked the hardware, because those two stores are the
just-completed and the next one, and only one can be written during a render.

## Two independent bugs found while doing this

1. **MB_FP_INVERT (word 219) was not bounded.** The code tested `!= 0`, and the firmware
   never writes that word: after a core reset it holds DDR contents (measured
   `0xF3F1xxxx`), so **the board had been running in the deliberately-wrong inversion
   mode** with nobody having asked for it. Now `== 1` only.
2. **`MB_TEAR_ROW/MB_TEAR_ROWN` (383/384) always read 100%** because the denominator was
   incremented only on renders that had a changed row. The denominator is now every
   render (`main.c`, the tear-window close). Measured 851/851 before, meaningful now.

## What replaces the selection

The one bit can identify a store **at an edge**:

* an edge to parity **1** is store 1 starting -> store **0 just completed**;
* an edge to parity **0** is store 3 starting -> store **2 just completed**.

`cap_read_index()` waits (bounded by 3 edge intervals) until the last observed edge is at
most 1/8 of an edge interval old, then returns that completed store. It is written again
three stores later, 81.6 ms after the edge; the render is ~48 ms, so the read finishes
first. `cap_read_index_short()` does not wait — it returns the store completed at the last
edge for short reads (camera-0 statistics, reference/background copies), which are 1-2
stores old and stay untouched for at least 54 ms.

The positive control is preserved and is now stronger: `MB_FP_INVERT = 1` returns the
store that the edge just STARTED, i.e. a read that is being overwritten at that instant.

Published words: `MB_CAP_RDIDX` (373) = the store read; `MB_CAP_PARITY` (374) = the bit at
the selection; `MB_CAP_ELAPSED` (391) = microseconds from the edge to the selection;
`MB_CAP_WAITS` (392) = selections that had to wait; `MB_TEAR_WIN/NOFLIP` (389/390) split
torn renders into "a handover happened inside the render" and "no handover" — different
causes. `MB_CAP_WRIDX` (372) now reads **0xFFFFFFFF**: this bitstream has no maintainable
two-bit index, and a plausible-looking number there would be worse than none.

## The measurement (static scene, board up, this build)

`ps_fft_dual/tear_ab_20261024.tcl <mode> <n>`, cumulative counters differenced over the
window. The row detector is index-independent and, on a static scene, a nonzero row change
can only mean the DMA wrote the store during the render.

| build / mode | torn renders | renders checked | rate | dmax range |
|---|---|---|---|---|
| old selection, MB_FP_INVERT garbage (=1) | 851 counted / 851 counted (denominator bug) | — | 100% by construction | 20..52 |
| old selection, mode 0 | +68 | +128 | 53.1% | 16..52 |
| old selection, mode 1 (control) | +66 | +125 | 52.8% | 8..72 |
| **new selection, mode 0 (steady)** | **+2** | **+69** | **2.9%** | **0** (last render dmax 0) |
| **new selection, mode 1 (control)** | **+40** | **+49** | **81.6%** | 36..72 |

The control proves the detector can see a written store; the normal mode is 28x lower.
All residual torn renders are in the `win` count (a handover inside the render), none in
`noflip` — i.e. they are renders that ran long enough to reach the selected store's next
write, not a selection that read the store being written. The measured loop is 136 ms
(41.6 ms of it is the class phase containing the edge wait, 47.9 ms the render), against
82 ms before this fix.

## MB_TEAR (97/98) is not an acceptance metric and is kept only as a true statement

It counts loops in which the capture bit changed between the start and the end of the
loop. At a 27.2 ms store period the bit toggles every 54.4 ms; the loop is now 136 ms, so
an even number of toggles often cancels and the word went from 92% (old loop) to **22%**
(new loop) **without any change in tearing**. A metric that improves because the loop
got longer is exactly the kind of number this project has been burned by; the tear
acceptance rests on the row detector and the A/B above, not on 97/98.

## What is NOT verified

1. **A scene with real motion.** The row detector does not need motion to see a rewrite
   (it compares the same memory before and after the render), and the positive control
   above is a known-answer case — but the task's acceptance wording assumes motion, and
   this session cannot create it. Exact experiment for an operator: move something in
   front of camera 0 (a hand, a sheet of paper) while `tear_ab_20261024.tcl 0 20` runs;
   the row detector should stay near 0% and `MB_DIFF_CELLS` should be the thing that
   moves. If the row rate rises with motion, the residual above is larger than measured.
2. **Whether the 2.9% residual disappears when the selection is moved to immediately
   before `draw_camera()`.** That is the next code change (the selection is currently
   ~5 ms after the edge, but the touch I2C poll and `measure()` sit between the selection
   and the render; a render that runs long enough reaches the selected store's rewrite).
3. **The proper fix.** Route `s2mm_frame_ptr_out[1]` to a free `vtc_probe_concat` input
   and read it next to bit 4. That is a block-design + bitstream change (a one-line
   connection, but a rebuild, a new XSA and a re-flash), explicitly out of scope for this
   session. With both bits the selection needs no wait, no calibration and no Gray
   decoder, and the 40 ms edge-wait cost disappears.
4. **The boot canary calibration** still runs and still sets `g_cap_wr_idx`, which the
   selection no longer uses; its diagnostic words (400..407) are unchanged. The `MB_CMD=6`
   probe overwrites 400..415, so read the boot diagnostics before running it.

## Cost and safety notes

* The `MB_CMD = 6` probe and the boot calibration write four canary words into DMA
  buffers (row 0 / row 719). The probe's words are overwritten by the capture within four
  stores (109 ms); no PL or VDMA register is touched. The probe is host-triggered only.
* The loop cost is ~54 ms per iteration (82 -> 136 ms). This is the price of needing an
  edge to identify the store from one bit. It is not hidden.
* The display still updates; the build passes `check_layout.py` (0 collisions) and the
  strict loader; the board reads FWID `TSC1` with the new hash, `MB_READY = 1` and the
  no-part refusal path unchanged (`MB_REG_STATE = 2`, `MB_DIFF_OK = 5`, verdict 2).
