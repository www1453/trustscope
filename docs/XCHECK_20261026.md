# Dual-camera cross-check: what was measured on 2026-10-26 (V1, V2) and what was not

Task: decide BY MEASUREMENT whether camera 1 can reject camera-0 single-view
false positives (shadows, specular highlights) before implementing anything.
Firmware `ps_ui/main.c` (newest build, flashed by the other agent before the
window); board time was granted for one 15-minute window, 19:50-20:05.

## 0. Conclusion, with its evidence level

**E2 for V1 and V2 only.**  On this bench camera 1 does see the part, fully
inside its frame, and a fixed cam0->cam1 plane homography maps the board with a
~1 px residual that a dense edge correlation confirms.  **V3 (contaminated board
in camera 1) and V4 (the shadow positive control) are NOT measured** -- the
window did not include those states -- so **nothing was implemented**: the
brief's own gate ("implementation, only if all four pass") is not met, and the
two missing measurements are the ones that decide the feature.

Do not read this document as "the physics fails".  It says: the instrument and
the correspondence work, the shadow control is still open, and one real
camera-0-only false NG was observed on a good board (section 4) that is
suggestive but confounded and must not be quoted as the V4 result.

## 1. Instrument and how it was validated before the board

- `ps_fft_dual/xcheck_dump_20261026.tcl` -- one read-only snapshot: mailbox
  before/after, cam0's completed store, cam1's completed store (named by
  `MB_CAP_RDIDX` / `MB_CAM1_STORE`, range-checked), the live mask.  connect +
  mrd only; no rst, no dow, no mwr, no VDMA access.  ASCII only, parses as one
  complete Tcl script, exercised end to end against a hardware-free stub.
- `dl/host_qc/xcheck_capture.py` -- runs it, enforces exact dump sizes, writes
  `capture.json`.
- `dl/host_qc/xcheck_analyze.py` -- SIFT+RANSAC homography on the board ROI,
  two independent dense checks, the camera-0 DAREA rule recomputed offline, and
  the same rule applied to camera 1 against a camera-1 reference.
- `dl/host_qc/xcheck_summary.py` -- one table from the capture directories.

Known-answer tests (all passed): a real board frame warped by a known H is
recovered to 0.16 px max at the board corners (RMS 0.39 px); a +55 grey patch
injected into both views reads 15 cells in camera 0 and 15 in camera 1; the
board-motion compensation takes a deliberately-shifted pair from 549 false
camera-1 cells to 0.

The pair image `dl/xcheck_20261026/png/pair_cam0_cam1.png` shows the same belt

## 3. V2 -- can a correspondence be estimated  (E2 for the still board)

| quantity | value |
|---|---|
| SIFT inliers on the board ROI | 103 (144 good matches of 1282/2755 keypoints) |
| reprojection RMS | **1.12 px** (0.25 % of the 448-px part width) |
| dense edge-NCC peak vs H's prediction | offset **(0, 0)** within a +-24 px search, NCC 0.547 |
| implied disparity / scale at the board | +177 px in x, ~1.19 scale |

`dl/xcheck_20261026/png/edge_overlay.png` is the evidence: cam0's edges warped
by H (red) over camera 1's edges (green).  The PCB's traces and pads coincide
(yellow) across the whole board, while the belt and the background do not -- the
signature of a correct plane homography with real parallax elsewhere.

The two mapping methods are both reported because the first estimate of this
session was WRONG in an instructive way: a whole-panel feature match fitted the
FLOOR plane and produced a self-consistent near-translation.  The dense edge
peak is the acceptance test now; a plain template search is kept only as a
coarse locator (it is explicitly labelled NOT evidence below score 0.65).

**Not measured: the placement half of V2.**  The brief asks for the mapping to
be tested by moving the part a known amount.  The window did not include a
second placement, so the fixed-H prediction across placements is still open.

## 4. Side finding: a real camera-0-only false NG on a good board (E1-E2, confounded)

During the window the good board read NG: `MB_DIFF_DAREA` 11 then 10,
`MB_LOCAL_VERDICT` 1, with `MB_DIFF_DX/DY` = -2.0/-13.9 px then -2.4/-15.8 px
(the board was 14-16 px off the reference vertically).  I dumped the firmware's
own reference image (`REF_BASE`, read-only) and replayed the camera-0 comparison:

- the deep group is a 40 x 24 px patch at cam0 source px **(448,400)-(488,424)**,
  14 cells, peak |d| 107 grey (firmware: 11 cells, 102 grey);
- the patch sits immediately under the belt edge, at the top of the board;
- in camera 1, at the same physical place (mapped through H), the patch's local
  contrast against its surround is **+1.4 grey**, against **-7.7 grey** in
  camera 0.  It does not stand out in camera 1.

This is *consistent* with a camera-0-only artefact, and a two-view check would
demote it to "single-view anomaly".  It is NOT reported as the V4 result, for
three stated reasons: (a) it is one patch observed in two captures 30 s apart,
not a controlled shadow; (b) it sits at a mask/background edge, so a mask
artefact and a lighting artefact look the same in one capture; (c) the board is
14-16 px off the reference, so it may be a placement/edge residual that a
correctly seated board does not show.  The next window should re-seat the board
for a PASS first, exactly as the protocol says.

## 6. What was implemented

**Nothing.**  The firmware was not modified; no bitstream, no power cycle, no
VDMA access, no mailbox writes.  V3 and V4 are unmeasured, so the brief's gate
is not met.  `dl/XCHECK_20261026_design.md` holds the conditional minimal
pipeline (one fixed homography, one camera-1 reference patch in the free DDR
hole, 10 words, <1 ms per flagged comparison against the measured 167 ms
comparison, 8-10 h) for the case the missing measurements pass.

Measured cost fact that changes the loop discussion: `MB_DIFF_MS` read
55,992,504 ticks = **167 ms** for the last comparison (the 2026-10-24 build
measured 91 ms), and `MB_AVG_N` was 1 (no frame averaging), not the 8 the
acceptance used.  A camera-1 cross-check that runs only when camera 0 is about
to say NG would therefore add under 1 ms to an already 167 ms comparison.

## 7. Unmeasured -- what the second window must produce

- V3: the contaminated board against the good reference, both views' numbers in
  the mapped DAREA box.
- V4: **the gate.**  shad0 (no shadow, board PASS) then shadL and shadR with a
  shadow that makes camera 0 reach DAREA >= 8, the caster outside both frames.
  Kill criterion: C1/C0 >= 0.5 in both directions means the shadow is not
  single-view (do not build); C1/C0 <= 0.1 means it is; between is inconclusive.
- V2's placement half: the same board slid two measured amounts.
- A PASS baseline before the shadow rows (the operator re-seats the board).
- Camera 1's exposure fixed (its AEC is stuck and it clips at 55-60 per-mille).

## 9. Facts about the current firmware found while measuring

- `MB_MAGIC` (word 0) is the HOST block written by `qc_mailbox.py`, **not** the
  firmware's identity.  After the other agent's flash, before any host tool ran,
  it read 0x0FCEC95F on a perfectly healthy board.  The firmware's identity is
  `MB_FWID0..2` (word 168..170): 0x31435354 "TSC1" plus the source hash.  Any
  host that gates on `MB_MAGIC` after a flash will refuse a good board.
- `MB_CAM1_TEAR`, `MB_CAM1_TEAR_N`, `MB_CAM1_US`, `MB_CAM1_WAIT` are dead words:
  nothing increments them in the live path, so they read 0 and must not be read
  as camera-1 health.  The live camera-1 indicators are `MB_CAM1_FP`,
  `MB_CAM1_STORE`, `MB_CAM1_PTR_BAD`, `MB_CAM1_MEAN/CLIP`, `MB_CAM1_AEC_*`.
- Camera 1 has no reference frame, no per-cell difference and no DAREA-like
  number: `cam1_verdict()` (`ps_ui/main.c:10169`, called at `main.c:13071`) reads
  exposure statistics only.  The two-view numbers in this document were computed
  offline by applying camera 0's rule to two camera-1 frames.
