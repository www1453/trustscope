> ### 相机 1 帧指针：一个被丢掉的第 10 位（2026-10-23 11:4x）
>
> **症状**：`CAM1_FP` 恒为 0、`0x41230008` 恒读 0；相机 1 的读取撕裂率 74%；
> `VIEW=1` 时面板看起来"帧率显示 0"（实际 `MB_FPSX10=170`，见下文）。
>
> **取证（三次只读 BD 遍历，结论逐次修正）**：
>
> | 发现 | 证据 |
> |---|---|
> | `touch_gpio` 是**单通道** AXI GPIO | 它没有 `gpio2_*` 引脚；固件读 `+0x08` 是在读一个未实现的寄存器 → 恒 0 |
> | 相机 1 的帧指针**并没有"goes nowhere"** | `axi_vdma_2/s2mm_frame_ptr_out` 有网络，端点是 `xlconcat` 的 **In9** |
> | 相机 0 走的是另一条 | `axi_vdma_0/s2mm_frame_ptr_out` → `frmptr_slice` → `vtc_probe_concat.In4` |
> | 拼接输出 | `vtc_probe_concat_dout` 宽 **15 位 [14:0]** |
> | 它接到哪 | `axi_gpio_0/gpio2_io_i`，而该通道 `CONFIG.C_GPIO2_WIDTH = 9`，即 **[8:0]** |
> | **结论** | 相机 1 的帧指针落在 **bits [14:9]**，**全部在 GPIO 捕获范围之外 → 被丢弃** |
>
> 所以信号一直在 fabric 里，只是软件够不到。`main.c` 里"相机 1 的帧指针 goes nowhere"
> 这条注释是错的（它把"读不到"当成了"没接"）。
>
> **改动（已做，已验证持久化）**：`CONFIG.C_GPIO2_WIDTH` 9 → **15**，与拼接总线等宽。
> `gpio2_io_i` 是**内部总线、不是封装引脚**，所以不涉及 XDC、不影响引脚方向红线、没有删除任何网络。

> **新的位映射**：`CAP_FRPTR`（0x41200008）bit4 = 相机 0 帧指针（原样）；
> **bits [14:9] = 相机 1 帧指针**，其 bit0（bit9）就是 store 选择位，语义与相机 0 的 `CAP_WRBIT` 相同。
>
> 固件已改：`main.c` 新增 `CAM1_FP_SHIFT 9u` / `CAM1_FP_RAW()`，两处旧的

## 二、采集通路：今天把范围收到了只剩一处

### 2.1 唯一能真正采集的组合

| 组合 | 采集 | 触屏 | 渲染循环 |

| **09-27 `design_1_wrapper_bitpair_50m.bit` + 应用** | **✅ 18.4 fps，`CAP SR` halted=0，store 持续变化** | ❌ 位流无此 IP | ✅ 在跑 |

09-27 组合下 1 s 跳 18 次；两个完整版都是 **0 次**。

### 2.2 一条必须撤回的旧结论

交接文档写"完整版 `SR=0x00000000` 两路干净"。回看 `run_complete.tcl`：
`CAP SR` 在第 104 行读，而**传感器初始化在第 113 行**。传感器还没被叫去出图时读到干净状态，
**证明不了采集能用**。这条读数作废。

### 2.3 今天用证据排除掉的假设（不要再走回头路）

| 假设 | 怎么排除的 | 结果 |
|---|---|---|
| 传感器没在流 | 两路 chip id `0x56`/`0x5640`、表 303/303 写入、PLL `0x3035=0x21`、格式 `0x4300=0x60`；GPIO 时序位在动 | 排除 |
| 应用干扰采集 | 停掉 CPU（`rst -cores`，PL 不动）后边沿仍为 0 | 排除 |
| 第二个缓冲写进 `START_ADDR_MSB`(+0xB0) 导致 64 位越界 | `C_M_AXI_S2MM_ADDR_WIDTH=32`（hwh L2930），且把 `0xB0` 清 0 后仍 halted | 排除 |
| GPIO 方向没配成输入 | `GPIO0 ch2 TRI=0xFFFFFFFF`，bit4 = 1 = 输入 | 排除 |
| 启动模式字是 DDR 垃圾导致等交接 | `MB_BRACKET=0`（单曝光）、`MB_TIMER_OK=1`、全局定时器 delta 3.4e8 | 排除 |
| 主机写 PL 被 MMU 挡导致配置没生效 | 冷启动后**装应用之前**写通道（`write errors: 0`），仍 halted | 排除（但热 poke 确实不可靠，见下） |
| PS7 的 HP 端口没使能 | `PCW_USE_S_AXI_HP0=1`、`HP1=1`，都映射 DDR 0..0x3FFFFFFF | 排除 |

### 2.4 现在剩下的唯一事实

完整设计冷启动、装应用之前、主机写全部成功的情况下：

```
CAP CR=0x00010002   (RS=0 -> 写进去的 RS=1 没有保持)
CAP SR=0x00011831   (halted=1, err_internal, err_slave, err_fsz_more, 帧计数=1)
store 0x10000000 = 50583450 34585030 50385850 58403C58  <- 有数据写进去了
frame pointer edges = 0
```

即：**写进去一帧，然后因错误自停。** 错误是 `err_slave`（S2MM 的写收到 AXI 从设备错误应答）
加 `err_fsz_more`（收到的帧比编程的 720×3840 更长）。

### 2.5 下一步应当查的位置

完整设计在"相机 → VDMA"之间多了 09-27 版没有的一段流水线：
`cam_switch` → `analyzer_fe_0` → `axis_subset_converter_*` → `rs_slice0/1` → `axi_vdma_0/S2MM`。
`err_fsz_more` 指向这段：**它送出的数据量比 VDMA 期望的多**（多了 tlast 缺失或行/像素计数不符）。

两条可行路线：
1. **查这段 RTL**：`analyzer_fe.v`（仓库里有）如何产生 `tlast`/`tuser`，`axis_subset_converter` 的
   `TDATA` 宽度与 `tkeep` 处理是否与 24-bit 匹配（hwh: `C_S_AXIS_S2MM_TDATA_WIDTH=24`）。
2. **绕开这段**：把 `alinx_ov5640_0` 的流直接接到 VDMA，先验证"直连能采集"，再逐段加回。
   这是一次 BD 编辑，但现在**构建链路已经修好**，代价可控。

## 三、方法层面的两条新坑（建议进案例集）

- **D6 兜底值伪装成有效读数**：`set v 0; catch {...}` 让"读失败"变成合法的 `0`
  （而 `CR=0` 正是"通道停止"的编码）。兜底值必须是不可能出现的值并单独标注。
- **D7 一位判据**：判"已进入 Park 模式"只查 `bit1==0`，被 `CR=0`（停止）骗过。
  正确判据是 `bit0=1 && bit1=0` 两条同时成立。
- **T48**：应用运行时从主机 `mwr` PL 寄存器不可靠（今天实测 `write_error=1` 且把显示停掉）。
  要改配置就改脚本、冷启动重跑，不要热 poke。
