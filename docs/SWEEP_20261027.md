# Board sweep, 2026-10-27 -- the operator's runbook

**STATUS: THIS PROCEDURE HAS NOT BEEN RUN ON THE BOARD.** Everything below is the
protocol the code implements, checked offline (`sweep.py --selftest`,
`sweep.py --sim`, `sweep_report.py --selftest`) and against the firmware source
(`check_words.py`: 100/100 words match `ps_ui/main.c`). The live half -- `xsdb`
reads, the prompts, the timing -- is a prediction, and section 10 says which parts
of it are unverified. Read section 3 before touching anything: those three rules
each cost this project a session.

Tools: `dl/host_qc/sweep.py` (acquisition) and `dl/host_qc/sweep_report.py`
(analysis). The numbers-only run writes the board exactly twice, `MB_CMD = 9` and
`MB_CMD = 20`; `--evidence` (section 11) adds a third, `MB_CMD = 21`, which asks for
one snapshot per board. All three are owned by the firmware. `MB_DIFF_LIM` is
**recorded, never written** by the sweep: a sweep that moved its own limit would
make its rows incomparable with each other.

---

## 1. What tonight produces

One CSV row per board, each row carrying the measurement (`MB_DIFF_DAREA`), the
group's amplitude (`MB_DIFF_DAMP`), the limit the firmware applied
(`MB_DIFF_LIM_USED`), the verdict words, the part geometry, the reference's own
quality (`MB_REFQ_*`) and the reference identity (`MB_PART_REF`). From that CSV:

* the good distribution and the defective distribution, by measurement;
* the limit the data implies, with its margin on both sides, or the explicit
  finding that the two distributions overlap and **no** limit separates them;
* the confusion matrix at the limit in force and at the suggested one;
* what the sample size actually bounds (a "0 of N false NG" result is an
  interval, never 0%).

Measured so far, and why tonight matters: the good population reads **0..8**
(three units under 8, unit #3 at 8 -- `dl/STAGE_H_20261025_registration_accuracy.md:200-205`)
and the one contaminated board reads **9** (`dl/ANOMALY_20261027.md:277-296`). At
the shipped limit 8 that is a **false NG on a good board**; at 9 nothing good fails
and the defective board is caught with **zero** cells of slack. Four good boards
and one defective cannot settle a one-cell window. Tonight's 40+ can.

## 2. Before the first board (about ten minutes)

1. **The station is already running and has been for a few minutes.** Do not
   power-cycle and do not reflash during the sweep: a new build changes what the
   words mean, and a row taken before it is not comparable with a row taken after.
   One JTAG user at a time -- do not run another host tool while the sweep runs.

2. **The firmware is the build with REFQ in it.** Check:
   ```powershell
   python dl\host_qc\check_words.py
   python dl\host_qc\preflight.py
   ```
   `check_words.py` must print `result : every defined word matches the host
   map`. `preflight.py` must exit 0 and print `PREFLIGHT PASS`. If REFQ words are
   missing, the sweep refuses to start (a reference whose own quality cannot be
   measured is not a baseline) -- that refusal is correct, not a bug.

3. **Empty belt, nothing in the frame, nobody leaning over it.** Take the
   background and check it:
   ```powershell
   python dl\host_qc\qc_inspect.py
   ```
   What a usable background looks like: `MB_BG_STATE` 1 (captured now) or 4
   (adopted from DDR), `MB_BG_MEDD` **<= 8**, `MB_PART_PTS` near 0 (the empty
   belt measures 0..9 cells, occasionally up to 85 with a belt artefact --
   `dl/AEC_EMPTYBELT_20261026.md:145-146`), `MB_PART_INVIEW` 0.
   If `MB_BG_STATE` is 0 or 5, or `MB_BG_MEDD` is over 8, the background does not
   describe this scene: re-capture it (`MB_CMD = 12`) with the belt empty and then
   check `MB_BG_MEDD` again **before** going on.

4. **Sort the boards.** Two piles and a list:

   * the **reference board**: a known-good board, in good cosmetic condition;
   * the **good** boards: provenance known, in the same orientation as the
     reference;
   * the **defective** boards: provenance known, *and you know what is wrong with
     each one*. Write the defect on a slip of paper and keep it with the board --
     you will type it in.
   * Anything whose good/defective status you are not sure of goes in a third
     pile and is **not swept tonight**. An unknown label is a coin flip in the
     confusion matrix, and the confusion matrix is the deliverable. (The tool
     cannot check a label: `g`/`d` is your keystroke and nothing on the board
     confirms it.)

5. **Write down the raw-material numbers now, before anything else:** how many
   good boards, how many defective, how many set aside, and the date/time. The
   report needs the counts even if a board later fails to be judged.

## 3. The three physical rules, and the price each one already cost

These are not style advice. Each of them has a measured incident behind it.

### 3.1 The operator leaves the frame before any capture

> **2026-10-26, the first reference after a flash read `MB_PART_REF = 480` with a
> box of `1,5..158,77` -- the WHOLE FRAME.** `MB_BG_MEDD` had read **9** (over the
> stale bound of 8) between the fresh background and that capture: the operator's
> shadow, because they were still leaning over the belt placing the board. The
> station then refused every comparison (`MB_DIFF_OK` 5, `MB_REG_STATE` 2, DAREA
> unmeasured). Once the operator stepped clear, the live mask went back to
> board-sized and a retake gave 536 with a board-sized box and PASS.
> -- `dl/AEC_EMPTYBELT_20261026.md:122-128`, which ends with the station rule:
> *take the reference only after the operator has left the frame.*

**So:** place the board, **stand back, hands out of the frame, count two
seconds**, then press Enter. The same applies to every background or reference
capture, and it applies *between* boards too: do not hover while a comparison is
being taken -- `MB_READY = 0` is what the sweep reports when the scene is moving,
and a board whose comparison never settles is a board you have to re-place.

### 3.2 The belt is verified empty before a background capture

A background capture of a belt with anything on it teaches the mask rule that the
object belongs to the belt; the "empty" count then sits at the object's size, and
every later part is masked wrongly. The check is the words, not the eye:
`MB_PART_PTS` near 0 and `MB_BG_MEDD <= 8` **after** the capture (section 2.3).

This is also why the runbook takes the background *before* the sweep and does not
re-take it during: the mask rule is part of what the comparison measures, and
changing it halfway makes the first half of the file incomparable with the second.
If the words say the background has stopped describing the scene
(`MB_BG_STATE 5`, or `MB_DIFF_OK = 4 REFUSED_CONDITIONS_DRIFTED` on every board),
**stop and ask** -- do not re-take it mid-sweep.

### 3.3 The board goes to the same spot and the same orientation every time

The comparison is against ONE reference, so placement is part of the measurement.
The registration corrects a few degrees and tens of pixels -- units were judged at
(17.9, 6.4) px, (-6.0, 8.5) px / -1.52 deg and (38.8, 16.5) px against the same
reference (`dl/STAGE_H_20261025_registration_accuracy.md:200-203`) -- but the
leftover spread is **unit-to-unit, not alignment** (`STAGE_H:205-213`), and a
board placed rotated or half off the edge is not measured, it is mis-measured.

**So:** use the same corner of the same pocket. Put the board's long edge against
the same guide. Do not re-seat a board "better" between boards -- if you do, note
it, because the row's DAREA now includes your improvement.

## 4. The run, step by step

From the repository root, in one PowerShell window, with the station running:

```powershell
python dl\host_qc\sweep.py
```

Everything the tool needs is in the prompts. In order:

### 4.1 Step A -- the reference (once)

```
    place the REFERENCE board (a known-good board, label g0) at the same spot, then press Enter>
```

Put your known-good reference board in the pocket, step back, press Enter. The
tool writes `MB_CMD = 9` and then **checks the reference before recording
anything**. A passing reference prints:

```
  reference      : MB_PART_REF=503 (floor 400)  MB_DIFF_OK=1 (COMPARED)  MB_REFQ_STATE=0 (PASS)
  refq numbers   : dark=54 part=27136 cnt=0 area=0 cov=19 thr=54 declf=0
  preflight      : PREFLIGHT PASS code=0 fail=0x00 | ref=503/400 bg(...) aec=1 clip=0 ...
  limit in force : MB_DIFF_LIM_USED=8 MB_DIFF_LIM=8 (this tool never writes it)

  REFERENCE ACCEPTED. ...
```

Read those four lines and check them against your own eyes: `MB_PART_REF` at or
above 400, `MB_DIFF_OK` 1, `MB_REFQ_STATE` 0, `PREFLIGHT PASS`. If any of them is
not what is printed above, the tool stops (section 5) and **nothing is recorded**.

Note the `limit in force` line. Write it on your sheet. It is what the report will
call "the limit in force", and it is the number tonight is arguing about.

### 4.2 Step A2 -- the reference board gets its own row

The tool asks for the reference board's label (Enter accepts `g0`) and its defect
(Enter = none). That row is the only board judged **against itself**, and the
report uses it to answer whether a map learned on one board holds on another.

### 4.3 Step B -- one board at a time

```
    board 1: place it, then press Enter  [q = finish]>
```

For each board: place it (same spot, same orientation), **step back**, press
Enter. The tool then waits for a **new** comparison that is judgeable --
`MB_DIFF_N` must change, `MB_DIFF_OK` must be 1 and `MB_READY` must be 1. While it
waits it may print lines like:

```
    MB_DIFF_N=9003 not judgeable yet: MB_DIFF_OK=1 MB_READY=0
```

That is normal: the board is still settling. **Keep your hands out of the frame**
-- `MB_READY` 0 means the scene is moving, and if it is you, it stays 0.

When the comparison is judgeable it asks for the label:

```
  board 1: label it (gN good / dN defective)>
  defect (free text, Enter = none)>
```

**The label prompt is deliberately blind:** the tool does not show you the DAREA
or the verdict before you type, because a confusion matrix built from labels that
were shown the verdict measures the operator, not the station. Type the label from
the board in your hand:

* `g7` -- good board number 7 (any number you like, as long as it is unique);
* `d3` -- defective board number 3;
* the first letter is the claim: `g` = good, `d` = defective. Nothing checks it.

Then the defect: a few words (`scratch`, `contamination`, `solder bridge`,
`missing part`) or Enter for none. It is free text and it goes in the CSV
verbatim -- it is for the person reading the file later, not for the analysis.

The row prints **after** the label, three lines, and the file is written after
every row:

```
  board 1   label=g1   good      darea=0    damp=0    limit=8   diff_ok=1(COMPARED)
            diff_n=9004    fvalid=143  ready=1 reg=1 bg=4 part(pts=590 ref=503 inview=1 edge=6 bbox=44,50..93,79)
            verdict: MB_VERDICT=0 MB_LOCAL_VERDICT=0 MB_DIFF_VERDICT=0 cam0=0 cam1=0 | refq(state=0 cnt=0 cov=19) avg(n=8 cnt=8)
```

At any placement prompt, `q` + Enter finishes the sweep and writes the summary.
Ctrl-C also finishes; the rows already taken are kept (the CSV is rewritten after
every row, atomically, so a crash cannot leave half a file).

### 4.4 Throughput, so you can plan

One board is: placement + one settling comparison (~1 s) + a full dump of 41
words plus one repeat (`--samples 2`, ~2 x 4 s on the `xsdb` path) + the prompts.
Budget **30-45 s per board**: 40 boards is 25-30 minutes, plus the reference step.
If a read is slower than the 16-frame comparison period, `MB_DIFF_N` can jump by
more than 1 between polls -- harmless: the tool wants "changed", not "changed by
one", and it records the newest comparison.

## 5. If the reference is refused

The tool prints this and stops -- the sweep does not start, and nothing is
recorded:

```
  REFUSING TO START THE SWEEP: the reference is not clean.
    1. <the failing check, in words>
    ...
  Nothing was recorded.  Re-place the reference board and run again;
  a sweep judged against this reference would measure the reference.
```

What the numbered lines say, and what to do:

| the line says | what it means | what to do |
|---|---|---|
| `MB_PART_REF=394 < 400 (PART_MIN_PTS): the reference contains no part` | the capture happened with no board in view, or the board was half out of the frame | put the reference board in the pocket, step back, run again |
| `MB_DIFF_OK=0 (NO_REFERENCE)` / `=5 (REFUSED_REGISTRATION)` | the comparison after the capture did not compare | check `MB_PART_INVIEW` / `MB_PART_EDGE` in the block above; re-place; if it repeats, `preflight.py` |
| `MB_REFQ_STATE=1 (FAIL): the reference's own surface is not clean` | the reference board has marks on it (four black marks were measured at `cnt=4 area=1076 cov=292`, against a clean board's `cnt=0 cov=19`) | **use a different reference board.** This is the 2026-10-26 incident that made every clean board read NG |
| `MB_REFQ_DECLF=1 ... DECLARED unusual` | someone left an A/B reference (or a deliberately marked board) installed | re-take the reference on a clean good board; do not sweep against a declared reference |
| `MB_REFQ_STATE ... NOT MEASURED` | the firmware is older than REFQ, or the words were never written | the build is wrong for this procedure: stop and ask |
| `the preflight predicate does not agree: PREFLIGHT FAIL \| ...` | a firmware self-test check failed: the background, the AEC, the mask or the reference | read the `PREFLIGHT` line; it names the failing check. Fix that, not the sweep |
| `the reference's comparison words did not repeat` | the scene was changing while the words were read | step out of the frame, wait, run again |

If it refuses **twice on two different attempts, stop and ask** -- do not keep
retrying, and do not "make it pass" by declaring the reference. A declared
reference is an experiment; it is not a production baseline, and a sweep against
it measures the reference.

## 6. If a comparison is refused (during the sweep)

A board whose comparison is not judgeable is **not recorded as a measurement**.
The tool prints a block like this and moves on only after you acknowledge it:

```
  ==========================================================================
  REFUSING TO RECORD board 6 (attempt 1): the comparison is not judgeable.
    no judgeable comparison in 20.0 s: 5 new comparison(s) arrived and the last one says
    MB_DIFF_OK=5 (REFUSED_REGISTRATION), MB_READY=0 (not settled enough to judge), MB_DIFF_DAREA=unreadable (no area published, so no measurement exists)
    words: MB_DIFF_N=9017 MB_DIFF_OK=5 MB_READY=0 MB_DIFF_DAREA=unreadable MB_DIFF_DAMP=unreadable
           MB_REG_STATE=2 MB_BG_STATE=4 MB_PART_PTS=590 MB_PART_INVIEW=1 MB_PART_EDGE=6
    No measurement row is written: a refused comparison is not "0 cells",
    it is no measurement at all.  The event goes to the refusals file.
  ==========================================================================
    [Enter] re-place the board and retry   [s] record the refusal and skip>
```

`MB_DIFF_OK` is the firmware's own code (`qc_mailbox.DIFF_OK_LABELS`). Match it
against this table:

| `MB_DIFF_OK` | label | the usual cause here | what to do |
|---|---|---|---|
| **1** | COMPARED | a comparison happened | if it is a row, fine; if the tool refused, the block will say why (usually `MB_READY=0`) |
| **0** | NO_REFERENCE | there is no reference (lost, or never taken) | **stop and ask**; the run is invalid |
| **2** | REFUSED_LIGHT_CHANGED | the light changed: someone crossed the frame, or a lamp changed | step clear, wait two seconds, Enter (retry) |
| **3** | REFUSED_IMAGE_UNTRUSTWORTHY | the clip gate tripped, or the AEC is stuck | `python dl\host_qc\preflight.py`; do not continue until it passes |
| **4** | REFUSED_CONDITIONS_DRIFTED | the scene drifted from the background | **stop and ask**; do not re-take the background mid-sweep |
| **5** | REFUSED_REGISTRATION | registration could not lock: part not in view, or the picture is not the one the reference was taken of | check `MB_PART_INVIEW` and `MB_PART_EDGE`; re-place the board squarely; Enter (retry) |
| **6** | REFUSED_PART_NOT_FULLY_IN_VIEW | the board is cut by the frame edge (`MB_PART_EDGE` 1) | move the board fully into the frame; Enter (retry) |

And when `MB_DIFF_OK` is 1 but the tool still refuses:

* `MB_READY=0` and `MB_DIFF_N` **advancing** -- the scene is still moving. Hands
  out, wait, retry. If it stays 0 for a minute on a still board, **stop and ask**.
* `MB_DIFF_N` **frozen** -- the block says `no new comparison in 20.0 s (MB_DIFF_N
  stayed at N)`: the comparison loop is not advancing. **Stop and ask**; do not
  power-cycle.
* `MB_DIFF_DAREA=unreadable` while `MB_DIFF_OK=1` -- the firmware says it compared
  and published no area. **Stop and ask**; that combination is a firmware bug, and
  recording anything from that board would be inventing a number.

Then the tool asks for the label anyway:

```
  board 6 was NOT judged; label it so the refusal is attributable, or Enter to leave it blank>
```

Type the label you would have given it. That is how the report can say **which**
board the station could not judge: a board the station cannot judge is a finding
about the station, not a gap in the data.

The refusal goes to `sweep_<session>_refused.csv` with every word it carried. It
does **not** go into the measurement CSV. That separation is the point: one file
is data, the other is events.

**If three boards in a row are refused, stop and ask.** Something changed at the
station (the light, the background, the reference, the board population) and
continuing produces a file of refusals, not a distribution.

## 7. Stop and ask -- the list

Stop, write down what the screen says, and ask. Do not improvise a fix:

1. The reference is refused **twice**.
2. Any `MB_DIFF_OK` of **0** (no reference) or **4** (conditions drifted).
3. `MB_DIFF_DAREA=unreadable` while `MB_DIFF_OK=1`.
4. `MB_DIFF_N` frozen (no new comparison for 20 s on a board that is placed).
5. Three consecutive refused boards.
6. The tool prints `WARNING: MB_PART_REF changed ... during the sweep` -- the
   reference was re-taken mid-run and the rows on either side are not comparable.
7. A board whose good/defective status you are not sure of -- set it aside rather
   than guess. Guessing is recorded as truth.
8. `WARNING board N: the full dump changed while it was read` (`coherent=0`) --
   the row is still written, but note the board number on your sheet.
9. Anything that makes you want to reflash, power-cycle, re-take the background or
   write `MB_DIFF_LIM` mid-sweep. **Do none of those.** Finish or abandon the
   sweep, then ask.

Abandoning is a valid outcome: rows already taken are already on disk, and the
report can run on them. A file with 12 boards and no ambiguity is worth more than
40 with a re-taken reference in the middle.

## 8. After the sweep

```powershell
python dl\host_qc\sweep_report.py dl\host_qc\logs\sweep_<session>.csv
```

It prints, by measurement: the two distributions (count, min, median, max, every
value, count per value); the limit the data implies with its margin on both sides,
or `OVERLAP` and the statement that no limit separates these boards; the confusion
matrix at the limit in force and at the suggested one, with the false-NG rate and
the detection rate; the exact 95% interval behind every rate; how many boards a
"0 of n" result needs for a given bound; and the reference board (in sample)
against the held-out good boards.

**Reading it:**

* **`SUGGESTED LIMIT: MB_DIFF_LIM (word 220) = 9`** -- the sample met the stated
  minimum (10 good, 3 defective) and the two distributions separate. The margin
  lines say how much room there is on each side. To install it:
  ```powershell
  python dl\host_qc\record.py --set-limit 9 --no-loop
  ```
  then sweep again on **fresh** boards and confirm the confusion matrix --
  a limit installed and not re-measured is a hope.
* **`NO SUGGESTION PRINTED ABOVE, AND THIS IS WHY`** -- the sample is below the
  minimum. The distributions and the window are still printed; they are
  arithmetic, not a calibration. Sweep more boards; do not write the limit.
* **`OVERLAP: ... NO limit separates these boards`** -- this is a real finding.
  It means the good and defective populations share values on this measurement,
  and no limit can pass every good board while failing every defective one. Do
  not ship a limit from that run; the report's compromise line is for information
  only. Ask before doing anything else.
* **`exit 0`** means a suggestion was printed; **`exit 2`** means no limit may be
  shipped from this run. The report never writes the board.

Keep the CSVs (`sweep_<session>.csv` and `sweep_<session>_refused.csv`) and the
report output together -- the refusal file is evidence about the station and the
report quotes it.

## 9. What this harness cannot do

Stated plainly, because the report cannot say it for you:

1. **It cannot verify a label.** `g`/`d` is your keystroke. A mislabelled board
   moves the limit, and nothing in the mailbox or on the board contradicts you.
   That is why section 2.4 sends unsure boards to a third pile.
2. **It cannot see a defect the rule cannot see.** `MB_DIFF_DAREA` is the area of
   the largest connected group of 8x8 cells whose mean differs by more than the
   amplitude threshold. The rule's measured floor is a 24 px blob, and it can see
   a 2 px-wide scratch only when it is 96 px long (`dl/ANOMALY_20261027.md:347`).
   A defective board whose defect is below that floor reads PASS, and the report
   counts it as a MISS -- correctly, because the station did miss it.
3. **It cannot judge a board against itself.** Every board is compared with the
   one reference. A good board that is far from that reference carries that
   distance in its DAREA, and these numbers cannot separate it from a defect.
   Only the reference board is judged against itself, and only it.

And one more, about the file: a row is **one comparison** of **one board** against
**that** reference. It is not the board's defect score, and the reference's
identity (`MB_PART_REF`) is in every row so a mid-sweep re-take is visible rather
than silent.

* that the firmware's `MB_CMD = 9` publishes a fresh `MB_DIFF_N` (the sweep waits

  never read that word off the board;
* everything about how long the operator takes, which is the throughput number in
  section 4.4.

## 11. `--evidence`: the same run, plus one frame per board (2026-10-27)

**What it adds.** With `--evidence`, every board that gets a row also gets one
coherent 1280x720 frame, its part mask and the two fine grids, filed under
`dl/sweep_frames/<session>/<label>/` with a `meta.json` that names the row (label,
DAREA, comparison index `MB_DIFF_N`, `MB_PART_REF`) and every check the frame
passed. The numbers CSV is byte-for-byte the same schema as without the flag; a
small ledger `logs/sweep_<session>_frames.csv` (one line per board) is written
beside it. This is the dataset the tolerance-map vs learned-model comparison needs:
without the images, the 40 DAREA numbers cannot be re-judged by any other method.

**The command, at the same point in the procedure:**

```powershell
python dl\host_qc\sweep.py --evidence
```

Everything in sections 2-4 is unchanged, with TWO additions:

1. **Before the first board**, the tool checks that the running firmware is the
   image this tree builds (`MB_FWID0..2` against `ps_ui/build_id.h`) and that there
   is room for ~3 MB per board. A mismatch stops the run before anything is
   recorded -- `MB_MAGIC` (word 0) is the HOST block and says nothing about the
   firmware, so the build stamp is the gate.
2. **After each board's numbers are printed**, the tool asks the firmware for a
   snapshot (`MB_CMD = 21`), waits for it (0 to ~2.2 s), then dumps and verifies
   ~2.8 MB (~10-13 s per board in total). It prints the cost of every frame.
   **Do not move the board until the next "place it" prompt appears.** That prompt
   is printed only after the frame is on disk; moving the board earlier would give a
   coherent frame of the belt under this board's label, which no later check can
   detect.

**If a frame is refused**, the run prints which check failed and keeps the rejected
dump under `<session>/_partial/REJECTED_...` (never in the set), then continues. It
stops only if three boards in a row produce no coherent frame -- that is a station
problem, and forty rows with no images is worse than a short run. A frame refusal
never removes the board's measurement row: the numbers were measured and are kept.

**If the reference is re-taken mid-run**, the board is refused AND the run stops:
the frames already captured would be described by numbers measured against a
different baseline, and that cannot be repaired afterwards. Start a new session with
a new reference; the old frames stay valid for the old session's rows.

**Before the run, prove the request once** on a good board, outside the sweep:

```powershell
python dl\host_qc\evidence.py --request --label probe --session probe1
```

It must print `COHERENT`, with `why=2` (host request), `cap_kind=1` and every check
ok. This is the only way to know the PASS path works before 40 boards depend on it:
the NG path (section 16 of `dl/host_qc/README.md`) proves nothing about it.

**What to watch.** The firmware copy time is printed per frame (`copy_ms`). It was
30.7 ms in the 2026-10-26 version; this version adds a word sum and a hash, and the
copy must stay well under the store's 81 ms safe window. Approaching it means the
snapshot is eating its own margin.
