## 一、实测到的现象（不是道听途说）

命令：`xsdb .tmp\touch_tri_probe.tcl`（只读，无 rst，无 fpga -f）

| 量 | 读数 | 备注 |
|---|---|---|
| DDR 邮箱 `0x10F0001C`（MB_FPSX10） | **190** | 19.0 fps，与交接的 19–20 fps 一致 |
| MB_PROGRESS (w11) | 1 | 主循环在转 |
| MB_TOUCH_OK (w87) | **0** | 固件确实写入了 0 |
| MB_TOUCH_ST (w90) | **0** | |
| MB_TOUCH_PID (w91) | **0** | 关键 |
| MB_TOUCH_EV (w88) / MB_TOUCH_ERR (w89) | 0xFFFFFFFF | **从未被写过**（只在 `g_touch_ok!=0` 时发布）→ 所以拿不到 err |

**测量通道的自检（纪律 1）**：
- 已知答案对照 1：`MB_FPSX10 = 190` 与交接文档独立记录的 19–20 fps 吻合 → 读 DDR 邮箱这条路径可信。
- 已知答案对照 2：`mrd 0x41220000` 报
  `Blocked address ... PL AXI slave ports access is not allowed`，
  且 `0x41200000/0x41210000/0x41230000` 同样被拒 → **不是本设计的问题，是 DAP 不允许直接读 PL**。
  因此 **JTAG 读不到 touch_gpio 的任何寄存器**，唯一诊断通道只能由固件自己发布（纪律 3）。

## 二、当前源码 vs 交接文档的判断

交接写：「`touch_start()` 第一行就写 `g_last_pid = 0xAAAA0000`，固件确认是新构建（FWID 对得上），
却仍读到 0 ⇒ **`touch_last_pid()` 返回的不是 `g_last_pid`**」。

复核 `ps_ui/touch.c:91`：`uint32_t touch_last_pid(void) { return g_last_pid; }` —— 返回的就是 `g_last_pid`。
`ps_ui/main.c:4104` 发布 `R32(MAILBOX+MB_TOUCH_PID*4) = touch_last_pid();`。
`python dl/build_id.py --show` = **8EE12942**，与 ELF 里的 FWID 一致 ⇒ 源码与镜像同源，不是陈旧构建。

⇒ **交接的那个推论不成立**。PID 读到 0 只说明「`g_last_pid` 当时的真实值就是 0」。
`g_last_pid` 只在三处被写成 0 以外的值：三个阶段标记、`0xEEEEEEEE`（传输失败）、以及读回的 PID。
读到 **0** 唯一自洽的解释是：**4 个 PID 字节全读成 0x00，且每一次「ACK 检测」都判定为 ACK**。

## 三、根因候选（假设矩阵，R5）

| # | 假设 | 若成立应观测到 | 若成立**不应**观测到 | 区分实验 | 成本 |
|---|---|---|---|---|---|
| H1 | **`touch_gpio` 通道 1 没有 TRI 寄存器**（导出 BD 里 `C_TRI_ENABLE` 缺失），引脚恒被驱动、`sda_read()` 恒读回 0 | PID=0、ST=0、OK=0、**ERR=0**（每次 ACK 都"成功"）、所有数据字节=0x00 | 任何非零 PID/ST；任何一次 `g_errors` 增加 | 固件写 TRI=0x3 再读回 | 低 |
| H2 | 编译器把 `0xAAAA000x` 这几条"死存储"优化掉了，标记从未落进 `g_last_pid` | PID 只会是 0 / 0xEEEEEEEE / 真实 PID | 0xAAAA000x 永不会出现 | 标记改 `volatile` 后重构建 | 低 |
| H3 | I2C 传输真的失败（`g_last_pid=0xEEEEEEEE`），是邮箱发布路径丢了这个值 | PID 应当 = 0xEEEEEEEE | PID=0 | 已读：**PID=0** ⇒ H3 被现有数据推翻 | — |
| H4 | `0x41220000` 基址/位号错，写的东西根本没到引脚 | 与 H1 同现象 | — | 读 AXI GPIO 的 IP 版本/回读 | 中 |

H1 与 H2 的现象完全相同，**必须靠"写一个已知值再读回"来区分**：这是唯一能给出"已知答案"的输入。

### 支撑 H1 的文件证据（E1，不是结论）

`submission/fpga_prize/board/design_1_bd.tcl:1090` 导出的是：

```
CONFIG.C_ALL_INPUTS {0}  CONFIG.C_ALL_INPUTS_2 {1}  CONFIG.C_ALL_OUTPUTS {0}
CONFIG.C_GPIO2_WIDTH {1} CONFIG.C_GPIO_WIDTH {2}    CONFIG.C_IS_DUAL {1}
```

**没有 `CONFIG.C_TRI_ENABLE`。** 而 git 历史显示：
- `dc92cf3`（触屏做通，实测 PID "911"）时 `bd_touch_bitbang.tcl` 写的是 `C_TRI_ENABLE {1}`、`C_IS_DUAL {0}`；
- 之后 `bd_cam1_frmptr.tcl` 把该 GPIO 改成双通道（`C_IS_DUAL {1}`），**`C_TRI_ENABLE` 就丢了**。

即：**不是触屏驱动坏了，是给相机 1 接帧指针那一步把这个通道的三态使能弄丢了。**
这与 H1 完全一致，也与「10-16 能做通、10-18 之后一直 MB_TOUCH_OK=0」的时间线一致。

## 四、预测（改动前写死）

**本次改动（固件，一次构建）**：
1. `g_last_pid` 改 `volatile`（消掉 H2）。
2. `touch_start()` 里加一段**已知答案自检**：
   - 先读 `TRI(0x04)`，写 `0x3`，再读 `TRI(0x04)`；
   - 若读回 ≠ 0x3 → `g_last_pid = 0xDDDD0000 | 读回值`，返回 -4（TRI 寄存器不存在）；
   - 若读回 = 0x3 → 读 `DATA(0x00) & 0x3`；若 ≠ 3 → `g_last_pid = 0xBBBB0000 | 该值`，返回 -3（线不是空闲高）。
3. 其余 I2C 时序一行不改（它本身经复核是正确的：`scl_line(0)`=释放、`scl_line(1)`=拉低，采样点都在 SCL 高电平期间）。

| 量 | 若 H1 成立 | 若 H2 成立而 TRI 正常 | 若 H4 成立 |
|---|---|---|---|
| `MB_TOUCH_PID` | **`0xDDDD0000`**（高位全 0）| `0xBBBB000x` 或 `0x000003XX` 之类，**绝不会是 0xDDDD0000** | 视具体而定，但 TRI 也不会读回 0x3 |
| `MB_TOUCH_OK` | 0 | 0 | 0 |

**判据**：只要 `MB_TOUCH_PID` 低 16 位在高 16 位为 `0xDDDD` 时非零 → H1 成立 → 必须改 BD 加 `C_TRI_ENABLE 1` 并重建比特流。
若 TRI 读回 0x3（即三态寄存器确实存在）→ **H1 被推翻**，不再重建比特流，转查 H4。

## 7.2 两次固件实测（都先过"新镜像是否真的在跑"的已知答案对照）

| 次数 | `MB_TOUCH_PID` | 解读 |
|---|---|---|
| 第 1 次（只测"写 TRI=3 再读回"） | `0xDDDD0000` | 写 0x3 到 `GPIO_TRI`，回读 0 |
| 第 2 次（先测功能后果再记录回读） | `0xCCCC0000` | 写 `GPIO_TRI=0x3` 后，`GPIO_DATA` 读回 `lines=0,0`；`GPIO_TRI` 回读 0 |

## 8.1 现在的判别状态（一边两个假设）

| 观测量 | 若"释放根本没生效"（i） | 若"读回的是输出锁存"（ii） |
|---|---|---|
| `GPIO_DATA` 释放后读数 | 0,0（引脚被驱动为低） | 0,0（读的是锁存，与引脚无关） |
| `GPIO_TRI` 回读 | 若寄存器存在应为 3 —— **读到 0 不符合 (i)** | 也应为 3 —— **读到 0 同样不符合 (ii)** |

**两个假设都无法解释 `GPIO_TRI` 回读为 0**，所以还有第三个因素（地址没落到这个 IP、
或者该寄存器在双通道配置下不可读/被屏蔽）。这就是下一步必须先做网表/地址核对、
而不是再去猜寄存器语义的原因。

## 8.2 已排队但**未完成**的取证

`dl/touchfix/netprobe.tcl`（离线，不综合、不上板）：用交付的 BD 原样重建，然后打印
`touch_gpio` 每个 pin 所在的 net，特别是 `gpio_io_t` 有没有 net ——
有 net = 三态控制接出去了（偏向 ii）；无 net = 输出使能被接死（偏向 i）。

**已跑完（2026-10-22 20:25），结论与原先设想相反：**
- `touch_gpio` 的 `gpio_io_i/o/t` 在 pin 级查询里都显示 `<UNCONNECTED>` —— 这是**正常的**：
  它们是通过 interface（`/touch_gpio_GPIO`，`gpio_rtl`）连接的，成员不走 pin 级 net。
- 生成的 wrapper 里确实有 `lcd_touch_gpio_tri_t_0/_1`，并接到 IOBUF 的 `.T`
  （`IOBUF lcd_touch_gpio_tri_iobuf_0/1`），BD 侧端口 `lcd_touch_gpio_tri_t` 也存在。
- **⇒ 导出 BD 的三态控制是端到端接通的。** 所以"输出使能被接死"这个方向和"缺 TRI 使能"一样，
  在**导出的设计**里都不成立。

| 该文件 mtime | **2026-09-27 22:52:56** |

**推不出来的那一半（必须承认）**：0x41220000 上确实有 AXI 从设备在应答（否则访问会 data abort、
程序会冻在 fault handler 里），而程序一直在 19 fps 跑着。所以"现在跑的一定是 09-27 那个比特流"
**没有被证明** —— 只证明了"启动脚本所指的文件是 09-27 的、且与所有存档都不一致"。

**下一个会话的第一件事（成本最低，判别力最强）**：
1. 先确认 FPGA 里到底是哪一版：重新 `fpga -f` 一个**哈希已知**的存档（`safe_bitstreams/BIT_20261018_2130.bit`

3. 若仍是 `0xCCCC0000` → 再回来看 §8.2 的网表结论，此时才值得做一次真正的 BD 改动 + 重建。

## 10.2 哨兵实验：`0xCCCC0000` 是实时值，不是静态残留

（measurement-discipline 纪律 2：区分"静态残留"与"实时状态"）

做法：`rst -cores` → `dow` 新 ELF → **在核还停着的时候**把 `0xDEADBEEF` 写进邮箱 w87/w90/w91
并回读确认写进去了 → `con` → 等 10 秒 → 再读。

| 量 | 哨兵写入后、跑之前的回读 | 跑 10 秒后 | 结论 |
|---|---|---|---|
| w87 (TOUCH_OK) | 0xDEADBEEF | 0x00000000 | 固件真的写入了 |
| w90 (TOUCH_ST) | 0xDEADBEEF | 0x00000000 | 固件真的写入了 |
| w91 (TOUCH_PID) | 0xDEADBEEF | **0xCCCC0000** | 固件真的写入了 |
| TEAR_N (w98) | — | 291 → 329 | **主循环在转（~19 fps）** |

⇒ 固件**确实**执行到 `0x41220000` 的读写并拿到 0，**没有 data abort**。
所以当前加载的设计里 `0x41220000` **被译码**，只是它不表现出 axi_gpio 的 TRI 行为。

# 十一、**结论：找到了**（2026-10-22 20:40，冷启动 + WITH_TOUCH 版比特流）

## 11.1 结果

用户断电 10 秒重上电后，用 `safe_bitstreams/WITH_TOUCH_20261018.bit` 走标准 bring-up：

| 步骤 | 结果 |
|---|---|
| `live14_bitpair.tcl`（`LIVE14_BIT` 指向 WITH_TOUCH 版） | **BOOT ASSERTIONS PASSED（table, both channels running, capture live）** |
| 载入固件（哨兵 0xDEADBEEF 预置到 w87/w90/w91） | 哨兵被覆盖 ⇒ 下面全是**本次运行新写入**的值 |
| `MB_TOUCH_PID` (w91) | **`0x39313100`** = ASCII `"911\0"` —— GT911 的真实产品 ID |
| `MB_TOUCH_OK` (w87) | **1** |
| `MB_TOUCH_ERR` (w89) | **0**（I2C 零错误） |
| `MB_TOUCH_ST` (w90) | 0x00（空闲） |
| 主循环 | `TEAR_N` 515→542（~18 fps），没被打断 |

**与 §九 预注册的判据逐字吻合**（`MB_TOUCH_PID = 0x39313100`、`MB_TOUCH_OK = 1`）。

## 11.2 根因

> **板子一直在跑一个不含可用 touch GPIO 的比特流。** 触屏驱动（`ps_ui/touch.c`）从头到尾没问题。

之前所有"驱动坏了"的印象，都来自"在这块板子的当前镜像下测"的结果。
`0x41220000` 在旧镜像下被译码但不表现出 axi_gpio 的 TRI 行为，
所以释放两条线无效、ACK 全被误判成功、每个字节读回 0x00、PID 读成 0 —— 一条自洽的假象链。

**代价**：为了这个假象，今天先后怀疑了 `touch_last_pid()`、BD 属性、TRI 寄存器语义，
其中两次是我自己提出的错误归因（都已按 R7 撤回）。真正的判别只需要一次冷启动 + 一个哈希已知的比特流。

## 11.3 仍未解决的部分（与根因无关，是第二个问题）

`MB_TOUCH_EV = 0`、`MB_TAP = 0`、`MB_TOUCH_X/Y` 从未被写过 —— **面板身份读得到，但还没有观测到手指点击**。
这不是新现象：10-16 19:18 那次成功日志同样是 `OK=1 PID=39313100 EVENTS=0 TAPS=0 ERR=0`，
当时的结论就是"下一个嫌疑是面板自身的检测与排线接触，不是驱动"。

**判据**：用手指点屏幕上的按钮框后，`MB_TOUCH_EV`(w88) 与 `MB_TAP`(w94) 是否递增。
- 递增 ⇒ 输入链路完全打通。
- 仍为 0 ⇒ 问题在面板检测/排线/GT911 配置表，与本次根因无关，需要另外的排查（例如读 `0x814E` 状态字节、
  检查 `gt911_cfg` 的触发方式）。

## 11.4 交付物的连带影响（重要）

交付包里的是 `submission/fpga_prize/board/BIT_20261018_2130.bit`（= `WITH_VSYNC_20261018.bit`，同哈希），
**它是否含可用的 touch GPIO 还没有验证过**；而本次证明可用的是 `WITH_TOUCH_20261018.bit`。
两者是同一晚不同时刻的构建，必须二选一地确定"交付哪个"，并且**用冷启动流程复验一次**
（`BIT_20261018_2130` 在无断电条件下曾 bring-up 失败，那次失败原因已查明是没断电，不能作为它坏的证据）。

显示 `DIS CR=0x00010003 SR=0x00011000`，**屏上有质检 UI**（用户确认）。

## 12.2 `BIT_20261018_2130.bit`（交付那份）冷启动也过不了 bring-up

已用**断电冷启动**复验：`FATAL bring-up did not leave both VDMA channels running`。
所以先前那次失败**不是**"没断电"造成的，而是这份比特流的地址映射与
`live14_bitpair.tcl`（以及固件里硬编码的 `DIS_VDMA=0x43010000` 等）对不上。
**⇒ 交付包里的比特流目前无法用本项目的标准流程复现**，必须在提交前二选一：
换成 `WITH_TOUCH_20261018.bit`（已验证可启动+触屏可用），或者查清 VSYNC 版的地址映射并同步脚本/固件。

## 12.3 为什么之前"没有 UI"（是我的错，不是比特流）

`live14_bitpair.tcl:179-181` 把显示 VDMA 指向**采集缓冲** `BUFA/BUFB`（预览模式），
而固件里把显示指回 `UI_A/UI_B` 的代码在 `video_bringup()` 内部，被
`WANT_VIDEO_BRINGUP 0` 整段编译掉了 ⇒ 固件从不接管显示。
交接文档第二节"第 4 步（显示寄存器的唯一正确组合）"就是补这一步，我一直没做。
**结论：UI 的有无取决于这一主机步骤，与比特流版本无关。**

## 12.4 还剩一个缺陷：相机 1 的画面区域全白

用户确认：UI 正常，但相机 1 该出画面的地方是白的。
已知 `live14_bitpair.tcl` 自己的断言说 "both channels running, capture live" 通过，
所以 VDMA 在转；白画面更可能是**曝光/增益**（过曝）或该通道的帧存内容不对，
需要先读 AEC 相关邮箱字（`MB_AEC_*`、`MB_MEAN_RENDER`、两路的曝光行数）再判断，
**不要**先怀疑比特流。

# 十三、重建路径上逐个排除的失败点（2026-10-22 21:16–21:40，全部实测）

按"改一处、撞下一处"的顺序记录，每一条都是**判据本身或脚本的错**，不是设计错：

| # | 失败原文 | 真实原因 | 修法 |
|---|---|---|---|
| 1 | `[BD 41-396] S_AXI is already connected to ps7_0_axi_periph_M09_AXI` | 这份源 BD 里 `touch_gpio` **早就被补丁连到 M09**，而 M09 上是 `lcd_touch_i2c`；`0x41220000` 因此表现得像 I2C 控制器 | 用 `disconnect_bd_intf_net` **只断引脚**（绝不删网络） |
| 2 | 抢到 M11 仍报 M09 | 补丁"找空闲口"依赖 `NUM_MI`，而该属性与实际端口数不一致（读到 11，实际 M09 有连接） | 不去猜：强制 `NUM_MI` 到 12，直接占用最高的 **M11** |
| 3 | `[BD 41-758] M10_ACLK is not connected to a valid clock source` | **设计里原本就悬空**的端口，与本次补丁无关 | 遍历 `M*_ACLK` / `M*_ARESETN`，把**所有悬空**的接上（幂等，顺带修前几版） |
| 4 | `*** 2 ERROR(s), NOT saving ***`，而 `validate` 是 `2 -> 2` | 判据数的是**消息条数**；被 `catch` 吞掉的重复连接也会留一条 ERROR。且 `reset_msg_config -count` 清不掉它（三次尝试读数都不变） | 判据改为"**validate 有没有新增**"，即 `$a > $b`。**AGENTS.md §三① 那段写法也漏了这一层** |
| 5 | 打完补丁后整个 Vivado 直接退出 | 补丁脚本**结尾有 `exit 0`**，被 `source` 时会杀掉会话（交接 §五#3 记过这个坑） | 把结尾 `exit 0` 改成 `return 0` |
| 6 | `can not find channel named "file20d7147f060"` | 补丁脚本定义了同名的 `L` 过程并 `close` 了自己的日志通道，`source` 之后**覆盖了调用方的 `L`** | `source` 之后立刻 `proc L {...}` 取回自己的版本 |
| 7 | `Run 'synth_1' needs to be reset before launching` | `make_wrapper -import` 之后综合运行需要先 reset | `catch { reset_run synth_1 }` |

**经过这 7 条，综合已跑到 `synth_design completed successfully` / `synth progress: 100%`** —— 说明设计本身是通过的。
