## 候选改动全清单（按证据强度分层；量是"理想 II=1 推算"，必须先用阶段 0 的实测核对）

总的形状：**每行的相位是「载入 3 行 -> bias 播种 out_acc -> 像素循环 -> requant 存储」，
四者里只有像素循环在真正做乘法。** 按源码结构推算的每行周期：

| 模块 | 载入 | bias 播种 | 像素循环 | requant | 理想/行 | 实测/行 |
|---|---|---|---|---|---|---|
| conv1 (cin=1, cout=16, W=64) | 192 | **1,024** | 128 | **1,024** | 2,368 | 2,717 |
| conv2 (cin=16, cout=32, W=32) | 1,536 | 1,024 | 2,048 | 1,024 | 5,632 | 12,319 |
| conv3 (cin=32, cout=32, W=16) | 1,536 | 512 | 2,048 | 512 | 4,608 | 17,723 |

两条读出来的事实（这是排序依据）：
  - **conv1 有 75% 的行时间花在 bias 播种 + requant 存储上**（1,024+1,024 of 2,717），
    而它占整体 17% 的周期。这两个相位不随 cin 缩小，**对通道少的层伤害最大**。
  - conv2/conv3 理想远低于实测（5,632 vs 12,319；4,608 vs 17,723）——缺口在"喂数据"，
    不在相位。具体是什么，阶段 0 回答。
  - 两条独立路径给出同一个占比：2,048/12,319 = 16.6% 与 12/72 MAC/周期 = 16.7%。
    **两个算法同一个答案，说明这个分解站得住。**

### 第一梯队：纯结构、不加资源、bit-exact 由构造保证（风险最低，先做）

1. **消掉 bias 播种相位**：现在每行单独跑一遍 `out_acc[oc][x] = b[oc]`。
   改成 `ic==0` 时初始化而不是累加，或折进 requant 的常数项。
   量：conv1 省 1,024/行（38% of its row time）、conv2 1,024（8%）、conv3 512（3%）。
2. **requant 存储融合进最后一个 ic 迭代**（`ic==cin-1` 时直接 requant 并写出）。
   量：与 #1 同量级（1,024 / 1,024 / 512）。
3. **行载入双缓冲**：载入第 y+1 行与计算第 y 行重叠（`lb` 两份，共 12.6 KB，BRAM 够）。
   量：conv1 192/行、conv2 1,536（12%）、conv3 1,536（9%）。
4. （白送）**表填充拆成两个循环**（一个只读 M、一个只读 sh），消掉最后 3 条 200-885。
   量 96 周期 = 0.01%，不值得单独一轮，搭在别的改动里做。

**第一梯队合计预期约 1.3-1.4×。**

### 第二梯队：加资源，但资源有余（BRAM 55% / LUT 35% / FF 32%）

5. **conv1/2/3 权重片上缓存（共 13.9 KB = 144 + 4,608 + 9,216）**——文献的 "local weight caches"。
   fc1 的 128 KB 不缓存。**警告：历史上 v5 把整层权重搬片上并完全分区，导致综合卡死 29 分钟。
   只做 conv 三层、每层独立小数组、不要完全分区。**
6. **maxpool 改流式滑窗**（行缓存 + 滑动寄存器，顺序读，不再 4 个随机地址）。
   回收分库给 conv 写出端带来的 **+36,992 周期（3.7%）**，并消掉第二级联的 II 违规。
   风险：结构性，需重新验证关键路径。**先与 #3 比较再选，两者都动 BRAM。**

### 第三梯队：量最大，但被 DSP 静态分配卡住（必须先取证）

7. **FC1 并行化**。现状：FC1 用 **0.99 MAC/周期**，占 **13.1% 的时间**却只做 **1.7% 的 MAC**——
   相对效率比 conv 差约 8 倍。把 k 循环按 8 路展开（8 个部分和）可到 8 MAC/周期，
   预期把 FC1 从 132,745 压到约 1.7 万周期 = **全推断的约 11%**。
   **卡点：DSP 只剩 1 个。** forensics 显示静态分配是 `grp_conv3x3` **210**、`grp_linear` **2**、
   `grp_maxpool` 0、`mul_64` 7 —— **三个卷积层把 DSP 静态吃光了，而它们整机只跑 17% 占空比。**
   这条要么把 DSP 从 conv 挪出来（重新平衡分配），要么用 LUT 织构做乘法。
   **取证：这 210 个 DSP 在任何给定时刻真正在动的是几个。**

### 第四梯队（本线已选定为主攻方向；用户明确"报告不着急"，停止判据放宽）

**先纠正原清单里的一个方向错误**：原先 #10 写成"用 LUT 织构重做卷积乘法阵列"——那是重写，
而且它的前提（阵列不够宽）**恰恰不是我们的问题**（占空比 17%）。真正的入口在 FC1，而且极便宜：

```
FC1 现状：0.99 MAC/周期，占 13.1% 的时间，却只做 1.7% 的 MAC
并行 8 路只需 7 个额外的乘法器（8x8）
7 个 8x8 乘法器用 LUT 约 700 个 LUT —— 我们空闲 34,000 个
=> 那 11% 卡在一个只需要 700 个空闲 LUT 的地方，被卡的原因是 DSP 的静态分配
   （grp_conv3x3 210 / grp_linear 2），不是资源不够。
```

**第四梯队的正确顺序：**

**阶段 4.0（零成本取证，必须先做）**
  a) 从 w6d 的 synth 产物确认：三个卷积实例（`grp_conv3x3` / `_3` / `_4`）各自的 DSP 数，

     DSP 可能在工作，2/3 的阵列结构性闲置**。这一条要用模块延迟的时间轴证明，不要推。
  c) 确认 `grp_linear` 只分到 2 个 DSP，以及它的 k 循环能否展开成 8 个部分和
     （读 HLS 报告里的 loop 表，看 k 循环的 II 与 trip）。
  d) **确认这个三实例结构是否是历史遗留**：查 step 2/3 时期的报告里是否已存在

**阶段 4.1（一轮，最便宜的第一步）**
  把 **FC1 的乘法绑到 fabric（LUT）**，让它能展开 8 路部分和。
  **必须查 Vitis HLS 2023.1 手册确认绑定 pragma 的正确形式**
  （`BIND_OP` / `RESOURCE` / `USE_DSP` 几代语法不同），**不许凭记忆写**。
  预写预测（已按带宽墙修正，不要用因子 8）：
    FC1 的 MAC 总量 = 131,072；权重总量 = 131,072 字节（每个权重每次推断只用一次，缓存省不掉）；
    32 位权重端口 @150 MHz = 4 B/周期 -> 32,768 周期是硬地板。
    所以 FC1 ≈ max(131,072 / 展开因子, 32,768)：
      因子 1 -> 131,072（实测 132,745，吻合）
      因子 2 ->  65,536（省 6.6%）
      因子 4 ->  32,768（撞带宽墙，省 9.9%）  <- 选这个
      因子 8 ->  16,384 < 32,768，仍被带宽卡住，白展开
    => 用 `#pragma HLS UNROLL factor=4`（3 个额外乘法器），不要 factor=8。
    预测：FC1 132,745 -> 约 3.3 万周期；总周期 1,011,225 -> 约 91 万（1.11x）；
    板上实测相应下降；bit-exact 200/200 不变。
    注意：这只是把 FC1 推到它的带宽墙。若要继续，必须加宽权重端口或改数据复用——
    那是 4.2/4.3 的事，不要在这一轮里混做。
