# 逐格容差图审计：10-29 -> 10-31 的检出塌陷能归因于"容差图退化为常数"吗

审计 2026-10-31。只读审计：只新增本文件，未改任何 .c/.tcl/.py，未碰硬件。被审假设：`tol0.raw` 中位数=最大值=30 说明 STAGE I 容差图没学出来、回落到固定 30 灰门槛，33 灰的划痕残差因此不再越线。

## 0 结论

1. **不能。** 容差图在 **10-29 就已经是常数 30**，而且正是在这个状态下检出了 darea=41 的缺陷（§2.2：161 份存档转储，0 份出现 >30 的字节）。两天之间它没变，不是这次的变量。
2. **代码方向也相反**：`tol_at()` 的下界是 `TOL_FLOOR=30`（main.c:5557-5563），容差图只能**放宽**判决，永远不能收紧。常数 30 是这套机制允许的**最严**状态，不是退化态。
3. **假设在自己的数字上就不成立**：33 > 30，确实越过了 30 灰门槛。10-31 d1 只读到 1 格，是 `DEFECT_AREA=8` 的**连通面积**判据没过，不是振幅没跨过门槛。
4. 真正塌掉的是**残差本身**：d1 的 `|d|` 最大 129 -> 33，超 30 灰的格 82 -> 1，最大连通组 41 -> 1。
5. 证据等级：**E2（直接测量）**，范围仅限"容差图的状态"与"残差塌陷"两件事。"到底是什么造成的"**未定**（E0）；板号跨批**不能对应**（§2.5）。

- **`tol_at()` 永不低于 30**：`scale<256` 时返回 `30 + ((v-30)*scale>>8)`（`scale=0` 恰好 30），`v<30` 被夹回 30。所以任何状态的容差图对每一格都 `>= 30`，只会把格判松，不会更严。
- **两种"常数 30"数值上不可区分**：(A) `g_tol_n<3` -> `tolmode=0` -> 每格 30；(B) 学过但每格仍压在 30，或 `MB_TOL_SCALE=0` -> `tolmode=1`、每格仍 30。区分只能读 `MB_TOL_N`/`MB_TOL_USED`/`MB_TOL_VAR`，**两天都没记录过**。注意 `MB_TOL_USED=1` **不能**证明地图放宽过任何一格。
- **host 侧没有这三个字**：`dl/host_qc/qc_mailbox.py` 的 `WORDS` 共 230 条，索引 12..20 与 38..48 里只有 39 被占用（逐条核过），13..17 与 40..45 全部缺席。任何"host 读到 `tol_used=0`"都不是来自这张表。

### 2.5 板号能不能对应：**不能**

- 10-29 有 79 个板目录（d1..d39、g0..g40），10-31 是 30 块尝试 / 22 份有效。标签重叠不代表同一块板。
- 检验：把 10-29 的缺陷格膨胀 +-3 格（容纳最多 6 格的摆放漂移），取 10-31 同标签板的同一位置，组内 `|d|` 中位数**不比其它位置高**（10 块板比值 0.70..1.17，多块恰好相等）。即**没有**"同一缺陷、信号变弱"的痕迹。
- 旁证：同标签的 mask 格数 10-31 比 10-29 大 18%~29%（g1 614 -> 794），两天画面里的板子占格不同。
- 项目自己的 `dl/for_review_20261031/REVIEW_QUESTION.md` §8 未解决(2) 已写明跨批板号不得假设像素级对应。本审计同意并遵守。

## 3 判定与证据等级

| 命题 | 等级 | 依据 |
|---|---|---|
| 10-29 那次判决用的逐格容差就是 30 | **E2** | `fine_tol.bin` 全 30 + `tol_exact=1` + 复算 cc8 与固件 darea 21/21 相同 |
| 10-31 的逐格容差也是 30 | **E2** | 34 份 `tol0.raw` 全 30（含 fix/fix2/ref1） |
| 容差图只能放宽、常数 30 是最严状态 | **E2** | 5557-5563, 5507-5510, 11830 |
| 残差塌陷：d1 129->33、>30 格 82->1、cc8 41->1 | **E2** | 由两侧转储直接算，并与各自发布的 darea 对齐 |
| **容差图不是这次塌陷的原因** | **E2** | 上四条 + 单调性：图的状态两天相同，且只会让判决更松 |
| 10-31 d1 与 10-29 d1 是同一块板 | **E0** | 无法建立；检验结果是"同位置无抬升"（§2.5） |
| 到底是什么造成的 | **E0** | 盘上没有能分辨的数据；候选见本节末三条 |

- 假设为什么看起来成立：把"今天=tol 常数 30"当成变化（10-29 也是常数 30 且那天 cc8=41 判 NG）；把只放宽的机制当成能收紧；并把 33>30 写成"没跨过门槛"。
- 更正一处：简报写 10-31 d1 `darea=2`，`dl/pop_scan_20261031_pop.csv` 记的是 `1`，我复算也是 `1`。两者都远小于 8，不改变判断，但记录应以 CSV 为准。
- 两天之间真正变了的东西（全是候选，未测，不构成结论）：固件几乎肯定换了 —— sweep 之前最后一次 `ps_ui/main.c` 提交是 149faf4（`build_id.h` 的 `FW_SRC_HASH=327CD597`），10-31 同日台架日志里的 stamp 是 `TSC1EDC634BF`（23e9b57）；但 sweep 的 meta 与 pop_scan 的 CSV 都不记 `fwid`，所以这是旁证、不是测量。sweep 之后到 10-31 台架之间 `ps_ui/main.c` 有 8 次提交，其中 `c38cc64`（10-29 21:29，晚于 sweep）把比较的增益/偏置改成"与参考冻结"（10447-10449，`ref_take` 后 1.0/0），10-29 用的是逐帧 `g_diff_scale=(ref_mean<<8)/live_mean` 加实测偏置 —— 这是真实混淆变量，但量级不够：10-31 有符号残差中位数只有 +3..+6。
- 已排除一条：`cell_mean8_ex()` 在 149faf4 与当前文件之间逐字节相同（我 diff 过），格内统计量没变。
- 一致的现象：良品类两天都安静（10-29 cc8 1..2，10-31 0..1），变化**只发生在划痕类**；这更像"样本或光路"变了，而不是全系统的阈值变了。未测：照明（10-31 环灯已摘、k=2）、镜头/相机距离、参考板身份、配准、AWB。
