# Stage 1 — why MB_READY never opens: predictions before the change

Written 2026-10-23, BEFORE the instrumentation build. The point of writing it down
is that a prediction that fails is worth more than one that quietly changes.

## What is already measured (board, 2026-10-23, read-only mailbox sampling)

| word | value | meaning |
|---|---|---|
| 144 MB_AEC_STATE | 1 in 20 of 20 samples | the gate's AEC condition is satisfied |
| 152 MB_AEC_STEPS | 0 across 2,519 -> 2,531 evaluations | the controller has made **no** adjustment |
| 153 MB_AEC_EVAL | 2,519 -> 2,531 (12 in 7.2 s) | the controller is evaluating, not idle |
| 154 MB_AEC_LAST | 0 | in-band = converged |
| 155/156 EVCLIP/EVMEAN | 0 / 443 | not clipping, inside the deadband |
| 145 MB_AEC_EXP | 2369, constant | exposure is not walking |
| 199 MB_SETTLE_MOTION | 0, 290, 783, 317, 542, 0, 750 ... | the motion metric |
| 224 MB_READY | 0 in all samples | the symptom |
| 225 MB_SETTLE_MS | resets (12548 -> 773), grows again | `ready` DID reach 1 briefly |

`MB_SETTLE_MS` restarting is the strongest single clue: `g_settle_t0` is only reset
when `ready == 1`. So the gate is not stuck shut by a permanent condition -- it
closes and re-opens, and the hold counter is repeatedly broken.

## Hypotheses

| # | Hypothesis | If true we should see | If true we should NOT see |
|---|---|---|---|
| H1 | camera-0 AEC flickers 1 -> 2 -> 1 faster than READY_K = 6 loops, resetting the hold | MB_AEC_STEPS advancing; MB_AEC_STATE out of 1 in a large fraction of loops | steps frozen at 0 with thousands of evaluations |
| H2 | the frame-to-frame difference is a real, ROW-UNIFORM brightness modulation (rolling-shutter/flicker band) whose amplitude exceeds READY_CELL_DIFF = 10 | per-row bias-free means form a smooth curve, |mean| up to ~15 counts, and the changed-cell count is high and similar right across each bad row (near 64 of 64) | a smooth curve with a LOCALISED x extent; or a curve whose shape is steppy |
| H3 | the metric is an artefact of the measurement (wrong store, stale/torn capture, ring handing the same store twice) | changed counts concentrated at particular rows; motion = 0 exactly when the ring repeats; ΔMB_GATE_HO < Δframes | a smooth row curve at all |
| H4 | the part or the scene really is moving | a localised blob of changed cells, moving in x between frames | full-width row uniformity |

H1 is already contradicted by the numbers above: 2,531 evaluations, `steps` never
moved, state 1 in every sample. Stage 1 therefore has to be about H2/H3/H4, and the
instrument has to separate them.

## The measurement that separates H2, H3 and H4

Publish, from the gate's own comparison of its own two grids (no JTAG dump
involved, so nothing can be a dump artefact):

* the bias-free mean signed change **per grid row** (34 values)
* the number of cells over threshold **per grid row** (34 values)
* `g_ready_still` (the consecutive-still counter the decision uses)
* loop counters: gate evaluations, loops with AEC state 1, loops with ready 1,
  AEC state transitions, `g_ho_n` at evaluation time

## Predictions for THAT build (to be checked against the numbers)

| prediction | expected value if H2 holds |
|---|---|
| MB_READY_STILL | small (0..5), never 6 |
| rows with \|mean\| > 10 counts | a contiguous group, and the sign flips between groups |
| changed cells in a bad row | >= 40 of 64, spread across the width |
| Δframes vs ΔMB_GATE_HO | equal (no capture stall) |
| loops with AEC 1 / loops | ~1.000 |
| AEC state transitions | 0 |

If instead the per-row means are all near zero while the changed counts are high,
H2 is refuted and the difference is cell-random noise or the measurement (H3).
If the changed cells form a compact blob in x, H4.

## The fix this implies (only if H2 holds)

Make the gate's own metric invariant to a per-row-uniform brightness term: subtract
a per-row mean instead of a single whole-frame mean. A rolling-shutter bar is
constant across a row by construction, so it disappears exactly; a part moving into
the scene is not row-uniform and survives. This is the same reasoning that already
removed the global term on 2026-10-23, applied one order of smoothness higher.

**It must be measured, not assumed:** if the per-row means turn out to be ~0, this
fix would be a no-op and the real cause is elsewhere (H3/H4).

## An instrument that was tried and REJECTED

`mrd -bin -file <store> 691200` (the established "how you see the picture" method)
was used to dump two capture stores and replay the gate's arithmetic in Python
(`ps_ui/st1_gate_replay.py`). It reproduced the published number (616 changed cells
against 300..800 published) -- which looked like validation. The control killed it:
two dumps of the **same** store, 6.9 s apart, differ by 501 cells with the same
+-15-count row pattern. Measured dump time: **6,696 ms**, while the ring rewrites
that store every ~240 ms -- so a dump splices ~28 different frames together.

Conclusion: a JTAG dump of a live capture store is **not atomic** and must not be
used for frame-to-frame structure at this frame rate. It remains usable for
large-scale geometry (the board's bounding box), which is what Stage 2 needs from
it, and for looking at the picture.

# RESULTS

## Which condition actually failed

Measured with the instrumentation build (`FWID TSC16167E148`), 12 samples over 20 s:

| quantity | value | verdict |
|---|---|---|
| `MB_GATE_AECOK / MB_GATE_LOOPS` | 510 / 517 = **98.6%** | the AEC half of the decision passes |
| `MB_GATE_FLIPS` (AEC state changes) | **1** (the boot 0 -> 1) | no flicker at all |
| `MB_AEC_STEPS` over 2,531 evaluations | **0** | the controller never moved the exposure |
| `MB_GATE_STILLN / MB_GATE_LOOPS` | 182 / 517 = 35% | the MOTION half fails on 2 of 3 loops |
| `MB_READY_STILL` (max over samples) | **1** of the 6 needed | the hold counter never reaches 6 |
| delta `frames` vs delta `MB_GATE_HO` | equal | no capture stall |

**H1 is refuted and H2 is confirmed.** The AEC reports converged and is converged:
2,531 evaluations, `steps` frozen at 0, state 1 in every sample, `flips` = 1 for the
whole boot. The gate is shut by the motion criterion, not by the exposure.

## What the motion metric was actually measuring

Coherent snapshots (core stopped around the read; histogram sums to exactly 2176,
which is the proof the snapshot was coherent). Two populations of loops:

| loop type | motion | sigma of the cell difference | row profile |
|---|---|---|---|
| one loop in four | 0 | **0.00** -- all 2176 cells identical | flat |
| the rest | 45..183 | **~6.0 counts** | a smooth oscillation, +-10 counts |

* The sigma = 0 loops were the ring handing the gate **store 2 twice in a row**:
  store 3 is shared with camera 1 and was substituted by store 2, which the next
  loop reads anyway. The gate published the absence of a measurement as perfect
  stillness.
* The other loops showed a **row-uniform, periodic brightness modulation of +-10
  counts with a period of roughly 8-14 grid rows (160-280 source rows)**, whose shape
  repeated between samples with a different phase: per-row means
  `-7, -9, -10, -8, -5, 0, +4, +7, +9, +9, +7, +4, -1, -4, -7, -9 ...`.
  `READY_CELL_DIFF` is 10 counts, so the threshold sat **inside the body of this
  distribution**, and the cell count moved between 45 and 820 on a scene nobody
  touched. A 244-row period at the frame's row rate is the spatial period a 50 Hz
  mains ripple makes under a rolling shutter.

## The fix, and the before/after on the same frames

1. `settle_gate()` now subtracts **each row's own mean** instead of one whole-frame
   mean. A rolling-shutter bar is constant across a row by construction, so this
   removes it exactly, and it removes nothing that varies across a row -- which is
   what a moving part produces.
2. The shared-store substitution now reads **store 1** (complete, unshared, never the
   store the previous loop used), so every loop compares two different real frames.

Controlled comparison -- same frames, two statistics, `MB_SETTLE_MOTION` (per-row)
next to `MB_SETTLE_MOTG` (the same data, old whole-frame rule):

| | before (whole-frame) | after (per-row) | |
|---|---|---|---|
| sigma of cell difference | ~6.0 counts | **2.0 counts** | /3 |
| cells over threshold | 36, 47, 150, 159 | **0, 0, 1, 0** | |
| mean of the bar | +-10 counts still published | unchanged | the bar is still there; it is no longer counted |

Histogram after (one loop, sums to 2176): `0:423 1:784 2:546 3:254 4:110 5:37
6-7:21 8-9:1 10-12:0` -- the 10-count threshold now sits at ~5 sigma instead of
~1.7 sigma.

## Acceptance

22 samples over 22 s on the static scene (`FWID TSC1E7E06F81`):

* **`MB_READY` = 1 in 22 of 22 samples (100%)** -- was 0 in 20 of 20.
* `MB_SETTLE_MOTION` = 0 in all 22; the old rule on the same frames read 2..81.
* `MB_READY_STILL` grew 199 -> 512, i.e. the gate held, not just touched.
* The diff arm's verdict is no longer `CANNOT JUDGE` in any sample.

## What is NOT verified, and what the number does not mean

* **The positive control has not been run for this statistic.** The gate closing on
  *real* motion has not been demonstrated on this build. It is scheduled with the
  Stage 2 board move, which is the first time the operator touches the scene; if the
  per-row subtraction turns out to be too aggressive, that is where it will show.
* The bar's physical origin is not established. What is measured is that it is
  row-uniform, +-10 counts, ~160-280 source rows in period, and that its phase
  changes between frames every time. Whether it lives inside each frame (flicker
  against a rolling shutter) or only in the difference (a capture-timing effect
  interacting with scene texture) is still open: the published single-frame row
  profile (`MB_GRID_ROWM`) shows only +-2-count waviness, which is smaller than the
  +-10 seen in the difference. Publishing the PREVIOUS grid's row profile as well
  would settle which of the two frames carries it.
* The verdict is now **NG, not PASS** (cells 24..52 against a limit of 8) on a scene
  nothing is touching. That is a pre-existing false-positive source in
  `diff_frame()` that the gate was previously masking; the row bar is a plausible
  cause and the same per-row treatment applies there. It is Stage 3's job.
