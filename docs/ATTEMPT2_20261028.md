# The second attempt: the PL front end fits

**Date:** 2026-10-28 evening (PL front-end attempt 2 — the one attempt)
**Question:** the front end needed ~449 slices more than the xc7z020 had free. Is there area
that can be freed without changing anything the owner has decided, and does the design then
place?
**Answer: yes.** Removing the two diagnostic ILAs freed **5,755 LUT / 7,782 FF / 30 BRAM** —
three times the deficit — and the design with the front end in it **places, routes, meets
setup and hold, and produces a bitstream**:

```
place_design completed successfully (4m47s)
WHS = +0.028 ns      WNS = +1.032 ns      (0 failing setup endpoints, 0 failing hold endpoints)
Slice LUTs 34,520 (64.89 %)   Slice Registers 53,432   BRAM 108.5/140 (77.50 %)   DSP 219/220
```

Every number below says where it came from. Nothing is estimated.

Vivado project directory was backed up, and the backup was **verified by rebuilding**.

## 2. Step 2 — where the area is: the two ILAs, measured

Measured on the **post-opt netlist of the build that failed to place**
(`impl_1/design_1_wrapper_opt.dcp`, copied to
`dl/pl_frontend/prev_opt_with_frontend_20261028.dcp` before any new build could overwrite it;
`report_utilization -hierarchical`):

| instance | total LUT | logic LUT | SRL | FF | RAMB36 |
|---|---|---|---|---|---|
| `ila_5mp` | 2,873 | 2,315 | 558 | 3,903 | 24 |
| `u_ila_vid` | 2,882 | 2,324 | 558 | 3,879 | 6 |
| **both** | **5,755** | | | **7,782** | **30** |
| `pl_fe_top_0` | 2,710 | 1,768 (+942 LUTRAM) | | 1,576 | 0 |

Two things this changed:

1. **The free area was three times the deficit, in the right resource.** The device was short
   ~1,800 LUT-equivalents; the ILAs held 5,755 LUT. And the same netlist was at **BRAM
   138.5 / 140 = 98.93 %** — slice capacity was the reported blocker, but the design was
   simultaneously one tile away from a BRAM failure. The ILAs held 30 of the 140.
2. **Most of the ILA area bought nothing.** Both cores are configured for **44 probes /
   215 bits**; the block design connects **12 nets**. The other 32 probes are tied off.

**What is lost.** The 12 nets that were actually observed:

| ILA | clock / depth | observed nets |
|---|---|---|
| `u_ila_vid` | FCLK_CLK1 (33 MHz) / 1024 | `v_tc_0` active_video, hsync, vsync, hblank, vblank; `v_axi4s_vid_out_0` locked, overflow, s_axis_video_tready; `axi_vdma_1/m_axis_mm2s_tvalid` → `v_axi4s_vid_out_0/s_axis_video_tvalid` |
| `ila_5mp` | FCLK_CLK0 (50 MHz) / 4096 | `alinx_ov5640_0/m_axis_video` tuser, tlast, tvalid |

So a future session loses **logic-analyser capture of the display timing and video-output
handshake, and of camera 0's AXI-Stream handshake**. It does **not** lose:

* register-level observability — mailbox words, AXI-Lite registers, VDMA status, `capture_ram_0`,
  `analyzer_fe_0`, `cam_pclk_cnt`, `clk_probe_cnt` are cells, not probes, and are untouched;
* the picture on the panel;
* the `xlconcat` taps (`dcat`, `vtc_probe_concat`) that the PS reads.

**But the debug path does not go away.** Removing the two BD ILAs did **not** remove all debug
cores: the vendor camera IPs contain their own (`design_1_i/alinx_ov5640_0/inst/ila.ila_0_m0`
and `..._1/...`, from the impl log), so Vivado still inserts a `dbg_hub`
(471 LUT / 753 FF in the placed design) and JTAG debug remains available. What is gone is
specifically **capture of those 12 video/display nets**; the vendor cores capture whatever the
camera IP exposes internally. Bringing the two BD ILAs back is a rebuild plus a bitstream load,
not a runtime switch.

## 3. Step 3 — the attempt

**Prediction, written before the attempt build was read:** LUT would land *below* the
baseline (~35,300), because the ILAs cost 5,755 and the front end plus its interconnect ~3,700;
BRAM would fall to 108.5/140; placement would succeed; and **`WHS` was the open risk**, since
the baseline's hold margin was only +0.037 ns.

**Result: confirmed, and the risk did not materialise.**

```
BD|clk_pins=67|hp2=1|num_mi=19|errors=0|pl_fe_top_cells=1|ila_cells=0
GATE|pl_fe_top_cells=5652|mode=attempt     <- the front end IS in the netlist
place_design completed successfully (4m47s)   write_bitstream Complete!
WHS = +0.028 ns    WNS = +1.032 ns    (THS 0.000, 0 failing hold endpoints)
```

The block-design change and its gates (`ps_fft_dual/attempt2_bd_edit.tcl`,
`GATE|PASS`, `SAVE|saved`):

```
BASE|clk0_pins=62|clk1_pins=8|hp2=0|num_mi=18
S1|CLKPIN|ila_5mp|/ila_5mp/clk|net=/processing_system7_0_FCLK_CLK0
S1|CLKPIN|u_ila_vid|/u_ila_vid/clk|net=/processing_system7_0_FCLK_CLK1
S1|clk0=61|clk1=7|gone0=/ila_5mp/clk|gone1=/u_ila_vid/clk
S2|CELL|created pl_fe_top_0|S2|HP2|value=1|S2|LITE|NUM_MI 18 -> 19
S2|ADDR|mapped=/processing_system7_0/Data/SEG_pl_fe_top_0_reg0|offset=0x40000000
S3|clk_pins_final=67|ila_cells=0|pl_fe_top_cells=1|hp2=1|num_mi=19|errors=0
```

Three things in that log are worth keeping:

1. **The clock-net gate had to be per-net.** The first run refused to save because it assumed
   both ILA clocks were on `FCLK_CLK0`; `u_ila_vid` is on `FCLK_CLK1`. The refusal was right in
   substance and wrong in arithmetic, and because the script saves only at the end, **nothing
   on disk changed**.
2. **`get_property OFFSET` on the *physical* address segment returns an empty string here.**
   The offset lives on the segment **as mapped into the address space**
   (`/processing_system7_0/Data/SEG_pl_fe_top_0_reg0`). The address matters because the
   firmware hard-codes `PLFE_BASE 0x40000000`.
3. **An ERROR-only gate is not enough.** `validate_bd_design` reported 0 ERRORS on a block
   design whose front end had **no master address segment at all** — that condition is a
   warning. See §5.

## 4. Utilisation, before and after

| | baseline (restored, ILAs in, no front end) | attempt (ILAs out, front end in) | delta |
|---|---|---|---|
| Slice LUTs | 36,513 (68.63 %) | **34,520 (64.89 %)** | **−1,993** |
| Slice Registers | 58,900 (55.36 %) | **53,432 (50.22 %)** | **−5,468** |
| Block RAM Tile | 138.5 / 140 (98.93 %) | **108.5 / 140 (77.50 %)** | **−30.0** |
| DSPs | 219 / 220 (99.55 %) | 219 / 220 (99.55 %) | 0 |
| Occupied slices | 13,300 / 13,300 | 13,272 / 13,300 | −28 |
| WHS | +0.037 ns | **+0.028 ns** | −0.009 ns |
| WNS | +0.908 ns | **+1.032 ns** | +0.124 ns |

The accounting closes with measured parts: −5,755 (the two ILAs) + 3,762 (front end + the 1x1
interconnect + the two automatic protocol converters + the extra `ps7_0_axi_periph` port) =
**−1,993 LUT**, which is what the placed design shows. The front end costs the device *less*
than the diagnostics it replaced, and it improved setup slack because the removal of 7,782 FFs
relieved the congestion that was making the router work harder.

**On the "placement margin".** Vivado does not print a slack number for a successful placement.
What is measured: at the LUT level the design now uses **64.89 %** (18,680 LUT unused, was
98.93 % of BRAM and is now 77.50 %), and the placer still packs the device to **99.79 % of its
slices occupied** — the device remains packed to the edge; what changed is that the demand now
fits, by a margin of one ILA-and-a-half.

## 5. First light on hardware — and a defect that the build could not see

Bitstream loaded with the standard bring-up (`ps_fft_dual/stereo_bringup_byname.tcl`), firmware
`ps_ui/ps_ui.elf` (**TSC1EAA4676C**, the build that speaks `MB_PLFE_ON`) loaded with `dow`+`con`.

**The bitstream does not regress the station:** FCLK_CLK0 50 MHz verified, display timing
configured and verified, both cameras accepted their **303/303** register tables, and the
bring-up's own control check read **camera0 CONTROL = 29/32 words, camera1 = 28/32** — both
captures live. Loop advancing at ~4 loops/s.

**The front end answers its registers** (`dl/plfe_visible_20261028.tcl`, with a known-good PL
register read in the same session as a control):

```
CONTROL|v_tc_CTRL(0x43C00000)=0x03F7EF07|FRAMES(10)=0x00000067
PLFE|ID(0x40000000)=0x504C4645  -> "PLFE", the address the firmware uses
PLFE|VER=0x00010000|STATUS=0|VALUES=0|ERRS=0
```

**One pass runs on silicon and writes all 46,800 words** (`dl/plfe_func_20261028.tcl`,
`MB_PLFE_ON=1` for 4 s, then restored to 0):

```
STATUS(0x24) = 0x00D10008   -> bit3 err set, done NOT set, seq_echo 0x00D1 advancing
VALUES(0x28) = 0x0000B6D0   = 46,800   <- the full statistics count
ERRS(0x2C)   = 0x00039A90   = 236,176 non-OKAY write responses
MB_PLFE_USED(578) and MB_PLFE_VALS(582) unchanged -> the PS never consumed a pass
```

So: the front end's engine, FIFO and register file all work; the statistics count is exactly
right; but **its AXI master writes are being rejected**, so `done` never asserts and
`plfe_try_sample()` correctly refuses and runs the PS pass instead. **That fallback is the
design working as documented** — the station's QC is unaffected by a broken front end. It also
means an A/B run now would measure *nothing* (the block is never used), which is why **no
timing measurement was taken and no operator steps were requested.**

**The writes really do not land** (`dl/plfe_probe2_20261028.tcl`, same loaded bitstream): the
statistics buffer at `0x12AC0000` is written *only* by the front end, and eight words of it
were identical before and after a pass:

```
BEFORE|STATUS=0x00E00008|VALUES=0x0000B6D0|ERRS=0x00073527
ENABLE|PLFE_ON=1     ->  AFTER|STATUS=0x10C90002  (busy, err bit CLEAR)
                      ->  AFTER2|STATUS=0x10CA0008 (idle, err bit SET again)
BUF_CHANGED_WORDS_OF_8|0
```

The err bit is clear while the pass is busy and set when it completes — so the error is
reported *by the transaction*, not by a stale flag. The buffer's content looks like
uninitialised DDR, which is what it would look like if nothing ever wrote it.

**What was ruled out, and how:**

| candidate | verdict |
|---|---|
| the front end is not in the bitstream | no — `ID(0x40000000) = 0x504C4645`, read over JTAG with `v_tc` as a working control in the same session |
| the firmware cannot see it (wrong address) | no — the slave segment is at `0x40000000`, the value `ps_ui/main.c` uses |
| burst geometry (4 KB crossing) | no — `BL=8` beats of 64 bits, `AWBURST=INCR`, `AWSIZE=3` |
| illegal AXI attributes | no — `AWCACHE=4'b0011`, `AWPROT=3'b010`, `ARCACHE=4'b0011` are ordinary normal-memory values |
| the master address space is unmapped | **tested by rebuild, reload and re-probe: it is not the cause.** `design_1.bd`'s `addressing` had no entry for `/pl_fe_top_0`, so `SEG_pl_fe_top_HP2_DDR` (1 GB at 0x0 onto `S_AXI_HP2/HP2_DDR_LOWOCM`) was created and the design rebuilt (`ps_fft_dual/attempt2_bd_addr_fix.tcl`, gate PASS). The rebuild placed and timed identically (WHS +0.028 / WNS +1.032, 34,520 LUT, 108.5 BRAM) but produced a **different bitstream**; it was loaded and the probe re-run, with the same result: `ID=0x504C4645`, `VALUES=46,800`, **err bit set, buffer unchanged, ERRS=188,973**. The mapping is still worth keeping — it is what every other PL master has, and it silences a warning that the ERROR-only gate could not see — but it is not the fix. |

**Where the next session should look.** The failure is confined to the AXI **master** path:
`pl_fe_top/m_axi` → `plfe_hp` (a 1x1 `axi_interconnect`) → *two automatically inserted protocol
converters* → `S_AXI_HP2`. The block has only ever been simulated against a testbench slave
that always answered OKAY, so the protocol corner that this hardware is rejecting has never been
exercised. Two concrete instruments, in order of cost:

1. **An ILA on `m_axi`** (AWADDR/AWLEN/AWVALID/AWREADY, WVALID/WREADY/WLAST, BVALID/BRESP/BREADY)
   — note the two ILAs that were removed tonight were on the video path and would not have
   helped here; an `m_axi` ILA never existed.
2. **Re-run the RTL testbench with an AXI protocol checker / VIP slave** instead of the
   always-OKAY stub, which is cheaper and catches the same class of bug in simulation.

Until that is understood, `MB_PLFE_ON` must stay at **0**: at 1 the station keeps working (the
fallback is taken every loop) but the PL burns 187 KB of rejected writes per pass for nothing.

## 5b. A second surprise: the documented "safe bitstream" is not what the station runs

Restoring the station to `safe_bitstreams/BIT_20261024_fp1.bit` — the file the failure report
names as the station's bitstream — gave a **dead capture path**: the bring-up script's own
control check read

```
camera0 CONTROL=0/32 words   camera1=0/32 words
*** the CONTROL did not move -> THIS MEASUREMENT IS VOID
```

cameras accepted their 303/303 register tables and the display timing verified, but no store was
written. Loading the attempt bitstream straight afterwards gave 28/32 and 24/32. So the file is
**not interchangeable with the design the station was running**, and it must not be treated as a
rollback target without testing it. The pre-integration design *as rebuilt tonight*
(`safe_bitstreams/BIT_20261028_baseline_rebuilt.bit`) is the one that corresponds to the current
block design; it has not been tested on the board either.

## 7. What is left to do

1. **Fix the AXI master defect** (§5). It is the blocking item: the front end is present,
   answers its registers, computes 46,800 values, and cannot write them. The A/B cannot produce
   a result until this is fixed, because the PS takes the fallback every loop (correctly).
   Cheapest instrument first: an AXI protocol checker / VIP slave in the existing testbench.
2. **Pin down which bitstream the station was actually running** (§5b). `BIT_20261024_fp1.bit`
   is not it, or not for this bring-up; the pre-integration rebuild from tonight is the candidate
   that matches the current block design, and it needs a board test before anything relies on it.
3. **Only then the A/B**, which needs the operator: pin the exposure
   (`ps_fft_dual/a3_restore_20261028.tcl`), **empty belt** → `MB_CMD = 12` (background),
   **one good board** → `MB_CMD = 9` (reference), `python dl\host_qc\preflight.py` must PASS,
   then `xsdb dl\measure_plfe_ab_20261028.tcl <tag> 12 EAA4676C` (A/B/A, 12 windows per arm,
   writes only `MB_PLFE_ON`) and `python dl\plfe_ab_analyze.py dl\measure_plfe_ab_<tag>.log`.
   Primary statistic `MB_T_CAM` (word 73); control group `class + qual + panel + tail + pub`;
   the A/A arm is the resolution limit.
4. Never headline `MB_T_TOTAL`: its own between-arm spread was 79 % of the mean.

**The station's original firmware** was `TSC1904A1527`; it is recoverable from git
(`git show HEAD:ps_ui/ps_ui.elf` → a 200,504-byte ELF containing the string `904A1527`), which
was verified by scanning the committed blob, not assumed. It is *not* preserved in
`safe_firmware/`, which holds only a 2026-10-22 build.
