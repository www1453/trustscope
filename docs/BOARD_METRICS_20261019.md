## 2. 判决接口（已实现，待上板）

`ps_ui/verdict.c` 提供一个**只会偏安全**的状态机：

| 输入 | 输出 |
|---|---|
| `MB_VERDICT`(164) = 1 (OK) | `GPIO1_DATA = 0x01`（放行） |
| `MB_VERDICT`(164) = 2 (NG) 或 3 (UNKNOWN) | `GPIO1_DATA = 0x02`（保持停带） |
| 超时未收到判决 | `GPIO1_DATA = 0x02`（保持停带） |
| 判决的 `job_id` 与当前板不符 | **不动作**，状态记 `S_STALE` |

**四条硬规则**（写进代码注释，也在这里重复）：

1. `V_NONE = 0`，所以一块全零的 DDR 永远不会被读成 PASS；
2. **UNKNOWN 不是 PASS**；
3. **超时不是 PASS**；
4. **上一块板的判决不能复用到下一块**（按 job_id 拒绝）。

状态码写在 `MB_VSM`(167) 高 8 位，输出位在低 8 位——这样"为什么板子不动"可以当场读出来，
而不是靠猜。

## 3. 验收规程

### 3.1 连续运行（驱动/采集）

```
时长：30 分钟（首轮门槛；已做过 10 分钟，需延长）
动作：物体在两路相机前持续移动，中途切视图、触摸各 3 次
通过：两路缓冲在整个窗口内"能变"的次数 ≥ 95%，fault 全程 0
```

### 3.2 停带抓拍（闭环）

```
次数：≥100 次停带抓拍
每块板记录：job_id、frame_id、判定、动作、端到端耗时
通过：100% 的板都有对应的 job_id 与动作；无一次"沿用上一次 PASS"
```

### 3.3 故障注入（这是最容易漏、也最加分的一项）

| 注入 | 期望行为 | 现状 |
|---|---|---|
| 不写 verdict | 超时后 HOLD，屏幕显示原因 | 代码就绪，未测 |
| 写错 job_id | 不动作，`S_STALE` | 代码就绪，未测 |
| 写 UNKNOWN | HOLD | 代码就绪，未测 |
| 运行中断开网络 | 保持停带，不继续放行 | `TBD`（无以太网） |
| 运行中相机停流 | 侧判断为"无法检测"，不放行 | `TBD` |

### 3.4 记录要求

每次实验必须同时保存：`bit`/`ELF` 的 SHA256、当时的视图、时间、原始邮箱快照。
**没有这三样，数字不能进报告。**

## 4. 与 PC 侧指标的分工（报告里必须分开写）

| 归属 | 指标 | 不能混用 |
|---|---|---|
| **板端** | 采集吞吐、控制时延/抖动、超时行为、网络带宽 | 不能拿 PC 的推理速度当 FPGA 性能 |
| **PC 端** | 检测耗时（0.46 s @ 5 MP 实测）、检出/误报 | 不能写成"FPGA 加速后达到" |

## 5. 已知缺口

- 控制时延/抖动**没有数据**——需要板子 + 一次 verdict 往返；
- 网络带宽**没有数据**——以太网未实现；
- 端到端节拍**没有数据**——传送带未接线；
- `verdict_step()` **没有被主循环调用**：它已编译进 ELF，但需要在一个确定的时刻
  （每块板开始时传入 `job_id`）被调用，这属于上板联调的一部分，现在不宜盲接。
