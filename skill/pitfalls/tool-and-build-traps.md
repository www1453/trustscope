## T0 · Vivado 的 JVM 会在半路静默死掉，只留下一个 0 字节的 `hs_err`

**现象（2026-09-22）**
`batch_build.tcl` 跑到 `launch_runs impl_1 -to_step write_bitstream -jobs 12`
这一行就结束了：

- 进程退出码 1
- 日志停在 `IPCACHE: runCacheChecks() calling threadPool finishWork()`，**没有任何 ERROR**
- 工作目录里出现 `hs_err_pid15304.dmp`，**大小 0 字节**
- `reset_run` 已经把旧比特流删掉了，**磁盘上什么都不剩**

**根因（高置信，非证实）**
`-jobs 12` 会同时拉起 12 个 vivado 子进程。JVM 被系统杀掉（最可能是内存），
崩得太快，连 `hs_err` 都没来得及写完，所以拿到的是一个**空文件**。

**这不是"构建失败"** —— 构建根本没走到会失败的地方。
把它当成"某条约束不满足"去查，会浪费很多时间。

**修复**
```tcl
launch_runs impl_1 -to_step write_bitstream -jobs 4
```
只损失墙钟时间，不动设计。再跑就正常走完 `opt_design → place → route → write_bitstream`。

**教训（两条）**
1. **`-jobs` 不是越大越好**：它是"同时开几个 vivado"，不是"用几个核"。
2. **`reset_run` 会先删掉产物**。任何"重建"脚本在执行前必须**先备份现有比特流** ——
   这次正是因为备份了，失败时才有东西可退。

**适用 / 失效条件**
- 适用：Vivado/Vitis 的 `launch_runs`、任何会 fork 大量子进程的批量流程
- 失效：机器内存充足且 `-jobs` 与核数匹配时，确实更快 —— 前提是你**盯着它跑完**

## T1 · 构建"成功"了，但产物根本没重新生成

**触发条件**
用脚本或 Makefile 构建，且**源文件是通过拷贝/同步方式更新**的（而不是直接编辑）。

**现象**
- `make` 输出 `Nothing to be done for 'main-build'`
- **退出码是 0** —— 任何只看退出码的流程都会判定"成功"
- 烧进板子后，行为还是旧版本的

**根因**
构建系统靠**时间戳**判断是否需要重建。而 **PowerShell 的 `Copy-Item` 会保留源文件的
修改时间**。于是目标 `.c` 的时间戳仍然早于已编译的 `.o`，构建系统认为"无需重建"。

**排查步骤**
1. 比较三类文件的时间戳：**源文件 / 中间产物 / 最终产物**
2. 特别确认**最终产物的时间戳**是否晚于你最后一次修改
3. 看构建日志里有没有 `Nothing to be done` / `up to date` 这类词
   —— 出现即代表**没有真的重编**

**修复**
```powershell
# 拷贝后强制刷新时间戳
Copy-Item $src $dst -Force
(Get-Item $dst).LastWriteTime = Get-Date
```
然后**用产物时间戳**确认真的重编了（不是看退出码）。

**适用 / 失效条件**
- 适用：任何基于时间戳的构建系统（make、ninja、部分 IDE）
- 失效：使用内容哈希做增量判断的构建系统（如部分 Bazel 配置）不会踩这个坑

**来源**
本队真实踩坑：相机测试程序改了源码、`make` 报了 `Nothing to be done` 且退出码 0，
连续两次运行"新版本"其实都是旧二进制。**这个坑最危险的地方是它不报错。**

## T2 · 比特流下载报 `DONE PIN is not HIGH`

**触发条件**
把厂商提供的 `BOOT.bin` 拆开、取出其中的比特流分区单独下载。

**现象**
```
ERROR: fpga configuration failed. DONE PIN is not HIGH
```
看起来像**硬件故障**（FPGA 没配置成功）。

**根因**
**两个容器的字节序不同**：
- 启动镜像里的比特流分区是**小端 32 位字**
- `.bit` 文件的载荷是**大端**

直接把分区数据套上 `.bit` 头，数据整体是反的，FPGA 当然不认。

**排查步骤**
1. 确认你是不是从 `.bin` 里直接截取的数据
2. 用 `bootgen -read <boot.bin> -o out.bif` 打印分区表，
   **注意：分区表里的 length 单位是"字"，字节数要 ×4**
3. 检查 `.bit` 头的合法性：13 字节魔数 `00 09 0F F0 0F F0 0F F0 0F F0 00 00 01`，
   之后是 `a`(design) `b`(part) `c`(date) `d`(time) 四组 tag+长度+字符串，
   最后是 `e` + **4 字节大端**载荷长度

**修复**
把分区载荷**按每 4 字节整体翻转**，再套上正确的 `.bit` 头。

**适用 / 失效条件**
- 适用：Xilinx 7 系列启动镜像 ↔ `.bit` 互转
- 失效：如果原始文件本身就是 `.bit`，不需要转换

**来源**
本队真实踩坑：误判为"比特流损坏/硬件问题"，实际是字节序。
修复后日志变为 `VENDOR BITSTREAM LOADED`。

## T3 · 脚本能跑通，但硬件毫无反应

**触发条件**
用命令行工具（如 XSCT）执行一系列配置动作。

**现象**
脚本逐条执行、没有报错，但设备行为完全没变。

**根因**
**命令根本不存在，而错误被 `catch` 吞掉了。**

**排查步骤**
1. **先确认命令存在** —— 不要假设某工具一定有某个子命令
2. 检查脚本里每一处 `catch`：**捕获后有没有把它变成可观测的输出**
3. 用"全量命令列表"验证：把工具的可用命令打出来，搜索你用的那条

**修复**
- 把 `catch` 改为"捕获后**打印错误**"，而不是静默继续
- 对关键命令做**存在性检查**，不存在就明确报错退出

**适用 / 失效条件**
- 适用：任何带 `catch`/`try` 的自动化脚本
- 失效：—

**来源**
本队真实踩坑：脚本里用了 `program_flash`，一路无输出、看起来正常，
实际上 **XSCT 根本没有这条命令**。后来打印完整命令列表才确认。

## T4 · 代码逻辑没问题、但性能差好几倍（Debug 构建默认 `-O0`）

**触发条件**
在 IDE 生成的工程里直接构建并测性能，**从未检查过编译优化等级**。

**现象**
功能完全正确，但性能远低于预期。实测对比（同一块板、同一份源码，只改编译选项）：

```
-O0 :  29.4 fps    单帧 33.6 ms
-O2 :  80.6 fps    单帧 12.4 ms      ← 2.74 倍
```

分项来看，热点函数提速约 **4.7 倍**。

**根因**
**IDE 生成的 Debug 配置默认使用 `-O0`（完全不优化）。**
在这种模式下，每一次数组下标、每一次边界检查、每一次指针算术
都会生成真实指令。例如一个"写一个像素"的函数里有：
4 次边界比较 + 2 次乘法 —— 在 `-O0` 下全部照单执行。

**排查步骤**
1. **先去构建产物里找编译命令行**（不是看 IDE 界面上的"优化等级"选项）：
   ```powershell
   Get-ChildItem <build_dir> -Recurse -Include *.mk |
     Select-String -Pattern 'gcc .*-O'
   ```
2. 确认实际生效的是 `-O0` 还是 `-O1/-O2/-Os`
3. 用**同样的源码**跑一次 `-O2`，对比数字

**修复**
把构建配置的优化等级改成 `-O2`（或 `-Os`）。

⚠️ **注意**：改了 `.mk` / 生成文件后需 `make clean` 才能全量重编，
否则部分目标文件仍带着旧参数。

⚠️ **改完必须回归验证**：`-O2` 会暴露依赖时序的代码问题
（缺 `volatile`、依赖未定义求值顺序）。本例中所有硬件寄存器访问
本来就用 `volatile` 声明，所以直接通过；**但如果没加，`-O2` 下会出诡异故障**。

**适用 / 失效条件**
- 适用：任何 IDE 生成的 Debug 构建（Vitis / STM32CubeIDE / Keil / Xilinx SDK）
- 失效：发布构建 / 手工编写的 Makefile 通常已经是 `-O2`

**来源**
本队真实踩坑：UI 帧率卡在 29.4 fps 且明显闪烁，
先后改了离屏渲染、32 位填充都收效甚微。**逐阶段插桩测出热点在绘制函数（24.77 ms/帧）**，
再回头查构建参数，才发现一直是 `-O0`。**改一个字母，帧率翻 2.7 倍。**

**教训**：**性能问题先看构建参数，再改代码。**

## T5 · 脚本报"缺少右括号"，但错误行看起来完全正常


**触发条件**
在**中文 Windows** 上写 `.ps1` / `.tcl`，且脚本**内含中文**。

**现象**
- PowerShell 报解析错误
- 或 Vivado Tcl 报 `missing close-brace`，但指向的位置完全无关

**根因**
Windows PowerShell 按**系统代码页（GBK）**解析 `.ps1`；
Vivado Tcl 在中文环境下也会按 GBK 读 `.tcl`。
**UTF-8 的中文字节被按 GBK 解码时，可能吞掉一个引号/括号**，
于是语法结构在解析器眼里彻底错位。

**排查步骤**
1. 检查文件里有没有非 ASCII 字节：
   ```powershell
   $b=[IO.File]::ReadAllBytes($f); ($b | Where-Object {$_ -gt 127}).Count
   ```
2. 报错位置和肉眼看到的"问题行"**对不上**时，优先怀疑编码

**修复**
**脚本内容一律只用 ASCII。** 中文只出现在**人读的文档**里，不进脚本。
（需要输出中文时，用字符串拼接或让调用方翻译。）

**适用 / 失效条件**
- 适用：中文 Windows 上的 `.ps1` / `.tcl` / `.bat`
- 失效：英文系统默认代码页为 437/1252，风险低但**仍然建议只用 ASCII**

**来源**
本队真实踩坑：一个含中文的 `.ps1` 报解析错误，改成全 ASCII 后立刻正常。
Vivado BD 脚本也踩过同类问题，因此 `templates/bd_patch_template.tcl` 全程英文。

## T6 · 顶层构建"成功"，但链接进比特流的是过期缓存

**触发条件**
设计中存在**独立综合的层次** —— 例如 Vivado Block Design 里以 HDL `module_ref`
形式加入的模块（`SYNTHESISFLOW = OOC_HIERARCHICAL`），
或任何带独立综合运行的单元。

**现象**
- 构建日志显示 `impl_1 STATUS = write_bitstream Complete!`、`PROGRESS = 100%`
- **顶层综合与实现确实重跑了**（时间戳会更新）
- **但你改的 RTL 逻辑没有任何效果** —— 行为与改动前**逐位相同**

**根因**
每个 HDL module_ref 有自己的 **out-of-context 综合运行**，
产物是一份缓存的检查点（`.dcp`）：

```
<proj>.runs/<module>_0_0_synth_1/<module>_0_0.dcp
```

顶层只是**链接**这份 dcp。而构建脚本只重置了顶层运行：

```tcl
reset_run synth_1
reset_run impl_1        # 漏掉了 design_1_<module>_0_synth_1
```

于是 dcp 停留在源文件被修改**之前**，而顶层每次都在"成功"地链接一份旧逻辑。

**真实数据（本队踩坑）**
```
<module>_0_0.dcp   2026-09-17 13:44   ← 缓存，没动
rtl/capture_ram.v              2026-09-18 14:55   ← 我改的源文件
synth_1                        2026-09-18 18:08   ← 重跑了
impl_1                         2026-09-18 18:17   ← 重跑了，报 Complete!
```
**整整一天的 RTL 修改，一版比特流都没进去。**

**排查步骤**
1. 列出工程里**所有运行目录**及其时间戳：
   ```powershell
   Get-ChildItem <proj>.runs -Directory |
     ForEach-Object { "{0,-45} {1}" -f $_.Name,$_.LastWriteTime }
   ```
2. 对每个 `*_synth_1` 目录，检查其中 `.dcp` / `__synthesis_is_complete__` 的时间戳
3. **把每个缓存产物的时间戳与对应源文件对比** —— 任何一个旧于源文件就是陈旧

**修复**
```tcl
# 重置全部运行，而不是只重置顶层那两个
foreach r [get_runs -quiet] {
    if {[catch { reset_run $r } e]} { puts "  reset_run $r FAILED: $e" } else { puts "  reset_run $r ok" }
}
```
并在构建末尾**加断言**，让构建自己报告有没有陈旧产物：
```tcl
if {[file mtime $dcp] < [file mtime $src]} {
    puts "*** FAIL: dcp is OLDER than the source -- RTL edit NOT linked in ***"
}
```

**适用 / 失效条件**
- 适用：任何有分层/独立综合缓存的流程（Vivado OOC、module_ref、部分增量综合）
- 失效：全平铺、每次从源文件全量综合的设计不会踩这个坑

**来源**
本队真实踩坑。这个坑最有欺骗性的一点：**它的每一层输出都是"成功"的** ——
脚本不报错、日志写 `Complete!`、退出码 0。唯一的异常是"改了等于没改"。
而"改了等于没改"极易被误判成**另一个逻辑问题**（见 T7）。

⚠️ **一个看似正确、实则会给出假阳性的检查**
踩坑当时我用过这么一个验证，并且据此写了一行错误结论：
```
bitstream  modified : 2026/9/18 18:17:30
capture_ram.v       : 2026/9/18 14:55:42
VERDICT: bitstream is NEWER than the trigger fix -> fix IS in the bitstream
```
**这个结论是错的。** 比特流确实比源文件新，但它是**用一份过期的 OOC 检查点组装**出来的。

> **当构建存在分层/独立缓存时，"最终产物比源文件新"不能证明
> "源文件进了产物"。**

要证明这一点，必须**逐层验证**：每个中间缓存产物（`.dcp`、`.o`、生成文件）
都要比它自己的输入新。所以修复方案里加的是**逐层的断言**，而不是只比最终产物。

## T7 · 一个改动"完全没有效果"时，先怀疑它压根没进去

**触发条件**
改了一处逻辑，重新构建、重新烧板，**观测结果与改动前逐位相同**。

**现象**
行为**一模一样**，没有任何细微差别。

**根因（一般化）**
"改动没效果"有两类完全不同的原因，处理方式**相反**：

| 类别 | 含义 | 证据特征 |
|---|---|---|
| **A. 改动没进产物** | 构建 / 链接 / 缓存问题 | 新旧行为**逐位相同** |
| **B. 改动进去了，但被更早的故障遮住** | 上游还有一个没解决的故障 | 通常**有细微差别**（耗时、计数） |

**A 类的特征是"完全一样"。** 哪怕测量里只出现一点点差异，也更可能是 B。

**排查步骤**
改动**之前**先记下当前可观测量的数值；改动**之后**：
1. 若**逐位相同** → 先验证改动是否真的进了产物
   （比对时间戳 / 反查网表 / 加一个"必然可见"的输出，例如把某计数器强制成常数）
2. 若**有细微差别** → 改动进去了，去查被遮住的上游故障

**修复**
- 建立**产物新鲜度断言**，让构建自己回答"我的改动进去了吗"
- 即使时间紧，也先用**一个必然可见的改动**（例如强制某输出恒为 1）验证整条链路
  —— 成本几分钟，能避免整天在错误的前提上推理

**来源**
本队真实踩坑：把"改动完全无效"误判成"另一个时序问题"，
并据此写了第二个修复。**两个问题都真实存在，但顺序错了** ——
必须先确认改动进了产物，才有资格讨论第二个问题。

## T8 · 无害的 stderr 让整条构建"失败"，其实它本来能成功

**触发条件**
在 **PowerShell** 里调用原生命令（`make` / `gcc` / `xsct` / `vivado`），
同时满足：① 脚本设了 `$ErrorActionPreference = "Stop"`；② 命令输出用 `2>&1` 合并。

**现象**
- 脚本在构建**中途**报错退出，`exit code = 1`
- 报错内容是一条**看起来无害的告警**
- 产物**没有生成** —— 因为脚本被中断了

**根因**
PowerShell 在 `Stop` 模式下，**原生命令写到 stderr 的任何输出都会被当成终止性错误**
（表现为 `RemoteException`）。而很多工具（`make`、`gcc`）本来就会往 stderr
打**正常的进度/告警信息**，那不是错误。

真实例子：Vitis 生成的 makefile 里有这么一段
```make
pre-build:
	-a9-linaro-pre-build-step      # 前缀 - 表示"失败也忽略"
```
`a9-linaro-pre-build-step` 是 Vitis IDE 环境里的钩子，纯 shell 下不存在。
`make` 把它报成
`process_begin: CreateProcess(NULL, a9-linaro-pre-build-step, ...) failed.`
写进 stderr —— **但 makefile 作者用 `-` 明确声明了可以忽略**，构建会照常继续。

而 `$ErrorActionPreference = "Stop"` + `2>&1` 让 PowerShell **在这一行直接终止**，
`make` 只编了一部分，`FFT22.elf` 根本没生成。

**排查步骤**
1. 看到"构建失败"但日志里只有一条**看起来无关的告警** → 怀疑这个坑
2. 检查脚本里有没有 `$ErrorActionPreference = "Stop"` 和 `2>&1` **同时出现**
3. **不要只看退出码**，去看产物：
   - 产物不存在 → 确实没编完（但原因可能是被假错误打断）
   - 产物存在且时间戳正确 → 那只是纯告警

**修复**
```powershell
# 方案一：不要用 Stop
$ErrorActionPreference = 'Continue'

# 方案二（更稳）：用 cmd /c + 文件重定向，彻底绕开 PowerShell 对 stderr 的处理
cmd /c "make all > build_out.txt 2>&1"
$code = $LASTEXITCODE
Get-Content build_out.txt
```

**适用 / 失效条件**
- 适用：PowerShell 5.1 与 7 都有此行为；调用任何会写 stderr 的原生命令
- 失效：改用 cmd、或用文件重定向 + 事后读文件，可完全规避

**来源**
本队真实踩坑。脚本报了 `exit code 1`，我一度认为 Vitis 构建失败；
**真正的证据是 `Debug\` 下既没有 `.elf`、也没有任何一个 `.o`** ——
说明 `make clean` 跑完了，而 `make all` 只干了一部分就被人为掐断。
与 T1 同属"不要只看退出码"，但成因完全不同。

## T9 · "Project is read-only"，其实是环境权限，不是工程坏了

**触发条件**
工程不在当前工作目录下（例如在另一个盘），且运行在**受限权限/沙箱**环境里。

**现象**
```
ERROR: [Project 1-228] Project '<proj>' is read-only.
       To save your work, please use the 'File | Save Project As...' command first.
```
看起来像工程被加了只读属性，或被别的进程占用了。

**根因**
**工作区之外不可写。**
Vivado 在 `generate_target all` 那一步要往 `<proj>.gen/` 和 `.runs/` 写产物，
写不进去就报这个错。

实际情况：`.xpr` 的属性是 `Attributes = Archive, IsReadOnly = False` ——
**文件本身完全可写**。而**同一条命令在更早的时候是成功的**（比特流已经写出来了），
说明权限策略是**中途变过**的。

**排查步骤**
1. **不要先怀疑工程**，先做一次裸写入测试：
   ```powershell
   try { Set-Content "$projdir\__wtest.txt" 'x' -ErrorAction Stop; "WRITE OK" }
   catch { "WRITE FAILED: $($_.Exception.Message)" }
   ```
2. **对照实验**：往工作区里写一次，确认工作区是可写的
3. 检查文件属性 `IsReadOnly` —— **它如果是 False，那就不是只读属性问题**
4. **回忆这条命令以前成功过吗** —— 成功过就说明是环境/策略变了，而不是工程坏了

**修复**
在允许写入该路径的模式下运行，或把工程放到可写目录里。

**适用 / 失效条件**
- 适用：任何"工具报权限错、但文件属性正常"的场合（容器、沙箱、只读挂载、网络盘）
- 失效：文件真的是只读属性时，改属性即可

**来源**
本队真实踩坑。差点去改工程的 `.xpr` 属性，而那和真正原因完全无关。
**"这条命令以前能跑"是一条极有价值的线索** —— 它把"工程配置错误"
直接排除掉，指向环境变化。

## T10 · `Set-Location` 之后，.NET 的相对路径仍然指向别处

**触发条件**
在 PowerShell 脚本里 `Set-Location` 切到某个目录，
然后**用 .NET 静态方法操作相对路径**（`[System.IO.File]::ReadAllBytes` 等）。

**现象**
```
input : 0 bytes
Exception calling "ReadAllBytes" with "1" argument(s):
  "Could not find file '<working-dir>\fb_dump.bin'."
```
文件明明就在刚 `Set-Location` 过去的目录里，
报错里显示的却**是另一个目录**。

**根因**
**PowerShell 的"当前位置"和 .NET 进程的"当前目录"是两个东西。**
`Set-Location` 只改 PowerShell 自己的位置，**不改 `[Environment]::CurrentDirectory`**。
而 `[System.IO.*]` 用的是后者 —— 也就是**启动脚本时所在的目录**。

所以同一个脚本里：
- `Get-ChildItem .\x.bin` → 找的是**新目录** ✓
- `[IO.File]::ReadAllBytes(".\x.bin")` → 找的是**老目录** ✗

**排查步骤**
1. 看报错信息里的**绝对路径**，判断它到底在哪儿找文件
2. 对比 `Get-Location` 和 `[Environment]::CurrentDirectory` —— **两者会不一样**
3. **凡是 .NET 文件 API，一律传绝对路径**

**修复**
```powershell
# 不要这样：
Set-Location $dir
& "$dir\script.ps1" -In '.\dump.bin'          # 可能解析到别处

# 要这样：
& "$dir\script.ps1" -In "$dir\dump.bin"       # 全程绝对路径
```
或者显式同步两者（不推荐，容易漏）：
```powershell
[Environment]::CurrentDirectory = (Get-Location).Path
```

**适用 / 失效条件**
- 适用：PowerShell 调用 .NET 文件 API、或调用内部用 .NET 的脚本
- 失效：纯用 PowerShell cmdlet（`Get-ChildItem` / `Get-Content`）时不受影响

**来源**
本队真实踩坑。一个帧缓冲转 PNG 的工具脚本报"文件不存在"，
而文件清清楚楚就在当前目录里。**是工具脚本自己的路径解析问题，不是文件问题。**

## T11 · 函数里直接写字符串，被 `if` 吞掉后什么都不打印

**触发条件**
PowerShell 函数里用**裸字符串**输出信息，然后这样调用：
```powershell
if (Show-Something ...) { $count++ }
```

**现象**
**计数是对的，但明细一行都不打印。**
```
  channels rendered : 9 of 9        <- 数字对了
  (下面本该有 9 行通道明细，全都没有)
```

**根因**
**PowerShell 函数的"输出流的全部内容"就是它的返回值。**
函数里每一句裸字符串都进了输出流，于是 `if (...)` 拿到的是一个
**"9 个字符串 + 1 个布尔"的集合**，它对这个集合求真假后就**丢弃**了 ——
字符串从来没被打印过。

而布尔判断仍然正确，所以**计数看起来完全正常**，
只是明细凭空消失 —— 非常容易被当成"脚本就是这样设计的"。

**排查步骤**
1. 函数里有裸字符串，并且调用点用它的结果做判断 → 立刻怀疑这条
2. 把 `if (F ...)` 临时改成 `$r = F ...; $r | ForEach-Object { $_ }`，
   如果明细突然出现了，就是这个坑

**修复**
- 想把内容**打到屏幕上** → 用 `Write-Host`
- 想把内容**返回给调用方** → 用 `Write-Output`，并在调用点显式接收
```powershell
function Show-Color {
    param(...)
    Write-Host ("  {0,-28} ..." -f ...)     # 只打印，不进返回值
    return $true                             # 只返回布尔
}
```

**适用 / 失效条件**
- 适用：所有 PowerShell 函数（这是 PowerShell 与其他语言差别最大的一处）
- 失效：—

**来源**
本队真实踩坑。一个帧缓冲分析脚本汇报"9 of 9 通道"，
**却没有任何证据行** —— 我差点就接受了这个没有明细的结论。
和 M10 是同一件事的另一面：**"有结论、没证据"，要当场发现。**

## T12 · 连续开 XSCT 会话时，`connect` 返回了但目标树还没枚举完

**现象（2026-09-24）**
一条命令里连着跑三个 xsct 脚本（启动 → 切换模式 → 读数），第三个失败：

```
xsct.bat : no target with id: 2
    invoked from within "targets -set 2"   (file "run_diag4.tcl" line 35)
```

**排查（关键：先看目标到底在不在）**
另开一个**只读**脚本把真实目标表打出来：

```
  1  APU
  2  ARM Cortex-A9 MPCore #0 (Running)
  3  ARM Cortex-A9 MPCore #1 (Running)
  4  xc7z020
  5  Legacy Debug Hub
```
**目标一直在**，板子是好的。所以问题不是"编号变了"，而是**时序**。

**根因**
`connect` 返回 ≠ JTAG 链已枚举完成。前一个会话的 `hw_server` 还在退出，
下一个会话连上去时目标树是空的，紧接着的 `targets -set 2` 就报"no target"。

**修复（重试，而不是换编号）**
```tcl
if {[catch { connect } e]} { puts "CONNECT FAIL: $e"; exit 1 }
set cpu_ok 0
for {set attempt 0} {$attempt < 40} {incr attempt} {
	if {![catch { targets -set 2 } e2]} { set cpu_ok 1; break }
	after 500
}
if {!$cpu_ok} { puts "NO CPU TARGET after 20 s"; targets; exit 1 }
```

**为什么不"改成按名字选"**：改名/换板都会变，**重试**才是对准根因的做法。
排查时用名字确认目标存在，运行时用重试等待它出现。

**教训（两条）**
1. **硬编码 JTAG 目标号**在单次会话里没问题，在连续会话里会偶发失败
2. **报错说"没有目标"时，先验证目标是否真的没有** —— 这次它一直在，
   如果直接相信报错去改编号，就会把偶发的时序问题"修"成一个稳定的错误

**适用 / 失效条件**
- 适用：任何"启动/配置/读数"分多次会话执行的自动化流程（XSCT、OpenOCD、脚本化调试器）
- 失效：会话之间没有 hw_server 复用、或启动本身就等目标就绪的平台

## T13 · `reset_run impl_1` 只重跑实现，**静默复用上一次的综合**

**触发条件**
改了**会影响综合**的东西（BD 里的时钟频率、IP 参数、RTL），
但为了省时间只 `reset_run impl_1`，然后 `launch_runs impl_1`。

**现象**
构建"成功"，比特流也生成了，**但行为和你刚改的配置不符**。
（本例：BD 里 FCLK0 明明已改回 50 MHz，产出的却是带 100 MHz 时序违规的比特流。）

**根因**
Vivado 的 run 依赖管理会复用前一级：
**只 reset impl 就只重跑 impl**，synthesis 仍是**上一次配置**的产物。
"旧综合 + 新约束"从日志上看不出任何异常。

**排查**
- 看 `get_property STATUS [get_runs synth_1]` / `[get_runs impl_1]` **是不是刚重跑的**
- **最可靠：看产物里的关键配置**。本例在时序报告里一句话就露馅：
  `Clock Summary` → `clk_fpga_0 = 100.000 MHz`
- 更快的旁证：生成的 `ps7_init.tcl` 里 `FPGA0_CLK_CTRL` 的低位
  （`0x00600600`=50 MHz / `0x00300600`=100 MHz）

**修复**
改动影响综合 → **`synth_1` 和 `impl_1` 都要 reset**。

**规律**
> **"增量重跑"省的是时间，赌的是"这一改动不影响前一级"。**
> 每次这样省时间，都必须**主动验证产物里的关键配置**，而不是相信"构建成功"。

**适用 / 失效条件**
- 适用：Vivado / Vitis 这类有 run 依赖管理的增量构建
- 失效：每次全量重跑（慢，但没有这个风险）

## T13b · 程序在跑、帧率正常、屏幕全黑 —— 漏掉了 PL 模块的 PS 侧初始化

**现象（2026-09-24）**
重写的质检界面下载运行后：

- 应用**正常运行**：`frame` 计数持续增长、`fps = 75`、每帧渲染 13 ms
- 快照读到的一切都对（magic、自检、判定、质量特征）
- **屏幕全黑，什么都没有**

没有任何报错，没有崩溃，所有可读的指标都显示"正常"。

**根因**
新的 UI 只做了两件事：往 `DISP_BUF` 写像素、`memcpy` + flush。
但**这块屏不是"写内存就有画面"** —— 它由 PL 里的两个模块驱动：

| 模块 | 作用 | 谁配置它 |
|---|---|---|
| `v_tc` | 产生 800×480 的行/场时序 | **PS 必须写它的寄存器** |
| `axi_vdma_1` (MM2S) | 扫描 `DISP_BUF` 送进视频通路 | **PS 必须设地址并使能** |

这次是**全新启动**（`rst -system` → `ps7_init` → 下载 ELF），这两个模块的寄存器是空的
→ **没有任何东西在扫描显存** → 屏黑。

重写界面时，我把旧程序里那整段 `display_init()` **漏掉了**。

**为什么难发现**
"程序在跑"和"画面在出"是**两条独立的链路**，而所有能自动读到的证据都来自第一条。
CPU 报告 75 fps 是真的（它确实在写显存），但这与"屏上有没有东西"**根本不相关**。
这和 T6（构建说成功但链接的是过期缓存）是同一类：**证据的覆盖面被高估了**。

**修复**
从**已确认能点亮这块屏**的程序里移植初始化，并保留它踩出来的两个细节：

1. **`C_NUM_FSTORES = 3` → 三个 FrameStore 地址都必须设成合法值**
   （只设 FS0 会让 FS1/FS2 指向 `0x0` → `SLVERR` → VDMA 自停）
2. **v_tc 要在 VDMA 启动之后"再使能一次"**（既有验证顺序，不要自己重排）

**顺带解决的定位问题**
新增的 `display_init()` 有返回值，并且**把它写进快照**：

```c
if (display_init() != 0) { sn[1] = 0xDEAD0001u; while (1) { } }
sn[1] = 0x600D0002u;
```
于是"初始化是否成功"变成**一次 JTAG 读数就能判定**的事，
而不是靠"屏上有没有东西"这种只能靠人眼、且分不清故障层次的信号。

**规律**
> **"我的代码在运行"和"我的输出被外部世界接收了"是两回事。**
> 只要后者依赖一个**你没有初始化的外部模块**，它的开关状态就不会出现在你的任何日志里。

**适用 / 失效条件**
- 适用：CPU + PL 协同（Zynq/MPSoC）、任何"CPU 写入 + DMA/外设消费"的结构、
  驱动重新初始化后未复位的硬件模块
- 失效：外设由硬件上电自动工作、或由操作系统驱动全权负责时（那时问题会出现在驱动层）

## T14 · Tcl `proc` 里直接用全局变量 → 变量不可见 → 被 `catch` 吞掉 → **什么都没做**

**触发条件**
在 `proc` 里引用脚本顶层定义的变量（输出路径、地址、文件前缀），
而调用处套了 `catch`。

**现象**
脚本"跑完了"、退出码 0、日志也没有红字 —— 但**什么都没发生**。
（本例：帧存 dump 一个文件都没生成，日志里只是少了那几行 "dumped ..."。）

**根因**
Tcl 的 `proc` 默认只有**局部作用域**。引用未定义的 `$OUT` / `$BUFA` 会抛错，
而这个错被外层 `catch {}` 吃掉 → 静默继续。

**排查**
1. **凡是"应当产生副作用"的步骤，必须显式检查产物**：
   `file exists` + `file size`，并把结果打进日志
2. **不要写裸 `catch {}`**：
   `if {[catch { ... } e]} { L "FAILED: $e" }`
3. 所有跨 proc 使用的变量**显式 `global`**，或干脆**传参**

**规律**
> **裸 `catch {}` 是"静默失败"的温床。**
> 凡是你期望产生某个产物的地方，**产物本身就是判据** —— 去检查它，
> 不要因为"没有报错"就认为它做成了。

**适用 / 失效条件**
- 适用：任何"作用域 + 异常吞掉"的组合（Tcl / PowerShell / shell）
- 失效：变量全部显式传参且异常全部带日志

## T15 · PowerShell 里 `"$name.bin"` 被解析成**属性访问**，参数直接消失

**触发条件**
在 PowerShell 里用 `$var.suffix` 拼接文件名/参数，例如 `py script.py $n.bin`。

**现象**
命令"成功"，但处理的**永远是默认文件/默认参数**。
（本例：四个不同文件的测量输出了**四个完全相同的数字** —— 因为全都读的是同一个默认文件；
那个默认文件恰好是上一轮留下的，于是"四个都测到了 117.8"。）

**根因**
PowerShell 把 `$n.bin` 解析为**对 `$n` 取 `.bin` 属性**。
字符串没有这个属性 → 展开为空 → 参数丢失 → 被调程序退回默认值。

**排查**
**"几个不同的输入产出完全相同的输出"** —— 这就是标志。
立刻回头确认参数是否真的传进去了（而不是去怀疑算法）。

**修复**
用 `"${n}.bin"` 或 `"$($n).bin"`；更稳的是先 `$f = "${n}.bin"` 再传 `$f`。

**规律**
> **在 PowerShell 里 `$a.b` 永远是"取属性"，不是"拼字符串"。**
> 凡"多输入同输出"，先怀疑参数没传进去。

**适用 / 失效条件**
- 适用：PowerShell（bash 的 `$n.bin` 没有这个问题）
- 失效：始终用 `${n}` / `$(...)` 显式界定变量名

## T15b · 连续三次改"计算结构"，而瓶颈一直在"数据通路"

**现象（2026-09-24，同一份 HLS 卷积核的三次重写）**

| 版本 | 结构性改动 | 延迟 | 说明 |
|---|---|---|---|
| 1 | 朴素直接卷积 | 79.6 ms | 每 MAC 约 1.6 周期 |
| 2 | + 8 路输出通道展开 | 56.1 ms | LUT 111%，HLS 又自动展开了 ic |
| 3 | 窗口寄存器 + 行缓存 | 56.8 ms | LUT 121% |
| 4 | 3 改成加法树累加 | **完全相同** | 全量重跑确认 |

四次实测换算下来，**始终是约 1.09 周期 / 每个 MAC** —— 也就是说并行度**一次都没有生效**。

**真正的问题不在计算结构，而在权重怎么来**
报告里一直有一行没被认真读：

```
INFO: [HLS 214-115] Multiple burst reads of length 131072 and bit width 8
                    in loop ... has been inferred on bundle 'gmem1'
```
**权重是从 DDR 经 8 位宽 AXI 端口读进来的**。如果每个 MAC 都要取一个权重字节，
那么无论并行多少个乘法器，速率都被"每周期读 1 字节"卡死 ——
**正好就是观测到的 1 MAC/周期**。

**规律**
> **在优化计算之前，先确认数据能不能及时喂到计算单元。**
> 三次改结构、六次综合、一个多小时，而瓶颈一直在一行日志里写着。

**怎么避免**
- 看到"加了很多并行资源但延迟没动"，**第一件事是算带宽**，
  而不是继续调流水线/展开参数
- 资源报告里 **DSP 用了 185 个却只有 1 MAC/周期**，这本身就是矛盾 —— 矛盾就是线索
- 落地做法通常很简单：**把该层的权重先搬到片上缓冲（BRAM）**，
  再从片上读，而不是让每个 MAC 去打 DDR

**适用 / 失效条件**
- 适用：任何"计算单元 + 外部存储"的加速器（CNN/DSP/矩阵）
- 失效：权重已全部在片上、或访问模式天然是流式单次读取时

## T16 · 会让设备"掉流/掉线"的实验，恢复手段必须是**重推整表**，不是"写回旧值"

**触发条件**
做寄存器扫描/穷举实验，其中某些组合会让设备进入**不可用状态**
（相机掉流、PHY 挂死、PLL 失锁）。

**现象**
脚本内置的"检测到异常就回滚上一组好值"**回滚无效** —— 设备仍然不工作。
必须**重推整张寄存器表**（本例 303 条相机寄存器）才恢复。

**根因**
这类器件在坏配置下会进入**需要复位序列才能退出的状态**：
单纯的"把寄存器写回旧值"不足以让它重新初始化（PLL 失锁、内部状态机卡住）。

**排查 / 修复**
- 实验**开始之前**就准备好"重推整表"这条恢复路径（本例就是重跑上板脚本）
- 脚本里**两条都写**：先试回滚，失败立刻走重推
- **把最激进的组合放在最后**，并且一次只改一个寄存器

**规律**
> **"回滚 = 写回旧值"只对纯配置型器件成立。**
> 对有内部状态机 / PLL 的器件，**恢复 = 让它重新初始化**。

**适用 / 失效条件**
- 适用：任何寄存器扫描实验，尤其涉及时钟 / PLL / 复位
- 失效：纯查找表型寄存器（写回即恢复）

## T16b · Tcl 的 `for` 少一个子句：lint 不报，运行到那一行才崩

**症状**：一个采集脚本"跑完了"、**一张图都没产出、退出码还是 0**。
下一次运行读到帧计数不推进，于是弃权。

**机制**：脚本写的是

```tcl
for {set i 0} {[incr i] <= $n} {        ;# 只有 3 个参数，漏了 next 子句
    ...
}
```

Tcl 的 `for` 需要 **4 个参数**（start / test / **next** / body）。
3 个参数**不是语法错误**（花括号是平衡的），**只在执行到那一行时报**
`wrong # args: should be "for start test next command"`。

**为什么代价翻倍**：那一行前面正好是 `stop`（停 CPU）。
脚本崩在 `for` 上 → 收尾的 `con` 永远执行不到 → **CPU 被留在 halt**。
下一次运行读到"帧计数不推进"并弃权 —— 弃权是对的，但真因是**上一个脚本没收拾现场**。

**这次我连续误诊两轮**：先怪 `stop` 选错了 target（APU 容器 vs Cortex-A9），
再怪自动 `con` 不生效。**两处都不是原因。**

**排查步骤**：
1. 脚本"跑完但没有产出" → **先看退出码和最后一行输出**，不要先猜逻辑
2. 凡是"停止类"操作（stop / halt / 独占）之后的语句，都要怀疑它有没有执行到

**防护（已实现）**：
- `tcl_lint.py` 增加 `for` 参数个数检查。**注意：这条规则的第一版是死的** ——
  它把多行 `for`（body 的花括号在头行）当作多行语句跳过了，恰好跳过它存在的唯一理由。
  正确计数是「**闭合于深度 0 的组数，加上行末仍未闭合的那一个**」。
  **是阴性对照跑出来的**（详见 M21）。

**代价**：三轮运行 + 两轮误诊 + 每次都要重新 `ps_run` 拉起 CPU。

## T17 · 交付脚本前先跑**机械自检**（括号配平 + 非 ASCII 扫描）

**触发条件**
写出了一段 Tcl/XSCT 脚本，准备交给工具运行。

**现象**
运行时报 `missing close-bracket`，而错误行**看起来完全正常** ——
因为括号写在了错误的位置（把 `]` 写进了 `{}` 里面）：

```tcl
return [expr {(($a & 0xFF) << 8) | ($b & 0xFF)]}   ;# 错：] 在 } 里面
return [expr {(($a & 0xFF) << 8) | ($b & 0xFF)}]   ;# 对
```

**根因**
这类错误**用眼睛看不出来**（两行只差一个字符的位置）。
而中文 Windows 上 Vivado 的 Tcl 控制台按 **GBK** 读脚本，
脚本里的 UTF-8 中文字节被误解码时还可能**吃掉引号或括号**，产生与中文看似无关的语法错误。

**排查 / 修复**
写完脚本**先过一遍机械自检**（成本几秒）：
- **非 ASCII 字节数必须为 0**
- **大括号 / 方括号配平**，且不出现 `}` 早于 `{` 的情况
- 参考实现：`ps_fft_dual/tcl_lint.py`

**规律**
> **能用脚本一键检查的东西，不要用眼睛检查。**
> 尤其"差一个字符位置"的错误 —— 眼睛对它们几乎没有分辨力。

**适用 / 失效条件**
- 适用：所有交给工具执行的脚本（Tcl / XSCT / PowerShell / shell）
- 失效：无

## T17b · Tcl 双引号里的 `[...]` 是**命令替换**，不是格式字面量

**症状**：一个采集脚本跑到"开始"那一行就退出，**退出码 1**，
但**第一帧的 .bin 文件确实生成了** —— 文件在、日志里没有对应那一行。

**根因**：那一行是

```tcl
L [format "  [%3d.%1d s]  frame %2d / %d ..." ...]
             ^^^^^^^^^^ 双引号内的方括号 = 命令替换
```

Tcl 会去执行一个名叫 `%3d.%1d s` 的命令，报错，脚本当场终止。

**为什么症状具有误导性**：
- 报错发生在 `mrd`（dump）**之后**、记日志**之前** → **文件存在但没有日志行**
- 收尾的 `con` 永远执行不到 → **CPU 被留在 halt** → 下一次运行读到"帧计数不推进"并弃权
- 于是真因被两层症状（"没产出"和"帧不动"）盖住

**`tcl_lint.py` 没报** —— 它查"括号是否平衡"，而这里是**平衡的**。
**这是第三次遇到 lint 只查形状不查语义**（另两次见 T16 与 M22）。

**修法**：格式化字面量里**不要用方括号**，用圆括号或 `format` 的转义 `\[`。
**排查步骤**：
1. 脚本"跑了一半"→ **看它最后成功到哪一步**，那一步的**下一行**就是嫌疑
2. 凡是字符串里含 `[` 的 Tcl 行，都要问一句"这里是想写字面量还是想执行命令"

**代价**：一次采集（约 4 分钟）+ 一次排障 + 一次 `ps_run` 恢复。

## T18 · 移动到"不存在的目标路径"**不会报错，而是把文件改名**

**触发条件**
用脚本批量移动/整理文件，目标路径是**拼出来的**（尤其是拼接里有变量）。

**现象（真实经过）**
脚本打印了一串 `OK`，看起来整批都归好了 —— 但文件**根本没进目标目录**，
而是**在原地换成了目标目录的名字**。随后同批的其余文件全部报
`Cannot create a file when that file already exists`。

本例的具体样子：本想移进 `Documents\_archive\dsh-harness\`，
结果文件变成了 `Documents\dsh-harness`（一个文件，不是目录）。

**根因**
`Move-Item` / `mv` 的语义是**二义的**：
- 目标是**已存在的目录** → 把文件**移进去**
- 目标**不存在** → 把文件**重命名**成那个名字

而且**两种情况都不报错**。所以"目标目录不存在"这一个前提错，就能把整批操作
变成"改名 + 一堆莫名其妙的 already exists"。

**本例的真正成因**：把目标路径的拼接写在了函数里、引用了函数外的变量，
而该变量在调用点没有被解析到 ——
`"…\_archive\dsh-harness"` 退化成 `"\dsh-harness"`（相对当前目录），
于是变成"在当前目录里改名"。

**排查 / 修复**
1. **动手前断言目标是目录**：`Test-Path <dst> -PathType Container`，不是就中止
2. **动完断言结果**：目标文件存在 **且** 源已消失（两个条件都要）
3. **用体积/数量复核**：本例四个被改名的文件按**字节数逐一比对**原文件，确认零丢失
4. 让批处理函数**只收参数、不引用外部变量**；目标路径用 `Join-Path` 显式构造
5. 名字里可能有特殊字符时用 `-LiteralPath`

**规律**
> **凡"移动 / 复制 / 写入"，"目标是否存在"会改变操作语义 —— 而两种语义都不报错。**
> 所以：**先断言类型，再动手；动完用产物复核，不要用"没报错"当成功。**

**适用 / 失效条件**
- 适用：任何文件整理/搬迁脚本（PowerShell `Move-Item`、`mv`、`robocopy`、Python `shutil.move`）
- 失效：目标路径是硬编码且已确认存在的单次操作

## T18b · 冷启动与热启动**不一样**：同一个引导脚本，第一次读不到相机 ID

**症状**：断电重上后的**第一次**引导，打印

```
  chip id = 0xFFFFFFFF        <- 读失败
  table ok=303
  BOOT ASSERTIONS PASSED      <- 断言照样过
```

**而第二次引导（传感器已热）就正常**：

```
  chip id = 0x56              <- 正确（OV5640 的 ID 高字节）
```

**根因（已独立证实）**：引导脚本的时序是
「拉低复位 → 等 400 ms → 释放复位 → **等 600 ms** → 读寄存器 `0x300A`」。
**600 ms 对冷启动的 OV5640 不够** —— 其内部 PLL 还没锁定，I2C 读不到。
等写完 303 条配置表、开始出帧时，它早就准备好了，**所以采集一直是正常的**。

**为什么这特别危险**：
- 引导脚本**只打印这个值、不对它断言** → 所以 `ASSERTIONS PASSED` 照打
- 如果哪天有人把"相机 ID 正确"加进断言**而不加延时**，
  **冷启动会稳定地误报失败**，而热启动永远复现不出来

**与 T12 是同一族**：**"第一次尝试和后续尝试行为不同"** ——
T12 是 `connect` 返回但目标树没枚举完；这条是相机没准备好。
**凡是"第一次"就异常的现象，先怀疑时序，再怀疑硬件。**

**排查步骤**：
1. 现象只在**断电重上后的第一次**出现 → 高度怀疑时序
2. **重试一次**：如果第二次就好了，基本可以定性（但不要就此收工 —— 要弄清差多少时间）
3. 把"需要等待"的那一步的**等待时长记进代码注释**，别只留在脑子里

**修法**：把复位后的等待加长（或改成"读不到就重试，最多 N 次"），
并把 ID 读**纳入断言** —— 有断言 + 有重试，才是可靠的双保险。

**代价**：一次误判为"硬件坏了"的风险（当时差点去查相机排线）。

## T19 · **手工产物**与脚本产物并存 —— 手工那个必然过期，而且**没有任何症状**

**触发条件**
构建脚本产出 A（`.elf`），但**真正被送进板子的**是 B（`.bin`），
而 B 是某次手工敲命令生成的。

**现象**
板子执行的代码和正在阅读的源码**不是同一份**。
本例：`ps_ui.bin` 停在 8064 字节，而当时的 `.text + .data` 已经是 8199 字节 ——
它旧了整整两版。所有基于源码的推理（"这个函数会不会对齐出错"、
"这里应该不会越界"）**全部失去依据**，但没有任何一步会报错。

**根因**
"手工生成"这个动作**不在任何自动化路径上**，所以它不会被重新触发，
也没人会在构建日志里看到它。它不报错、不警告、不提示过期。

**排查 / 修复**
1. **让构建脚本自己产出每一个会被使用的产物**（本例把 `objcopy` 收进 `build.ps1`）
2. **加一条独立的一致性断言**：`.bin` 长度必须等于**最后一个可加载段的结束地址**
   （从 `objdump -h` 里算出来），不等就直接 `throw`。这一条能挡住"过期"和"截断"两种
3. **打印开头几个字**（本例是复位向量），成本几乎为零，能在上板前发现入口点不对
4. 每次改动后都问一句：**"我要送到板子上的那个文件，是这次构建生成的吗？"**

**规律**
> **只要有一个被使用的产物不在构建脚本里，它就会过期，而且不会有人告诉你。**
> **"脚本生成"和"手工生成"不能共存于同一条交付路径上。**

**适用 / 失效条件**
- 适用：所有带"下游二进制/镜像/打包产物"的构建（`.bin`、`.mcs`、`.img`、`.tar`、固件合并）
- 失效：产物由单一工具链一步生成且无人工介入

## T19b · 打包好的 IP **不是**验证过的那一版（"有一个 IP 能用" ≠ "能用的是它"）

**症状**：要往 Block Design 里集成一个自研加速器。目标目录里**确实有一个打包好的 IP**
（`component.xml` + `.zip` + HDL 齐全），看上去拿来即用。

**但对比"循环编号"就露馅了**（循环编号由源码行号决定，源码一变就变）：

| | Pipeline 循环编号 |
|---|---|
| 打包的 IP（`ip_w6i_backup/hdl/...`） | `LOOP_169_1`、`182_5`、`192_7`、`204_10` |
| 验证过的源 v12（`v12_bias_fold_report_full/`） | `LOOP_181_1`、`195_5`、`212_8`、`253_15` |

**编号完全对不上。** 而且目录名 `ip_w6i_backup` 里的 **"w6i" 是 v11 那一代的代号**
（源版本历史里有 `ts_cnn_v11_w6i_maxpool3d.cpp`）—— **那个 IP 比冻结的 v12 还旧。**

**进一步查证**：整个 `dl/hls` 树里**只有一个** `component.xml`。
**验证过的 v12 从来没有被打包过。**

**为什么危险**：如果直接集成它，
**你集成的那个东西和你验证过 200/200 的那个不是同一个东西**——
而这正是 T6（"构建成功但链接了过期缓存"）的同族。
更坏的是它**不会报错**：IP 合法、BD 能连、时序能过、比特流能出。

**排查步骤**：
1. **别信"目录里有 IP 就能用"** —— 要问"**这个 IP 是从哪一版源码编出来的**"
2. 最便宜的对照物是**编译产物里的结构标识**（循环编号、函数名、层名）——
   它们随源码变化，且不需要重跑任何东西就能比对
3. 查打包日志（`vivado.log` / `pack.bat`）里的 **`Current directory`**，
   它指出 IP 是从哪个工程目录导出的
4. 最后一道：**从冻结的源重新综合 + 重新打包 + 重跑一致性测试**，
   不要试图"论证旧 IP 等价"

**本条的实际处置**：从冻结的 v12 源重跑 `csim`（**200/200 逐位一致，worst delta = 0**）
→ 重跑 `csynth` → 重新 `export_ip` → 集成**新打包的**那个。

**顺带记一条路径坑**：`csim_design` 编译出的 `csim.exe` 的工作目录是
`hls_proj/sol1/csim/build`，**不是脚本所在目录**。脚本里写 `-argv data`（相对路径）时，
测试台 `fopen("data/params.bin")` 必然失败，报

```
cannot open data/params.bin
@E Simulation failed: Function 'main' returns nonzero value '1'
```

**而这个报错看起来像内核 bug，其实只是路径 bug。**
改成绝对路径（`file normalize` 在 Windows 上返回正斜杠）即可。
凡是"编译成功、运行失败、报找不到文件"，先怀疑工作目录，别先怀疑代码。

## T20 · 校验里写死"**某次构建的常量**" —— 校验自己会腐烂，还会训练所有人忽略它

**触发条件**
给"加载/烧写是否成功"加一个校验，为了省事直接把**期望的机器码**写进脚本。

**现象**
本例：`run_ps_ui.tcl` 里有这么一行
```tcl
foreach {off want} {0 0xE59FD020 4 0xE59F0020 8 0xE59F1020} { ... }
```
那是**某一次**构建的头三条指令。之后每次构建，这个校验都会打印 `MISMATCH`，
而脚本**并不会因此中止** —— 于是它变成了一段长期输出错误信息、
但所有人都学会跳过的噪声。**它还在，但已经不起作用了。**

**根因**
校验的是"**内存里的字节等于我记住的那几个数**"，
而不是"**内存里的字节等于这次要跑的那个文件**"。
前者是**关于过去的断言**，后者才是**关于当前的断言**。

**排查 / 修复**
- 让校验**和产物对齐**：读回内存，**逐字和刚落盘的 `.bin` 文件比对**
  （Tcl 里 `binary scan` 出每个小端字，再和 `mrd` 的结果比）
- 校验**必须能失败并中止**：`bad != 0` 就直接退出，不要只是打印
- 报告要给出**规模**（`verified 8200 bytes against the file: 0 mismatching words`），
  而不是只给一个真假 —— "校验通过了"远不如"我比了 8200 字节"有说服力

**规律**
> **校验必须断言"当前这次"，不能断言"我记得的某一次"。**
> **一个长期输出告警却不阻止任何事情的校验，比没有校验更糟 —— 它教人忽略告警。**

**适用 / 失效条件**
- 适用：所有"加载/烧写/下载后确认"的环节
- 失效：无

## T20b · 答案是**我自己写进文档的**，而我没查

**同一天内犯了四次同一类错，形态各异，根因相同**：

| 次 | 我做了什么 | 而记录在哪 |

> **答案经常就在里面，而且是我自己写的。**

**为什么特别值得记**：这四条单独看都是"小坑"，
但它们的**共同代价是重复**——同一个错误犯第二次时，第一次的记录就白写了。

**做法上的修正**：
1. 写任何工具脚本之前，**先 grep 一遍项目里的相关关键词**（命令名、引脚名、API 名）
   —— 项目里已有的 `.md` 和 `.tcl` 是最快的答案来源
2. 写 Tcl 时，凡是要用**工具特有的命令或端口名**，先在本项目里搜一次有没有现成用法
3. **提交信息一律走文件**（`-F`），不要内联 —— 带引号的内联文本已四次截断命令

## T21 · Tcl 行尾的 `#` **不是注释**，是**参数**

**触发条件**
习惯性地把说明写在命令行尾。

**现象**
```tcl
WM $MB 0x00000000        # 先把魔数清零
```
在 Tcl 里这句话不是"调用 `WM` 并加注释"，而是**用三个参数**调用 `WM`，
于是报的是
```
wrong # args: should be "WM a v"
```
——**错误里提的是过程名，一个字都没提到注释**，所以第一眼完全看不出跟那行注释有关。

**根因**
Tcl 只在**"命令本可以开始的位置"**把 `#` 当注释：
行首（前面只有空白），或者跟在 `;`、`{`、`[` 之后。
一条命令**已经开始了**之后再出现 `#`，它就是一个普通字符/普通参数。

**排查 / 修复**
1. **注释一律单独占一行**
2. 把它加进**机械自检**（见 T17 / `tcl_lint.py`）：
   扫描"`#` 前面有非空白字符、且不在 `; { [` 之后、且不在引号里"的行并报出来
3. 本例实测：把这条规则加进 `tcl_lint.py` 后，
   在**350 个已有脚本里报出 0 条**（无假阳性），说明这条规则既准又便宜

**规律**
> **一个"看起来像语法错误、实际上不是"的报错，几乎总是因为你对这门语言的
> 某条小规则做了想当然的假设。** 把它变成机械检查，比记住它更可靠。

**适用 / 失效条件**
- 适用：所有 Tcl（Vivado / XSCT / xsdb / XSim）
- 失效：无（这条规则没有例外）

## T21b · Vivado Tcl 要的是**对象**，不是**路径字符串**

**症状**：一天之内多次"查询返回空"，而东西明明是存在的。

| 我写的 | 结果 | 应该写的 |
|---|---|---|
| `get_bd_addr_spaces -quiet ts_cnn_top_0/m_axi_gmem0` | 空 | `get_bd_addr_spaces -of_objects [get_bd_intf_pins ts_cnn_top_0/m_axi_gmem0]` |
| `assign_bd_address "$seg"` | `ERROR: [Common 17-161] Invalid option value '...' specified for 'objects'` | `assign_bd_address [get_bd_addr_segs ...]` |
| `get_bd_addr_segs processing_system7_0/Data/*/$seg` | 空 | 遍历地址空间按名字过滤 |
| `get_bd_pins dwc/aclk` | 0 个（**而且 cell 根本没建出来**） | 先建 cell，再 `get_bd_pins -of_objects` 读真实名字 |

**后果的严重性**：这些"返回空"被我用成了**判断依据** ——
"没有地址空间"→ 跳过分配；"没有引脚"→ 认为这个 IP 用不了。
**于是基于假前提做出了真改动**（去掉 `axi_dwidth_converter`），
而那个改动最终导致上板算不对。

**教训**：
1. **Vivado Tcl 里，凡是要传给命令的对象，一律用 `get_bd_*` 取出来。**
   路径字符串在有些命令里能自动解析，在另一些里**静默地解析成空**。
2. **"查询返回空"永远是"我的查询有问题"的第一候选，不是"东西不存在"的第一候选。**
   正确的下一步是**用另一种方式再查一次**（换 `get_bd_*`、换遍历、换 `-of_objects`），
   而不是据此下结论。
3. **`get_bd_*` 的返回值要当列表处理**（它是 Tcl 列表，空格安全）；
   而**某些命令返回的是字符串**（例如 `make_wrapper`），
   `foreach` 会按空格把它切开 —— 路径里带空格就会切错（本项目栽过一次，见 T17 附近）。

**与 B16 的关系**：B16 是"错误被吞掉"，T21 是"空结果被当成事实"。
两者都让**没有发生的事看起来发生了**。

## T22 · 自动检查脚本持有和代码**同一个错误认知** —— 于是它只会确认你的错误

**触发条件**
自己写了一个检查器（linter / 校验脚本 / 断言助手）来防某一类错误。

**现象**
本例：上面的 T21（Tcl 行尾 `#`）被写进了脚本，跑了自检，**自检说 OK**。
因为 `tcl_lint.py` 当时的实现里也有这么一行：
```python
if ch == "#" and depth_brace == 0 and depth_brack == 0:
    break          # 把行尾的 # 当成注释，直接跳过
```
——**检查器和被检查的代码共享了同一个错误假设**，
所以它对这类错误**天生免疫**，只会给出"通过"。

**根因**
检查器是**用写代码时的那套理解写出来的**。
凡是"我没想到"的错误，检查器同样想不到；
而且它还会给出一个**权威感很强的"OK"**，比没有检查更让人放心。

**排查 / 修复**
1. **故意把检查器弄坏一次**：造一个**已知有这种错**的最小样本，喂给检查器，
   **确认它会报错**。本项目现在的做法是每次改完 linter 就跑一个探针文件：
   ```powershell
   "set a 1`nWM 0x10 0x20  # trailing comment`n" | Set-Content probe.tcl
   python tcl_lint.py probe.tcl     # 必须报错，不报错说明检查器失效
   ```
2. 检查器要**同时**报告"我检查了什么规模"（比如此例的 350 个文件 / 0 条），
   规模为 0 的检查等于没跑
3. 把"检查器放过了一个真 bug"当成**一等事故**记录下来（本条就是这么来的）

**规律**
> **一个从没被故意弄坏过的检查器，不知道它到底检查了什么。**
> **"检查通过"的价值，取决于你验证过"它在该失败的时候会失败"。**

**适用 / 失效条件**
- 适用：所有自制的校验/检查/断言工具
- 失效：用成熟第三方检查器（它们的失效模式已经被人踩过）

## T22b · `targets -set N` 的编号在不同状态下指向**不同的对象**

**现象**
同一份脚本里的 `targets -set 2`：
* 目标列表正常时 -> `2 = ARM Cortex-A9 MPCore #0`（CPU）-> 内存访问可用
* **DAP 出错时** -> 列表只剩 `1 = DAP / 2 = xc7z020` -> `2` 变成了 **PL** -> 内存访问全失败

**实测两种列表**
```
正常:    1 APU / 2 ARM Cortex-A9 #0 (Running) / 3 #1 / 4 xc7z020
DAP出错: 1 DAP (AHB AP transaction error, DAP status 0x30000021) / 2 xc7z020
```

**后果**：脚本"跑完"了，但所有 `mrd` 返回 `0xFFFFFFFF`，
而**下游把 `0xFFFFFFFF` 当成了真实读数**（见 M17）。

**对策**
1. **动手前先断言目标存在**：
```tcl
set tgs [targets]
if {![string match "*Cortex-A9*" $tgs]} { error "PS target missing: $tgs" }
```
2. **内存访问统一用 `targets -set 1`（APU 容器）** —— 本项目的脚本一直这么用，是能工作的；
   具体 CPU 核（Running 状态）上 `mrd` 会失败。
3. **DAP 错误是瞬态的**：实测 `disconnect` + 重连、或跑一次完整的 `ps7_init` 引导就能恢复。
   不要因为一次读到 DAP 错误就下"板子坏了"的结论。

## T23 · 用 PowerShell **往返读写**含中文的文件 —— 内容会被毁掉，而且**只能部分恢复**

**触发条件**
想对文件做一次"读进来、替换几个字、写回去"，于是写了
```powershell
(Get-Content file.md -Raw) -replace 'a','b' | Set-Content file.md
```

**现象**
文件**没有报任何错**，但里面的中文全部变成乱码；更糟的是，
**skill 加载失败了** —— 因为 YAML frontmatter 也被毁了，
`fpga-casebook` 直接从可用 skill 目录里消失。

**根因**
两处编码不一致，而且都不会警告：
- `Get-Content -Raw` 在 Windows PowerShell 下按 **ANSI 代码页（这里 936/GBK）** 读，
  UTF-8 的中文字节被当成 GBK 解码 → 乱码
- `Set-Content -Encoding UTF8` 会写 **BOM**，与乱码一起固化成新文件

GBK 解码遇到非法字节对时会**丢一个字节并写成 `?`**，所以这不是可逆的换码，
是**有损**的。本例实测：7227 字节的乱码能还原回 5322 字节，
但其中约 **57 字节永久变成了 `?`**（都是 `—`、`"` 这类标点），
可以还原的部分也不是简单往返 —— 字节分组已经错位了。

**排查 / 修复**
1. **绝不用 PowerShell 的字符串管道改文本文件**（尤其是中文）。
   用专门处理 UTF-8 的工具：本项目的 `edit` / `write` 文件工具，或 Python：
   ```python
   open(p, encoding='utf-8').read()   # 读
   open(p, 'w', encoding='utf-8', newline='').write(s)   # 写，无 BOM
   ```
2. **动手前先备份**：`Copy-Item SKILL.md SKILL.md.bak_<date>`。
   本次能恢复，靠的就是目录里恰好有一个旧备份。
3. 确认写入结果：`open(p,'rb').read()[:3] == b'\xef\xbb\xbf'` 必须为 False
   （**不要有 BOM**），并且 `decode('utf-8')` 能成功。
4. 万一已经毁了：可以试"还原"（乱码字符串按 `mbcs` 编回字节再按 UTF-8 解码），
   但**先按有损来预期**，别把还原结果直接覆盖原文件。

**规律**
> **"读进来改一改写回去"是最危险的一步操作 —— 它同时改了内容、编码和 BOM，
> 而这三件事都不会有报错。** 纯文本处理一定要显式指定 `utf-8`，
> 并且**编辑不可再生的文件之前先复制一份**。

**失效条件**
- 失效：文件本来就是纯 ASCII，或全程显式指定 `-Encoding utf8` 且不写 BOM
  （注意：Windows PowerShell 5.1 的 `Set-Content -Encoding UTF8` **会**写 BOM，
  pwsh 7 默认不写 —— 同一个参数在不同版本语义不同，所以不要依赖它）

## T24 · 用 JTAG 重新下载程序时，**CPU 不会被复位** —— 上一次的缓存/MMU 会原封不动地留着

**触发条件**
裸机程序原本不开缓存，跑得好好的；某一天为了性能**打开了 D-cache**，
然后继续用"下载 + 运行"（`dow -data` + `con`）反复烧同一块板子调试。

**现象**
改完之后的程序出现**非确定性的数据中止**：同一份镜像，每次跑**死在不同的 PC**。
更离谱的是寄存器里出现**反汇编上不可能存在的值** ——
本例 `r5 = 0x08C5107E`，而它上游那条指令是 `movt r3, #0`，
**保证 r3 < 0x10000**，所以 r5 绝不可能是那个值。

**根因**
`dow -data` 只写内存，`con` 只是让核继续跑 —— **两者都不会复位 Cortex-A9**。
所以缓存和 MMU 完全保持**上一次运行**留下的状态。程序一旦开过 D-cache：
- 上一次留下了**脏行**，迟早被替换写回，**盖在新下载的镜像上**；
- I-cache 里是**上一版镜像的指令**，取指直接命中陈旧行。

于是"刚下载的代码"和"CPU 正在执行的代码"是两回事。**只有开了缓存之后才会这样**，
所以它在开启缓存的那次改动里才第一次出现 —— 很容易被误判成"我把缓存配错了"。

**排查步骤（顺序很重要，本例正是照这个顺序才锁定）**
1. **把内存里的代码逐字和 ELF 比**：本例完全一致 → 排除"镜像被改坏"。
2. **把每个被调用的函数都反汇编一遍**，确认它遵守 AAPCS（保存 r4-r11）：
   本例全部合规 → 排除"某个函数踩了寄存器"。
3. 剩下的唯一解释就是**执行的不是内存里的指令** —— 即缓存陈旧。
   判据很硬：**寄存器里出现了代码上不可能产生的值**。
4. 直接去读 PMC/缓存状态，或干脆先修再验（修法很便宜）。

**修复**
`_start` 的**第一条指令之前**就把状态复位到与上电无异：
```asm
关 D-cache 位  /  关 I-cache 位
按 set/way 作废整个 D-cache      @ 关键：丢弃脏行，而不是写回
ICIALLU / BPIALL / TLBIALL
关 MMU 位
```
注意是**作废**（invalidate）而不是清（clean）：脏行属于上一次的程序，写回只会搞破坏。
几何参数从 `CCSIDR` 读（`CSSELR=0` 选 L1 D），不要写死 ways/sets。

**规律**
> **"下载 + 运行"不是一次复位。** 只要程序会改变 CPU 的全局状态（缓存、MMU、时钟、
> 外设配置），它就必须**自己在入口把这些状态设成已知值**，不能假设它们是干净的 ——
> 因为它可能被同一个调试流程启动第二次。
> **判据：寄存器里出现源码/反汇编上不可能产生的值 → 先怀疑"执行的不是这份代码"。**

**适用 / 失效条件**
- 适用：所有"经调试器反复下载运行"的裸机程序，尤其是开启缓存之后
- 失效：每次通过上电/复位启动（例如 FSBL 正常引导），此时 CPU 状态天然是干净的

## T25 · 把**记忆里的期望值**当成"金标准"去比对，然后相信自己造的假警报

**触发条件**
写一个检查脚本，需要"期望值"作对照。

**现象**
脚本报 `*** DIFFERS ***`，于是得出了一个**重大结论**：
"OCM 里的代码和 ELF 不一致 → 有东西把代码改坏了"。
基于这个结论开始去找"谁写了 OCM"。

**实际上那个不一致是我自己编的**：期望值那一列是我**凭印象写的**，
其中两个地址的值我当时没看过，就顺手填了猜测。真实 ELF 一比对，**完全一致**。
**假警报把排查方向整个带偏。**

同一次会话里我还犯了两个同类的错：
- 读寄存器时把**字节偏移算错**（`g_fault_word` 从字节 48 起算，我却按 80 读），
  于是"CPU 的寄存器全是垃圾"这个结论其实是**读的人错**；
- 读 MMU 页表时**索引算错**（第 i 项在 `基址 + i*4`），
  于是"页表项是 0"这个结论也是假的。

**根因**
**期望值不是来自产物，而是来自"我以为"。** 一旦把它当成金标准，
脚本就会把作者的误解**变成一条看起来很硬的证据**（`*** DIFFERS ***`）。

**排查 / 修复**
1. **期望值必须从产物本身机械地取出来**：本例应该用
   `objdump`/`readelf` 直接读出那个地址的字节，而不是手敲。
   （`python: struct.unpack_from('<I', elf, fileoff + (addr - vma))`）
2. **凡是"对照"类脚本，都要问一句：这个期望值是从哪来的？**
   答案里出现"应该是"、"大概是"、"我记得"就是红灯。
3. **算术错误和测量错误一样致命**：偏移/索引表达式要**写出来核对**，
   不要心算。本例两次都是"读的人错"，却被当成"被测对象错"。

**规律**
> **假警报比没有警报更贵**：它会消耗一整轮排查，而且方向是错的。
> **"我发现它有差异"这句话，必须能回答"那你期望值是从哪个文件里读出来的"。**
> 与 T20 是一对：T20 是"期望值写死了会过期"，本条是"期望值根本是编的"。

**适用 / 失效条件**
- 适用：所有"实际值 vs 期望值"的比对脚本（字节比对、寄存器比对、时序比对）
- 失效：期望值由被测系统自身在已知条件下产生（自校验）

## T26 · 诊断脚本**自己把被测状态改坏了**，然后把结果当成"被测对象的问题"

**触发条件**
写一个脚本去"冻结现场、取出证据"。为了冻结，它必须临时改一点东西
（停掉采集、停掉 DMA、把某个通道停下来）。

**现象**
脚本跑完、报告一切正常，但从那之后**被测系统就再也不是原来那样了**。
本例：`ps_lutcheck.tcl` 为了拿到"原始帧 + 渲染帧"的一一对应，
先**停掉采集通道**，dump 完之后**只写了一次 `CR = RUNSTOP`** 把它启起来。
通道报告 `SR` 正常（`Halted = 0`），但**一个像素都不再更新** ——
于是 PS 之后一直在渲染**同一张冻结的帧**。

**它是怎么暴露的**
靠另一条**独立判据**："两张相隔 1.5 秒的 dump，相机区域应该变化约 88%"。
实测 **0.0%**。也就是说：
**"画面不动"这件事，是从我自己的诊断脚本跑完之后才开始的。**

**根因**
两条老坑叠在一起：
- **重新启动一个 VDMA 通道只写 `CR` 是无效的**（必须 `几何/地址 → CR → VSIZE 最后`，见 B14）；
- **诊断脚本没有把状态"恢复到与进来时一致"的责任写进自己的代码里**，
  它只是"做了个近似恢复"。而近似恢复**不报错**。

**排查 / 修复**
1. **诊断脚本要么完全只读，要么显式记录并恢复它改过的每一个寄存器**，
   不能靠"再写一次 CR 应该就回去了"。
2. **停止后重启的序列，直接抄已经验证过的那一段**（本例应抄 `ps_capture.tcl`），
   不要凭记忆重写。
3. **给"我改了状态"配一条独立的健康判据**：本例就是那条"两张 dump 应该有差异"的
   liveness 检查。**如果没有它，这个副作用会一直被当成"场景是静止的"。**
4. 更一般地：**任何一次"冻结现场"的操作，都要在脚本最后自问一句
   "现在的状态和进来时一样吗？我怎么证明？"**

**规律**
> **测量会改变被测量的东西 —— 这条不只适用于物理。**
> **诊断脚本是程序，它会留下副作用；而副作用通常不报错。**
> 所以每一个"为了取证而改变状态"的动作，都必须配一条**证明状态已恢复**的判据，
> 否则下一次的结论就建立在一个被自己改过的世界之上。

**追加（同一天，同一个坑的第二种形态）：不要"假设"前置条件，要"测量"它。**

接着做曝光实验时又栽了两次，而且两次的输出**看起来完全一样**：
"改曝光前后，图像统计量逐位相同" —— 看上去像"曝光寄存器不起作用"这个重大结论。
真相是**采集通道早就被上一个失败的脚本停掉了**，两次 dump 都是**同一张冻结帧**，
脚本里写的是 `capture left RUNNING` —— 那是**我的假设，不是测量**。

三个版本才做对，差别只在脚本开头多了一段：
```tcl
set tr [CAPLIVE]                    ; 数帧指针在 1 秒内翻转了几次
if {$tr == 0} { REARM; set tr [CAPLIVE] }
if {$tr == 0} { FATAL "采集没在出帧，任何 dump 都不可能反映这次改动" }
```
修好后第一次跑就打印 **`transitions in 1 s: 0` → 重新 arm → 33**，
说明前两次确实在量一张死图；实验随即给出清晰结果（luma 91.7 → 14.0，白削顶 4.10% → 1.44%）。

> **一个"看起来是重大发现"的结果（"这个寄存器没用"），先怀疑你的前置条件没成立。**
> **脚本里凡是有"当前应该是……"的句子，都要变成一次测量 + 一次断言。**
> 尤其当你**为了让测量稳定而冻结某个东西**时 —— 冻结的正好是必须响应的那一个。

**适用 / 失效条件**
- 适用：所有需要"先停下来再看"的诊断（停 DMA、停采集、停时钟、改多路选择）
- 失效：纯只读的观测（读寄存器、读内存、抓 ILA），那不会改变系统状态

## T27 · 代码注释把**一次过期的实测数字**写成了"依据"，然后它一直在替一个错误决定辩护

**触发条件**
代码里有一段**确实测过**的数据被拿来当某个参数的依据，写在注释里。
后来代码改了、负载变了，**那个数字不再是同一件事的测量结果**。

**现象**
本例（曝光包围的双缓冲同步）注释原文大意：

> "实测：融合渲染只要 ~73 ms，而 740 行的采集帧是 ~62 ms，
> 所以过渡发生在每次渲染中间、会被漏掉。把 VTS 从 740 提到 1450 → ~8.3 fps，
> **渲染就塞得进去了**。"

读了会点头，参数也就照着定了（VTS 1450）。但上板实测：
**融合循环是 4.7 fps ≈ 213 ms**，而 VTS 1450 的采集帧只有 **≈122 ms**。
**渲染从来就没塞进去，差了将近一倍。** 那个"73 ms"是**改造早期某个中间版本**的数字，
后来每帧多了缓存维护、两次均值、两次亮样本计数、以及等待交接的自旋 —— 早已不是 73 ms。

**根因**
注释里的数字是**当时那一版代码**的测量结果，而代码和注释**没有绑定关系**：
- 数字没有记录**是在哪个版本、哪种模式下测的**；
- 没有**任何机制**在代码变慢时让这条注释失效（注释不会编译，也不会报警）；
- 于是这条注释从"依据"变成了"**替一个错误决定辩护的理由**"，
  而且它看起来比"我猜的"可信得多 —— **因为它引用了一次真实测量**。

**这正是 M35 的孪生形态**：M35 是拿两个不同 stage 的数字比，
T27 是拿**同一个 stage 但不同版本**的数字当依据，然后**再也没复测过**。

**排查 / 修复**
1. **凡是注释里出现"实测/measured"，必须写清楚三件事**：
   测的**对象**（哪一版、哪种模式）、**数值**、以及**什么时候/怎么复测**。
   例：`实测 fused loop 213 ms (2026-10-03, 单曝光关闭, ps_brackwatch.tcl)` —— 而不是"73 ms"。
2. **参数与依据之间要有可执行的联系**：把"必须满足的不等式"变成一条**断言**，
   让它在不成立时**当场报错**（本例应断言 `loop_ms < frame_ms`，
   并在 `ps_run` 里把两者都打出来对账）。
3. **每次改动性能路径之后，重跑那条依据**。若不想重跑，就把结论降级成"未复测的历史值"。
4. 找到这类注释后，**不要只改数字** —— 要把"这个数字支撑的结论"重新验一遍。
   本例重验后的正确结论是：**双缓冲方案在这块板子上根本达不到无撕裂融合**
   （见 T28），而这条注释让这个结论晚了整整一轮才出现。

**规律**
> **注释里的"实测"会腐坏，而且腐坏时不出声。**
> 一段引用了真实测量的注释，比一句凭空的猜测更危险 ——
> **因为它看起来有证据。** 数字必须有主人（版本 + 模式 + 复现命令 + 日期）。

**适用 / 失效条件**
- 适用：所有"用一次实测值来定参数/做取舍"的地方（时序、帧率、带宽、延迟、资源）
- 失效：那个量是**物理常数或器件规格**，不随自己的代码变（如 IO 电平、晶振频率）

**来源**
本队真实踩坑（2026-10-03 曝光包围+融合）。这条与 M35 一同促成
`ps_brackwatch.tcl` 现在会**同时打印**采集/渲染的实际帧率和逐帧状态，
而不是引用注释里的数字。

## T28 · 假设"两个 DMA 缓冲区会同时是完整的" —— 这个窗口可能是**零**

**触发条件**
要在**两个** DMA 缓冲区上做某种联合处理（融合、差分、比较、取平均），
而**只有 2 个 frame store**，DMA 一直在两者之间轮流写。

**现象**
本例：想让每一帧都拿到"一帧长曝光 + 一帧短曝光"去融合。代码里的推理是：

> "等采集的帧指针翻转，它刚离开的那个 store 就是完整的，
> **此刻两个 store 都是完整帧**，可以安全融合。"

**这句是对的，但只对了一个瞬间。** 帧指针翻转的**同一时刻**，DMA 已经开始
**覆写另一个 store** 了。上板实测：融合循环 **213 ms**，采集帧 **122 ms** ——
渲染读到一半，第二个 store 已经从"旧帧"变成"一半旧帧 + 一半新帧"。
逐帧采样（`ps_brackwatch.tcl`）直接看到状态在两档之间摆动：
要么两个 store 亮度几乎相同（两帧同档，没配成对），
要么一个暗、一个中等（那个"中等"正被覆盖，是**混帧**）。

**根因**
把"**在某一时刻**两个缓冲区都是完整的"（真，但**瞬时**）当成了
"**在一段足以完成处理的时间内**两个缓冲区都是完整的"（假）。
用 2 个 store 做乒乓时，**DMA 永远在写其中一个**，
所以"两个都完整"的**时间窗口长度是 0**，而不是"一帧那么长"。
这个窗口长度 = `采集帧周期 − 0` 的前提是**渲染快到能在 DMA 没动之前读完**，
否则就必须有**第三个缓冲区**。

**排查 / 修复**
1. **不要用"事件发生的瞬间"论证"一段时间内可用"** —— 把窗口**算出来**：
   `可用窗口 = 到该缓冲区下次被写的剩余时间`。用 2 store 乒乓时它就是从交接点开始算的
   `0 → 帧周期`，而**两个都要完整**时窗口是 **0**。
2. **把不等式写成断言并打印实测值**：
   `处理时间 < 帧周期` 才可能无撕裂；本例 `213 ms > 122 ms`，直接判死。
   （这与 T27 是同一条纪律：**别用注释里的数字，用当场测的。**）
3. 真正的修法是**架构级**的：把采集 VDMA 配成 **≥4 个 frame store**，
   融合读"最近两个已完成"的 store，DMA 在渲染期间不会碰它们
   （可用窗口 = `(N-2) × 帧周期`）。
   代价是 **Block Design 改动 + 重新综合 + 新比特流**，
   并且要多检查一遍 `C_NUM_FSTORES` 与地址寄存器（`ADDR1..ADDRn`）的一致性。
4. **先算收益再改架构**：本例做完上面全部测量后发现融合的收益是 **0.09%**
   （见 M34），于是**不值得动 BD**。这个结论只有在"帧率/窗口都量清楚了"之后才站得住。

**规律**
> **"两个缓冲区同时是完整的"通常成立，但只成立一个瞬间；
> 用它撑起一段耗时处理，是把瞬时条件当成了持续条件。**
> **用 2 个 store 做乒乓时，双缓冲区联合处理的可用窗口是 0 —— 不是"一帧"，是 0。**

**适用 / 失效条件**
- 适用：只有 2 个 frame store 的 AXI VDMA / DMA 乒乓（融合、HDR、帧差、运动检测、两帧去噪）
- 失效：处理能在**远小于**帧周期内完成（此时窗口近似等于帧周期）；
  或 store 数 ≥ 3 且只读"已完成、且不在 DMA 下一个目标里"的那些

**来源**
本队真实踩坑（2026-10-03 曝光包围+融合）。这条与 T27 一起解释了
"为什么一个看起来推理正确的双缓冲设计，上板后既配不成对、又总有撕裂"。

## T29 · 主机负责写的那个控制字，主机从来没写过 —— 于是守卫**朝"放行"失效**

**触发条件**
一个可配置的阈值/限值/开关，**由上位机（脚本）负责写入**，设备端读它来做判断。

**现象**
本例：给渲染器加了个"饱和闸门"——画面饱和超过限值就判"无法判断"。
上板第一次跑：**画面 4.40% 的通道已经削顶，闸门却是 0（放行）**。

读数：`CLIP_LIM = 0x91C8D0B2`。**这个限值从来没人写过**，
设备端读到的是 DDR 垃圾值，被 clamp 到上限 1000‰，于是条件**永不成立**。

**根因**
- 那个字在启动脚本里**没有被种入**（只种了相邻的一批），
  于是它既不是"默认值"也不是"用户的设置"，而是**上次上电随机留下的内容**；
- 设备端的兜底只处理了 `限值 == 0`，**没处理垃圾值**。
  垃圾值被 clamp 到"最大" = 阈值最松 = **永不触发**；
- 而 "**永不触发**" 与 "**一切正常**" 在读数上**长得一模一样**。

**排查 / 修复**
1. **凡是由上位机写的控制字，脚本里必须有显式的一次写入**，
   并且把**"要求的值"和"设备实际采用的值"分别发布**（本例新加了一个
   "实际采用的限值"字）。否则这类事故**永远不可见**。
2. **设备端的兜底要覆盖"不可能的值"，不只是 0**：
   超范围一律回落到**安全默认值**，而不是回落到"禁用"。
   > 测量设备必须朝"**我判断不了**"的方向失效，**绝不能朝"看着挺好"的方向失效**。
   > 阈值型守卫的失败方向，比阈值本身更重要。
3. **给守卫做一个"它会不会触发"的检查**：本例的闸门有阈值可调，
   把限值设成不可能达到与可能达到两种情况各跑一次，**确认它真的会翻面**。

**规律**
> **没有初始化的控制字不是一个默认值，是一个意外。**
> 而且它造成的失败**恰好是最难发现的那一种**：守卫还在、日志还在、
> 代码也"执行了"，只是它永远说"没问题"。

**适用 / 失效条件**
- 适用：任何"上位机配置、设备端执行"的阈值/限值/使能位
- 失效：设备端对每个控制字都有 CRC/魔数校验，能识别出"没被写过"

**来源**
本队真实踩坑（2026-10-03 饱和闸门）。同一轮里另一个相关教训：
**异常的失败方向也要检查**——闸门修好后，主机端把 "要求" 与 "实际采用" 都打出来，
才发现此前那个垃圾值一直在。

## T30 · 算速率时用**标称**时间做分母，而不是**真实**经过时间

**触发条件**
测速率（帧率、吞吐、事件率）：数出一个时间窗内发生的事件数，再除以窗口长度。

**现象**
本例：PS 每渲染一帧就递增一个计数器，主机每 600 ms 采一次样，共 10 次。
脚本用 **`i × 600 ms`**（标称间隔）做分母，算出 **18.7–19.3 fps**。
换成 `clock milliseconds` 量**真实**经过时间，同一份固件是 **16.3–16.4 fps**。
**偏高了约 10%。**

**根因**
每次采样除了 `after 600`，还要做两次 JTAG 读，**真实墙钟比标称间隔长**；
而被计数的对象（PS）在 JTAG 停顿期间**照常出帧**。
于是：**分子（帧数差）没变，分母（间隔）偏小 → 速率偏高。**
偏差大小 = 每次采样的额外开销 / 采样间隔，本例约 5–10%，**采样次数越多越严重**。

**排查 / 修复**
1. **分母永远是测出来的**：`clock milliseconds` / `time.monotonic()`，**不是名义值**。
   名义值只配用来"安排什么时候采样"，不配用来"算速率"。
2. 更稳的做法是**读时间戳要紧贴着读数**，把 JTAG/IO 抖动排除在单个采样之外
   （本例的起点/终点时间就是这样取的）。
3. **跨会话比较速率之前，先确认两次用的是同一种计时方式。**
   本例"比加新功能之前慢了 11%"这个说法，就建立在那个偏高的旧数字上 ——
   更正之后，这条归因**必须撤回**（新功能的实测代价是 0.2 ms，用 A/B 量过）。

**规律**
> **"分母"是速率测量里最容易作弊的一环，而且它偏向"更好的数字"，
> 所以没有人会去怀疑它。** 任何速率数字旁边都该写清楚：分母是怎么得到的。

**适用 / 失效条件**
- 适用：所有"数事件 / 除以时间"的速率测量，尤其是采样本身有非零开销时
- 失效：采样开销远小于间隔（例如间隔 1 s、开销 1 ms）且不要求高精度

**来源**
本队真实踩坑（2026-10-03 帧率计时）。

## T33 轮询 PL 寄存器的"守卫循环"不是超时，是**阻塞**

- **触发条件**：等 PL 的一个完成位，写成 `while (!(reg & DONE)) { if (++guard > N) break; }`，
  而 `N` 是按"循环次数"估的。
- **现象**：主循环几乎全程被卡住；屏幕看起来"冻住"；帧率掉到 1~2 fps；其它一切读数都正常。
- **根因**：每次迭代是一次 **PL 寄存器读**，本板实测约 **5 µs**。
  `N = 3,000,000` ⇒ **约 15 秒**。而它每 16 帧被调用一次 ⇒ 主循环几乎一直在等。
- **排查**：
  1. 把 `N` 乘以实测的每次读耗时，得到真实时长 —— **不要凭"循环很快"想象**；
  2. 读被等的那个状态位（本例 `AP_CTRL` bit1 `ap_done` / bit2 `ap_idle`）：
     `ap_idle=1 且 ap_done=0` ⇒ 设备空闲但**永不完成** ⇒ 守卫必然走满；
  3. 对比"调用被禁用"前后的帧率 —— 这是最直接的证据。
- **修复**：
  - **守卫上界按时间给**（例如 100 ms 对应的读次数），不要按"感觉"；
  - 更根本的是**先证明完成位会置起**，再接进主循环；
  - 调用点加开关（宏/标志），这样"先关掉"是一行改动，而不是一次重构。
- **失效条件**：寄存器在本地总线（非 PL）上时，单次读代价低几个数量级。
- **来源**：2026-10-18。这条与 B19 一起，构成了"屏冻住"的两个独立原因。

## T34 守卫循环按"读了多少次"计时，等于没有计时

**事故**：CNN 驱动的等待写成 `while (!(ctrl & 2)) { if (++guard > 20000) return TIMEOUT; }`，
注释假设"20000 次读约 100 ms"。**但一次 AXI-Lite 读只要几十纳秒**，20000 次 ≈ 1-2 ms，
而一次推理实测要 **44 ms** —— 于是每一组已知答案都在 `ap_done` 到来之前被判超时，
面板上的 `CNN PASS 0/8` 是**量具的错**，不是加速器的错。

**反证**：超时之后再读一次 `0x43C20000` 得到 `0xE`（done/idle/ready 全在）——
完成标志一直在，只是没人等到。

**修法**：用墙钟计时。本项目有 32 位全局定时器 `0xF8F00200`，实测 3 ns/tick，
于是写成 `while (!(ctrl & 2)) { if ((gtimer() - t0) > 66600000u) return TIMEOUT; }`（200 ms）。

**判据**：任何"等某个标志"的循环，上界必须与被等对象的**真实耗时单位**一致。
用"读次数"当时间，必须先量出**一次读**到底多久，而且那个数会随总线、缓存、编译器变化。

## T35 静态变量初值在这块板上可能不生效，需就地兜底

**事故**：控制器里的 `static uint32_t aec_exp = CAM_LONG_L;` 板端读回来是 0。
同一块板上，其它 `static` 变量也有类似现象（初值非 0 的读出来是 0）。
推测与链接/加载方式有关，**没有定位到确切机制，不写成结论**。

**处置**：在函数入口就地兜底 —— `if (aec_exp == 0u) { aec_exp = CAM_LONG_L; }`。
代价是一行代码；收益是"变量的初值不再依赖一段没验证过的启动逻辑"。

**判据**：任何一个**影响判定或控制的**静态变量，如果它非 0 的初值很重要，
就必须在使用处兜底，而不是相信 `.data` 段已经按预期初始化。

## T36 交付的二进制由"另一份副本"编出 —— 校验和全对，源码却不是它

**触发条件**：交付包里同时存在"可读源码目录"（`src/`）与"能单独构建的目录"（自带 build 脚本 + 源码拷贝），
两份靠人手同步。

**现象**：
- 包内 `MANIFEST` 的哈希、ELF 的 SHA256、脚本自检**全部自洽**；
- 但交付固件的行为与"最新源码"不符：曝光 10000 而不是 3000、CNN 推理被 `if (0 && ...)` 关掉。

**根因**：构建脚本编译的是**旧拷贝**。哈希自洽只能证明"文件没被改动"，
**不能证明"二进制来自这份源码"** —— 两者之间没有任何连接。

**怎么在三行内发现**：反汇编交付 ELF，找源码里的特征常量。

```
arm-none-eabi-objdump -d ps_ui.elf | grep -c '#10000'   -> 3
arm-none-eabi-objdump -d ps_ui.elf | grep -c '#3000'    -> 0
```

而两份源码的差别正是 10000 与 3000。**不用跑板子、不用综合。**

**修复（把连接变成机器检查，而不是纪律）**：
1. **只留一个源**：能单独构建的目录改为由刷新脚本从源目录生成，不再人工维护。
2. 构建时对源文件集取哈希，写进镜像（`"TSC1" + 8 位十六进制`），运行期发布到邮箱；从此板子自己回答"我是谁编的"。
   **坑中有坑**：`static const char[]` 若只被常量索引读取，编译器会把它折叠成立即数并**丢掉整个数组**
   （实测：第一次上线，镜像里根本没有这个串，检查脚本报 UNSTAMPED 并且是对的）。
   需要 `__attribute__((used))`，并让检查脚本在 ELF 里按**字节**搜索它，而不是解引用符号。
3. 打包检查三件事：每个生成副本 == 其源；交付镜像带当前哈希；MANIFEST 与磁盘一致。
4. 终极验证：**在包内单独重建**，产物与交付件**逐字节比较**。

**适用 / 失效条件**：
- 适用：任何要交付二进制的项目（固件、HLS IP、比特流）。
- 失效：构建过程本身不确定（嵌入时间戳/路径/随机文件顺序）时"逐字节相同"不成立 ——
  降级为"哈希一致 + 关键常量核对"，并明确写出降级理由。

**来源**：2026-10-21 外部审查；当天实现并验证（包内重建产物与交付件逐字节相同）。

## T48 · 两个 agent 改同一个文件 / 两个 xsdb 客户端插同一根线

**触发条件**：并行工作。多个 agent（或"你 + 另一个会话"）共享同一个工作目录；
或者连着开两个 xsdb / 调试器会话，对同一根 JTAG 说话。

**现象**（两条都真实发生过，不是设想）：
- **文件**：`ps_ui/main.c` 十分钟内从 15,044 行涨到 15,396 行，mtime 动了两次。
  两边的改动各自"编译通过"，但邮箱字编号是按**各自的本地视图**分配的 ——
  只要有人用"下一个空闲字"**猜**编号而不是去读空闲表，两块改动就会撞在同一个字上
  （撞号的后果见 M45 / M47：读到的值是别人的）。
- **JTAG**：第二个 xsdb 会话的读会失败，而读数层把 `-1` 掩码成 `0xFFFFFFFF`，
  于是脚本报出的是"程序没在跑或偏移错了"——**两条都不对**，而且都很有说服力。

**根因**：两种资源都没有"锁"的概念。文件没有租约，JTAG 线没有独占。
而两类错误都会被上层的"合理默认值"（无符号掩码、默认偏移、默认下一个字编号）
翻译成**看起来正常的错误信息**。

**排查步骤（检测，而不是忍受）**：
1. 动手前后各采一次 `git status --short` + 目标文件的 `mtime` + **行数**；
   两次不一致就停下来问"这个改动是谁的"。
2. 行数与 mtime 只是**看得见的那一半**；真正危险的是"同一份内容被两个视图各改一半"。
3. JTAG 侧：同一时刻只允许一个 xsdb 会话；脚本把"读失败"与"读到全 1"分开报
   （`0xFFFFFFFF` 必须是"读失败"，不能是"值是 2^32−1"）。

**修复（比纪律可靠的三条）**：
1. 把共享点的"**编号**"换成"**命令**"：请求一个动作，而不是请求一个槽位 ——
   没有索引就没有编号可撞。本项目把快照请求做成了 `SNAP_CMD` 而不是一个新邮箱字，
   原因就是这次碰撞。
2. 在一份**临时目录的拷贝**上开发、编译、测量（而不是在共享文件上改），
   半写状态的文件永远不会被构建。
3. 提交前用 `git status` + mtime 复核"这个文件是不是只有我在动"。

**早期检出**：写一个**并发自检**：开工时记录（路径、mtime、字节数、行数），
收工时比对，不一致就拒绝提交。二十行代码，能拦住一整类"两边都以为自己在改"。

**适用 / 失效条件**：
- 适用：任何多 agent / 多人共享工作区，以及任何独占设备（JTAG、串口、烧录器、
  单实例 license、同一个 COM 口）。
- 失效：工作区是每 agent 一份（git worktree / 容器）时，**文件**冲突不成立；
  但**设备**冲突仍在，而它恰好以"读失败被掩码成合法值"的形式出现。

**来源**：2026-10-27。`dl/EVIDENCE_SNAPSHOT_20261027.md` §6
（"Process note: two agents, one file"，含 15,044→15,396 行与两次 mtime）；
`ps_fft_dual/ps_shot.tcl` 的守卫注释（两个 xsdb 会话与 `-1` 掩码）；
`dl/mb_free.py`（空闲字表"只在该瞬间成立"）。

## T49 · 备份逐文件哈希校验全过，但 Block Design 还是改过的那个

**触发条件**
用"备份文件 → 改设计 → 还原文件"来撤回一次 Vivado 工程改动。
尤其是**只备份了 `design_1.bd`（外加 `.xpr` 和几个 XDC）**的时候。

**现象**（2026-10-28 实测，不是设想）
`python dl/backup.py restore 20261028_161217__plfe_day1_before_anything` 逐文件打印
`恢复 design_1.bd  OK`，`backup.py verify` 报"问题 0 处"，`.bd` 的 SHA256 与
`MANIFEST.txt` 逐字节一致。**可是设计还是改过的那个**：

```
BEFORE|hp2=1|periph_num_mi=19        <- 还原之后仍然是 1 / 19；应为 0 / 18
BEFORE|cells_pl_fe_top=0|cells_plfe_hp=0
```

于是 `validate_bd_design` 报 1 条 ERROR（多出来一个悬空的 `M18_*` 主口）。
**真正危险的不是这条 ERROR，而是它很容易被读成"还原带来的小毛病"** ——
如果当时忽略它，下一步构建的就是一个**半新半旧**的 Block Design。

**根因：一个 Block Design 的状态不是一个文件，至少三处**

| 位置 | 里面有什么 | 只还原 `.bd` 时 |
|---|---|---|
| `bd/design_1/design_1.bd` | 图：cell、连线、地址段 | 回来了 |
| `bd/design_1/ip/<cell>_<n>/<cell>_<n>.xci` | **每个 IP 实例自己的配置**：`PCW_USE_S_AXI_HP2` 在 `processing_system7_0_0.xci`，`NUM_MI` 在 `ps7_0_axi_periph_0.xci` | **没回来** |
| `*.gen/sources_1/bd/design_1/**`、`*.srcs/utils_1/imports/synth_1/<top>.dcp` | **生成物**，是 build 的输入 | **没回来** |

第二行就是"文件对了、参数没对"的来源：`.bd` 里存的是这些参数的**拷贝**，
改了一个不改另一个，看上去两边都很正常。

第三行与 T6 同族，本次有直接的 mtime 证据：BD 在 **17:15** 被还原，
而 `two FFT.srcs/utils_1/imports/synth_1/design_1_wrapper.dcp` 的 mtime 仍是
**16:54** —— 它**还在描述带前端的设计**。它是否会被 `launch_runs` 自动刷新取决于版本
与时机，本次不去赌：脚本先 `reset_target all` + `generate_target all`
（实测 76 s，刷掉了那份 dcp），再用**内容闸门**验证最终网表里到底有没有那个 cell。

**第二个缺口：工程的一半源文件在工程目录之外**
从 `.xpr` 的 `File Path=` 直接读得出来：

```
C:/.../ps_fft_dual/rtl/analyzer_fe.v        <- RTL 在仓库里
C:/.../ps_fft_dual/vivado/two_fft.xdc       <- 约束在仓库里
C:/.../dl/touchfix/two_fft_rgb888.xdc
C:/.../dl/pl_frontend/pl_fe_top.v           <- 这次要集成的模块也在仓库里
```

所以"备份整个 Vivado 工程目录"**仍然不够**：它保住了 `.bd`/`.xci`/`.gen`/`.runs`，
但保不住被**引用**的 RTL 和 XDC。

**排查步骤**
1. 还原之后**不要**拿 `restore`/`verify` 的输出当结论（它们只证明"拷过去的字节对"）。
   去读**设计的状态**：`get_property CONFIG.PCW_USE_S_AXI_HP2`、
   `get_property CONFIG.NUM_MI`、`FCLK_CLK0` 网上的**引脚数**、
   `get_msg_config -count -severity {ERROR}`（B18b：`validate_bd_design` 的返回值
   成功失败都是空串）。
2. 从 `.xpr` 里列出"工程引用了哪些**目录之外**的文件"，逐个确认在备份范围内。
3. 还原后**必须重新构建**，并且在构建脚本里放一条**内容闸门**：
   `[llength [get_cells -hier -filter {NAME =~ "*pl_fe_top*"}]]`
   在"不该有前端"的设计里必须是 **0**，在"该有前端"的设计里必须**不是 0**。
   **构建状态 `Complete` 不能替代这一条** —— T6 就是这样骗过人一整天。

**修复**
1. 备份**整个工程目录全量**（`.bd` + `ip/` + `.gen` + `.runs` + `.xpr`），
   **再加**`.xpr` 引用的全部工程外源文件。
   本次实测：`python dl/backup.py save <名字> "<工程目录>" <工程外源文件...>`
   → **2,292 个文件**，覆盖全部 **78** 个 `ip/` 实例目录，`verify` 0 问题。
   *工具本身是好的*（它本来就支持目录），坏的是**交给它的路径范围**。
2. 还原后重建 + 内容闸门，两条都过才算还原。
3. `ps_fft_dual/plfe_bd_revert.tcl` 这种脚本作为最后一道：把参数**显式写回**并断言，
   保存前以 ERROR 消息数为闸门。它比"再还原一次文件"可靠，因为它是按**语义**还原的。

**适用 / 失效条件**
- 适用：任何 Vivado IP Integrator 工程，以及任何"配置分散在父文件与实例文件两处"的
  工具链（Quartus 的 `.qsf`/`.ip`、Vitis 的 `.xsa`/BSP 是同一族问题）。
- 失效：备份若是**整盘快照**，"文件不在备份范围内"这条不成立；但**生成物过期**
  那条仍然成立（`.gen` 里的东西不会因为文件回来了就自己变新）。
