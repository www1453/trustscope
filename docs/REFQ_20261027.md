# REFQ: a reference-quality check at capture (2026-10-27)

Firmware: `ps_ui/main.c` (REFQ block at the word map, `refq_invalidate()` /
`refq_measure()` before `boot_selftest()`, check 5 inside it, the call at the end of
`ref_take()`). Host: `dl/host_qc/{qc_mailbox,preflight,record,check_words}.py`.
Offline instrument: `ps_ui/refq_replay.py`. Build: 394 mailbox words, **0 collisions**,
layout checks pass, the same four pre-existing warnings; ELF 198,804 bytes.

**The board acceptance was NOT produced.** The station was cold when this work
started and is cold now: the DDR controller is held in reset (`Cannot access DDR`,
reading 0x10F00000), OCM holds no image, the PL register range times out, and the DAP
later reported `APB AP transaction error 0x30000021`. Configuring the station needs a
bitstream and a PS init, both outside this task's rules ("no bitstream, no power
cycle"), and a PS-only init would not give camera frames either (the capture path is
in the PL). So section 7 states exactly what was not measured, and the two acceptance
directions are demonstrated on the frames on disk through the firmware's own rule
(section 3) rather than on a live station.

---

## 1. The incident, and the gap this closes

`dl/NG_GOODBOARD_20261026.md`: a reference was taken of a board carrying **four black
marker marks**, and every clean board afterwards was judged NG. The marks are content
in `REF_BASE`; the comparison reports them as a difference on every part. Measured in
that report: inside the board box at green < 60, the marked reference had **2,249 dark
pixels and the clean board in front of the camera 186** (the same report labels that
threshold "< 55"; the numbers are the `a1_marks.py` run at 60). Nothing in the system
could tell a good reference from a bad one: `MB_PART_REF` is a *size* (671 marked /
420 clean), and every published comparison word describes the difference a reference
*produces*, never the reference itself. A reference that is 10-12x darker than a clean
board was accepted without a word.

REFQ is that word. It runs **once per accepted reference** (the boot reference,
`MB_CMD = 9`, `MB_CMD = 17` and the touch button all pass through `ref_take()`), it
measures the **reference's own part region**, and the boot self-test's fifth check
reports it in the same PASS / FAIL / NOT MEASURED shape as REF, BG, AEC and MASK.

## 2. What is measured, and what is published

The region is the reference's own `BASE_MASK` — the same mask the comparison will use,
built from the same frame in the same `ref_take()` call.

For every part pixel the green channel is compared with the **reference's own board
level** (the median of the 4-pixel lattice over the part cells, computed with the
firmware's own median rule), so the threshold follows the exposure instead of being one
grey level for every light:

* **dark** = green < `REFQ_DARK_NUM`/256 × the board median (100/256 = 0.39 x)
* **bright** = green > `REFQ_BRIGHT_NUM`/256 × the board median (410/256 = 1.60 x)
* a dark pixel is **isolated** when no pixel in its 3×3 neighbourhood is bright — a
  pad's or a component's shadow belongs to the pad, and is not ink on solder mask
* an 8×8 cell is a **dark cell** when it holds ≥ `REFQ_CELL_MIN` (6) isolated dark pixels
* dark cells are connected 8-ways; a connected structure whose **isolated dark area** is
  `REFQ_AREA_MIN`..`REFQ_AREA_MAX` (72..2048 px) is a **small isolated dark structure**

The check fails (state 1) when there is more than `REFQ_CNT_ACCEPT` (0) such structure,
**or** when the part's coverage exceeds `REFQ_COV_MAX` (173 dark pixels per 10,000 part
pixels). The coverage term is the net for a dark addition that is not small (a smear, or
contamination): the structure term cannot see it, the coverage term can.

Nine words, indices 544..552, each one the quantity its name says:

| word | index | meaning |
|---|---|---|
| `MB_REFQ_STATE` | 544 | 0 pass, 1 fail, 2 not measured, **3 declared unusual** |
| `MB_REFQ_DARK` | 545 | dark part pixels |
| `MB_REFQ_PART` | 546 | part pixels the statistic was measured over |
| `MB_REFQ_CNT` | 547 | small isolated dark structures |
| `MB_REFQ_AREA` | 548 | their total area, px |
| `MB_REFQ_COV` | 549 | dark pixels per 10,000 part pixels (coverage) |
| `MB_REFQ_THR` | 550 | the dark threshold used, grey |
| `MB_REFQ_DECL` | 551 | HOST: 1 = the next reference is declared unusual (one-shot) |
| `MB_REFQ_DECLF` | 552 | PS: the declaration frozen with this reference |

Cost: two passes over the part region's pixels (median histogram, then the dark and
isolated counts) and one 14,400-cell flood fill with the existing `PART_CC_STK`
stack, on existing scratch grids (`PART_LATT`, `PART_CC_TMP`, `g_part_hist`). No new
buffer, no OCM, no mailbox beyond the nine words. It is paid at reference capture only —
no comparison, no AEC cycle.

the three 2026-10-26 frames at 8698 (the sessions' `MB_DIFF_REFEXP` dumps), so the
population spans two exposures as well as several placements; the two `synth/` frames

* **Clean reference: PASS.** The good population reads **0 structures**, coverage
  **1..103** per 10,000 (0.01%..1.03%), and the largest isolated dark structure on any of
  them is **54 px**. The `cnt=0` holds at both exposures and at all three placements.
* **Marked reference: FAIL.** The incident reference reads **4 structures, 1076 px total,
  coverage 292 (2.92%)**, threshold 52 grey. The four structures are exactly the four
  marks, in the cells the incident report identified: `(11 cells, 407 px, x52..54 y59..63)`,
  `(11, 328, x57..63 y52..54)`, `(11, 244, x47..54 y70..73)`, `(4, 97, x58..60 y60..61)`;
  the group the firmware judged NG (`DAREA` 11, cells x52..59 y68..71) is the third one.
* **Known-abnormal references also fail**, which is the correct direction: the two
  references taken of the contaminated board (6 and 13 structures) and the populated
  board's reference (4 structures on component edges).

The **thresholds are the geometric midpoint of the two measured edges**, so the margin
is stated on both sides:

| constant | value | bound below | bound above | margins |
|---|---|---|---|---|
| `REFQ_AREA_MIN` | 72 px | good max structure 54 px | smallest mark 97 px | 1.33x / 1.35x |
| `REFQ_COV_MAX` | 173 / 10,000 | good max 103 | marked 292 | 1.68x / 1.69x |
| `REFQ_CNT_ACCEPT` | 0 | good max 0 | marked 4 | 0 / 4 |

The two populations do not overlap on any of the three axes, so a threshold is
shippable (had they overlapped, this report would say so and ship nothing).

## 4. Why the constants are where they are (measured, not chosen)

`REFQ_DARK_NUM` / `REFQ_BRIGHT_NUM` / `REFQ_CELL_MIN` were swept with the exact rule
(`python ps_ui\refq_replay.py --sweep`; the decision is stable where the constants sit):

| dark/256 | good max (cnt, cov) | marked (cnt, cov, area) |
|---|---|---|
| 80 | (0, 65) | (3, 220, 780) |
| 90 | (0, 82) | (4, 260, 971) |
| **100** | **(0, 103)** | **(4, 292, 1076)** |
| 110 | (0, 103) | (4, 333, 1209) |
| 128 | (2, 143) | (4, 380, 1308) |

The verdict is identical for dark 80..110 (the chosen 100 is the middle of the
plateau; 128/256 starts counting structures on good frames). The bright threshold is
immaterial over 1.40..2.00 x median (the small structures are not near pads), and the
cell floor is immaterial over 4..8 of 64 px (the marked area shifts by ~2%, the counts
do not). `REFQ_AREA_MAX` 2048 px is a definition of "small" (32 cells), not a
calibrated bound: the marks are 97..407 px, so it is 5x above the largest one.

**Exposure invariance** was measured by replaying the same frames at synthetic gains
0.55..1.20 x (the relative threshold follows the median): the clean reference stays
coverage 19 and 0 structures at every gain; the marked reference stays coverage 292,
4 structures, 1076 px at every gain. It is not a substitute for a second real exposure
population, and the two real exposures above (4349 and 8698) are the stronger evidence.

## 5. The check in the self-test, and the preflight line

Check 5 (REFQ) has the same shape as the other four: PASS / FAIL / NOT MEASURED, a
named code (`MB_ST_CODE` 5), a bit in `MB_ST_FAIL` (0x10) and two bits in `MB_ST_RES`
(bits 8-9). The aggregate verdict is FAIL if any check failed, else INCOMPLETE (2) if
any check is not measured, else PASS — a not-measured REFQ is never printed as PASS
(D6 rule).

The check is **declarable**, mirroring the averaging arm's `--expect-avg` (commit
38f8080). A host writes `MB_REFQ_DECL` = 1 **before** `MB_CMD = 9`; the firmware freezes
it into `MB_REFQ_DECLF` with that reference, **consumes** the host word (one-shot, so it
cannot stay in force the way `MB_AVG_N` did) and reports state 3 instead of 1. The check
passes, the numbers are still published, and `preflight.py` labels the line
`DECLARED-REFERENCE`. A production run (`--expect-refq clean`, the default) refuses a
declared reference with exit code 5, so an experiment cannot be left installed and
silently judged against; `--expect-refq marked` declares the A/B and passes.

The line the tool prints for the four states.  These are the head and the REFQ segment
of real `preflight.evaluate()` output, decoded from the words in sections 3 and 5 (the
middle of the line - ref/bg/aec/mask/avg - is elided: those words describe the live
station and are not part of this measurement.  `python dl\host_qc\preflight.py
--selftest` cases 9a-9d print the same strings).  **Offline decode: no board, no board
line was read.**

```
PREFLIGHT PASS code=0 fail=0x00 | ... refq(dark=54 part=27136 cnt=0 area=0 cov=19 thr=54 state=0 decl=0 expect=clean)
PREFLIGHT FAIL code=5 fail=0x10 first=REFQ | ... refq(dark=1254 part=42944 cnt=4 area=1076 cov=292 thr=52 state=1 decl=0 expect=clean) failed=REFQ
PREFLIGHT PASS code=0 fail=0x00 | ... refq(dark=1254 part=42944 cnt=4 area=1076 cov=292 thr=52 state=3 decl=1 expect=marked) DECLARED-REFERENCE (the reference was declared intentionally unusual; an A/B, not a production reference)
PREFLIGHT FAIL code=0 fail=0x00 first=REFQD | ... refq(... state=3 decl=1 expect=clean) DECLARED-REFERENCE (...) failed=REFQD REFQD: MB_REFQ_DECLF=1: this reference is DECLARED unusual (an A/B or a deliberately marked board); a production run must not judge against it.  Re-take the reference, or declare the experiment with --expect-refq marked
```

Exit codes: FAIL on the firmware's check → 3; a declaration mismatch (declared
reference in a clean run, or `--expect-refq marked` that the firmware did not record) →
5; not measured → 4.

## 6. What was verified offline (and how)

* **The part-region replay reproduces the firmware's own mask exactly.**
  `python ps_ui\refq_replay.py --mask-check` rebuilds `BASE_MASK` from the marked
  reference's frame (4-pixel lattice + `bg_grid.bin`, `bg_scale_median` `bg_diff_fill`,
  erosion at `BG_MASK_THR` 24, `PART_CC_K` 2 cluster) and compares it with the
  firmware's dumped mask: **671 cells, 671 shared, 0 replay-only, 0 dump-only**. So the
  region the statistic is measured over is the region the firmware used.
* **The replay is the firmware's rule, line by line** (`ps_ui/refq_replay.py` mirrors
  `refq_measure()`: the firmware's median rule, strict `<`/`>`, 8-connected cell
  components, area = isolated pixels, the integer coverage). The nine words it prints
  are the words the replay says the firmware would publish — this is the instrument the
  board run would be checked against, not a second opinion.
* `python dl\host_qc\preflight.py --selftest`: **32/32** offline checks (was 20; +12 for
  REFQ, the declaration and the not-measured cases).
* `python dl\host_qc\check_words.py`: **99/99** host words match `ps_ui/main.c`
  (was 90; +9 REFQ).
* `python dl\host_qc\selftest.py`: 56/56 (unchanged — the panel path is untouched).
* `python dl\host_qc\qc_conveyor.py --selftest` and `--sim` are **not extended**: the
  conveyor's own judging gate does not consult REFQ yet (section 8).
* Build: 394 words, 0 collisions, layout checks pass, the same four pre-existing
  warnings.

## 7. The board acceptance: NOT PRODUCED, with the evidence of why

The task's acceptance is a live reference of a clean board (PASS, numbers quoted) and a
live reference of a marked board (FAIL). Neither was produced. The reason is physical,
not a judgement call:

* The station is powered and JTAG-visible (Digilent JTAG-HS1, `xc7z020`, A9 present on
  the first probe) but **cold**: `mrd 0x10F00000` fails with `Cannot access DDR: the
  controller is held in reset`; OCM word 0 reads `0x9FA90DDC` (no image); the PL
  register range (`0x40400000`) times out, i.e. the PL is not configured. pc read
  `0xffffff28`.
* This was read **before any reset or write** — the first client this session was a
  read-only probe (`ps_fft_dual/a0_probe_20261027.tcl`). A later read of the PL range
  put the DAP into the documented `APB AP transaction error` state
  (`0x30000021`); the APU target is no longer listed. The normal bring-up
  (`ps7_init` + `ps7_post_config` + the bitstream) recovers that state — it is the
  recovery `ps_fft_dual/aec_target.tcl` documents — but it is exactly the class of
  operation this task forbids, and without the bitstream there are no camera frames to
  take a reference from.
* Therefore no `MB_CMD = 9` reference was taken on the board, no `preflight.py` line was
  read from it, and no words were quoted as a board measurement. **No board line is
  invented here.**

What the offline data supports, stated exactly: *the statistic separates a clean
reference from the marked reference on every frame the firmware has ever dumped*, with
the margins in section 3. It does **not** establish that the firmware's REFQ block
publishes those numbers on the board (the C is a re-implementation of the replay and
has not been run), that the board's own clean reference reads `cnt=0`, or that the
marked board available to the operator would read `cnt>=1`. Those are the three
checks the board run would settle.

## 8. What remains unverified, and the limitations that are real

1. **No live REFQ word on any board.** The firmware has not been flashed: the station's
   DDR could not be read at all (the controller is held in reset), so even `MB_FWID0..2`
   could not be checked, and the boot reference's REFQ words have never been produced by
   this build.
2. **The C has not been compared with the replay on a real reference frame.** The
   intended known-answer test is: take a reference, dump `REF_BASE` (0x12400000) and
   `BASE_MASK` (0x126C4000), run `refq_replay.py --frame/--mask`, and require the nine
   words to match `MB_REFQ_*` exactly. It is written but its board half is missing.
3. **The marked-board reproduction was not made.** A black mark on the spare board's
   solder mask (or the contaminated board) would give a second, independent positive —
   the incident's own reference is the only marked one on disk.
4. **Blind spots by construction:** a mark inside a bright pad or on a component is not
   in the part region (the mask excludes bright metal); a mark larger than 2048 px is
   not a "small structure" and is only caught by the coverage term if it moves the
   coverage above 173; a reference of a *different board* (the populated `pairA` board)
   fails, which is the correct direction but shows the check is board-specific.
5. **`qc_conveyor.py` does not consult REFQ.** Its `judgeable_reason()` carries the
   averaging-arm gate; the same one-line predicate (`mb.refq_expect_state`) belongs there
   and is not wired in — the conveyor would still judge against a marked reference while
   `preflight.py` would have refused it.
6. **Storage of the declaration is a host word, not evidence of intent.** A host that
   writes `MB_REFQ_DECL = 1` can declare anything unusual; the firmware records it and
   the line labels it, but nothing prevents a careless declaration. That is the same
   property as `--expect-avg`, stated rather than hidden.
7. **Stale DDR on an older build is not distinguishable from a measurement.** The words
   are written by this build's boot block and by `ref_take()`; a build older than this
   one never writes them, so what a host reads there is whatever DDR holds (0xFFFFFFFF
   on a cold boot, the previous session's bytes on a warm one). `preflight.py` reports
   INCOMPLETE only for the 0xFFFFFFFF case; a stale plausible value cannot be told from
   a real one, and the guard for that is the build identity (`MB_FWID1/2`, quoted in the
   line) and the flash procedure, not the REFQ words.

## 9. Reproducing it

```
# offline (no board):
python ps_ui\refq_replay.py --mask-check       # the part region replay vs the firmware's mask
python ps_ui\refq_replay.py --table            # the population and the two directions
python ps_ui\refq_replay.py --frame <f> --mask <m>   # the nine words for one reference
python dl\host_qc\preflight.py --selftest
python dl\host_qc\check_words.py
cd ps_ui; powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1

# on a station that is up (NOT run here):
xsdb ps_fft_dual/strict_load_cores.tcl          # flash THIS build; MB_FWID0..2 must change
xsdb ps_fft_dual/b1_bg_guard_20261026.tcl       # MB_CMD=12 on a verified-empty belt
xsdb ps_fft_dual/a2_refq_ref.tcl                # MB_CMD=9 (clean board, operator out of frame)
python dl\host_qc\preflight.py                  # expect: refq(... cnt=0 ...) PASS
xsdb ps_fft_dual/a2_refq_ref.tcl                # MB_CMD=9 with a mark on the spare board
python dl\host_qc\preflight.py                  # expect: FAIL code=5 first=REFQ
# the declared arm: write MB_REFQ_DECL=1, MB_CMD=9 on the marked board, then
python dl\host_qc\preflight.py --expect-refq marked   # expect PASS + DECLARED-REFERENCE
# and back to a clean reference: remove the mark, MB_CMD=9, preflight PASS again.
```
