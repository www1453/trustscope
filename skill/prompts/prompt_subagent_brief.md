# 提示词工作流 · 交给子智能体的任务书（task brief）

> **任务形状**：你要把一块**自包含**的工作交给一个子智能体（或另一个会话、或明天的自己）。
> 它**看不到你的对话**，所以你写下的每一句都是它的全部世界观。
>
> **为什么这算"提示词工作流"**：任务书就是提示词，只不过它长、有文件路径、
> 有边界条件。写得好不好，直接决定它做出来的东西能不能进提交物。
>
> 本项目的所有离线整理工作（技能包、报告章节、离线分析）都是用这个形状派出去的。

---

## 提示词原文（骨架，按需删减）

```
# 任务
<一句话：产出什么、放在哪里。不要写"帮我看看"。>

# 背景（只写它读不到的部分）
<它看不到我们的对话。写出：项目是什么、这个仓库的结构约定、相关文件在哪。>

# 必须遵守的边界（逐条，可执行）
- 离线：不连板子、不开调试器、<具体到命令或设备名>
- 不修改：<文件/目录清单>。要改就先说明理由并等确认。
- 语言：内容可以用中文，**文件名与目录名只用小写英文/数字/下划线/连字符**。
- 提交：用消息文件提交（UTF-8 无 BOM），显式列出路径，不要 `git add -A`。

# 素材在哪（它应该从里面取材，而不是自己编）
- <路径1> —— 提供什么（例：真实失败案例的编号与数字）
- <路径2> —— 提供什么（例：可复用的校验脚本）
- 如果某件事在素材里找不到证据，**写"未找到"，不要发明**。

# 验收判据（它自己就能检查的部分）
- <可机械检查的项，例：脚本从新位置能跑通、`--selftest` 通过>
- <可机械检查的项，例：泄露扫描零命中>
- <需要人判断的项，例：每一条都写了适用/失效条件>

# 输出要求
<要它回报什么：做了什么 / 每项的用途与失效条件 / 跑过的检查与结果 / 故意没做什么>
```

---

## 四条要点（每条都来自一次真实的返工）

### 1. 边界要写到"可执行"

❌ "不要动硬件"
✅ "离线：不连板子、不开 xsdb、不改固件源文件"

第二条让它可以自己判断"我这个动作算不算违规"。第一条只能靠猜。

### 2. 素材要指到**文件**，不要指到"项目里应该有"

❌ "参考我们之前的案例集"
✅ "`pitfalls/` 下有编号案例，编号与数字由 `scripts/casebook_index.py` 数出来，不要手写"

**素材指得准，它就不会编。** 本项目最强的一段材料（撤回记录、三个失败的 null）
全都在已有文件里，所以任务书里写的是"从这些文件里取材"，不是"总结一下经验"。

### 3. 明确允许"未找到"

写一句：**"如果素材里找不到证据，写'未找到'，不要发明。"**
没有这句，模型会用最像的东西填上，而"最像的"在工程记录里就是假的。

### 4. 验收判据要分成"它能自己查"和"人要判断"

能自查的（脚本跑通、扫描零命中）应该在它交付**之前**就跑过；
需要人判断的（这条对陌生队伍有没有用）只能由你来看——
**但要在任务书里写出来，否则它不会朝那个方向努力。**

## 真实失败案例

1. **任务书写了"整理一下这个模块的经验"，没有给路径。** 结果它写了一份
   "如何写好 FPGA 代码"的通识总结，与本项目无关，全部作废。
   **修法**：素材指到文件，并规定"每一条都要写来源文件与编号"。
2. **任务书没写"不要发明对话"。** 于是"大模型协作记录"里出现了从未发生过的
   提示词与回答。**修法**：明确写"不要编造对话；只写有文件/提交记录支撑的事件"，
   并要求每个事件带日期与 commit。
3. **任务书没写文件命名规则。** 产出物叫 `案例 整理.md`，与 `3.3.5.4` 的
   "纯英文文件名"冲突，提交前全部改名并修引用。
   **修法**：把命名规则写进"必须遵守的边界"，越早越便宜。

## 适用 / 失效条件

- **适用**：任何自包含、可验收、需要从既有材料取材的委派。
  尤其是"整理/提炼/审计"这类**不需要实时反馈**的工作。
- **失效**：需要频繁来回确认的探索性任务 —— 那时应该短回合对话，
  而不是写一份长任务书（写它的成本比任务本身高）。
- **失效**：委派方**自己也不知道验收判据**的时候。先把判据想清楚，
  否则任务书只会把你的模糊转移给它，而它会用自信的语气交付模糊。
