评审范围：`dl/update_report_1030.py`、`dl/scan_report_leak.py`、`dl/verify_report_1028f.py` 的正文，
以及 update/verify 家族的总体结构。**结论：批评成立，且全部集中在"不响亮的失败"这一类。**

## 它认可的部分（原文保留）

- 事务性编辑：写前形状断言、快照、"除了预期的几块谁都不许动"、插入后置条件、唯一一次 save

## 它指出的缺陷（按严重度）

1. `scan_report_leak.py:123` —— `parse_tounicode` 的 bfrange 对超过 256 项的映射范围**静默截断**，
   无警告、无测试覆盖；种植对照没有走到那条分支。
2. `scan_report_leak.py:135` —— 解压失败三次的流被静默丢弃（`if s: streams.append(s)`），
   不计数不报告；**"零命中"与"看不见"在输出里不可区分**。
3. `scan_report_leak.py:77` —— `line = text[:0].join("")` 是死代码（且属于一个多行语句）。
4. NODE/KIT 运行时路径在三个脚本里有三种写法（`update_report_1030.py` 有候选机制，
   另两个是单路径）——verify 系列会被反复重跑，恰恰是它们各抄了一份。
5. 以段落索引做主键、内容做校验，顺序反了（安全但 brittle）。
6. 小账：`fill()` 的幂等检查忽略加粗差异；`report()` 的 gbk-replace 会弄损打印出来的证据；
   `--files` 少参数是裸 IndexError；`open(path,"rb")` 无 `with`；函数中途 import；`hits[:25]`
   截断没有"还有 N 条"尾注。

## 本轮的处置（诚实记录）

- **尝试修 1 和 2，失败并已回滚**：第一次补丁误删了第 3 条那行（它是一个多行语句的首行）导致
  IndentationError；第二次补丁语法通过但扫描器在干净报告上 exit 1。
- **回滚到已提交版本**，并重新验证：干净运行 0 命中、种植对照通过。
- **结论**：这三条以"已知限制"形式留在本文件，**不以未验证的补丁形式进入交付物**。
  修它们需要一次独立的、带回归的工作轮次（约 30 分钟），不应压在截止前的最后一小时。
