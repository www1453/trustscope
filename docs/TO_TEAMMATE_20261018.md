## 3. 为什么"电脑检测"比"板端 CNN"更可能出结果（不是偷懒）

1. **现有 CNN 的能力边界**：64×64 灰度、两个 logits。1280→64 是 20 倍缩小，5 像素宽的断线只剩
   0.25 像素。它适合做 **ROI 复核**，不能做整板定位。
2. **板端算力已接近饱和**：实测循环 126 ms（融合态）/ ~55 ms（单曝光）。再加整网推理会把帧率
   压到不可用，而**检测节拍取决于机械稳定时间，不取决于 fps**。
3. **电脑上迭代快**：模板/配准/形态学的参数当天可调，板端每改一次要 25 分钟重建 + 烧录 + 冷启动
   （今天为此付出过两次锁屏代价）。
4. **先证明"看得见"，再谈"在哪算"**：如果这套镜头+光照下 0.1 mm 缺陷只有 2 像素，任何网络都
   救不回来——那是光学/机械问题，不是算力问题。

## 4. FPGA 在这条路线里仍然承担什么（作品完整性）

```
到位传感器 → PL/PS：去抖、停带、计时、联锁、采集成帧、帧所有权、显示
           → 以太网发送（PS GEM0）
电脑：完整性校验、切块、推理、结果合并
           → 返回 job_id/frame_id + 框 + 类别 + 分数
板端：匹配任务、AN970 显示、执行放行/保持停带
```

板端保留的实质工作：DVP 接收与像素组装、AXI Stream/VDMA、帧描述符与所有权、控制状态机与超时、
显示与触摸、网络发送、**以及"结果回传后由板端执行物理动作"这一闭环**。
可选（有实测依据再加）：ROI 裁剪、灰度化、图像质量门控。

## 5. 我认为最可能推翻这条路线的四件事（请重点审这段）

**5.1 交付包仍不能独立重建**
缺 `ts_cn_font.h`、`startup.S`、`check_layout.py`、PS7 初始化、Vivado 工程。
→ 这是 M0，必须先补；补不齐，"可复现"这一项在评分里是硬伤。

**5.2 以太网在当前 BD 里是关闭的（实测）**
```
PCW_ENET0_PERIPHERAL_ENABLE = 0
PCW_EN_ENET0               = 0
```
→ 启用 GEM0 需要 BD 改动 + 一次 25–40 分钟重建 + MIO 分配复核（不能与现有 I2C/UART/触摸冲突）
+ BSP 集成 lwIP（约 1–2 天）。**这不是接根网线的事。**

**5.3 最小缺陷像素尺度未知**
它决定：是否需要换镜头/缩视野、ROI 大小、形态学核尺寸、CNN 是否还有意义。
→ 拿一块真实缺陷板、在固定视角下量一次即可，但这个数现在没有。

**5.4 冻结根因未定位**
10 分钟未复现 ≠ 已修。我们只知道两种表现形态，不知道触发条件。
→ 需要更长的运行（30 分钟）+ 冻结时的现场抓取（你的 `capture_readonly.tcl`）。

## 6. 如果上述任一条不成立，路线怎么退

| 风险 | 退路 |
|---|---|
| 以太网集成代价过高 | JTAG/USB 取图或 SD 卡交换（仍是板端采集，只是不实时联网） |
| 缺陷太小（<2 px） | 换镜头/缩视野/加补光，这是光学问题，换算法无用 |
| 机械重复精度不够 | 加定位治具；模板法命门在此，不是配准算法能救 |
| 冻结复发 | 回到单相机固定曝光基线，暂停融合与双路 |
