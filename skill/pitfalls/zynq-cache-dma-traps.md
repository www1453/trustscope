# Zynq / PYNQ 缓存与 DMA 一致性：踩坑清单与排查步骤

> **适用场景**：任何让 PS 与 PL 通过共享内存交换数据的项目 —— PYNQ overlay + DMA、
> Vitis 裸机 + AXI DMA、Linux + udmabuf、Zynq-7000 / UltraScale+ 均适用。
> **不与本队题目绑定**：换题目、换板卡仍然可用。
>
> **证据等级说明（重要，请连同结论一起读）**：
> 下面每一条的**实测数字来自本队在 Zynq-7020 裸机**环境下付出代价后的记录。
> 机制（ARM Cortex-A9 的 L1/L2 与 PL 不参与缓存一致性）在 PYNQ 上**完全相同**，
> 但**"PYNQ 对应做法"一栏是本队按机制推导的，未在 PYNQ 上实跑验证**。
> 两条分开标注，请勿把它们当成同一等级的结论。

---

## 为什么这件事必然踩

Zynq 的 PL（含 DMA 引擎）**不参与 ARM 的缓存一致性**。PS 侧看到的 `0x1000_0000`
是**物理地址经缓存翻译后**的值。于是：

- PS 写了 buffer，但数据可能还躺在 L1/L2 里没落到 DDR → **DMA 搬走的是旧内容**
- DMA 写了 buffer，但 CPU 读到的是缓存里**上一次的旧行** → **看到过期数据**

这两件都不会报错，只会给出**看起来合理但错误的结果**。这是本类问题最难的地方。

---

## 坑 1：`dow -data` + `con` **不会复位 CPU**，旧缓存行会写回覆盖新镜像

**触发条件**：反复"下载新镜像 → 运行"（Vitis/JTAG 调试的常态）。

**症状**（实测）：
- **随机位置的数据中止**（data abort）
- **寄存器里出现反汇编上不可能的值**
- 刚下载的代码和 CPU 正在执行的代码**不是一回事**

**机制**：`dow -data` 只写内存，不清缓存。上一版留下的**脏行**会在后续被写回 DDR，
盖在新下载的镜像上；I-cache 里还留着上一版的指令。于是"新代码"被"旧数据"覆盖。

**排查步骤**：
1. 变量/PC 出现**不可能的值** → 先怀疑缓存，而不是先怀疑逻辑
2. 用 `mrd` 读该地址：**如果 JTAG 读到的值与 CPU 看到的不一致**，就是缓存问题

**正确做法（裸机，实测有效）**：`startup.S` 的 `_start` **第一件事**就是
关缓存 → 按 set/way **作废整个 D-cache**（**丢弃脏行，不是写回**）→
作废 I-cache/TLB → 关 MMU。之后反复下载运行才可靠。

> **PYNQ 对应（未实测）**：反复重载 overlay 时，`pynq.Overlay` 的 buffer
> 若被复用，同样可能出现上一轮残留。每次重跑前重新 `allocate` 或显式 invalidate。

## 坑 2：读写方向不同，维护操作不同 —— 搞反了不报错但不生效

| 数据流向 | 需要的操作 | 记法 |
|---|---|---|
| **PS 写 → PL/DMA 读** | **clean / flush**（把脏行推到内存） | "推出去" |
| **PL/DMA 写 → PS 读** | **invalidate**（丢弃缓存行，强制重读） | "扔进来" |

**最容易犯的**：读了 DMA 结果却只做了 flush —— 缓存没作废，CPU 读到的还是旧值，
**看起来"数据没更新"**，于是你去查 PL，而问题在 PS 侧。

**排查步骤**：接收 buffer 读到**恒定不变的旧值**（尤其第一次运行是对的、之后一直是同一份）
→ **先怀疑只 flush 没 invalidate**。

## 坑 3：L2 开不开，决定你要不要额外编程 L2C-310

**实测**：`L2C-310` 的 `Control` 寄存器读出 `0x00000000` → **L2 是关的**。
所以本队环境里**只有 L1**，`DCIMVAC`/`DCCMVAC` 就够了。

**如果 L2 是开的**，同样的操作**不完整** —— 还要编程 L2C-310
（`L2C310_Flush/Invalidate` 系列），否则 L1 干净了、L2 还脏着。

**排查步骤**：**先去读 L2C-310 的 Control 寄存器**，不要凭"芯片有 L2"就假设它开着。
本队就是靠先读这个寄存器，才避免了多写一段无效代码。

> **PYNQ 对应（未实测）**：PYNQ 跑 Linux，**L2 是开的**。
> 所以裸机那套"只有 L1"的假设**在 PYNQ 上不成立**，必须用完整的
> clean+invalidate（或 PYNQ/Xilinx 提供的 DMA 一致性 API）。

---

## 坑 4：PS 与外部主机共享的内存被判为**可缓存** → 外部写、CPU 读不到

**场景**：主机（JTAG / PCIe / 网络）写一块内存，CPU 轮询它。

**实测症状**：主机写了，CPU 反复读到**旧值**，而主机读回来是对的
（因为主机走物理地址，绕过缓存）。

**正确做法（实测有效）**：在 MMU 里把这块内存映射为**不可缓存**
（我们把它设成 Normal Non-cacheable，1 MB 区）。这样 CPU 每次访问都直落内存，
缓存维护对它无效这件事也就不再是坑。

> **PYNQ 对应（未实测）**：用 `pynq.MMIO` / `xlnk` 分配并标记为 device 或
> non-cacheable 的区域；不要用普通 numpy buffer 去接 DMA。

## 坑 5：逐字段读取一个"结构体"会读到**撕裂值**

**场景**：PL 或另一个核在一段内存里更新一组计数器，宿主逐字读出来。

**实测症状**：**行与行之间不属于同一帧**。我们一度得到"相位占比加起来 136.8%"
这种物理上不可能的结论 —— 根源就是**读的每个字来自不同帧**。

**排查步骤**：
1. 各分量**加起来不等于总数**（或占比 >100%）→ 立刻怀疑撕裂
2. 对照：把读的次数、顺序改动一下，**如果异常随之改变**，那就是读的问题不是被测对象的问题

**正确做法（实测有效）**：**一次一致快照** —— 用一个"帧号/序号"字段包裹，
先读序号→读数据→再读序号，两次序号相同才算一次有效快照；或让 PL 提供一个
原子的锁存脉冲，把整组数据同时锁进影子寄存器。

> **PYNQ 对应（未实测）**：`pynq.MMIO` 支持一次读多个寄存器（`read(offset, length)`），
> 优先用它而不是多次单字读；必要时在 overlay 里加影子寄存器 + 握手。

## 坑 6：**不要为了回避一致性问题而关缓存**

**实测数字**：打开 MMU + D-cache 让 PS 侧渲染从 **2.87 fps 提升到 19.60 fps（6.8×）**。
反过来，如果为了"省掉缓存维护的麻烦"而把缓存关掉，就是**用 6.8 倍的性能损失
去换一个本来可以正确处理的义务**。

**判断标准**：缓存一致性是一件**必须做对的事**，不是一个可选的优化。
如果你发现自己在"为了避免不一致而关缓存"，正确动作是**补上 flush/invalidate**，
而不是把缓存关上。

## 一页速查

```
PS 写、PL 读   ->  clean/flush
PL 写、PS 读   ->  invalidate
两边都写       ->  两个都要

读到恒定旧值           -> 只 flush 没 invalidate
变量出现不可能的值     -> 缓存脏行 / 没复位 CPU
各分量加起来不等于总数 -> 撕裂，要一致快照
外部主机写、CPU 读不到 -> 那块内存要映射为不可缓存
不知道要不要编程 L2    -> 去读 L2C-310 的 Control 寄存器
```
