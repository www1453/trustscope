# Item 5 (2026-10-26, session B1): a host instrument for camera 1's 12-move budget -- and what it measured

Firmware `ps_ui/main.c`, source hash **434636D9**. Camera 1's control law was NOT changed;
this adds one host word and the block that consumes it.

## 0. The one-paragraph answer

`MB_CAM1_AEC_TRIES` had read 0 in every trace ever taken on this bench, so the path AFTER the
move budget is exhausted (hold with state 2 rather than 3, `dl/CAM1_AEC_20261026.md` s.7.3)
had no bench evidence. The lever ladder makes it hard to reach by scene alone: k is 1..2 and
the gain ladder is 16/40/64/88/112/128, i.e. **six moves in one direction**, and a monotone
traversal ENDS at a rail where the loop stops demanding moves (state 3) instead of asking for
a thirteenth. A host word `MB_CAM1_AEC_SEED` (543) now seeds the counter once, magic-guarded
(`0x5EED0000 | n`), so the post-exhaustion code can be OBSERVED. Measured on the board: the
word is **inert in the product path** (DDR junk 0xFD1EF9A5 at boot was correctly ignored, no
stray seed), it **acts exactly once** (writing 0x5EED000C set `MB_CAM1_AEC_TRIES` to 12
immediately and the word read back 0), and the usable-image branch **clears it on the next
evaluation** (12 -> 0 in 1.9 s). The hold itself -- TRIES pinned at 12 with an unusable image
-- was NOT measured: it needs a dark scene (the operator covering camera 1's lens) and the
bench was closing.

## 1. What changed (file:line)

* `main.c:1647-1671` -- the word `MB_CAM1_AEC_SEED` 543 and `CAM1_SEED_MAGIC` 0x5EED0000.
  The magic guard exists because the mailbox is DDR junk after a power cycle; the value is
  clamped to 0..AEC_STUCK_TRIES and the word is written back to 0 when consumed.
* `aec_control_cam1()` -- one block at the top that reads the word and adopts the count. It
  writes the counter for no other reason and changes no branch: with the word at 0 (or
  anything that is not the magic) the controller behaves exactly as before.
* Mailbox 384 words, 0 collisions.

## 2. Measured on the board

```
BEFORE  CAM1 st=1 k=2 exp=8698 gain=16 mean=521 clip=7 last=0 tries=0 seed=0xFD1EF9A5
wrote MB_CAM1_AEC_SEED = 0x5EED000C (n=12)
AFTER   CAM1 st=1 k=2 exp=8698 gain=16 mean=521 clip=7 last=0 tries=12 seed=0x00000000
t=1.9s  CAM1 st=1 k=2 exp=8698 gain=16 mean=521 clip=7 last=0 tries=0  seed=0x00000000
t=6.4s  CAM1 st=1 k=2 exp=8698 gain=16 mean=521 clip=7 last=0 tries=0  seed=0x00000000
```

Three facts: (a) the boot word held **0xFD1EF9A5**, i.e. DDR junk, and produced no seed --
the magic guard is doing work, not decoration; (b) the seed was adopted and consumed
(`tries` 12, word 0); (c) the next evaluation whose image is usable clears the counter and the
state stays 1 -- so a stray seed cannot make the station hold a usable image.

## 3. Why the budget cannot be exhausted by a dark scene (analysis, not measurement)

From the shipped ladder in `aec_control_cam1()`: brightness levers are k (1..`MB_CAM1_KMAX`
= 2 on this bench) and gain (16 -> 128 in five +24 steps). A monotone traversal is therefore
at most **six** accepted moves (five gain + one k), and the sixth leaves the ladder at a rail
where the next evaluation finds no lever and publishes state 3 (`dec` 7) without asking for a
move -- the budget check is never reached. The counter needs 12 ACCEPTED moves with no usable
frame in between, which requires the scene to reverse direction at least once (e.g. very dark
then very bright) while never measuring a usable frame; any usable frame resets it (measured
above: 12 -> 0). That is what the operator-driven dark/light test was for, and it did not
happen tonight.

## 4. What this means for the code

If a bench cannot reach the budget naturally, the guard is close to dead code and the honest
simplification (for a session that is allowed to touch camera 1) is to replace it with a bound
of ~6 or to remove it from the locked law, keeping only the reversal debounce. That is stated
as a recommendation, NOT done -- camera 1's controller was out of scope for this item.

## 5. Limits

* The hold path (TRIES at the budget, state 2, `dec` 7, lever frozen) is **unverified on the
  board**. The instrument that makes it reachable is installed and verified.
* The seed ceiling is a clamp to AEC_STUCK_TRIES = 12; a value above it reads as 12.
* The magic guard leaves a 2^-16 chance per power-on that DDR junk matches `0x5EED0000|n`;
  if that ever happened the count would start high for one boot and be reported in
  `MB_CAM1_AEC_TRIES`, and the usable-image branch would clear it at the first usable frame.

## 6. Reproducing it

```
xsdb ps_fft_dual/b5_seed_20261026.tcl 12     # write the seed, prove consumption and inertness
xsdb ps_fft_dual/b1_trace_20261026.tcl .tmp/b5 t.csv 120 400 "MB_CAM1_AEC_STATE,MB_CAM1_AEC_K,MB_CAM1_AEC_EXP,MB_CAM1_AEC_GAIN,MB_CAM1_MEAN,MB_CAM1_CLIP,MB_CAM1_AEC_LAST,MB_CAM1_AEC_TRIES,MB_CAM1_AEC_FLAGS,MB_CAM1_AEC_SEED"
```
For the hold: cover camera 1's lens (opaque) so its image is out of band, let ONE move be
accepted (state 2), then seed 12 -- the next demand must be refused (`dec` 7, no lever write,
state 2), and uncovering the lens must clear it (`dec` 8, state 1, TRIES 0).
