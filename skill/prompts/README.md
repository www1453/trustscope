# 提示词工作流

本目录收录**经过本队实际验证**的提示词模板。

## 使用前提（重要）

这些提示词的效果**强依赖模型能否读到你的实际工程文件**。

| 场景 | 效果 |
|---|---|
| 模型能直接读工程文件（头文件、BD 导出、报告） | ✅ 好 |
| 只能靠你粘贴片段 | ⚠️ 一般，且**更容易凭记忆编造 API** |
| 模型无法访问任何工程信息 | ❌ 差，**它会用"记忆中的版本"回答你** |

> **本队最强的单条经验**：**凡是 API 调用、端口名、寄存器名，一律要求模型先读文件再回答。**

## 索引：什么任务形状用哪一条

| 工作流 | 任务形状 | 失败案例（真实） |
|---|---|---|
| [P1](#p1--从记忆切换到证据最有效的一条) 证据优先 | 要模型写 API / 端口名 / 寄存器名 / 引脚号 | 模型凭记忆给了个不存在的参数，编译才发现 |
| [P2](#p2--从时序报告定位瓶颈) 时序报告定位 | 实现跑完了，WNS/TNS 有违例 | 报告不存在时它开始编"常见违例原因" |
| [P3](#p3--从波形差异定位跨时钟域问题) 波形差异 | 同一信号在两个时钟域下不一致 | 直接问"为什么"得到一堆猜测，没有一条被排除 |
| [P4](#p4--把踩过的坑结构化沉淀) 失败→案例 | 刚踩完一个坑，要沉淀成条目 | 它补了原始记录里没有的细节，整条作废 |
| [P5](#p5--生成可复现的构建脚本) 构建脚本 | 需要可重复执行的构建/修改脚本 | 脚本打印 "done" 但什么都没改（见 pitfalls B1） |
| [`prompt_retraction.md`](prompt_retraction.md) 撤回记录 | **一个已经写进报告的结论被测量推翻了** | 模型把撤回写成辩护，原句一字未动 |
| [`prompt_null_first.md`](prompt_null_first.md) 地板先行 | **还没采数据**，准备采一批来定阈值 | 采完 54 个工位才发现地板在信号上面（M53） |
| [`prompt_subagent_brief.md`](prompt_subagent_brief.md) 任务书 | 把一块自包含工作交给子智能体/另一个会话 | 任务书没给路径，它写了一份通识总结 |

> 后三条各自是独立文件，因为它们的**输入**（原句 + 新证据 / 测量计划 / 委派目标）
> 需要按格式准备，而不是粘贴一段就完事。前五条在本文档内。

**三条提示词工作流的公共判据**（不满足就别用它的产出）：

1. 它有没有**说出名字来自哪个文件哪一行**？没有 ⇒ 大概率在编。
2. 它有没有**新增你没提供的数字**？有 ⇒ 要么删掉，要么标成"未提供"。
3. 它有没有给**可执行的下一步**（实验、判据、kill criterion）？没有 ⇒ 它只是在安慰你。

## P1 · 从"记忆"切换到"证据"（最有效的一条）

```
在回答之前，请先读取以下文件，并只依据文件内容回答：
  <列出文件路径>

如果你无法读取其中任何一个文件，请直接说"无法读取"，不要凭记忆回答。
回答中每一个函数名、参数、宏名，请标注它来自哪个文件的哪一行。
```

**为什么有效**：模型最容易犯的错是**凭记忆编造 API**（参数个数不对、字段名不对、
宏名拼错）。强制它标注来源，等于强制它去读文件。

**怎么判断它的回答不可信**：
- 它说不出名字来自哪个文件 → **大概率是编的**
- 它给的 API 在当前版本不存在 → 让它"先在头文件里搜索确认"

## P2 · 从时序报告定位瓶颈

```
读取 <path>/impl_1/*_timing_summary_routed.rpt。

请回答：
1) WNS / TNS / WHS 分别是多少
2) 如果有违例，列出违例路径的起点和终点（含时钟域）
3) 哪些违例集中在同一个时钟域或同一个模块
4) 针对第 3 条，给出 2~3 个**具体的**修改建议，每条说明它为什么能改善该路径

不要给出泛泛的"优化逻辑"这类建议。每一条建议必须指向报告里的具体路径。
```

**失效条件**：报告不存在（还没跑实现）时无意义。

## P3 · 从波形差异定位跨时钟域问题

```
这是同一信号在两个时钟域下抓到的波形数据：
  <粘贴或给出数据>

请：
1) 找出两者不一致的采样点位置
2) 判断不一致的模式：是固定偏移、随机抖动、还是周期性丢失
3) 基于第 2 条的结论，列出 2~3 个可能的根因，按可能性排序
4) 说明**如何用一次实验区分**这些根因

不要直接下结论。先给区分实验，再给结论。
```

**为什么这样写**：直接问"为什么"会得到一堆猜测。
要求它**先设计区分实验**，才是工程做法。

## P4 · 把踩过的坑结构化沉淀

```
下面是本次调试中发生的一次问题，包含现象、我的排查过程和最终根因：
  <粘贴记录>

请把它整理成如下格式（不要添加我未提供的信息）：
  触发条件 / 现象 / 根因 / 排查步骤 / 修复 / 适用条件 / 失效条件

其中"适用条件"和"失效条件"必须写 —— 说明什么情况下这条经验不再适用。
```

**注意**：模型容易**编造它不知道的细节**。
整理完成后**必须逐条对照原始记录核对**，删掉原始记录里没有的内容。

## P5 · 生成可复现的构建脚本

```
读取当前工程的 <列出文件>，生成一个从零复现的构建脚本。

要求：
1) 只用 ASCII 字符
2) 幂等：重复运行结果一致，不因"已存在/已连接"报错
3) 每个查找都打印结果，空结果显式打印 NOT FOUND
4) 末尾打印明确的 DONE 或 FAILED: <原因>
5) 不要使用 catch 静默吞掉错误

输出后，请列出你认为**最可能失败的三步**，以及失败时会看到什么输出。
```

**第 5 条要求很有用** —— 它会把"脚本看起来成功其实没生效"的风险提前暴露出来。

## 通用反模式（看到就要警惕）

| 模型输出 | 问题 |
|---|---|
| "这个函数应该是 `XIc_xxx()`" | **"应该是"= 在猜** |
| 给出 API 但不给参数类型 | 大概率在凭记忆写 |
| 一次性给出 200 行大改 | 违反小步验证，出错难定位 |
| 用 `catch { }` 包住所有东西 | 可能制造静默失败 |
| 说"已修复"但没有可核对的输出 | **无法验证 ≠ 已修复** |
