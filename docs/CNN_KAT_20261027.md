## 1. What was actually wrong

Two facts, and neither was the accelerator:

1. **The weights were never in DDR.** `cnn_init()` writes six *pointers* into
   `s_axi_control_r`; the 147,672 bytes of `wq/mtab/stab/btab` were only ever compiled into
   `cnn_weights.h`, which `main.c` does not include. The IP therefore read DDR power-up
   garbage. `MB_CNN_OK = 1` is true and proves only that AXI-Lite works; `MB_CNN_PASS` and
   `MB_CNN_RUNS` read implausible values (1,747,587,060 / 236,249,359) because nothing had
   ever written them.
2. **The on-demand path already existed.** `main.c:15267` handles `MB_CMD = 7` by calling
   `cnn_selftest_run()`, which runs all eight vectors and publishes `MB_CNN_PASS`. The
   boot-time copy is disabled (`if (0)`, main.c:14260) for a good reason: without weights it
   could only fail, and the old read-count guard could wedge boot.

So the fix is host-side and the firmware is unchanged. That was the deciding constraint: any
rebuild changes `build_id.h` → new FWID → reload/flash → **the verified reference is lost** and
the station needs the ~40 min re-sweep. Not worth it for a gate that can be cleared without
touching the image.

## 3. Does `ap_done` ever arrive? **Yes.**

- Inside `cnn_run()` it arrives in ≈**29–31 ms** per vector at the board's 50 MHz
  FCLK (measured end to end, including JTAG polling).
- `AP_CTRL` during a run: `0x00000001` (start=1, idle=0); on completion the latched bits read
  `0x0000000E` (done=1, idle=1, ready=1), and the next read clears done — bit 1 is the HLS
  `int_task_ap_done` **clear-on-read latch** of a one-cycle pulse
  (`ts_cnn_top_control_s_axi.v` lines 42–44, 258–266). A missing done in a poll is easy to
  fake and was, three times today, until the control experiment below.
- The IP also completes **with the PS CPU halted** (`halt_vs_run_cnn_20261027.log`), so the
  accelerator does not depend on the processor being in its loop.

The old statement "`ap_done` never asserts (idle but never done)" is not what the board does
with valid weights; whatever produced it, it is not the current state of this bitstream.

## 4. OCM cost: **zero**

No firmware change, no rebuild, no flash. The footprint stays **131,016 of 131,072 bytes
(56 bytes free)** exactly as it was; `ps_ui.elf`/`ps_ui.map` were not touched by this work.
Nothing was added to OCM, because nothing was rebuilt.

**One side effect is real and must be said out loud.** A non-zero `MB_CNN_PASS` turns on the
per-frame inference at `main.c:15243` (`frames % CNN_EVERY == 0`). So from the moment the KAT
passes, the loop pays one `cnn_run()` every 16 loops — ≈30 ms each (measured via the KAT:
220–247 ms for eight). The loop period is capture-paced at 100–200 ms
(`loop_rate_20261027.log`: 8.4 loops/s, `MB_CAP_PERIOD` 104–200 ms; `final_state` 192 ms), so
one inference per ~2–3 s costs **≈1–2 % of loop time**. Live-frame logits are plausible and
change frame to frame (`MB_CNN_L0/L1 = -45880/48432`, `-50132/53150`, …), and `MB_CNN_RUNS`
now increments (206 → 207). The QC decision path does not read any CNN word (searched:
`g_cnn_pass`/`g_cnn_ok` appear only in publish and display code).

**Before any demo:**

- After a reload or reboot the weights are gone (they live only in DDR) and `MB_CNN_PASS`
  returns to garbage/0. **Re-run the one command** — it reloads the weights and re-runs the
  KAT in ~10 s.
- A flash or a firmware reload still destroys the reference and requires the ~40 min re-sweep,
  exactly as before. This work does not change that; it also did not trigger it.
- The panel line at `main.c:13556` still reads **"CNN NOT IN PATH"**. That is now stale. It is
  a one-line display change, but it requires a rebuild and reload, i.e. the re-sweep, so it is
  deliberately **not** done here. Until then, demonstrate the KAT with the log, not the panel.

## 6. What remains unverified

- **Per-vector words read back over JTAG.** The firmware's 8/8 is a per-vector exact
  comparison, so it is authoritative; but my independent per-vector replay over JTAG could not
  be made trustworthy (see §7) and is not evidence. Only vector 0 was measured directly
  (`[-49511, 51420]`), and it matches.
- **Per-inference latency in CPU cycles.** `MB_CNN_CYC` reads 0 because `PMCCNTR` is not
  enabled in this firmware, so `cnn_last_cycles()` always returns 0. The 29–31 ms figure is
  end-to-end host timing, not a cycle measurement.
- **Long-run stability** of the per-frame inference (≈15 min observed) and whether the
  ≈1–2 % loop-time cost leaves the 0/21 false-NG rate of the 41-board sweep unchanged. That
  needs the acceptance sweep run with `MB_CNN_PASS = 8`.
- **Boot-resident weights.** Not implemented, on purpose (§8).

## 7. Instrument lesson (worth a casebook entry)

The A9 debug path on this board is **cacheable**. A small JTAG write (8-byte canary, 4 KB
image) can stay in the 32 KB L1 (write-back; L2 is disabled per `mmu.c`) and never reach DDR,
and a JTAG read of a line the core already holds returns the stale line. Three separate
attempts concluded "the IP does not complete" — `replay_kat_8`, `8b`, `8c` — and all three
were **wrong**. The control experiment (`halt_vs_run_cnn_20261027.tcl`), using `AP_CTRL`
(AXI-Lite = Device memory = never cached), showed the runs finishing in under 100 ms in every
configuration, including with the CPU halted.

The 145 KB weight load is self-evicting (it cannot sit in a 32 KB cache), which is exactly why
step 1 was valid; and the firmware's own `cnn_run()` does `dcache_clean`/`invalidate`, which is
why the firmware path is trustworthy. **Rule: read results from the mailbox (mapped
non-cacheable), never from a raw DDR logits buffer over JTAG once the firmware has touched
it.** The three failed scripts are committed with their headers explaining the trap.

## 8. If a later build window wants it self-contained

- **Weights in a DDR linker section**: generate one `.c` from the four blobs, place it at
  `0x11010000`/`0x11040000…` via `lscript.ld`, so `MB_CMD = 7` works after `dow` with no host
  load. Cost: +145 KB ELF, a linker-script change, a new FWID, a reload/flash and the re-sweep.
  Only worth it if the demo must boot without a host.
- **Gate `cnn_infer()` on its own enable word** (e.g. `MB_CNN_EN`) so publishing the KAT does
  not change loop timing, and update the panel line to `CNN KAT 8/8`.
- **Enable `PMCCNTR`** (`PMCR.E`, `PMCNTENSET.C`) if a real per-inference latency number is
  wanted; today `MB_CNN_CYC` is always 0.

Recommended for the competition: keep the host load (§2), run the one command at bring-up, and
show the log. It is the only path that leaves the verified QC configuration untouched.
