### 结论（按预注册的判定规则）

1. **纸箱遮光是有效的：灯亮 125.29 → 灯灭 4.20，降 29.8 倍。**
   环境光残量 = **1.6% 满量程**。对照此前合成研究"方向未知的光把法向误差从 0.72° 吹到 9.04°（12.6 倍）"，
   **这个纸箱把那个根因去掉了**。P1 的预测（< 10）成立。
2. **当前曝光对这一场景是合适的**（均值 125.3，落在 80–180 内，p99=224 未削顶）。
   → 之前 `ps_run` 采样里看到的 8–22% 削顶**与这次不一致**，是另一次采样的状态，需单独解释，本次不涉及。
3. **噪声地板已实测确定**（这是本次最有复用价值的数字）：

   > **逐像素：灯亮 ~3.2 灰阶，灯灭 ~1.6 灰阶。整帧均值：灯亮 ~0.25 灰阶，灯灭 ~0.08 灰阶。**
   > **以后任何"差异"claim 必须先超过这两个数。**

   预注册里那个 3.0 的门槛是看不到数据时拍脑袋定的，**刚好卡在边界**；现在它被实测值取代（3.2 / 1.6）。
   注意地板**随信号变化**（亮 3.20 对 暗 1.60 ≈ 2 倍），符合光子散粒噪声随信号增长的特征 ——
   这是一条自洽性检查，说明量到的是真实噪声而不是固定偏移。

## 结果 v4（**这一节取代 v3 的全部数字**）：解码方式修正后重算

### 为什么 v3 的数字是错的

v3 把帧**解码成 `(360, 640, 3)` 的 32 位字**，理由是"渲染器报 `channels examined = 691200 = 640*360*3`"。
两处都错了：

1. **640×360 是 UI 上的相机画面尺寸，不是采集缓冲的尺寸。** `main.c` 写得很清楚：

   ```c
   #define CAM_W      1280
   #define CAM_H      720
   #define CAM_BYTES  (CAM_W * CAM_H * 3u)     /* = 2,764,800 */
   #define CAM_BUF    0x10000000u   /* capture store A: 1280x720, stride 3840, B,G,R */
   ```

   → 一帧是 **1280×720×3 = 2,764,800 字节**，即**每像素 3 字节的紧凑 B,G,R 流**。

2. **`mrd` 的计数单位是"字"，不是"字节"。** `mrd ... 691200` dump 出 691200 × 4 = 2,764,800 字节
   —— **长度其实完全正确**（我中途一度怀疑"超读了 4 倍"，那也是错的判断）。
   正确的解码因此是最朴素的那一种：`np.fromfile(f, dtype=np.uint8).reshape(720, 1280, 3)`。

> 单位混淆（字 / 字节）是这个项目反复踩的同一类错。这里它同时造成了**一次误判长度**和**一次错误解码**。

### 独立验证（这次不是我自己说对就对）

### 修正后的三家判据

| 判据 | 预注册门槛 | v3（解码错） | **v4（正确）** | 判定 |
|---|---|---|---|---|
| **P1 遮光残量** | < 10 | 4.20 | **6.923**（逐帧 6.90/6.97/6.90/6.93/6.92） | ✅ **PASS** |

**灯亮 118.38 → 灯灭 6.92 = 降 17.1 倍**，环境光残量 **2.7% 满量程**。
**削顶（任一道 ≥ 250）= 0.00%** —— 这一场景完全没有过曝。

→ **以后任何"差异"claim 必须先超过：逐像素 ~2.0 灰阶，整帧均值 ~0.24 灰阶。**

### v3 撤回的结论

1. **"图像是灰度的"—— 撤回。** v3 把一像素的 3 个字当成 R/G/B 去聚合，所以百分位看起来一致。
   按正确尺寸逐元素看：B 129.5 / G 118.4 / R 127.9，`|R-G|` 在 **89.75%** 的像素上非零，最大差 **56**。
   **图像是彩色的。**
2. **P3 的"marginal FAIL"—— 撤回。** 那个 3.20 是错误解码（4 字节当一个像素）算出的，它放大了量化误差；
   正确值是 **1.96**，通过。
3. 三家的**判定结论**（纸箱有效、曝光合适）**方向不变，且更强**。
