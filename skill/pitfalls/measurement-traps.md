## M1 · 抓到了一段"完美稳定"的波形（其实是残留）

**触发条件**
用片内逻辑分析仪（ILA）或类似工具观察信号，**且刚刚重新配置过设计/参数**。

**现象**
波形非常干净、稳定、完全符合预期 —— 干净到不像真的。

**根因**
ILA（及很多调试工具）显示的是**该触发位置最近一次捕获到的数据**。
如果在你的新配置生效**之前**就已经触发过一次，屏幕上一直显示的是**旧数据**。
**它不会因为你改了设计就自动刷新。**

**排查步骤**
1. **主动改变被测信号**（改参数、拉一下引脚、换个输入），然后重新触发
2. 看波形**跟不跟着变**：
   - 跟着变 → 是实时数据 ✓
   - 纹丝不动 → **极可能是残留** ✗
3. 更保险的做法：**先制造一个已知的变化**，确认工具能看到它，再去测真正关心的信号

**修复**
把"制造已知变化→确认能看到"作为**每次测量的前置步骤**，写进测量流程。

**适用 / 失效条件**
- 适用：所有基于触发捕获的调试工具（ILA、逻辑分析仪、部分示波器单次模式）
- 失效：连续刷新模式（Free-run / Roll）的示波器不会踩这个坑

**来源**
本队真实踩坑：一度根据"稳定波形"得出信号正常的结论，后来才发现那是残留。
**这条直接催生了本作品的核心功能之一**（可信度警告："未检测到新数据，可能是残留"）。

## M2 · 从极少量数据得出结论

**触发条件**
自动化统计/判定逻辑，**没有对样本数量做任何下限检查**。

**现象**
工具宣布"该信号是常量"、"频率为 X"，但实际信号并非如此。

**根因**
结论建立在样本量不足的统计上。
例如：在一个包含 1440 个采样点的窗口里，**只看了 3 个点**就判定"该位不跳变"。

**排查步骤**
1. 检查判定逻辑：**它用了多少数据？**
2. 检查是否存在"提前退出"逻辑（例如一发现不匹配就 return）
3. **故意构造一个反例**：给一个你确切知道答案的信号，看工具是否给出正确答案

**修复**
- 统计类判定必须**遍历整个窗口**，不能提前退出
- 加**样本量下限**：低于阈值时输出"样本不足，结论不可靠"，而不是给结论

**适用 / 失效条件**
- 适用：任何"从数据里得出结论"的自动化逻辑
- 失效：—

**来源**
本队真实踩坑：从 1440 个采样中仅凭 3 个点就判定"信号是常量"，
被自己后续的测量推翻。**这条同样变成了作品的"样本不足"警告规则。**

## M3 · 电平测出来"不高不低"，被当成正常

**触发条件**
被测器件与 FPGA 的 IO 电平标准不匹配，或供电异常。

**现象**
总线空闲电平测出来是 **1.79V** —— 既不是 0V 也不是 3.3V。

**根因**
**LVCMOS33 的输入电平规格是：**
```
VIL  <= 0.8V      （认得"低"）
VIH  >= 2.0V      （认得"高"）
0.8V ~ 2.0V       =【禁止区】，读出来是什么都不保证
```
**1.79V 落在禁止区。** 于是 FPGA 读这根线时结果是**随机的** ——
有时候读成 1、有时候读成 0、有时候抖。
表现为：大多数通信失败，偶尔"成功"但数据是垃圾。

**这种"时好时坏"极易被误判为软件 bug 或时序问题。**

**排查步骤**
1. **量空闲电平**（不发任何数据时），而不是忙时的电平
2. **对比"插上/不插上被测设备"两种情况** —— 差异能直接定位责任方
3. 对照电平规格表，确认是否落在禁止区
4. 同时确认**对方器件的 IO 电源轨**是接到哪一路的

**修复**
- 若对方是低压 IO（如 1.8V）：需要电平转换，或改用匹配的 IO 标准/电源
- ⚠️ **不要为了拉高电平直接换小阻值上拉到 3.3V** —— 若对方 IO 不耐压会烧器件

**适用 / 失效条件**
- 适用：跨电压域的数字接口（I2C、SPI、并行总线）
- 失效：同电压域、且双方 IO 标准一致的场合

**来源**
本队真实踩坑：用这条证据链最终定位了相机模块的故障
（同一条总线上换另一颗器件电平是干净的 3.3V，只有故障器件拖到 1.79V）。

## M4 · 通信完全正常，但功能完全不工作（状态位锁死）

**触发条件**
驱动一个有"状态寄存器 + 数据寄存器"的外设（触摸控制器、传感器、协议芯片），
读取状态后**只在"有数据"时才清除状态位**。

**现象**
- I2C/SPI 通信全部正常：能读到产品 ID、能写配置、能读回来校验通过
- 读错误计数为 0
- **但功能一个都不工作**
- 状态寄存器**恒定返回同一个值**

具体实测（GT911 电容触摸控制器）：

```
0x814E 返回 0x80   （bit7 = "缓冲区就绪"，但触摸点数 = 0）
在 42907 次轮询中，bit7 每次都置位 —— 从来没有被清掉过
触摸点数 > 0 的次数 = 0
```

**根因**
协议要求：**状态位被置位后，无论有没有数据，都必须清除它。**
代码只写了"有数据才清除"，于是状态位第一次置位后就**永久锁死**，
`芯片判定上位机还没取走上一次的数据，因此不再发布新数据` → 功能全挂。

清除之后：同样的读取逻辑，388 次触摸事件全部正常捕获。

**排查步骤**
1. **把状态寄存器的原始值记下来**（不要只记"有没有数据"）
   —— 本例中正是"恒为 0x80"这个原始值暴露了问题
2. 看这个原始值**是不是一直不变** —— 不变 = 状态位没被清
3. 回去读协议手册里"清除条件"那一句：
   **是"读到有效数据才清"，还是"只要状态置位就清"？**
4. 检查代码里清除语句的**位置和条件**

**修复**
把清除动作从"有数据时"移到"状态位置位时"（无条件清除）。

**适用 / 失效条件**
- 适用：任何"状态位 + 数据寄存器"的外设协议（GT911、多数传感器、部分 PHY）
- 失效：读操作本身就自动清标志的器件（这类器件不会踩这个坑）

**来源**
本队真实踩坑：AN970 触摸屏接入时，I2C 全通、产品 ID 正确、配置校验通过，
**但一个触摸事件都读不到**。根因就是清除条件写错。

**这条最难查的地方**：所有能测的指标都显示"正常" ——
所以**必须记录原始寄存器值，而不只是记录"成功/失败"**。

## M5 · 验证链路时看到的"漂亮方波"，其实是另一个信号

**触发条件**
搭好一条数据通路（采集 → 缓存 → 显示）后，**用"屏幕上有没有波形"判定通路是否打通**，
而没有独立确认数据源本身。

**现象**
- 屏幕上出现**非常干净的方波** ✓ —— 周期稳定、形状规整，看起来完全正常
- **但所有依赖这条通路的功能全部失败** ✗（协议解码解出乱码、测量结果不对）

**根因**
**采集模块的输入接错了**：接到了另一路内部信号上，而不是外部引脚。实测：

```
capture_ram_0/probe_i  dir=I  net=vtc_probe_concat_dout
   驱动源: /vtc_probe_concat/dout
```

采样器采的是 **LCD 自己的行/场同步时序**，不是被测信号。
屏幕上的"漂亮方波"是 **hsync**。

**怎么发现的（关键）**
1. 先量观测信号的**周期**：连续段 = 35 和 111 个采样点，采样周期 220 ns
   → 周期 = (35+111) × 220 ns = **32.1 µs**
2. 再算怀疑对象的理论周期：LCD 行同步 = 1056 像素 ÷ 33.33 MHz = **31.7 µs**
3. **两个数字几乎相等 → 确认采的是 hsync**

**排查步骤**
1. **不要看波形"像不像"，先量它的周期/频率**
2. 把测出的周期与板上已知信号的周期逐个比对（帧同步、行同步、时钟、分频计数……）
3. 用工具**查采集模块输入的真实连接**，不要靠"我应该接对了"：
   ```tcl
   set pi [get_bd_pins -quiet capture_ram_0/probe_i]
   foreach n [get_bd_nets -quiet -of_objects $pi] {
       puts "net: [get_property NAME $n]"
       foreach src [get_bd_pins -quiet -of_objects $n -filter {DIR == O}] {
           puts "  driver: [get_property PATH $src]"
       }
   }
   ```

**修复**
把采集模块的输入改接到正确的源（本例：`xlslice` 取外部引脚低 9 位 → 接 `probe_i`）。

**适用 / 失效条件**
- 适用：所有"采集 + 显示"型系统的联调
- 失效：—

**来源**
本队真实踩坑，**本项目最隐蔽的一个 bug**：
显示链、VDMA、BRAM、CPU 读回、渲染**全是好的** ✓，唯独**输入接错了** ✗ ——
所以屏幕上永远有漂亮波形，而所有解码/测量功能永远失败。

**教训**
> **"通路通了"不等于"数据对了"。**
> 验证数据通路必须同时确认两件事：
> ① 数据能从源头流到终点；② **源头送的确实是你以为的那个信号**。
> 只用"屏幕上有波形"验证，等于只做了第 ① 条。

## M6 · 万用表读到的"平均值"被当成直流电平

**触发条件**
用万用表（直流档）去测一个**正在翻转**的信号。

**现象**
读到 1.5V ~ 1.7V 这样的"中间值"，容易被当成故障。

**根因**
万用表直流档读的是**时间平均值**。一个 3.3V、占空比 50% 的方波，
读出来就是 **1.65V** —— 这不是故障，是信号在正常翻转。

**排查步骤**
1. 先判断"这个值是不是恰好接近 Vcc/2" —— 是则高度怀疑在翻转
2. 想确认是否翻转，**用 PL 计数器**（能精确计数边沿），不要用万用表
3. 或换用示波器/逻辑分析仪

**修复**
把"万用表只能测静态量"作为使用前提；**动态特性一律用能计数/采样的手段测**。

**适用 / 失效条件**
- 适用：任何用平均型仪表测动态信号
- 失效：—

**来源**
本队真实踩坑：分析相机 PCLK 时，万用表读到"半高"一度被误读为异常电平，
实际是**信号在翻转、万用表在取平均**。最终改用 PL 计数器才得到确定结论。

## M7 · 写了自检，却从没验证过自检本身

**触发条件**
按纪律给测量工具加了"已知答案自检"，然后**完全信任它给出的判定**。

**现象**
自检报 `FAIL`，于是把整批数据判为不可信 —— **而数据其实是好的**。

**根因**
自检的**比较逻辑**本身有 bug，与数据无关。真实例子：

XSCT 的 `mrd -value` 返回的是**十进制**数值，不是十六进制字符串。
脚本却拿它和十六进制字符串比较：
```tcl
set magic [mrd -value 0x310000FC]
if {$magic eq "0x600D0001"} { puts "PASS" } else { puts "FAIL" }
```
读回 `1611464705` —— 这**就是** `0x600D0001`，完全正确；
但与字符串 `"0x600D0001"` 比较**永远不相等** → 自检报 FAIL。

**排查步骤**
1. 自检报 FAIL 时，**先怀疑自检，再怀疑数据**
2. 把**期望值同时用十进制和十六进制打出来**，一眼就能看出是不是同一个数
3. 比较一律走**数值比较**，不要比较字符串：
   ```tcl
   if {$magic == 0x600D0001} { ... }
   ```

**修复**
- 自检输出里**同时打印十进制与十六进制**
- **自检本身也要先用已知答案验证一遍**：故意喂一个错值，
  确认它真的会报 FAIL（否则你不知道它有没有判定能力）

**适用 / 失效条件**
- 适用：任何"先验证工具、再信任数据"的流程
- 失效：—

**来源**
本队真实踩坑。这条的反讽在于：**写自检本是为了防"信了假数据"，
结果自检自己成了假警报**，一度把好数据判成不可信。
纪律里那句"先用已知答案验证测量工具"，**必须同样施加于自检本身**。

## M8 · 统计量早已溢出，却被当成有效数据

**触发条件**
用**定宽整数**累加一个高频计数器的差值，累加很多帧之后再整除求平均。

**现象**
算出来的"每帧耗时"忽大忽小、量级离谱，**每次读都不一样**。
同一份代码、不同时刻读到的三组值：

```
读到 frames=6   时：每帧 1901 ms
读到 frames=8   时：每帧  290 ms
读到 frames=353 时：每帧  2.90 ms
```

**同一套代码不可能差 650 倍。** 而我先后据此得出了三个互相矛盾的结论。

**根因**
```c
u32 acc_samp = 0;                 /* u32 */
acc_samp += (u32)(tB - tA);       /* 每次加约 3.3e8，即 1 秒的量级 */
```
tick 频率 333.333 MHz → **u32 每 12.88 秒绕回一次**。
一旦总时长超过它，读到的"总数"就是**绕圈后的余数**；再用它除以帧数，
得到的"每帧"纯属垃圾。

**只有第一次（总时长 11.4 秒 < 12.88 秒）恰好落在范围内**，后面全错。

**排查步骤**
1. 先算**溢出周期**：`2^32 / 计数频率`。333.333 MHz → **12.88 秒**
2. 把**预期总时长**和溢出周期比一下：超过就必然已经绕过
3. **自洽性检验**：拿一个独立的量去对（例如 帧数 × 目标帧时间），
   对不上就先怀疑统计量本身，而不是先怀疑被测系统
4. 最稳的做法：**不累加总量，直接存每帧的值**

**修复**
```c
u64 acc_samp = 0;                            /* 换 64 位 */
...
sn[21] = (u32)(acc_samp / frames);            /* 存"每帧"而不是"总量" */
```
**存每帧值比存总量更好**：总量天然会溢出、而且会掩盖帧间差异；
每帧值既不会溢出，又能直接看出异常。

**适用 / 失效条件**
- 适用：任何定宽整数累加器（C 的 `u32`、嵌入式定时器、统计计数器）
- 失效：用 64 位/浮点累加、或定期清零的场合

**来源**
本队真实踩坑。**这条最值得记的地方是它的隐蔽性** ——
溢出后的数字仍然"看起来像一个正常的毫秒数"，不报错、不越界。
是 **1901 / 290 / 2.90** 这三个互相矛盾的值暴露了它。

## M9 · "信号恒为 0" —— 先确认你真的在驱动它

**触发条件**
测量一条"源 → 导线 → 目的地"的通路，发现目的地读数没有变化。

**现象**
目的地读到恒定电平（本例恒 0），于是判断**导线断了 / 接头没插**。

**根因**
**源端根本没有被驱动。**

真实情况：应用里驱动该引脚的发生器，**只在某一种工作模式下被调用**：
```c
if (g_mode == MODE_UART) { gen_send_one(); }   /* 只有 UART 模式才驱动引脚 */
```
而当时设备处于另一种模式 —— 这个 GPIO **从头到尾没被写过**，停在复位值 0。

于是"目的地恒 0"是**必然结果**，与导线好坏**完全无关**。
这条证据根本**不能区分"线断了"和"信号源没开"**。

**排查步骤**
1. 先确认**源端在动**：
   - 源端是寄存器/GPIO → 读回**输出寄存器**，确认它真的被写过
   - 源端是软件 → 找"生成计数器"这类证据（本例中 `generated bytes` 就起了这个作用）
2. **制造一个必然可见的变化**（强制输出恒 1 / 恒 0），确认通路会跟着变
3. 只有当**源端确定在动、目的地仍然不动**时，才有资格怀疑导线

**修复**
- 让信号源在**所有需要的模式**下都运行
- 把"源端活跃度"与"通路连通性"做成**两个独立的观测量**，
  不要用一个观测量同时回答两个问题

**适用 / 失效条件**
- 适用：任何"源 → 通路 → 目的地"的验证
- 失效：—

**来源**
本队真实踩坑。我先说出"信号没有到达采样器"，
随后发现自己**从来没让发生器在测试的那个模式下运行过**。
**这是把"我没做"误判成"它坏了"的典型。**

## M10 · 把最有诊断价值的返回值丢掉

**触发条件**
调用一个会返回状态码/超时标志的函数，然后用 `(void)` 忽略它。

**现象**
一个故障拖了很多轮，直到把那个返回值记录下来才定位。

**真实代码**
```c
(void)sample_wait();        /* 采集等待：超时返回 -1，返回值被丢掉 */
sample_read();              /* 无论成败都读缓冲区 */
```
`sample_wait()` 超时是**整个 bring-up 里最大的故障模式**，
而它的返回值被 `(void)` 扔掉了。缓冲区读回来全是 0，于是
**"采集没启动"和"输入恒为 0"看起来一模一样** ——
我因此在这两个方向之间来回摇摆了好几轮。

改成一行之后，**一次就读出了结论**：
```c
sn[51] = (u32)((sample_wait() == 0) ? 1u : 0u);   /* 1=完成 0=超时 */
```

**排查步骤**
1. 搜代码里所有 `(void)` 修饰的函数调用 —— **每一个都是一条被扔掉的线索**
2. 对"可能失败但失败后仍会继续执行"的调用，问：
   *"它失败的时候，我能看出来吗？"*
3. 把状态码写进你能读到的地方（DDR 快照 / 日志 / 可回读寄存器）

**修复**
**关键函数的返回值一律写进可观测量**，不要 `(void)`。

**适用 / 失效条件**
- 适用：任何有错误码 / 超时标志的 API
- 失效：—

**来源**
本队真实踩坑。与 M4（状态位锁死）互补：M4 是"状态位没被清"，
这条是"状态位根本没被看"。

## M11 · 诊断通道够不到目标时，不要就此放弃

**触发条件**
想直接读某个外设 / PL 寄存器，但手上的调试通道到不了那里。

**现象**
```
Memory write error at 0x41210000. Blocked address 0x41210000.
PL AXI slave ports access is not allowed.
This address has not been added to the memory map
```
XSCT 的 JTAG 内存访问走 APU 路径，**只能到 DDR / OCM / PS 寄存器，
够不到 PL 的 AXI 从设备**。于是"直接读采样器寄存器"这条路走不通。

**根因**
**调试通道有覆盖范围限制**，不是所有地址都读得到。
这一点很容易被误判成"设备坏了"或"地址写错了"。

**排查步骤**
1. **先测通道的覆盖范围**：拿一个**已知可读的地址**试。
   本例中 DDR 里的快照 `0x31000000` 读得到 → **通道本身是好的**，
   只是够不到 PL。
2. 确认目标地址属于哪个区域（PS 内部 / DDR / PL AXI），对照通道能力
3. 够不到就**换一条路**，而不是放弃诊断

**修复（本例的做法）**
**让 CPU 把要看的量写进 DDR 的固定位置，再用 JTAG 读 DDR。**
```c
sn[51] = sample_wait_result;          /* CPU 把状态写进 DDR 快照 */
sn[54] = measured_sample_period_ps;
```
这是最通用的一招：**CPU 能看到的任何东西，都可以搬到 DDR 里让你看到。**

**适用 / 失效条件**
- 适用：所有调试探测（JTAG / 串口 / SWD）都有覆盖范围问题
- 失效：—

**来源**
本队真实踩坑。最初的结论是"这条路走不通"，
后来的结论是"这条路走不通，但可以绕"。

## M12 · 唯一的证据，放在会被后来数据覆盖的地方

**触发条件**
用一块**共享的、滚动的**输出缓冲（滚动文本、环形日志、"显示最后 N 条"）
去记录一个**只在某种模式下才产生**的结论。

**现象**
验证的当下是好的；**等你回过头去看，那个证据已经不在了** ——
缓冲里已经是别的内容，而且没有任何地方提示"这里曾经有别的东西"。

**真实情况**
协议解码结果放在一个**所有模式共用**的滚动文本缓冲里，只保留最后 78 个字符。
SPI 模式解出的十六进制，**在切到 UART 模式后被 UART 的文本立刻冲掉**。
留下的只有 `sn56=8`（SCK 上升沿数）、`sn57=364`（CS 低电平采样数）这类计数 ——
**"解出来的到底是什么"没有留下**。

**根因**
**证据的生命周期 < 结论的生命周期。**
"赶在它被覆盖之前读出来"不是解决方案 —— 那只是把测量变成一场赛跑，
而且**下一次也不一定跑得赢**。

**排查步骤**
1. 问一句：*"这个证据，在我需要它的时候还在吗？"*
2. 如果它和别的数据共用缓冲、或被后续数据覆盖 → **换一个独占的位置**
3. 尽量存**可判定的数值/短序列**，而不是长文本 ——
   数值好比对、好存档、不会被格式化或截断

**修复**
给关键结论分配**不会被覆盖**的独立存储：
```c
static u8  g_spi_seq[4];     /* 前 4 个解码出的字节，独立槽位 */
static u32 g_spi_nbytes;     /* 累计解码字节数               */
...
sn[58] = 小端打包的 4 字节;
sn[59] = 总字节数;
```
改完之后，无论之后切到哪个模式，**结果都还在**，而且能直接和已知答案比对：
`0x53555254` == `'TRUS'` ✓

**适用 / 失效条件**
- 适用：任何用共享/滚动缓冲做观测的场合（串口日志、环形缓冲、屏幕显示）
- 失效：写入即持久化的存储（文件、独立寄存器）

**来源**
本队真实踩坑。**"我当时看到了"不是证据，"你现在还能看到"才是。**
这一条和 M1（残留数据）是一对：
M1 是**旧数据伪装成新数据**，M12 是**新证据被旧机制吃掉**。

## M13 · 自测数据不可能证伪"只在自己数据上成立的假设"

**触发条件**
用一个**自己构造、且从项目一开始就存在**的测试向量，
反复验证一个解码器 / 解析器 / 协议栈。

**现象**
**每一次测试都通过**，功能看起来完全正常 —— 直到喂进一个
**不是自己挑的**输入，它立刻解错。

**真实情况**
UART 解码器用「**最短游程 = 1 个比特周期**」来估计波特率。
内建演示串是 `"TRUSTSCOPE "` —— **每一个字符恰好都含有孤立的一位**，
于是这条假设**永远成立**，测试永远通过。

换成由电脑那头发来的任意 payload，例如 `PC-0000-9999-0A0B-1614`：
里面有一堆 `'0'`（0x30），它 LSB-先发的位序是

```
0(起始) 0000 11 00 1(停止) + 空闲高
        └─5位低─┘└2┘└2┘   └──停止位和空闲高合并──┘
```

**所有游程都 ≥ 2 位** → 假设立刻崩塌 → 解出的字节是垃圾。
实测：期望 `0076`，得到 `..76`（后两位对，前两位错）。

**根因**
**测试向量本身就是假设的一部分。**
只要输入集合**固定**、而且是**你自己选的**，任何"在这个集合上成立"的假设
都会**看起来像定理**。

**排查步骤**
1. 问一句：*"这个测试数据是谁选的？换一个人选，还成立吗？"*
2. 找出解码/解析逻辑里**依赖输入分布**的假设
   （"一定有孤立位"、"一定有分隔符"、"长度一定是 N"、"数值一定连续"）
3. **让外部的人/进程/设备来选输入** —— 哪怕只是"另一个进程随机生成"

**修复**
- 让输入**不由被测系统选择**
  （本例：从 PC 串口把 payload 送进来，见 `vendor/send_console.ps1`）
- **持久化证据**：用**独立槽位**记录"解出来的到底是什么"，
  而不是塞进会被后续数据覆盖的滚动缓冲（见 M12）
- 修复要用**原理正确**的算法，而不是"再多试几个特例"：
  「最短游程只是**上界**，真实比特周期是它除以某个整数」
  → 逐个候选去**验证**（起始位低、停止位高），第一个通过的才是对的。
  多个整数倍的候选能通过起始位检查，但**通不过停止位检查**，
  所以这个校验天然能筛掉错的那个。

**适用 / 失效条件**
- 适用：任何解码器 / 解析器 / 协议栈 / 正则 / 词法分析
- 失效：输入空间确实封闭且有穷时，"在自己的集合上通过"就是充分的

**来源**
本队真实踩坑。**这是"自己发、自己解"的循环验证最有价值的一次证伪** ——
它暴露的不是时序问题，而是**一条从未被质疑过的算法假设**。
**这个 bug 在任何次数的自测里都不会出现。**

## M14 · 探针本身是坏的，却被用来下了结论

**触发条件**
用一个**刚写好、从没验证过**的一次性脚本去探测外部状态（网络、设备、服务、寄存器），
然后**直接拿结果下结论**。

**现象**
"**目标是坏的**" —— 而真正坏的是**你的探针**。

**真实情况**
用一行 `Invoke-WebRequest` 探测一个竞赛官网，失败：
```
https://<site>/  ->  FAILED: 基础连接已经关闭
```
**据此向用户报告"这个网站的 HTTPS 是坏的"。**

随后按纪律补做验证，同一个探针去测两个不可能挂的站点：
```
https://www.baidu.com/      ->  FAILED: 基础连接已经关闭
https://www.aliyun.com/     ->  FAILED: 基础连接已经关闭
SslStream www.baidu.com:443 ->  FAILED: No credentials are available in the security package
```
**百度、阿里也"挂"了** —— 它们不可能挂。
真因是本机 TLS 栈（Windows Schannel）有问题，
`No credentials are available in the security package` 是**客户端**的错。
**这个探针根本测不了 HTTPS：它对任何目标都返回失败。**

**根因（一般化）**
> **"探针失败"和"目标失败"是两件完全不同的事，
> 而探针的失败在输出上和目标失败一模一样。**

一个**对任何输入都返回失败**的工具，在**任何目标**上都"验证"了失败。
它不报错、不崩溃、不因目标不同而行为不同 ——
**它给出的假结论和真结论长得完全一样。**

**排查步骤**
1. **先用一个你已知答案的输入跑一遍探针**
   - 测网站 → 先测一个肯定正常的网站
   - 读寄存器 → 先读一个已知为真的值（版本号、刚写进去的值）
   - 读内存 → 先读刚写进去的内容
   - 测频率 → 先测一个频率已知的信号
2. **健康的期望值必须被明确写下来**（"应返回 200"、"应为 0x600D0001"），
   而不是"看它有没有报错"
3. **探针在健康输入上失败 → 该探针的全部结论当场作废**，
   并**明确宣告作废**（不要悄悄改口）

**修复**
把"先用已知答案验证"做成**函数**，而不是靠自觉：
```powershell
Test-ToolWithKnownAnswer -Name 'https probe' `
    -Probe     { ...探测目标... } `
    -IsHealthy { param($r) $r -eq 200 }
# Verdict = TRUSTWORTHY  或  *** DO NOT TRUST THIS PROBE ***
```
见 `templates/ps_lib.ps1`。**看到 `TRUSTWORTHY` 才允许把结果写进结论。**

**适用 / 失效条件**
- 适用：**所有**探测手段（网络、寄存器、内存、传感器、日志解析）
- 失效：目标本身不确定、找不到"已知答案"时 → 改用**两个独立手段交叉验证**

**来源**
本队真实踩坑。**这是配套操作纪律（`measurement-discipline`）里的第 1 条**：
「先用已知答案验证测量工具，再用它的数据」。
而**我在同一个会话里又违反了一次**。

**所以结论不是"要更小心"，而是：**
> **"知道这条纪律"不等于"会执行它"。**
> 唯一有效的办法是**把它变成代码里一个绕不过去的必经步骤** ——
> 于是它成了 `Test-ToolWithKnownAnswer` 这个函数。

## M15 · 读了滚动窗口的**错误一端**，把一秒前的文本当成实时状态

**现象（2026-09-18，板载协议分析仪）**
读数打印 `decoded text = 'RUSTSCOPE TR'`，而线上发的是 `TRUSTSCOPE ` 循环。
据此我判定"UART 解码器坏了"，并准备改解码算法。

**真相**
`sn[26..28]` 读的是 `g_dec_text[0..11]` ——
那是**滚动 78 字符窗口里最老的 12 个**，也就是**大约一秒前**的文本。
字符本身一个都没错：

- `a.txt` 的 9 个 run = `51, 84, 41, 84, 41, 42, 42, 41, 374`
  → 按电平还原就是 `0x52` = `'R'`，**解码完全正确**
- `RUSTSCOPE TR` 只是"开机第一帧的 'T' 没解出来"这个**丢字**造成的相位偏移
- `PE TRUSTCOPE` 同理：每个字符都对，中间**恰好丢了一帧**（后面接的正是空格）

**为什么会误判**
"改错的字符"和"漏掉的字符"在滚动窗口里**长得一模一样**。
要区分它们，必须有一个**与窗口无关的计数器**：
丢帧会让其它字符全部保持正确，解码错误则会污染若干字符。

**修复（三件事，缺一不可）**
1. 读数改读**尾部**（`SNAP+0x200`：最新 16 字符），并明确标注 `sn26..28` 为 **STALE**
2. 新增 `g_dec_miss`：**源在发、但本帧一个字符都没解出来**的帧数 —— 这才是决定性的数
3. 新增 `g_dec_total`：开机以来解出的字符总数（单调递增，不会被窗口滚掉）

**适用 / 失效条件**
- 适用：**任何**"滚动缓冲区 + 从固定下标读数"的组合（日志尾部、环形队列、屏幕最后一行）
- 失效：缓冲区长度 = 数据总量时（永不滚动），此时头尾等价

**同一动作的第三次出现**：M1（残留波形）、M12（证据被覆盖）、M15（读错一端）。
三次都是**把"缓冲区里的某个位置"当成了"当前状态"**。

## M16 · 分项之和对不上总数 —— 这是识别"残留数据"的唯一线索

**现象**
`a.txt` 打印出 11 个 run：`51, 84, 41, 84, 41, 42, 42, 41, 374, 41, 374`。

**关键一步（当时没有立刻做，做完立刻破案）**
把它们**加起来**：`51+84+41+84+41+42+42+41+374 = 800` —— **恰好等于窗口长度**。
于是后两个 `41, 374` 必然是**上一帧的残留**（`g_dbg_runlen[16]` 是 static，从不清零），
而"run count = 8"（8 次跳变 = 9 段）正好印证。

**规律（可推广）**
> **如果分项之和恰好等于总数，剩下的分项就不是本次的数据。**
> 如果不等于，那就说明你**漏读了**或**多读了**。

**为什么这条值得单独记**
它不需要额外仪器、不需要再上机、不依赖任何假设 ——
**纯算术**，却能把"看起来 11 个 run"直接砍成"实际 9 个"。

**适用 / 失效条件**
- 适用：任何**分区/分段/分通道**的统计输出（run-length、区间计数、DMA 分段、时间片累计）
- 失效：分项本身允许重叠或重复计数时（例如"进入次数"而非"覆盖长度"）

## M17 · 一次改两处，等于没做实验

**现象**
离线 harness 里我发现解码器两处可改（周期估计、采样点稳定性），
**一起改完**再测：D1 错误 8→304，抖动错误 36→127，**全面变差**，
而且**不知道是哪一处造成的**。

**修复**
把两个改动拆成可独立开关的变体，**逐个单独测**：

| 变体 | D1（256 字节 × 4 相位） | 5% 抖动 |
|---|---|---|
| 原始 | 8 / 1024 | 36 / 400 |
| 只加稳定性 | 3 / 1024 | 71 / 400 |
| 两者都加（第一版） | 304 / 1024 | 127 / 400 |
| 周期估计（含 runs[0]）单独 | 见下 | 见下 |

拆开后立刻定位：**是"包含 runs[0]"那一条把周期估小了**
（窗口开头被裁掉的空闲只有 22 个采样，被当成了 1 bit）。
另一条（稳定性）本身是轻微有益的。

**最终采纳的第三条路**：不做硬性稳定性约束，而是
**在多个能通过校验的候选里，挑"采样点离边沿最远"的那个** ——
D1 变成 0/1024，抖动在实测 ±2.4% 下无退化。

**规律**
> **一次只改一处，且必须在同一批输入上对比。**
> 两处一起改，得到的不是"更好的版本"，而是"另一个版本"。

**适用 / 失效条件**
- 适用：参数调优、算法替换、修复叠加
- 失效：两处改动**在物理上不可分离**时（例如同一段协议解析的收发两端）→
  此时必须**记录为"联合改动"**，并明确说明无法归因

## M18 · 自校准帧被当成协议帧喂进解码器，产出"幽灵字符"

**现象（2026-09-24，板载协议分析仪，UART 模式）**
读数：`newest 16 chars = 'RUS..TSCOPE TRUS'` —— 16 个字符里 **14 个正确、2 个是 `.`**。
按循环串 `TRUSTSCOPE ` 对齐，那两个 `.` 正好该是 `TS`。
第一反应是"解码器偶尔解错一个字符"或"线上有抖动"。

**真相：那两个 `.` 不是解错，是那两帧根本没有在发 UART。**

代码里有自校准逻辑：
```c
g_cal_frame = (g_src_on && ((g_mode == MODE_LOGIC) || ((g_frames % 32u) == 0u)));
if (g_cal_frame) { gen_square(); }   /* 每 32 帧发一次方波，不发协议字节 */
```
**每 32 帧里有一帧跑的是 CPU 定时方波**，却被送进了 UART 解码器 → 解出 2 个假字符。

**怎么确认的（关键：不是推理，是留证）**
单帧的原始采样 12 ms 后就被覆盖，所以**先加了一个"坏帧记录器"**：
凡是"源在发、但窗口没有解出恰好 1 个可打印字符"的帧，把那一帧的 800 个采样单独保存。
下一次读数就拿到了决定性数据：

```
bad frame count = 136                  (总帧数 4886 → 1/36 ≈ 1/32 ✓)
bad frame runs  = 166 112 111 111 112 111 77    (和 = 800)
bit period      = 19 samples
```
- `111/112 采样 × 220 ns ≈ 24.5 µs` = **方波的半周期**（`GEN_TICK_HZ/41667`），不是 UART 的 8.68 µs
- 136/4886 ≈ **1/32**，与代码里的 `% 32` 完全吻合
- 78 个字符的滚动窗口里按比例正好出现 **2** 个假字符 ←—— 与现象一一对应

**修复**
```c
if (g_cal_frame) { n = 0u; }          /* 校准帧不进协议解码器 */
else if (g_mode == MODE_UART) { ... }
```
修复后连续 3 次读数：`' TRUSTSCOPE TRUS'` / `'USTSCOPE TRUSTSC'` / `'STSCOPE TRUSTSO'`，
**零个 `.`，零缺帧**。

**规律**
> **仪器自己造激励的时候，必须把"激励帧"排除在被测通道之外。**
> 自己发的方波被自己的解码器解成字符，是自证式污染：看起来像"偶发错字"，
> 实际是"有一类帧本来就不该被解"。

**适用 / 失效条件**
- 适用：任何"自带信号源 + 自带解码器"的自检仪器（波形发生器、协议分析仪、回环测试）
- 失效：激励与被测物理上分离、或解码器只在监听模式工作时

## M19 · 两份分析结果不一致时，先证明它们是不是**同一帧**

**现象**
同一个 800 采样窗口，两份独立实现算出的游程不同：

| 实现 | run 列表 |
|---|---|
| 板上 C（`analyze_ch0`） | `51, 42, 83, 84, 41, 42, 42, 41, 374` |
| Tcl 脚本（独立实现） | `51, 125, 42, 42, 41, 42, 42, 41, 374` |

两者**之和都等于 800**（与窗口长度一致），首段和尾段还相同 ——

## M20 · 把只读的**输入端**当成可写的数据槽

**现象（自己引入的 bug，2026-09-24）**
为了多暴露一个计数器，我把 `g_dec_total` 写进了 `sn[62]`：

```c

g_ctl    = sn[62];                              /* 每帧读入控制字 */
g_src_on = (g_ctl & CTL_SRC_ON) ? 1u : 0u;      /* bit0: 打开内部源 */
```

> 把只读的输入端当数据槽，等于让数据去当控制命令 —— 而且症状会出现在**别处**。

**适用 / 失效条件**
- 适用：内存映射的寄存器 / 快照区 / 共享 mailbox / 任何 off-chip 调试通道

## M21 · 测试图案**对目标缺陷免疫** —— 六次"通过"，画面却一直是坏的（**最贵的一条**）

**触发条件**

**现象（真实经过）**
为了排查"颜色怪"，连续换用了六种判据，**六种全部通过**：

| 用过的判据 | 为什么对"位排列"免疫 |
|---|---|
| 纯色（byte=0xFF / 0x00） | 全置位/全清零，任何逐位排列下都不变 |
| 纯灰阶（R=G=B） | 三个通道受同样变换，仍然是灰 |

**根因**
判据选的不是"能暴露目标缺陷"的那一类。
**免疫的判据给出的结论是"通过"，不是"正确"。**

**排查 / 修复**

> **"如果缺陷正是我怀疑的那个，这个图案看得出来吗？"**

验"数值通路"要用**数值本身对变换敏感**的图案：
单价置 1（0x01,0x02,0x04,...0x80）、单个位翻转、互补值、递增序列。

**规律**
> **"测试通过"只说明"该测试看得见的东西没问题"。**
> 判据的**分辨能力必须单独论证**；一个恒真的判据毫无价值。

**适用 / 失效条件**
- 适用：任何"用测试图案验证数据通路"的场合
- 失效：无（只要判据对目标缺陷免疫，它就一定会骗你）

## M21b · 测试红了，先分清是"代码错"还是"期望错" —— 别调到绿为止

**现象（2026-09-24，int8 量化契约测试）**
写了 6 个边界用例测重量化公式 `(acc*M + (1<<(sh-1))) >> sh + z`，
结果 **3 个红了**。第一反应是"公式写错了"。

**手算之后：3 个全是我的期望值错，代码一直是对的。**

| 用例 | 我写的期望 | 实际 | 我错在哪 |
|---|---|---|---|
| `acc=4, M=1, sh=1, z=0` | 2 | 2 | 对（但用了 z=0，负值全被 clip，测不到舍入） |
| `acc=3, M=1, sh=1, z=0` | 1 | **2** | 真实值 1.5，半数进位应为 2 |
| `acc=-3, z=0` | -2 | **0** | 输出是 uint8，负值被 clip —— 这条根本没在测舍入 |
| `acc=4, M=1, sh=1, z=128` | 2 | **130** | 忘了加零点 |
| `acc=-1, z=128` | 127 | **128** | 公式是 `floor(x+0.5)`（向 +∞ 半数进位），`floor(-0.5+0.5)=0` |

**根因（两处，都是我）**
1. **z=0 时测不到舍入**：负的半值全被 clip 成 0，测试红得"有道理"但红在错的地方
2. **没有手算**：期望值是"看着顺眼"填的，而不是算出来的

**规律**
> **一个红的测试有两个可能的错误来源：被测代码，和测试自己。**
> 分不清时**手算一遍**，不要"改期望直到变绿" ——
> 那是把测试变成橡皮图章，从此它只会说"通过"。

**可操作的做法**
- 每个期望值旁边写上**怎么算出来的**（`floor(-0.5+0.5)=0`），而不是只写数字
- 边界测试要**先确认这个输入真的能刺激到被测行为**（z=0 就刺激不到舍入）
- 修完再问一句：**这个测试失败了会是什么信号？** 答不上来就是没测到东西

**适用 / 失效条件**
- 适用：所有单元测试/契约测试/回归测试，尤其涉及定标、舍入、饱和、边界
- 失效：期望值来自**外部权威规范**时（那就以规范为准，测试红意味着实现错）

## M23b · 中位数统计量在量化数据上会塌成 0

**症状**：一个"仪器漂移自查"过程，**阳性对照失败** ——
同一件工件、什么都没动，它却 5/5 报警说仪器漂了。

**真因**：地板用的是 `median(|该帧 − 参考图|)`。而

- 图是**整数灰阶**
- 参考图是若干帧的**中位数**（也是整数）

像素值聚集时，**约一半的（像素, 帧）对恰好等于中位数**，`|偏差| = 0`。
实测 **46.27% 的像素偏差为 0** → `median(|偏差|) = 0.000`。
阈值随之变成 `3 × max(0, 0.5) = 1.5`，**任何微小变化都报警**。

**修法**：地板与判据**都改用均值**（实测 2.189 灰阶），并确保**两者用同一个统计量**，
否则不可比。

**一般教训**：
> **中位数对"大量相等值"是不敏感的** —— 而量化数据天生充满相等值。
> 在量化/离散数据上做"噪声尺度估计"时，**均值或高阶分位数比中位数可靠**。
> 中位数的抗离群优势，在这种场景下变成了"塌成 0"的缺陷。

**这是阳性对照抓出来的**（同一件没动却报警 = 判据坏了）。

## M24 · 用**单次采样**判身份：有误码的通道既会误报"无效"也会误报"有值"

**触发条件**
用"读一个已知寄存器（型号 ID / 版本号）"判断通信通道是否可信，但**只读一次**。

**现象（两种相反的错法）**
- 单次读到 `-1`（偶发误码）→ 脚本判定"读通道不可信，整轮数据作废"，**白跑一轮**
- 单次读到错值 → 当成真值写进结论

**根因**
I2C/SPI/JTAG 的读有**低频偶发误码**（本例 0x300B、0x350A、0x350B 都出现过）。
单次采样把"误码率"直接当成了"可信度"。

**排查 / 修复**
- 身份校验用**重试 + 投票**：连读 5–10 次，**任一次**命中已知答案即判定通道可用
- 数值寄存器用**中位数**（连读 7–9 次取中位），并**把原始样本一起写进日志**
  （本例改中位数后立刻稳定：7/7、9/9 完全一致）
- 报告时**标出被丢弃的野值**，不要让它们凭空消失

**规律**
> **"读一次"是采样，"读多次"才是测量。** 有误码的通道必须用统计量。

**适用 / 失效条件**
- 适用：任何可能偶发误码的通信通道（I2C / SPI / JTAG / 串口）
- 失效：有硬件 CRC 保证无错的通道（但重试成本依然极低）

## M24b · 阴性对照救了一个**正确**的函数

**症状**：给"相位相关配准"写自检，断言是
「`phase_shift(ref, cur)` 的返回值应当等于施加的平移」。**五组全红。**

**当时的第一反应**是去修函数。但先停下来想清楚语义：

```
cur = roll(ref, (p, q))            ;# 施加 (p,q) 得到 cur
要让 cur 对齐回 ref，需要施加的是 (-p, -q)
而函数返回的正是 (-p, -q)           ;# 它是对的
```

**错的是我的断言，不是函数。** 如果当时去"修函数"，
**会把一个正确的实现改成错的**，而且之后所有配准都会更糟。

**改法**：把断言换成**功能性检验** ——
不问"返回值等于什么"，而问"**拿它返回的平移去移，能不能真的对齐回去**"：

```python
gy, gx, _ = phase_shift(ref, cur)
back, valid = apply_shift(cur, gy, gx)
assert median(|back[valid] - ref[valid]|) < 0.5
```

修完五组全绿（对齐后中位残差 0.000）。

**一般教训**：
> **自检要验"用途"，不要验"约定"。**
> 验约定的断言，会在实现正确时失败、在实现错误时也可能碰巧通过。
> 验用途的断言（"拿你的输出去做你想做的事，能成吗"）才是真的在测它有没有用。

**代价**：约十分钟。**但它避免的是一次"把对的改成错的"** —— 那种错很难再被发现，
因为改完之后自检会变绿（断言与实现一起错了）。

## M25b · 没有对照组的"对比测试"不成立 —— "两帧相同"可能只是两次失败的读

**事故经过**
判断"第二路相机有没有数据"时，我 dump 了两块内存、间隔 1.5 秒、比较内容，
得到"两帧相同"，于是下结论：**第二路没有数据**。

**那个结论当时是不可信的。** 因为：
* 那次 dump 用的是 `targets -set 2`，而第 2 号目标（CPU 核）当时是 **Running**，
  在运行中的核上 `mrd` 会失败；
* **读失败返回 `0xFFFFFFFF`**；
* 两次都失败 -> 两次都得到同样的 `0xFFFFFFFF` -> **"相同"**。

我拿一个"两次失败"当成了"内容没变"。

**修正后的做法（这次带对照组）**
```tcl
# 0) 先用**已知答案**证明读通路有效
set sr0 [RM 0x43000034]        ;# 应当等于已知好值 0x00015810
if {$sr0 != 0x00015810} { error "读通路无效，后面数据不可信" }

# 1) 同时采"已知在变的"和"待判定的"
#    相机0 帧存 0x10000000（对照） / 相机1 帧存 0x11200000（待判）
# 2) 先看对照组
if {对照组的字没有变化} { error "测量方法本身坏了，不能下任何结论" }
```
实测结果：
```
读通路自检 = 有效
相机0 帧存: 24/32 个字不同   <- 对照组成立
相机1 帧存:  0/32 个字不同
=> 结论成立：第二路确实没有数据
```

**教训**
* **任何"A 和 B 不同/相同"的结论，都必须先有一个"已知应该不同"的对照组通过。**
  否则你测的是"你的方法有没有在工作"，而不是"被测量的对象"。
* **"两次都失败"在数值上表现为"两次都相同"。** 判据里必须包含
  **"这次读到的是不是一个有效值"**，而不只是"两次是否一致"。
* 交付话术：说"X 没有变化"之前，先说出**你凭什么相信这次读到了 X**。

## M26 · 靠人的**定性描述**（"深灰/浅灰"）去反推**定量**映射

**触发条件**
需要"写入值 → 实际显示值"的映射，于是让人看屏口述"这块深、那块浅"。

**现象**
描述自洽、也符合直觉，但**无法唯一反推**：
同样的描述同时匹配上千种排列（本例暴力搜索出 **1680 种**一致解），推不出结论。

**根因**
人的描述丢掉的正是**数值**。而数值映射的辨识恰恰需要数值：
"深/浅"只给**序关系**，不给**比例**；再叠上噪声、削顶与环境光，序关系本身也不可靠。

**排查 / 修复**
- 让操作者**拍照**，由程序**定量测光**（大面积均匀色块取均值，摩尔纹与 JPEG 会被平均掉）
- 更彻底：**让被测系统自己测自己**（用板载相机/回路把结果读回）
- 只有"对看到的东西做**二元判断**"（"有没有颜色"）才适合靠人

**规律**
> **人适合"二元判断"和"发现异常"，不适合"定量测量"。**
> 需要数值，就去造一条能出数值的通道。

**适用 / 失效条件**
- 适用：任何需要"数值 → 数值"映射的辨识问题
- 失效：只需二值/序关系的场景（此时人的判断确实够用）

## M27 · 自己写的读例程**根本没发读相位**，所有读回都是 −1

**触发条件**
手写一段"透过 EMIO/桥读外部器件寄存器"的例程（而不是用现成驱动）。

**现象**
**每一个**寄存器都读回 `-1`（包括型号 ID 这种必然有值的寄存器）。
第一反应是"器件不支持这个读"或"这个寄存器是只读/保留的"。

**根因**
例程只做了"写寄存器指针"那一半，**没有发读相位**：
少了读位（RW）、少了传输字节数寄存器、也没有产生 Repeated-START。
所以总线上根本没有发生过一次读。

**排查 / 修复**
- **先读一个"已知答案"的寄存器**（型号 ID / 版本号），
  它读不出来，就说明**是你的读例程坏了，不是器件**。
- 修复：照抄一份**已被验证过**的读例程（本项目里 `final_all2.tcl` 的 `i2c_rx` 是好的），
  不要凭记忆重写时序。

**规律**
> **"全部读回 −1" 是"通道坏了"的指纹，不是"器件不支持"的指纹。**
> 出现"全部一致地失败"时，先怀疑**自己这一侧**。

**适用 / 失效条件**
- 适用：所有手写的总线时序（I2C / SPI / 自定义并口）
- 失效：用厂商驱动且驱动本身有自检

## M28 · 把"这块内存有多大、在哪"当成**文档事实**，而不是**量出来**的事实

**触发条件**
在任何内存区间里放代码/数据/栈 —— 尤其是那些"众所周知"的区域
（SoC 的 OCM、片上 RAM、保留区）。

**现象**
程序**一条自己的指令都没执行**就死了。
本例：PS 裸机程序把栈放在 `0x0003F000..0x0003FFFF`，而
`main_loop` 的第一条指令 `push {r4-r9,sl,fp,lr}` 要把 SP 压到 `0x0003FFDC` ——
立刻同步外部中止。表现出的现象只是"帧计数器不动"，看不出跟链接脚本有关。

**根因**
链接脚本按"Zynq-7000 的 OCM 是 256 KB，即 `0x00000000..0x0003FFFF`"来划分。
实测：**可用只有 192 KB（`0x00000000..0x0002FFFF`）**，
`0x00030000..0x0003FFFF` 读回 `0xFFFFFFFF`（根本没译码）。
另外 `0xFFFF0000..0xFFFFFFFF` 还有独立的 64 KB。
总数还是 256 KB，只是**不在文档暗示的位置**。

**排查 / 修复**
- **写一个"写进去再读回来"的扫描脚本**，把可疑区间逐点验一遍 —— 见
  `ps_fft_dual/ps_ocm.tcl`。判据是"**值有没有存住**"，不是"有没有报错"：
  总线译码错误经常既不报错、也不置任何你正在看的标志位。
- 找**边界**，不要只测两端：本例 `0x0002FFF0` 正常、`0x00030000` 就没了，
  一次测量就把可用范围钉死了。
- 顺手验一下**别名**是否真的是别名：写在 `0x00008000` 的东西**没有**出现在
  `0xFFFF8000`，于是知道那不是镜像而是两块独立内存（见 `ps_ocm2.tcl`）。
- 修完把**实测边界**写进链接脚本的注释里，并写明"如果改回去这个故障就回来"。

**规律**
> **"内存有多大"是硬件事实，必须量；文档写的是型号的典型值，不是你这块板子的实测值。**
> 而且**"没有译码"通常读回全 1、不报错、不置标志** —— 它长得就像"读到一堆 FF"，
> 很容易被当成别的问题（比如"PL 空了"）。

**适用 / 失效条件**
- 适用：任何"往某个地址区间放东西"的场合（链接脚本、堆栈、DMA 缓冲、保留区）
- 失效：区间由能自检的分配器管理，且分配失败会明确报错

## M29 · 把故障归因给一个"看起来很合理"的机制，却**没有验证该机制确实成立**

**触发条件**
拿到一个可信的故障码，但**故障现场**（出错指令、出错地址）取不到或取到了乱码。

**现象**
本例：故障处理器写下了 `faultcode`，但 `DFSR/DFAR/PC` 读回来是乱码
（`0xCF7EA688` / `0x6EB16FA7` / `0x8593BD92`）。
当时的解释是"**Abort 模式有独立 SP，我从没初始化它，所以处理器自己又挂了**" ——
听起来非常合理，而且确实是个真问题，于是照着这个方向去改了。

**根因**
两个独立的错误被**同一个现象**串在一起，于是谁都没被单独验证：
1. "Abort 模式栈未初始化"**是真的**（修了，也**应该**修），
   但**反汇编证明那个处理器完全不用栈**（没有一条 push/pop，全是固定地址存取）。
   所以它**不能**解释乱码。
2. 乱码的真实原因是：**板子上跑的是过期的手工 `.bin`**，
   那个旧版的处理器写的是别的偏移 —— 我读的地址和它写的地址根本不是一回事。
   换句话说：**我读的"现场"和产生故障的代码不是同一份东西。**

**排查 / 修复**
- 归因要**可证伪**："如果真是这个原因，那么反汇编里应该看到栈操作" —— 去看，结果是没有。
- **先验证"我看到的就是当前代码"**，再解释任何现场数据（本例就是上面那条 T19）。
- 拿不到现场时，**换一条不依赖现场的通道**：本例加了一个"进度信标"
  （每完成一帧的某个阶段就往一个固定地址写一个阶段号），
  一个词就说出"死在相机那一句"，完全不需要解释 DFSR/DFAR。
- **分阶段打点**比事后解读寄存器便宜得多，也可靠得多。

**规律**
> **"这个原因说得通"不等于"这个原因就是它"。** 修了一个真 bug，
> 不等于修了**你正在查的那个** bug；两个真 bug 叠在一起时尤其危险，
> 因为第一个修完"看起来有进展"，第二个就被掩盖了。
> 加一个**每阶段写一个数的信标**，通常比任何事后取证都便宜。

**适用 / 失效条件**
- 适用：所有"程序跑飞了、现场寄存器不可信/取不到"的调试
- 失效：能稳定复现且现场寄存器可信时，直接看现场更快

## M30 · 目视"看着没问题"，直方图里是**四色等量** —— 32 位字填进 3 字节像素

**触发条件**
往 3 字节/像素的帧缓冲里做"快速填充"，为了快用一个 `uint32_t` 反复写。

**现象**
画面**看起来完全正常**：一块深色背景，人眼只判断"是深色"。
但把这一块的颜色做统计，得到的是**四个等量颜色**（76800 像素里
16992 / 16392 / 16386 / 16318），而不是一种。

更隐蔽的是：把渲染出的 PNG 打开看，会在面板区看到一条**斜线**。
去看内存里的像素，那条斜线**根本不存在** —— 是 4 像素周期的竖条纹
在图片被缩放显示时产生的摩尔纹。**先量像素，再去"修"那条斜线。**

**根因**
```
gcd(3 字节/像素, 4 字节/字) = 1
```
写同一个 32 位字，每个字都比上一个**往像素周期里多走一个字节**，
于是同一块填充会产出**四种像素颜色，只有一种是对的**。
实测某一行：
```
x=644 1e160a   x=645 001e16   x=646 0a001e   x=647 160a00
x=648 1e160a   ...            （周期 4，只有 x%4==0 是对的）
```
**一个常量字永远不可能填出均匀颜色** —— 这不是"值没选对"，是方法本身不可能。

**排查 / 修复**
- **不要靠眼睛判断"背景是不是均匀"**，去数颜色：一个纯色区域应该只有一种颜色，
  出现"几种颜色、数量差不多"就是周期错位的指纹
- 修法：把图案做成 **12 字节（= 4 像素 = 3 个字）** 循环写。
  12 同时是 3 和 4 的倍数，所以图案可以无缝平铺。
  内层一次写 3 个字（保持速度），只有末尾 0~2 个字用取模
- **把这个判断写进检查脚本**：逐行统计"像素(x) == 像素(x+4)"且"像素(x) != 像素(x+1)"
  的比例，超过 90% 就报错。本例实测：坏的帧在面板 336/480 行、
  底栏 112/120 行命中；**修好后 0 行命中，照片区也从不误报**
- 先拿**已知坏掉的那一帧**验证检测器会报错，再拿修好的帧验证它不报
  （否则你只是加了一个恒返回"通过"的东西）

**规律**
> **人眼能可靠判断的是"二元"（亮/暗、有无），不能判断"均匀"和"定量"。**
> 凡是"看起来还行"的显示类结果，都要有一条**把它变成数字**的检查 ——
> 颜色直方图只需要几行代码，而它逮住的东西肉眼看了三轮都没看出来。

**适用 / 失效条件**
- 适用：任何"用宽于元素尺寸的字去填充/搬运"的场合
  （3 字节像素填 4 字节字、RGB888 填 RGB565、stride 与元素尺寸不整除）
- 失效：元素尺寸整除字宽（如 1/2/4 字节像素），此时常量字填充是正确的

## M31 · 一整轮都在验证**我能验证的那一端**，而不是**坏掉的那一端**

**触发条件**
一条链路上有好几段（A → B → C → D），**末端（D）由人眼判定**，而你只能量 A、B、C。
链路末端表现不对时。

**现象**
本例：LCD 面板**全黑**。而我花了一整轮去证明**帧缓冲的内容是正确的** ——
把缓冲区 dump 出来、转成 PNG、统计颜色数、检查填充图案、量像素变化率、
确认"88% 的像素在变化所以是实时画面"。**每一条都对，画面也确实是对的** ——
但面板上什么都没有。

原因是：**缓冲区正确根本不是我要证明的那件事。**
真正的问题是显示通道（VDMA MM2S）从来没有真正扫出画面。
我把"能测的那一段"反复测了很多遍，却从没测过"显示通道有没有在出拍"。

**根因（两条，都属于"看起来没问题的失败"）**
1. 显示通道的寄存器组被写错了地址（见 B13）
2. 停掉后再启动时**只写了 CR**，于是通道报告 `Halted = 0`
   ——**"没有停机"和"正在出拍"是两件事**，前者可以在完全不产出时成立

**排查 / 修复**
- **先画链路，再问"我最想证明的那一件事，在哪一段上"**。
  本例链路是 `引擎 → 缓冲 → VDMA(MM2S) → v_axi4s_vid_out → v_tc → LCD`。
  我一直在测最左边两段，而失败的候选几乎全在最右边三段。
- **通道是否在出拍，要看"完成事件"，不要看"没停机"**：
  - `SR` bit0（Halted）= 0 只说明它没停
  - `SR` bit12（IOC_Irq）**在清过一次状态之后又置起来**，才说明**真的完成了传输**
    本例修好后实测：`SR 0x00010000 → 0x00011000`（bit12 回来了）
  - 更硬的办法是数帧指针的翻转次数（见 `ps_capture.tcl`）
- **人眼能看到的只有末端**：如果末端是唯一判据，那就**先把末端恢复正常状态**，
  再用"末端变了"作为判据 —— 不要用中间段的正确去推断末端。
- **让脚本自己会因为"末端其实没在工作"而报错**：
  现在 `ps_run.tcl` 在显示器 `SR` bit0 为 1（停机）时直接打印
  `*** DIS reports HALTED`，而不是继续往下走。

**规律**
> **"我能测的都测过了，都是对的"是一个危险信号 —— 它常常意味着我在测错的那一段。**
> 在开始验证之前先问一句：**"如果故障在第 N 段，我现在的观测手段能看见吗？"**
> 看不见的那一段，就必须先造一个针对它的观测手段（本例：数帧指针翻转、看 IOC 位）。

**适用 / 失效条件**
- 适用：任何"多级链路 + 末端由人判断"的场合（视频链、通信链、控制环）
- 失效：链路只有一段，或每一段都有独立自检

## M32 · 把相邻**字节**当成相邻**像素**去平均 —— 画面"看着还行"，只是发灰

**触发条件**
为了性能，把逐字节的像素处理改成**按 32 位字**批量处理。
图像是 3 字节/像素（B,G,R），而字是 4 字节，两者的边界**不对齐**。

**现象**
画面**结构完全正确**，只是"发灰、发闷、饱和度低"。
人的第一反应是"曝光/对比度/白平衡不对"，于是去调色调曲线 —— 调了一轮，
**越调越糟**（削顶、发黑），因为**根因不在这里**。

**根因**
2×2 均值滤波写成了对**线性字节数组里相邻的两个字节**求平均：
```c
/* 错：s[c*2] 与 s[c*2+1] 是相邻字节，也就是两个不同的颜色通道 */
o[c] = (s0[c*2] + s0[c*2+1] + s1[c*2] + s1[c*2+1]) >> 2;
/* 对：输出像素 P 的通道 ch 来自源像素 2P 与 2P+1 */
o[P*3+ch] = (s0[6*P+ch] + s0[6*P+3+ch] + s1[6*P+ch] + s1[6*P+3+ch]) >> 2;
```
于是每个输出字节都是**两个通道的混合**：整幅画面被拉向"局部平均值" ——
**结构对、饱和度掉、对比度掉**。这正好就是"发灰"的样子。

**它为什么能活很久**
因为它**看起来是合理的**。"发灰"有太多合理的原因（曝光、gamma、镜头眩光、
白平衡、传感器调参），而这个 bug 产生的画面**在结构上无可挑剔** ——
没有错位、没有颜色反转、没有噪声。**肉眼无法把它和"色调需要调"区分开。**

**怎么找出来的（关键）**
停止采集，让 PS 反复渲染**同一帧**，然后同时 dump
**原始采集缓冲**和**渲染后的 UI 缓冲**，用**正确的算式**在主机上重算一遍，
**逐字节**比对：
```
  主机按正确算式算出的值 = 136
  PS 实际写进去的值       = 123     <- 不一致
```
比"看着有点灰"强得多：它直接把怀疑范围缩到"这一行算式"。
修好后同一比对变成 **691200 字节 0 处不符**。

**排查 / 修复**
1. **凡是"看着还行但有说不出的不对"，都要造一条逐字节的判据。**
   冻结输入 → dump 两端 → 主机重算 → 逐字节比。这一步不贵，而且一旦做了，
   结论是"是/不是"而不是"我觉得"。
2. **3 字节/像素 + 4 字节/字 = 必须显式写出通道索引**，不要靠 `2*c` 之类的线性步进"看起来对"。
3. **修完要重新量一次统计量**：本例修好后对比度 sd 从 **41 → 64**，
   色相 R/G 1.130、B/G 1.095（手机拍同场景 1.115 / 0.931）。
   **之前为"发灰"调出来的那条色调曲线，修完后全都不需要了** ——
   而且它会让 3.4% 的像素压黑、6.7% 过曝。**修了根因，辅助手段要跟着撤掉。**
4. 顺带：像素格式转换（565→888、BGR↔RGB、stride）都要**用已知图案验证**，
   而不是用自然图像 —— 自然图像对很多错误都"看起来没问题"。

**规律**
> **"看起来合理"是这类 bug 最好的伪装。** 它不产生任何视觉上的荒谬，
> 只让画面变差一点点，而"变差一点点"有一百个合理的原因。
> **只有逐字节的判据能把它和那些原因分开。**
> 另一半教训：**先证明根因，再去调参**。调参能在错误的根因上耗掉一整轮，
> 而且调出来的参数会把问题**掩盖得更深**。

**适用 / 失效条件**
- 适用：所有手写的像素格式转换、缩放、色彩变换
- 失效：用成熟的图像库（它们的边界处理已经被反复验证）

## M33 · 验证了"这个控制有效" ≠ 验证了"调它能改善结果"

**触发条件**
画面有一个**说得出机制**的毛病，而且你**找到了一个真的能影响它的寄存器/参数**。

**现象**
本例：画面里一有强光窗口就过曝。机制听起来很硬：
"传感器 AEC 优化的是**帧平均**，所以只要占大面积的暗部曝光合适，它就接受亮部过曝。"
于是去调 AEC 的**瞄准点** `0x3A0F/0x3A10`。

**实验做得挺像样**：先确认 I2C 能复现已知 chip ID；断言采集**在出帧**（否则 dump 是死图）；
扫了 5 个瞄准点；每个都等 3 秒收敛、读回曝光寄存器、dump 原始帧；
最后**再测一次基线**以证明场景没变。

**结果分两半，而且方向相反：**
```
  瞄准点            曝光寄存器        结论
  0x30/0x28(default) 10656 (666 行)
  0x28/0x20          10656 (666 行)
  0x20/0x18           5328 (333 行)   <- 寄存器确实被这个控制
  0x18/0x10           1776 (111 行)      （6 倍！）
  恢复默认            10656            <- 场景没变，实验有效
```
**"这个控制有效"这一半完美成立。**

但把**每个瞄准点对应的画面统计量**量出来，结论整个反过来：
```
  瞄准点     曝光    亮度均值   黑削顶    白削顶
  0x38/0x30  666      84.3      2.4%      14.1%
  0x30/0x28  666      69.2      7.5%      12.6%   <- 表默认
  0x28/0x20  666      52.6     19.2%       9.4%
  0x20/0x18  333      41.1     33.4%       8.1%
  0x18/0x10  111      33.6     50.2%       4.6%
```
**降低瞄准点确实减少过曝，代价是把 1/3 到 1/2 的画面压成黑**，
而且那个窗口**依然是过曝的** —— 因为它是**物理上超出传感器**，不是瞄准点不对。
把图调出来看，`0x20/0x18` 那张里主体几乎看不见了。

**我准备实施的"修复"会让画面明显变差。**

**根因**
两件事被混为一谈：
- **"这个寄存器影响这个量"** —— 可用读数验证，且这次验证通过了；
- **"把这个量往某个方向调就更好"** —— **只能靠结果指标验证，不能用控制量验证。**
控制量动得漂亮，恰恰掩盖了结果变坏。

**排查 / 修复**
1. **实验里必须同时记录"控制量"和"结果指标"**，而且**结论由结果指标决定**。
   本例控制量是曝光行数，结果指标是**削顶率 + 主体是否还看得见**。
2. **每个候选都要和基线在同一场景下比，并在末尾复测基线**
   （本例恢复默认后曝光回到 10656，证明场景没漂 —— 这一步让它成为有效实验）。
3. **"我以为的机制成立"不等于"我以为的改法有效"。** 本例机制（AEC 按平均优化）
   基本成立，但由它推出的改法（压低瞄准点）**错了**，因为瓶颈是**动态范围**。
   正确的结论是：**默认瞄准点已经接近最优，过曝是物理**。
4. 承认"这里没有可调的东西了"也是一个结果，而且往往是最该早一点得出的那个。

**规律**
> **一个控制量能让指标动，不代表它能让结果变好。**
> **只验证"控制生效"，等于只验证了"我有这个旋钮"，没验证"该往哪边拧"。**
> 每次调参实验都要问：**"我记录的是控制量还是结果？如果只有控制量，我其实什么都没证明。"**

**适用 / 失效条件**
- 适用：所有"找到可调参数 → 调它"的优化（AE/AWB、阈值、PLL、时序参数、编译选项）
- 失效：参数与结果之间是单调且已验证过方向的关系（那可以直接调）

## M34 · 造了一个"输出被自身定义锁死"的计数器（恒等式指标）

**触发条件**
需要一个指标来回答"我这次的改动有没有让它变好"，于是往代码里加一个计数器，
**判据直接写成了定义本身**。

**现象**
本例：加了曝光融合（长/短两档，长曝光削顶处换成 `短曝光 × 6.5`），
想量"融合之后还剩多少通道是削顶的"，于是计数 `o[c] >= CLIP`（救完之后）。
板上一跑：

```
  长曝光削顶通道        = 36738
  融合后仍然削顶通道    = 36738     <-- 一模一样，一个数字都不差
```

两个数**完全相等**。这不是"融合没效果"，这是**这个计数器不可能输出别的值**：
某通道落在 `>=248` 处，等价于"该点场景已达满量程"，于是 `6.5 × 短曝光` 必然 `> 255`，
被 clamp 回 255，**按定义一定仍然 `>= 248`**。

**根因**
判据和定义是同一个命题。这类计数器**永远给出一个"看起来像结果"的常数**，
而常数恰恰是最容易被当成"稳定的结论"接受的东西。它还会顺便掩盖真问题：
真正的答案是"这个融合在物理上不可能降低削顶"，而指标只说了"还是 36738"。

**排查 / 修复**
1. **在写计数器之前，先手算两个极端答案**，看它们会不会被同一个公式算成同一个数。
   若"有效"和"无效"两种情况代入后结果相同 → 这个指标没有分辨力，别写。
2. 把判据改成**可能为 0 的那个量**：本例从"救完仍削顶"改成
   "救完**真的低于满量程**"（`6.5 × 短曝光 <= 255`）。它才可能是 0 —— 而实测**确实是 0**
   （35 / 691200 = 0.09%），这个 0 才是有效信息。
3. **两个不同的组态跑出"完全相同的数字"（尤其到个位）时，先怀疑指标，不要先庆祝一致性。**

**规律**
> **一个输出被自己的定义锁死的仪器，什么都测不出来 —— 包括它被造出来要找的那个改善。**
> 判据必须在"有效"和"无效"两种情况下给出不同的值，否则它只是一句同义反复。

**适用 / 失效条件**
- 适用：所有"加个计数器/加个统计量来验证改动"的场合
- 失效：—

**来源**
本队真实踩坑（2026-10-03 曝光包围+融合）。同一轮里还顺手抓到一个真 bug
（长短曝光**每帧轮换**，而代码只判了一次），见 M36。

## M35 · "改善"的两个数字，量在**不同 stage**、用**不同定义**、甚至用**永远不会触发的判据**

**触发条件**
要证明"改动有效"，手上有一个**之前记录的**基线数字，于是把新数字和它一比就写结论。

**现象**
本例差点写进日志的结论：**"白削顶 12.6% → 0.4%，融合把过曝压下去 30 倍。"**

拆开看：
- **12.6%** 是**原始采集帧**上的 `min(B,G,R) >= 251`；
- **0.4%** 是**过完色调表之后**的渲染帧上**同一个**判据。

而色调表里 **B 通道增益 = 235/256**，满白 `(255,255,255)` 出来是 `(234,255,255)`，
`min = 234` —— **这个判据在渲染级上永远为假，它量的是蓝增益，不是融合。**

附带查清的第二件事更彻底：这条采集链路里 **`min(B,G,R)` 的最大值只有 248**，
所以 `min >= 251` 在**任何**原始帧上都是 `0.00%`。
也就是说那个 12.6% 连"基线"都不是 —— 它来自一个**没有存下来的脚本**，
而存档帧上最接近它的定义其实是 `green >= 248`（= 12.60%）。

**根因**
三个独立的东西被合成了一个数字：
1. **不同的 stage**（传感器原始帧 vs 过完色调表的渲染帧）；
2. **对 stage 敏感的判据**（蓝增益会把满白从 `min=255` 变成 `min=234`）；
3. **基线本身不可复现**（产生它的脚本没存，判据没记录）。
任何一条单独出现都足以让"改善"变成假象，这次三条同时凑齐了。

**排查 / 修复**
1. **报改善之前，先确认前后两次测量满足三条**：同一个 stage、同一套判据、同一批（或可比的）像素。
2. **判据必须能在被比较的两个 stage 上都"有分辨力"**。
   把定义套到同一帧的每一级上打印出来（本例脚本 `clip_stage_check.py`），
   一眼就能看出哪一级恒为 0。
3. **判据要能反查**：给一个阈值，扫一遍所有合理的判据/阈值，看哪个能复现那个历史数字
   （本例 `clip_find.py`）。**反查不出来 = 它不能当基线用。**
4. 顺带发现：`min(B,G,R) >= 251` 这种"三通道全饱和"判据在本链路上**天生为假**
   （上限 248），它能活到现在只是因为**从没人验证过它会不会触发**。

**规律**
> **"12.6% → 0.4%"这种 30 倍改善，先当成警报而不是成果。**
> 一个没记录判据、没存脚本、没写 stage 的历史数字，**不是基线，是传言。**

**适用 / 失效条件**
- 适用：任何跨版本/跨会话的"A 比 B 好"比较（削顶率、误检率、帧率、资源占用）
- 失效：比较是在同一次运行、同一段代码、同一批判据下当场产生的

**来源**
本队真实踩坑（2026-10-03）。同一轮的教训催生了
`ps_ui/clip_stage_check.py`（逐 stage 打印所有判据）与
`ps_ui/clip_find.py`（反向查找历史数字的判据）。

## M36 · 用**均值**去分辨一个"差 7%"和"差 6.5 倍"的问题

**触发条件**
要判断两个缓冲区/两帧**是不是同一档曝光**，而手边只有一个**均值**。

**现象**
本例：曝光包围把长/短两档分别写进 VDMA 的两个采集 store，需要验证"两个 store 确实各是一档"。
读回来的均值先是 **104 / 95**（差 9%），后来又读到 **30 / 32**（差 7%）——
而两档曝光的**标称比值是 6.5 倍**。

于是整个团队在"曝光到底有没有真的交替"上绕了好几轮，因为**均值同时支持两种解释**：
- "确实是两档，只是房间里大部分画面是暗的，均值被黑电平主导，6.5 倍被压缩成了几个数"；
- "根本没交替，两个 store 是同一档"。

**这两种解释在均值上看起来一样。这个均值没有分辨力。**

**根因**
暗场景里 `均值 ≈ 黑电平 + 少量亮部贡献`。
两档曝光都接近黑电平时，**6.5 倍的比例落在几个 LSB 上**，和噪声、和"没差别"无法区分。
**均值把"相差很大"压缩成了"相差 7%"。**

**排查 / 修复**
1. 换一个**两种假设下相差几个数量级**的统计量：
   本例改成数"亚采样样本中 **green >= 96** 的个数"。
   6.5 倍曝光会把一个像素从 20 抬到 130，**跨过阈值**，计数比值立刻拉开。
   实测：`BRIGHT_A = 88 / BRIGHT_B = 317`，并同时打印**它自己的决策**
   （`LONG_IS_B`），于是输入和判决都能被检查。
2. **判据的分辨力要事先算**：问"如果假设 A 成立读出来是多少，假设 B 成立读出来是多少"。
   两个答案如果只差百分之几 → 换统计量，不要靠"多测几次"。
3. 同样重要的是**把判决也打出来**：只打输入，仍然要人去猜代码怎么判的；
   本例正是靠 `LONG_IS_B` 与 `BRIGHT_A/BRIGHT_B` 的一致/矛盾，才定位到"每帧轮换"这个真 bug。

**规律**
> **均值最擅长把"相差很大"和"没有差别"变成一个样。**
> 需要一个能分辨的统计量时，问的不是"这个量是否有关系"，而是
> **"我的两种假设在这个量上分别等于多少"** —— 答案必须相隔得足够远。

**适用 / 失效条件**
- 适用：任何"判断两路数据是否相同/谁大谁小"的场合（曝光、增益、DMA 通道、时钟域）
- 失效：场景本身亮部占比很高、黑电平可忽略时，均值也是有分辨力的

**来源**
本队真实踩坑（2026-10-03）。这条与 M33 是同一类：
**M33 是"只量控制量、不量结果"，M36 是"量了，但量出来的量分不开两种假设"。**

## M37 · 一份"分解表"的各个分项，加起来不等于总数

**触发条件**
把一个耗时/占用/流量**拆成几段**分别测量，然后做成表或百分比印出来。

**现象**
本例：给 PS 装了七段相位计时，第一次上板，七段之和只占"总计"的 **40%**。
**表面上完全像被测对象的问题**——"有 60% 的时间不知道花在哪"。

修了总计的定义之后再跑，变成七段之和占"总计"的 **136.8%**。
同一个二进制连跑两次，最大的一段一次是 **67%**、一次是 **94.6%**，
而另一段反向移动几乎同样的量。

**根因（三个独立原因，一个症状）**
1. **总计的定义跨了两轮**：写成 `本轮结束 − 上一轮开始`，等于"本轮 + 上一轮"。
   旁证就在数字里：由它反推的时钟是 **786 MHz**，而 Cortex-A9 global timer 是
   CPU_3x2x ≈ **333 MHz** —— 786/333 = 2.36，正是"量了 2.36 轮"。
   **一个物理上不可能的推导值，是"分母量错了"最强有力的提示。**
2. **分项是逐字读的，不是快照**：七个计时字 = 七次独立 JTAG 读，各隔毫秒级，
   而**每帧只需要 65 ms**。于是表里混了不同帧的数字。被测对象的逐帧波动是真实存在的
   （`draw_camera` 的耗时随画面内容变），波动幅度足以把加法学反过来。
3. **一次采样配一个平均值**：分项来自**某一帧**，而旁边的帧率是**若干秒的平均**。
   拿单次采样去对平均值，稳定系统看起来就不稳定。

**排查 / 修复**
1. **写死在报告里的第一条断言：分项之和必须等于总计**（给一点读噪声容差）。
   不满足就**拒绝输出这张表**，而不是照样印百分比。
   > 一张各行列加起来不是 100% 的百分比表，比没有表更糟 —— **它看起来像知识。**
2. **要么一次读完，要么别比较。** 需要相互比较的一组寄存器，
   用**一次 `mrd -bin` 把整块取回来**，而不是 N 次 `-value`。
   顺手把**解析器本身**也验一下（拿一个常量字与直接读对比），
   免得"我的 scan 是哪种字节序"变成一个安静的错误。
3. **采样窗口要匹配。** 单帧偶发变慢（首次访问、被调试器打断、冷缓存）不是趋势。
   报**一个窗口的平均**（本例 32 轮累加和 + 轮数，除法放主机做），
   并且**溢出保护写在值上**（`sum > 3e9 就提前发布重置`），不写在"应该不会溢出"上。
4. **让一个你没假设过的已知量来确认仪器。** 本例修好后，由
   `(每轮 ticks) × (实测 fps)` 反推的时钟是 **330.8 / 333.0 / 330.0 MHz** ——
   落在 CPU_3x2x 本该在的位置。**这个频率程序里从没写死，是被量出来的**，
   它落在正确位置这件事，才是"这台仪器可信"的确认。

**规律**
> **分项之和 ≠ 总计，说明你的总计或你的分项有一个在量别的东西 —— 不要先去解释差值。**
> **单次采样与平均值并列在一张表里，就是在制造一个不存在的波动。**

**适用 / 失效条件**
- 适用：任何耗时/带宽/占用/流量的分解（性能剖析、DMA 带宽拆分、内存占用分项）
- 失效：分项本来就互不覆盖（比如分别统计不同对象），那它们本来也不该相加

**来源**
本队真实踩坑（2026-10-03）。修好后这张表给出了这一轮最有用的一个结论：
**一帧的 90% 就是那个逐像素渲染循环**，其余全部加在一起不到 10% ——
**想再快只能动渲染器，动管道没有意义。**

## M38 缓冲内容正确 ≠ 屏上正确；"可用"只能由人眼确认

- **触发条件**：通过 JTAG dump 帧缓冲并转成图片，看到界面正确，据此向用户报告"板子可用"。
- **现象**：用户看到的屏是**花屏彩条 / 完全静止**，而 dump 出来的 PNG 每次都是正确的界面。
- **根因**：dump 验证的是 **DDR 里的数据**，不是 **面板收到的像素**。显示链路末端
  (`v_axi4s_vid_out` / LCD 引脚 / 面板自身锁存) 出问题时，DDR 依然完好。
- **排查**：把"屏好不好"的判据限定为**人眼看到的样子**；寄存器只能证明"数据在"，不能证明"显示在"。
- **修复**：报告显示状态时区分三种证据等级：
  `寄存器在读` < `dump 内容正确` < **`用户看到正确`**。只有第三种可以说"可用"。
- **失效条件**：无。
- **来源**：2026-10-17，一天内因此错了两次（一次花屏、一次程序崩溃导致静止），
  两次都浪费了用户的信任和时间。

## M39 `DFAR=0` 且**原始版本也崩** ⇒ 不是代码回归

- **触发条件**：程序 `faultcode=0x11111104`、`DFAR=0x00000000`，每次都在第 0 帧死。
- **现象**：先怀疑自己最近加的代码（空指针、未映射地址），逐个排除后**连 git 里已知能跑的
  版本也崩**；断电重启后**仍然崩**。
- **根因判断**：这两个条件同时成立时，"代码改坏了"这个假设可以直接排除 ——
  剩下的变量只有：**比特流**、**板卡/线缆/跳线**、**初始化脚本**。
- **排查步骤**（按成本从低到高）：
  1. `git checkout <已知能跑的提交> -- <源目录>` + 重建 + 跑：**仍崩 ⇒ 不是代码**；
  2. 断电冷启动 + 同一流程：**仍崩 ⇒ 不是临时 PS 状态**；
  3. 查 AGENTS.md 的硬件红线（J10 跳线、相机 FPC、电源灯）；
  4. 核对当初能跑时用的**比特流文件**（时间戳/哈希）是否就是现在这个。
- **修复**：不要在这个阶段继续改代码 —— 会引入新的变量，把"唯一还活着的对照"也毁掉。
- **失效条件**：未做过"已知能跑版本"的对照时，本条的结论不成立。
- **来源**：2026-10-17 夜。为了排除自己的改动，先加了 NULL 保护、又 checkout 旧版本，

## M40 **中间环节正确就宣布完成** —— 同一个错误一天内复现四次

- **触发条件**：一条链路有多个环节（数据 → 配置 → 时序 → 面板），而测量手段只覆盖中间某一环。
- **现象**：一天之内四次宣布"好了/可用"，每次都有依据，每次都不是终点：

  1. "dump 的缓冲内容正确" ⇒ 屏是花屏；
  2. "旧版本也崩" ⇒ 推断"板子坏了"，而 DDR/定时器自检全过；
  3. "PROGRESS 读到 0" ⇒ 断定死在最前面，实际是上一轮崩溃留下的残留；
  4. "寄存器全对、v_tc 写进去了" ⇒ 屏仍是花屏。

- **根因（三层，逐层更根）**：
  1. **目标偏移**：在证明"我做了改动"，而不是"结果出现"；
  2. **没有事先写下终端判据** ⇒ 于是手边最容易拿到的证据被当成"完成"；
  3. **长会话漂移**：改动越多越想说"这次应该好了" ⇒ 越愿意接受弱证据。
- **排查 / 纪律**：
  - **汇报必须分三段**：【已测到终点】/【只测到中间环节】/【未验证·推断】；
  - **中间证据只能用于"排除"，不能用于"宣布"** —— 写"它排除了什么"，不写"它证明了什么"；
  - **终端判据必须在开工前写下**，中途任何"绿"都不改变它；
  - **由人眼判定的事项（屏 / 指示灯 / 手感）永远不由 agent 宣布**。
- **失效条件**：链路只有一环、且该环可直接测量时，本条不适用。
- **来源**：2026-10-17。M38 当晚写进本文件，几小时后又犯同一类 ⇒ **证明文档型条目不解决问题，
  必须把判据变成汇报格式里的必填字段**。

## M41 面板没有保持机制：它显示的是"最后收到的帧"，不是"当前状态"

- **触发条件**：用"屏上是什么样"判断链路是否工作，而面板本身没有帧缓存/重绘机制。
- **现象**：同一个"没有新像素"的原因，表现为三种完全不同的样子：
  - **黑屏**：从未收到过像素；
  - **白屏**：收到过但停在默认白场，或程序在出帧前崩了；
  - **冻在最后一帧**：曾经出过帧，之后流断了。
- **根因**：面板失去像素时钟后**保持最后一帧**。所以"屏上的画面"是**历史**，不是**现状**。
- **纪律**：
  - **截图/ dump 证明不了面板收到过任何像素** —— 它们证明的是 DDR 里的内容；
  - 判据必须来自**链路末端可读的状态**（显示通道 `SR` 的 IOC 位、`v_tc CTRL`、时序寄存器），
    而不是画面；
  - 若确实要看画，**先制造一个只可能由当前配置产生的变化**（例如把整块缓冲填成纯色再停 CPU），
    看面板是否跟着变 —— 不变就说明**它没在收**。
- **失效条件**：面板前有帧缓存/自身重绘时，"最后一帧"不代表断流。
- **来源**：2026-10-17/18。这一条解释了当天全部三种"显示故障"，而它们其实是同一个原因。

## M42 一个常量在 24 小时内被来回翻面 —— 因为每次只有"一次观察"

- **触发条件**：某个现象（屏幕黑 / 白 / 条纹）间歇出现，而每次观察都发生在**不同的板子初始化状态**下；
  手边正好有一个可疑常量（本例 `v_tc CONTROL`：`0x03F7EF06` vs `0x03F7EF07`）。
- **现象（时间线，全部真实）**：
  1. 看到条纹 ⇒ 把常量从 `06` 改成 `07` ⇒ 屏恢复正常 ⇒ 记为"修复"；
  2. 下一次（板子状态不同）又条纹 ⇒ 判断"`07` 是错的" ⇒ 改成 `06` ⇒ 屏又正常 ⇒ 记为"修复"；
  3. 第三次再翻回来，并把这两次结论分别写进 `main.c` 注释和案例集 ⇒ **两个文件互相矛盾**；
  4. 下一次会话读到哪个文件，就会把常量改向哪一边。
- **根因**：
  - **每次只有一次观察**，而观测对象（板子的初始化状态）在两次观察之间**自己变了**；
  - **常量并不是病因**：受控 A/B（冻结 CPU、以显示通道 `SR` bit12 `IOC` 为判据、两种值各两轮）
    显示 **两个值都产生 IOC=1**；
  - **真正的变量**是"板子有没有走完一次完整的 `ps7_init` + 程序启动"。
- **排查 / 纪律**：
  1. **嫌疑常量要做单变量 A/B，且每个值至少两轮**；判据必须是**不能被配置伪造的量**
     （本例 `IOC` 只在整帧真正完成时置位，而 `CTRL` 读回只证明"写进去了"）；
  2. **一次观察只能产生"嫌疑"，不能产生"结论"**；把"我改了 X 之后好了"写成
     "X 与现象相关，待 A/B"，而不是"X 已修复"；
  3. **同一事实不要在两处各写一份判断** —— 要么两处都引用同一次测量，要么只留一处；
     本次正是 `main.c` 注释与案例集各写一个相反结论，才让翻面得以继续。
- **失效条件**：现象可确定性复现、且两次观察之间环境未变时，单次观察即可成立。
- **来源**：2026-10-17/18。代价：**一整天**，以及用户多次明确的不满。
  最终由受控 A/B 终结，两个文件被改为引用同一结果。

## M43 重烧 PL 之后屏显示错 —— **先给屏断电，不要给板子断电**

- **触发条件**：每次 `fpga -file` 之后观察面板。**会烧比特流的只有一处**：
  `stereo_bringup_byname.tcl:251`。`ps_run.tcl` **不烧**（只 `dow` 下载程序），所以"只改程序 ⇒ 只跑 ps_run"
  是零锁存机会的做法。（原文曾写"ps_run 每次都会重烧"，与脚本实际不符，2026-10-18 更正。）
- **现象**：屏上是**条纹 / 花屏 / 停在旧帧**，而同期寄存器全部正常：
  `v_tc CTRL` 正确、显示通道 `SR` bit16 = 1（帧在完成）、DDR 缓冲 dump 出来是**完整的正确界面**。
- **根因**：面板**没有保持/重绘机制**，只显示"最后收到的帧"。重烧 PL 的瞬间 LCD 输出是未定义电平，
  屏抓到一帧垃圾后**失去同步并锁存**；此后即使正确的时序与像素回来了，它也不会自己重新同步。
- **第二种触发形态（2026-10-18 补）**：**像素流断掉**同样会造成"停旧帧/条纹"，而且不一定来自 VDMA。
  实测：逐帧 arm 曝光把相机 0 的 VTS 写成 `0x3501`（13569 行）或 `0x0102`（258 行，**低于 720 行图像高度**）
  ⇒ 传感器不再输出有效帧 ⇒ 捕获指针 4 秒只跳 1 次、`sync` 每循环空转约 950 ms、循环掉到 ~1 fps
  ⇒ 屏幕上就是上一帧静止/花屏。**I2C 写"成功"（回读正确、lost=0）也可能写错了对象**，
  所以"写进去了"不等于"写对了"。
- **排查（按顺序，每步都便宜）**：
  1. **dump 帧缓冲**：如果是完整界面 ⇒ **图像与 VDMA 都没问题**，问题在"屏"这一侧；
  2. **读显示通道 `SR` 的 bit16**（不是 bit12）⇒ 1 = 帧在完成 ⇒ 传输侧没问题；
  3. **先做软件显示重初始化**：停 MM2S → `v_tc CTRL=0` → 等 300 ms → 写回 `0x03F7EF07` →
     按序重配 MM2S（几何/地址 → CR → **VSIZE 最后**）。让屏经历一次干净的像素时钟起停，可能重新锁相。
  4. **若仍不对：整机冷断电再上电**（板子与屏一起断电、一起上电）。**这是冷复位，不是热插拔。**
     ⚠️ **"只给屏断电重插"在通电状态下是热插拔，禁止**（原文把这一步当成首选，2026-10-18 修正）。
- **修复 / 纪律**：
  - **锁存只能用一次冷启动清掉，软件修不好**（已证明：帧缓冲完整、`SR` bit16 置位、`v_tc` 正确时，
    屏依然是条纹）。所以防它的办法只有**少烧**：只改程序 ⇒ 只跑 `ps_run.tcl`；
    换比特流/改 BD ⇒ 才跑引导，且收工前冷启动一次；**演示当天禁止重烧比特流**。
  - "重启板子会清掉寄存器状态"这个代价，**在已经 dump 了帧缓冲与 `SR` 快照之后是可以接受的**——
    先取证，再冷启动，不要让"保住寄存器"绑住唯一有效的恢复手段。
  - 报告时把"板子"与"屏"分开说：**板子状态可以用寄存器证明，屏状态只能由人眼证明**。
- **失效条件**：面板自身带帧缓存/自动重同步时不需要这一步。
- **来源**：2026-10-18。为此浪费数小时，并两次给出"重启板子"的错误建议。
  附带更正一条判据：**`SR` bit12 不是"帧完成"，bit16 才是** —— 用错位读过整整一上午。

## M47 寄存器"回读能存"≠"它还在参与选择" —— 一个模式位把双缓冲变成单缓冲

**触发条件**：用软件写的**模式位**决定"选哪一份数据"，旁边另一个寄存器（指针/索引）看起来能读能写。
本次实例：AXI VDMA 的 `MM2S_VDMACR.bit1 = Circular_Park` 与 `PARK_PTR`。

**现象**：
- 代码按"翻转"写 `PARK_PTR`，回读值正确（写什么读什么），没有任何报错；
- 画面不黑、不冻，看起来"能跑"，只是偶发撕裂 / 两代画面混在一起；
- 所有基于"我确实停在某个帧存上"的推理（撕裂计数、等待交接）都建立在**一个不存在的机制**上。

**根因**：`CR.bit1` 的语义是 **0 = Park，1 = Circular**（PG020）。源码注释写反了，于是写入 `0x00010003`
实际是**循环模式**；循环模式下 `PARK_PTR` 根本不参与选择。
**回读只能证明"寄存器存住了这个值"，不能证明"硬件还拿它当选择用"。**

**排查步骤（不用示波器、不用读内部状态）**：
1. 做一个**只有两种状态、眼睛能二分**的测试图案：A 缓冲整帧蓝、B 缓冲整帧红（主机命令触发，图案常驻，
   不要自清——一帧的图案看不见）。
2. 看它是**按扫描率混色**（紫色抖、数不清）还是**按渲染率换色**（红蓝清晰交替、能数）。
3. 前者 = 硬件在循环；后者 = 真的停在某个帧存上。把 bit1 改一下再看一次即可定性。

**修复**：
- `CR = 0x00010001`（RS=1 / Park / 帧计数使能）。
- **同步修启动脚本里同一处写入**（`ps_run.tcl` 里的 `0x00010003`）——否则每次上电脚本又把它设回循环模式，
  而 PS 程序随后才纠正，中间那一段就是错的。
- 把说反的注释改成"0 = Park，1 = Circular"，并写明测量日期与现象。

**适用 / 失效条件**：
- 适用：任何"软件写模式位 + 另一个选择指针"的组合（VDMA park、DMA 链表、多路选择器配置寄存器）。
- 失效：设计把"当前扫描/写入位置"引出成可读寄存器的，直接读它即可，不必用图案。

**来源**：2026-10-21。外部审查（引用 PG020）指出注释与位义相反；随后用两色自检在板上判定并修复。
代价：这个错误在代码里活了数月，期间所有"翻转/撕裂"的调试都建立在一个不存在的机制上。

| 轮廓（OUT 面积，格子数） | 修前 **141 / 150 / 149**；修后 **825**，而参考掩膜本身只有 **766** 格 | 角上缺一小块，**3–4 格** | 死 |
| 单元内极差（EG cells） | 修前 **44–80**；修后 **20**（好 2.2–4 倍） | 划痕，最大读数 **11** | 死 |
| 四顶点中位偏移（格） | n=7：中位 **0.51**，最大 **3.58**，**2/7 超过 1 格** | 角缺，判据要求 < 1 格 | 死 |

注意后两个的**方向**：EG 的中位数从 44–80 降到 20（"变好 2.2–4 倍"），
但它的**尾部**从 95–109 变坏到 **132** —— 一个只看中位的改善会让人以为修好了。
轮廓更直接：修后读 825，比它要比较的参考掩膜（766）还大，
说明它在量**整个掩膜边界**，不是在量那个角。

**根因**（三个不同的几何原因，不是"参数没调好"）：

1. **轮廓**：对称差统计量量的是整条边界；每次掩膜量化抖动都会贡献一大片边界差异，
   而缺陷只占角上几格。**统计量的分母比现象大两个数量级。**
2. **单元内极差**：极差的极端值由**最差的那个格子**决定，所以中位变好、尾部变坏是同一个
   机制的两个面。它放大的是边界量化噪声，不是缺陷。
3. **顶点**：顶点是**两条外推直线的交点** —— 它是离每条线拟合点最远的点。
   板宽约 66 格，一条边的质心离顶点 20–30 格；斜率差 0.01–0.05 格/格，
   在 20–30 格的力臂上就是 0.2–1.5 格。**杠杆把噪声放大，顶点是读直线拟合最差的位置。**
   实测印证：同一块板两帧之间 `left` 边斜率 −0.2626 → −0.2658（Δ 0.0032 格/格）。

**排查步骤 / 早期检出（本该拦住它的检查）**：
- population 之前先做两次测量，**顺序不能反**：
  1. **null**：同一块参考板**对自己**，两帧，正确配准是恒等 —— 读出统计量的地板；
  2. **已知答案**：把一个**已知尺寸、已知位置**的缺陷画进去，读出它对同一个统计量的响应。
- 判据只有一条：`max(null) < min(known defect)`。不成立 ⇒ **统计量不能承担验收**，
  不要开始跑 population，也不要"多跑几块板看看"。
- 一分钟版本：一台只按一次回车就出一行的工具，让"两块板的 null 检查"变成两分钟的事
  （`dl/host_qc/accept_enter.py` 的默认目标就是 `g0,d2`）。

**修复**：这三个统计量都没有被"调参救活"，而是被**换掉**：
判据改为按颜色对手分割（PCB 掩膜与皮带的判别式 `2G−R−B`，d′ 3.45），
再在新的分割上重新做 null —— 也就是**先换工具，再重做地板**。

**适用 / 失效条件**：
- 适用：任何"先有数、再定阈值"的检测/计量（视觉、信号、日志异常、性能回归）。
- 失效：缺陷可以逐件精确标注、且能在**同一帧**上做配对比较时，null 应按配对差计算，
  门槛会低得多 —— 但那也要求配对是真的配对（同一帧、同一位置），不是"同一型号"。

`dl/_commit_msg_20261027_report_ch15.txt`（pre-fix null 与 post-fix 读数）、

## M54 · 一个"**没有收益**"的结论，用的是**看不见那个收益**的统计量和场景

**触发条件**：一次 A/B 得到"没有可分辨差异"，于是准备把一个功能关掉，
因为它要花 28–44 ms/次采样。关掉它是"省时间"，看起来无风险。

**现象**：2026-10-26 的一变量 A/B（只写目标字，场景与参考不动）：

| 臂 | sigma16 | grey |
|---|---|---|
| N=1 | 38.1 | 2.38 |
| N=8 | 34.6 | 2.16 |
| N=1 | 37.5 | 2.34 |
| N=8 | 41.1 | 2.57 |
| N=8（末次） | 42.4 | 2.65 |

N=8 的臂**跨在** N=1 两侧 ⇒ "平均对 `MB_DIFF_SIGMA` 没有可分辨收益"。

**根因（三层，缺一层这个结论都还站得住）**：
1. **统计量不对**：量的是 `MB_DIFF_SIGMA`（判过格子的有符号差的离散度），
   而判据读的是 `MB_DIFF_CELLS ≥ 8` 的**计数**。两个东西的分母都不同。
2. **场景不对**：那一帧的参考偏了 40 px（`MB_DIFF_DX/DY` +646/−288，`REG_STATE` 1 mode 2），
   sigma 已被**空间插值残差**支配（1.6–2.8 grey）；N=1 时 sigma 只有 2.4 grey ——
   比 10-24 那次 N=1 的 7.2 grey 安静三倍。**平均本来要去的帧噪声，在这个场景里已经没有了。**
   在噪声地板上做 A/B，测不出平均对噪声的作用。
3. **没有预注册的效应量**，5 臂 × 8 次比较，两个统计量连分母都不同。

**排查步骤**：见到"没有可分辨差异"，先问三件事，缺一条就不能下结论：
① 这个统计量是不是**判据自己读的那一个**？② 被测效应的量级在这台台架上是不是
**大于噪声地板**？③ 有没有**预注册**的效应量与样本量？

**修复（结论的写法，比代码重要）**：
把结论降级为"在这台工位、这个场景、这个统计量上**未复现**"，并把它**能**被推翻的
实验写出来（N=1 / N=8 各 ≥30 次独立比较、同一参考、预注册"没有一次达到限值"）。
**不要删掉** stage-2 的那条（判据自己的输入：2/43 → 0/47），
因为那才是唯一一条量在判据输入上的证据。

**早期检出**：任何"关掉/删掉一个功能"的决定，必须有一条**在判据自己的输入上**的对照，
且两臂必须**跨过同一个门槛**（这里是 `MB_DIFF_LIM`）。

**适用 / 失效条件**：
- 适用：任何"这个优化到底有没有用"的 A/B（编译选项、缓存、平均、降采样、阈值）。
- 失效：效应量可以解析计算、被测对象本身确定（无噪声）时，A/B 不是必需的 ——
  但那时也不该写"实测证明"。

**来源**：2026-10-26/27。`dl/NG_GOODBOARD_20261026.md` §5（A/B 表 +
"the N=8 arms straddle the N=1 arms"）、`dl/PERF_20261026_proposal.md`（"What its
benefit is measured to be" 表及其下三条：为什么这次 A/B **不是**反驳）、
commit `1efa33d`（把结论写成 "not resolvable"，并明确不引用 stage-2 的数字）。

## M55 · 固件每轮**回显**的主机目标字：一次误写就永久生效，读回来像一个新鲜设置

**触发条件**：主机写一个目标字，固件**每轮读进来、采纳、再写回去**（echo），
目的是让主机看到"当前生效值"。

**现象**：一个功能（帧平均 8 帧）在无人注意时变成 1 并**保持**。
它不是"掉回默认"，是"被写死成 1"。
`MB_AVG_CNT` 读 1 也不能自证 —— 它在 N=1 时被发布成 `(navg != 0u) ? navg : 1u`，
所以"平均关掉了"与"平均开着一帧"读数相同。

**根因**：echo 是一个**闩锁**。主机写 1 → 固件采纳 → 每轮写回 1 → 固件无法区分
"自己的回声"与"新的主机写"。没有任何复位路径恢复它（`avg_reset()` 只清累加器不清目标，
`ref_take()` 不碰它，开机自检不碰它），只有重启或**再一次**主机写能改。
更糟的是 `MB_AVG_TICKS` 在 N=1 时保留上一次 N=8 的 28.0 ms —— 一个"很合理的旧数字"。

**排查步骤**：
1. 列出这个字**所有**可能的写者（grep 全部工具，不要只看"应该写它的那个"）；
   本项目是 9 个 Tcl 站点、8 个文件能写它，主机侧 Python 工具**一个都不能**。
2. 找一个**只有目标路径会写**的旁证字（这里 `MB_AVG_TICKS` / `MB_AVG_SKIP`），
   从它们的存量反推"这个字曾经是 8" —— 这叫**旁证**，不是猜。
3. "谁写的"可能无法确定。那就写"**未确定**"，不要编一个最像的。

**修复**：
- 把"目标"与"生效值"分成**两个**字，且**不要回显目标**；主机看到的是生效值，
  写者看到的是目标，两者不再互相污染。
- 主机侧把这类字纳入 preflight（本项目的缺口正是"谁都不看它"）。
- 给 A/B 脚本加 `finally` + 读回断言：**脚本停在 `arm off` 就会把 1 留在板上**，
  而它打印的是 "reverted"。

**早期检出**：做一张"主机可写字的清单 + 谁恢复它"的表。
任何一行写着"**没有任何工具恢复**"的可写字，都是这种闩锁，都会在下一次事故里出现。

**适用 / 失效条件**：
- 适用：任何"主机/固件共享控制字"的设计 —— 邮箱、sysfs、寄存器窗口、配置中心。
- 失效：目标与生效值分成两个字、且各自只由一方写时，闩锁不成立。

**来源**：2026-10-26。`dl/NG_GOODBOARD_20261026.md` §5（"Target, not count" 与
"What does NOT reset it"）、`dl/AVG_N_AND_SPLICE_20261026.md` §1（9 个可写站点与
"the writer of tonight's 1 is outside the tracked tools"）、commit `1efa33d`。

## M56 ⭐ 从检测器自己的证据里训练的模型，继承那个检测器的盲区

> 一句话：**一个从检测器自己的证据里训练出来的学习器，继承那个检测器的盲区。**
> （a learner trained on a detector's own evidence inherits that detector's blind spot）

**触发条件**：想用"学习"改进一个已有判据，而逐样本标签只能从那个判据自己的输出里取
（超阈格子、告警片段、被判 NG 的记录），没有独立标注。

**现象**：模型训练收敛、量化逐位一致、留一也跑了，然后**每一类都输给原判据**，
而且分歧**全部单向**——原判据抓到的模型漏，模型抓到的原判据也抓到。

**根因**：标签不是"缺陷在哪里"，而是"**判据在哪里越过了自己的阈值**"。
判别面学到的正是判据的判别面，包括它看不见的地方：

1. **正样本的定位来自判据**。本项目实测：21 块良品每块都有一块 0..5 格的超容差连通块，
   而漏掉的 3 块划伤板是 4/4/5 格——**标签在良品与漏检缺陷之间重合**，
   模型没有可学的差别（`dl/LEARNED_RULE_20261028.md` §7）。
2. **良品的单点幅值可以比漏掉的缺陷更深**。本项目实测：良品 `g18` 块内峰值 108，
   漏掉的划伤 `d9` 只有 47、`d12` 92；于是"深而小 = 缺陷"的判断先打到良品，
   模型唯一的误判就是 `g18`。
3. **判据不判的地方，标签也不存在**。本项目实测：`fine_deep` 在掩膜外**恒为 0**
   （41/41 块，`ps_ui/main.c:9476/9482/9545`），外框内 46%–67% 的格从不参与判决。
   落在那里的一切既不在标签里，也不在任何特征里——**不是学不到，是没有数**。

**排查步骤**：
1. 先问"**标签从哪来**"。若答案是"现有判据的输出"，直接判定：上限就是现有判据，
   不要再花时间换网络、加层、调学习率。
2. 量**标签在两类之间的重合**：取正样本的那个量（本项目是最大连通块格数、峰值），
   在良品与"原判据漏掉的缺陷"上各画一遍。**重合区间就是学不到的部分。**
3. 量**被跳过区域有多大**：掩膜/ROI 之外、判据 `continue` 掉的格子在总判定面积中的比例。
   大于 10% 就要把"没测"和"测了没超阈"分开写。
4. 跑**同一条旧判据的重复测量**做噪声地板。本项目：同一块板前后两次比对，
   统计量差 0..6 格，而判据余量 1 格 —— 此时任何"模型比判据多抓 1 块"都不是信号。

**修复**：
- 训练标签必须来自**比对之外**：人工标注缺陷位置，或另一个**物理上不同**的测量
  （本项目已有候选：固件每帧算的格内极差统计量 `MB_EG_*`，`ps_ui/main.c:2583-2589`）。
- 若拿不到独立标注，就**不要训练**。把结论写成"这条路线未测"，而不是"AI 不行"。

**判据**：任何"用 AI/学习改进判据"的提案，必须先交三样东西：
**标签来源（与判据是否独立）**、**标签在两类间的重合度**、**重复测量的噪声地板**。
交不出来，提案不成立。

**适用 / 失效条件**：
- 适用：检测/判据/告警系统的任何"蒸馏式"再训练。
- 失效：存在独立标注（人工、另一模态、另一物理量），且该标注在判据漏掉的那部分上非空。

**来源**：2026-10-27/28。重训 `ts_cnn_top` 的 41 折留一：8/19 对 16/19、
误判 1/21 对 0/21、8 块单向分歧、McNemar p=0.0078（`dl/CNN_RETRAIN_20261028.md` §4）；
标签重合与掩膜盲区的逐块测量见 `dl/LEARNED_RULE_20261028.md` §7-§9 与
`dl/WHY_AI_FAILED_20261028.md` §2。


## M57 ⭐ 拍计数器**不是**数据到达的证据 —— AXI 的 RRESP/BRESP 必须被计数，而且计数必须被证明"能让这趟停下来"

> 一句话：**"收了多少拍"与"那些拍是不是错"没有任何关系；一个不管响应码的计数器，
> 在每一次传输都被拒绝时依然会给出一个健康的值。**
> （a beat counter is not evidence that the data arrived）

**触发条件**：要相信任何一个"发出去了多少 / 收进来了多少 beats / 这趟跑完了"的计数型指标；
或者一个 PL master 出现"DDR 一字未改，但计数器说它跑完了"的现象。

**现象**（本项目实测，2026-10-28）：1280×720 的前端每一趟都产出 `VALUES = 46,800`，
恰好等于应有的统计量个数；`STATUS.done` 不置位、`err` 置位；统计缓冲 `0x12AC0000`
前后 8 个字一比不变；写侧 `ERRS` 每趟 15,748-15,750（±2）。当时的结论写成了
"写坏了、读是好的"。**真相是读和写全被拒绝**：读侧每一拍都回非 OKAY，前端照样把整帧
走完，于是 `VALUES = 46,800`。

**根因**：
1. `pl_fe_rd` 只在 `RRESP != 00` 时置 `err`，而"接受了多少 beat"的计数器与 `RRESP`
   无关 —— 整帧走完与数据全错可以同时成立（`dl/pl_frontend/pl_fe_rd.v:182-189`）。
2. `pl_fe_rd.errs` 在顶层**根本没接**：`pl_fe_top.v` 里是 `.errs()`，连计数都读不到。
3. 于是同一个数字 `46,800` 在"数据全对"和"数据全错"两个世界里都成立 ——
   **这个数不是判据**。设计本身是诚实的（`err` 置位、PS 因此走了回退），
   但被读的人当成了"读侧没问题"。
4. 为什么全错：前端驱动 `AxPROT = 3'b010`（`AxPROT[1]=1`，non-secure），而这块板
   `TZ_DDR_RAM(0xF8000430) = 0`（DDR 全 secure）、`TZ_FPGA_M(0xF8000484) = 0`（对 PL 口
   开启检查），并且它用 JTAG 起（`ps7_init`+`dow`+`con`），**从来没有 FSBL 去打开 DDR**。
   设计里其它 PL master（两块 VDMA、CNN）的 `AxPROT` 被 IP 硬接成 `000`，所以只有这一个
   master 出事 —— 这解释了"为什么视频通路一直好的"。

**排查步骤**：
1. 见到"总数 / 计数 / 跑完了"型指标，先问一句：**它和响应码有没有关系？** 没有关系，
   它就不能用来证明数据到达；只能用来证明"总线动了"。
2. **先让它失败一次**：在仿真里注入故障（每个 `BRESP` / `RRESP` 回 `SLVERR`），断言
   `err` 置位、`errs` 非零，并断言 `done` 不置位。**不能失败的检查器不算检查器。**
   本项目 `dl/pl_frontend/tb_pl_fe_master.v` 的 `W2`/`R2` 就是这两个断言。
3. 把响应码计数**接出来**（本次读侧没接，这是真缺陷），让它能被主机读到。
4. 非 OKAY 的**数量**本身就是诊断量：本次 15,749/趟、±2，说明"每 burst 一次拒绝"，
   而不是"每 beat 一次"（23,400）或"每字一次"（46,800）。配合生产速率
   （1 字 / 19.7 clk）可以算出 burst 长 1-2 拍 —— 这段算术在任何重建之前就成立。
5. 换个角度验证"是不是策略性拒绝"：如果能找到**接收侧**的一个开关（本次是 TZ 寄存器），
   保持 master / 协议转换 / 互连**完全不变**，只改那个开关重跑一趟，比加一个从设备更干净。

**修复**：响应码计数必须接到可读寄存器；仿真必须有 `SLVERR` 注入用例并断言
`done` 不置位；任何"我还活着"的计数，必须与一个**只在成功时才动**的标志成对出现。

**判据**：一条 AXI 通路"通了"的证据只能是 **响应码 + 数据比对**。`beat count` 永远
不算，`VALUES == 应有值` 也永远不算 —— 除非它旁边有一个已注入故障的测试证明它会掉。

**适用 / 失效条件**：
- 适用：任何 AXI4 / AXI-Lite / AXI-Stream 的"计数型"指标；任何"跑完了 = 成功"的推理。
