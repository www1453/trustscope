## 二、融合的真实病因（已测量，不是推断）

1. **"相位/缓冲差一帧"不成立。** 融合开时，12 次相干快照里两个 store **永远一样亮**
   （ratio 1.00–1.25），并随 PHASE 一起在 17 与 4–5 之间翻。**根本没有 long/short 配对。**
2. **直接原因：arm 太慢。** `i2c_gap()` 是 1.4M 次循环（实测 15–20 ms，注释写 2 ms），
   一次 arm = 6 次 gap ⇒ 一次 arm ≈ 100–120 ms。而捕获周期 103 ms ⇒ 曝光每 ~3 帧才换一次
   ⇒ 每个 store 在下次 arm 前已被同曝光帧覆盖 2–3 次。
3. 旧记录"融合输出 MEAN=5"= **采样时刻正好落在两 store 都是短曝光的相位**，不是融合把画面弄暗。
4. 修好 arm（真 2.5 ms + 0x3500 不变不写）后：循环 105 ms ≈ 捕获 103 ms，**配对出现**
   （12/12 有效，比例 2.4–3.0，`MB_PAIR=1`），`CLIPLONG=0`、`CLIP_PM=0`。
5. **但屏幕亮度摆动**：融合开 14.8/14.2/17.4/14.4，单曝光 18.0/18.2/17.6。
   原因是结构性的：2 个帧存时"没被写的那块"只在交班瞬间完整，渲染 53 ms/帧必然读到正在被覆盖的块。
   ⇒ **免撕裂配对需要 ≥4 个捕获帧存（BD 改动）**，与 `dl/HARDWARE_SAFETY.md` 2026-10-03 的结论一致。
   ⇒ 因此 `g_bracket_on` 保持 **0**。
