# The fused QC reads only the rows the board occupies -- 5x fewer bytes over JTAG

2026-11-01, host-side only. No firmware, no PL, no XDC was touched (`git diff --stat` for
`ps_ui/`, `ps_fft_dual/` and `*.xdc` in this change: nothing).

Files changed
* `dl/qc_fused_20261101.py` -- new default path: mailbox first, then the board's row band, and
  the reference is not read at all once its identity has been proved. `--full` keeps the
  pre-change path runnable verbatim, for the A/B.
* `dl/corner_cov_20261101.py` -- `analyse(path, P, band=(y0,y1))`: a band dump is padded back to
  the full lattice, so the mask the fit sees is bit-identical to the full-frame one. Nothing else
  in the statistic changed (a regression on four archived frames is byte-identical, see below).
* `dl/_band_overlap_probe_20261101.py`, `dl/_band_rate_probe_20261101.py`, `dl/_argv_probe_20261101.py`
  -- the three measurements this change rests on, kept runnable.

## 1. What the corner statistic actually needs from a frame

`dl/corner_cov_20261101.py` needs the **whole board face**, not four windows:
four EDGE lines fitted to the silhouette's outer boundary over the middle 60 % of its bbox, a
polish over every boundary pixel, then rectification into the reference board's quadrilateral and
four 128 px windows centred on the reference vertices. It does **not** need the full 1280 px width
of the rows it uses, and it needs **no row the board is not on**: every step (closing, fill,
largest 8-connected component, edge fit, distance transform at the vertices) is local to the
silhouette.

The store is row-major at 3840 B/row, so a **row band is one contiguous byte range**.
The part box is already in the mailbox, in lattice cells (8 px): `MB_PART_BX0` 115,
`MB_PART_BY0` 116, `MB_PART_BX1` 136, `MB_PART_BY1` 166 -- the Y bounds are 116 and 166, NOT
adjacent to X0; `ps_ui/main.c:3721-3724` is where the indices come from, and the values are
`0xFFFFFFFF` when no part mask exists (`main.c:6757`).

## 2. The band, and why the numbers are equal rather than close

`y0 = by0*8 - 16`, `y1 = (by1+1)*8 + 16`, clipped to 0..720. The mask is built in the band and
then padded back into a (720, 1280) array, so `fit_quad` runs on **the same array the full-frame
path produces**. Measured silhouette clearance 16 px on all four archived boards (the tool asserts
clearance > 0 and refuses otherwise).

Band heights measured: 277-279 rows for the boards of 2026-11-01 = **1.02 MB**, against 2.76 MB
per full frame.

## 4. Acceptance B -- time per board, and the dump sizes

Dump cost at ONE session rate (`dl/_band_rate_probe_20261101.py`, one attach, core running):

| read | bytes | ms | KB/s |
|---|---|---|---|
| full frame (what the old path read, TWICE) | 2,764,800 | 6,931 | 390 |
| band 392 rows (widest box measured tonight) | 1,505,280 | 4,396 | 334 |
| band 279 rows (the board band of 2026-11-01) | 1,071,360 | 2,783 | 376 |
| residual grid | 28,800 | 91 | 308 |
| reference identity check (16 x 4 kB) | 65,536 | 523 | -- |

* **before**: 2 x 6,931 + 91 = **13,953 ms**, **5,558,400 B** over JTAG.
* **after**: 2,783 + 91 + 523 = **3,397 ms**, **1,165,696 B** over JTAG.
* bytes **4.77x** down; dump time **4.1x** down (the shorter transfer has the same per-call
  overhead, so it does not keep the full 5x).

End to end, measured on the same (empty) stage, same tool, same night, two runs each:

| run | verdict | bytes over JTAG | live dump | ref dump | grid | xsdb | host total |
|---|---|---|---|---|---|---|---|
| `--full` 19:56 | CANNOT JUDGE | 5,558,400 | 6,615 ms | 6,259 ms | 73 ms | 39 s | 40.2 s |
| `--full` 20:10 | CANNOT JUDGE | 5,558,400 | 6,339 ms | 6,360 ms | 70 ms | 39 s | 39.6 s |
| band 20:03 (392 rows) | CANNOT JUDGE | 1,599,616 | 3,402 ms | 0 | 65 ms | 30 s | 31.2 s |
| band 20:08 (400 rows) | CANNOT JUDGE | 1,630,336 | 4,191 ms | 0 | 105 ms | 31 s | 32.0 s |

Both paths carry the same 21 s young-window wait on an empty stage, which is why the totals
differ by less than the dump does: **the dump falls from 12.7 s to 2.8-4.2 s and from 5.53 MB to
1.07-1.60 MB, and the tool's own work per board from ~14 s to ~3.5 s.** With a board already
registered the gate costs nothing, so the same measurement puts end to end at ~20 s before and
~10 s after -- that pair is E1 (arithmetic on the E2 numbers above), not a measured per-board run,
because no board was in view for the whole session (see 6).
A note on the band height: it is whatever the firmware's part box says. For a board-shaped part it
is 250-310 rows; a 20:07 run with a frame-filling object in view published a 720-row box, and the
band then IS the whole frame (no saving, and the tool says so in the log). The 5x is a property of
the board's own size, not of the tool.

## 5. The overlap was measured and REFUSED, not assumed

The plan was to hide the dump inside the firmware's ~8 s young window. Measured with a control
window of the same length and no dump in it (`dl/_band_overlap_probe_20261101.py`, and again in a
live run's own log):

| phase | loop iterations | wall | rate |
|---|---|---|---|
| control, no dump | +20 | 2,087 ms | 9.6 /s |
| band dump 1.06 MB | **0** | 2,496 ms | 0 |
| gate wait (2 words per 500 ms) | +192 | 21,106 ms | 9.1 /s |
| band dump 1.51 MB (live run) | **+1** | 3,402 ms | 0.3 /s |

A large `mrd` leaves the A9 in state "Running" afterwards but does not let it **execute** while the
bytes come down, so the young window does not advance during a dump: overlapping would ADD the dump
to the window instead of hiding it. The tool therefore waits for `MB_DIFF_OK == 1` first and dumps
after (`--band-first` keeps the other order for re-measurement; it is not the default). Every run
prints the loop count of each phase, so the reason is in the record.
Consequence worth stating: the station is now frozen for 3.4 s per board instead of 14 s.

* **good board -> OK / contaminated board -> NG**: NOT MEASURED ON HARDWARE. No board was in view

  fusion rules, `gate_only()` and `explain()` are byte-identical to before (see the diff), and the

  cannot be produced without the board, and is not fabricated here.

## 7. Acceptance D -- a stale reference is refused, with evidence

The session reference is proved on every run by comparing 64 kB of 0x12400000 (16 blocks of 4 kB,
spread over the frame) with the file's own bytes. Two refusals, both real:

| named reference | sampled bytes differing | verdict |
|---|---|---|
| `dl/frames_20261031_ref/ref1.raw` (previous session, 31 Oct) | 53,852 of 65,536 | **REFUSED**, CANNOT JUDGE, exit 5 |
| `dl/frames_20261101_fus/ref.raw` (16:43 tonight, earlier session) | 45,779 of 65,536 | **REFUSED**, CANNOT JUDGE, exit 5 |

and the positive control (`--ref-frame` = the session reference itself): `match=1`, proceeds.
The tool refuses rather than substituting its own reference for a file the caller named, and it
also refuses to *use* one silently in that case. When it picks its own session cache and that cache
does not match DDR, it re-dumps the current reference once (7.6 s), says so, and stores it -- that
is a repair, not a stale read, and it is printed as `ref_dump ... reason=cache_not_the_stations`.

## 8. A trap this change hit, recorded so it is not hit again

`xsdb` **splits an argument at every comma**: 10 arguments arrived as 13 `$argv` elements
(`dl/_argv_probe_20261101.py`). A comma-separated sample list silently shifted every later
argument by up to 4 positions. All arguments are now comma-free integers or paths, and the sample
geometry is computed inside the Tcl.
