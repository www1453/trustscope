# Problem 2 (2026-10-26): camera 1 — the anti-flicker lock ported with camera 1's own words, and camera 0's empty-belt defect measured

Firmware: `ps_ui/main.c` + `ps_ui/cam_i2c.c`, source hash **5A92F6D2** (was 25666017). Built with
`ps_ui/build.ps1` (373 mailbox words, 0 collisions, all layout checks pass, the four pre-existing
warnings), flashed with `ps_fft_dual/strict_load_cores.tcl` only: no bitstream, no power cycle, no
VDMA register written. Camera 0's controller (`aec_control()`) is **not touched**; the comparison,
the tolerance map, the amplitude/area rule, the registration and camera 0's exposure are unchanged.

## 0. Two answers in one paragraph each

**Camera 1.** The old camera-1 law had no anti-flicker lock (its shutter was 0.61 of a 10 ms period
at 4x gain) and a dead-end STUCK latch; it sat at `MB_CAM1_AEC_STATE` 3, exp 2655, gain 64, mean 580,
clip 55-60 per-mille. It now runs camera 0's stage-C shape against **camera 1's own measurement**:
the shutter is k whole 10 ms periods with k limited by **camera 1's own VTS** (read over I2C: 740
lines -> k_max 2, published as `MB_CAM1_VTS`/`MB_CAM1_KMAX`), brightness is carried by the gain, the
usable-image test runs first for every state, and there is no total-step latch. Measured over 300
samples / 288.3 s on an empty, still belt: **state 1 in 300/300, k = 2 in 300/300 with 0
transitions, exp 8698 = 2 x 4349 in every sample, gain 16, clip 0 per-mille in 300/300 against the
limit 10, mean 490-541**. Camera 1 is not merely unclipped: against camera 0 in the same session it
reads mean 536.3 vs 523.3 per-mille with the same edge energy and zero saturated pixels.

**A new measured defect that is camera 0's, not camera 1's.** On that same empty belt camera 0's AEC
hunted **k 2<->3 with clip 109-144 per-mille** (13/300 samples at k=3, 14/300 over the limit), because
its reference contains a part and its mask term reads the part's absence as a lighting deficit. This
is the case `dl/STAGE_C_20261025_exposure_range_mask_latch.md` section 7.4 lists as unverified. It is
**not fixed here** (camera 0 is out of scope) and it froze the comparison for the whole 288 s.

## 1. The defect, as measured before the change

| word | value | how |
|---|---|---|
| `MB_CAM1_AEC_STATE` | **3** (stuck) | mailbox, both captures |
| `MB_CAM1_AEC_EXP` | 2655 | " |
| `MB_CAM1_AEC_GAIN` | 64 | " (= `CAM_GAIN` 0x40, i.e. the boot value, never moved) |
| `MB_CAM1_MEAN` | 580 per-mille | " |
| `MB_CAM1_CLIP` | 55-60 per-mille | " (limit `MB_CLIP_LIME` 10) |
| `MB_CAM1_AEC_STEPS` | 41 | " (41 lever moves without one usable evaluation) |
| `MB_CAM1_AEC_EVAL` | 2300+ | " (the loop was running) |
| `MB_CAM1_AEC_LAST` | 7 | " (the "still stuck, holding" code) |

2655 is **0.61 of a 10 ms period** (`MB_LINE10` 4349): under the 100 Hz illuminant the shutter was not
a whole number of ripple periods, so the frame carried the rolling-shutter band the whole lock exists
to cancel. The old law's shape (`main.c` before this change): `aec_state == 3` tested FIRST with a
body that moves nothing (the dead-end latch stage C removed from camera 0), brightness moved through
the *exposure* in 8/9 steps, the gain never left its boot value, and `aec_steps > 40` latched STUCK.
The sensor was not at fault: camera 0, same bench, same illuminant, was converged in the same session.

## 2. What changed (file:line)

| site | line | change |
|---|---|---|
| `cam_i2c.c` | 229 | `cam_read_bus()`, a read on an explicitly chosen I2C bus (the existing `cam_read()` only ever reaches bus 0) |
| `cam_i2c.c` | 437 | `cam_read_reg_bus()`, public; `0x100` = no answer, as `cam_read_reg()` |
| `main.c` | 312 | the declaration of the above |
| `main.c` | 1570-1574 | five words: `MB_CAM1_AEC_K` 527, `MB_CAM1_KMAX` 528, `MB_CAM1_VTS` 529, `MB_CAM1_AEC_TRIES` 530, `MB_CAM1_AEC_FLAGS` 531 |
| `main.c` | 6883 | `g_cam1_kmax`, `g_cam1_vts` (camera 1's frame length, not camera 0's) |
| `main.c` | 7059 | `cam1_timing_derive()`: reads camera 1's VTS twice over I2C (must agree, 64..4096), derives k_max = (VTS-4)*16 / g_line10; a failed read leaves k_max 1 |
| `main.c` | 12943 | the call, after camera 0's `sensor_timing_derive()` (it needs `g_line10`) |
| `main.c` | 10520 | `aec_control_cam1()` rewritten: the locked law, with the old law kept as the `g_line10 == 0` fail-safe |
| `main.c` | 9869, 13625 | `g_cam1_meas_n` = `s1.chan_total`, so "no decision on an unmeasured frame" uses camera 1's OWN pass size (`AEC_MEAS_MIN_N`) |

**Camera 1's k_max is its own, and that is the one non-obvious design point.** Stage C lengthened
**camera 0's** frame to VTS 1200 (`sensor_frame_length_set()` writes bus 0 only); camera 1 still runs
the mode table's VTS 740, i.e. a 27.2 ms frame. The OV5640 clamps the shutter to VTS-4 lines, so with
740 lines only **2** whole 10 ms periods fit; asking for k=3 or 4 would be clamped at 736 lines =
27.1 ms, which is not a multiple of the period and would silently break the lock camera 0 was fixed
for. Using camera 0's `g_kmax` (4) for camera 1 would have done exactly that. The board now publishes
`MB_CAM1_VTS` **740** and `MB_CAM1_KMAX` **2** in every sample of the trace, so the limit is a
measured word, not a remembered constant. The line time itself is shared and measured once (both
AN5642s run the same mode table: same HTS 1892 and PLL), which is why `g_line10` is used for both.

**What was not ported, and why.** Camera 0 also has a PART-MASK term (hysteresis, cooling,
anti-windup). Camera 1 has no segmentation - `cam1_verdict()` reads exposure statistics only, and no
camera-1 mask exists - so there is no mask input to feed; inventing one would be a second segmenter
with no reference. The anti-windup that is applicable is kept: the reversal debounce and a bounded
move budget (`AEC_STUCK_TRIES`) while the image is unusable.

## 4. The new defect: camera 0 on an empty belt (measured, NOT fixed)

The 300-sample trace was taken with the belt empty. Camera 0's words over the same 300 samples:

| word | value | count |
|---|---|---|
| `MB_AEC_K` | 2 or **3** | k=3 in **13/300** samples, **26 k transitions** in 288 s |
| `MB_CAM0_CLIP` | 0 at k=2, **109..144** at k=3 | over the limit 10 in **14/300** samples |
| `MB_AEC_STATE` | 1 or 2 | state 2 in **16/300** |
| `MB_CAM0_MEAN` | 478..639 | |

**Mechanism, from the code and the words.** The mask term (`main.c:10083-10240`) needs
`g_part_ref >= PART_MIN_PTS` (the reference has 634, a part) and `g_part_pts > 0`. On a bare belt the
live mask is **not** 0 (see section 5), so it reads 1..144 cells - non-zero and below the 400 floor -
and the controller concludes "the part is short: not enough light". It steps k 2->3; at k=3 the frame
clips 109-144 per-mille, the clip guard pulls it back to k=2, and the cycle repeats. The anti-windup
hold that is supposed to break this cycle is RELEASED whenever `g_part_pts >= PART_MIN_PTS`, and the
clipped frame inflates the mask past 400 (measured: part_pts reached 1287), so the hold is released
by the very frame the clip guard is about to reject.

**Consequence:** `MB_DIFF_N` stayed **60 for the whole 288.3 s** (frozen; ~130 comparisons should have
run). The comparison was refusing, honestly, with `MB_DIFF_OK` 3 (clip gate) and 5 (nothing to judge).
After camera 0 settles it reports `MB_AEC_LAST` 13 (mask short, no headroom, held) at k=2/clip 0 - so
the state is bounded and not a false PASS, but the empty-belt state is **not stable** for camera 0.

**The fix, in one line, for the next session (not applied):** the mask term must not treat the
*removal of the part that is in the reference* as a lighting deficit - it needs a presence/absence
test that does not depend on the mask it is chasing (or a release condition that a clipped frame
cannot satisfy), and it needs its own acceptance with the part removed and restored under a
reference that contains a part.

## 5. Why the empty-belt mask is not zero (measured, same root)

`MB_PART_PTS` read 0..1287 (median ~90) and `MB_BG_CELLS` 891..2515 on a belt that **was** empty:
a dumped camera-1 frame shows the bare belt, and two dumps 4 s apart give best shift **(0,0) px**,
identical frame means (136.8 / 136.8) and mean |diff| 1.49. The cells are real and they are not the
part: the mask is "not the background" over the **whole frame**, so room objects (the mask box sat at
source x 1080..1159, y 216..263 - the table/cable area ABOVE the belt) and the belt's own seam join it.
On a board-in-view frame the board is the largest connected component and the cluster rule keeps it;
on a bare belt those cells ARE the mask. This is the same class the mask rule's own note states as a
limitation ("a LOCALISED change on the belt since the capture joins the mask as a false part region").

Its two measured consequences beyond section 4: the boot self-test's check 2 (BG) and check 4 (MASK)
fail on an empty belt (`MB_ST_VERDICT` 1, code 2, fail 0xA, res 0x44) because `MB_BG_CELLS` 332 >= 32
while `MB_PART_PTS` 89 < 400 - the two detectors disagree about a bare belt; and `preflight.py` cannot
pass on a bare belt for the same reason. Both are honest refusals of a state the instrument was not
built to pass, not new faults.

**This is a defect of the mask's SCOPE, not of one script.** The station cannot distinguish "no part"
from "part" while the mask is populated by room objects: on a bare belt the mask read 3520 cells with
a box covering the whole frame, and my own "wait for a part" gate (`MB_PART_PTS >= 400`) - written to
that number - fired on it. That is how a bare-belt reference was taken in the first place. Any host
that treats `MB_PART_PTS` as a part-presence word has the same bug; the honest part-presence word is
the camera-0 image, or `MB_DIFF_VERDICT`/`MB_DIFF_OK` (which refused), not the mask count. The fix
belongs with the mask's scope (judged region / room exclusion), together with camera 0's mask term.

**One more consequence, stated:** one `MB_CMD = 9` was sent before the placement was confirmed, so a
bare-belt reference was taken (`MB_PART_REF` 2744, box the whole frame). It was discarded and replaced
after the board was actually placed - see section 5b.

## 7. What remains unverified

1. **The k *transition* is now observed** (k 2 -> 1 with the board placed, exp 8698 -> 4349, mean
   533 -> 333, then stable). What is still not observed is a k step *upward* (a scene dark enough to
   run out of gain), and a step at the top of the ladder (k_max 2).
2. **The bright-end floor**: at k=1 and gain 16 a scene brighter than one period still clips, and the
   law latches STUCK. Correct but unmeasured here (the bench belt is not that bright).
3. **The 12-move budget path was never entered** (`MB_CAM1_AEC_TRIES` stayed 0). Note that after the
   budget is exhausted the code holds with state 2 (adjusting) rather than 3; the re-test still runs
   every evaluation, so it can still clear, but "adjusting" is the wrong word for "holding". No bench
   evidence either way.
4. **Camera 1's verdict still uses camera 0's `g_aec_state`** for the CANNOT-JUDGE half
   (`cam1_verdict()`'s own header states this pre-existing view coupling). Not touched.
5. **Camera 1's board-in-view operating point is k=1, mean 333** (1.5x darker than camera 0). It is
   inside the band and unclipped, but a finer gain ladder or a per-camera clip limit would put it
   closer to camera 0 - neither is in this change.
6. **The camera-0 empty-belt defect** (section 4) has no fix and no acceptance yet, and the mask-scope
   defect (section 5) is the same family.
7. **The contaminated board's registration at a different placement** and the **second cross-check
   window** (V3/V4) remain open from `dl/XCHECK_20261026.md`.
