## 七、行缓存版 HLS 加速器 · 设计（2026-09-24 定稿，待实施）

### 为什么要重写，而不是继续调 pragma

两次失败的原因已经明确，**都是"每算一个输出通道就把 3x3 窗口重读一遍"**：

| 版本 | 延迟 | 资源 | 失败点 |
|---|---|---|---|
| 朴素直接卷积 | 79.6 ms | DSP 55、LUT 35% | 每 MAC 约 1.6 周期（地址计算 + 访存） |
| + OC_PAR=8 全展开 | 56.1 ms | **LUT 111%** | HLS 又自动展开了 ic，每轮 576 个 MAC，组合逻辑爆炸 |

共同根因：**窗口像素每次从内存重新取，每个 tap 都要算地址**。
展开只是把这个开销乘以并行度 —— 于是 LUT 先炸，延迟没降。

### 新结构（窗口寄存器 + 行缓存）

```
每个输出像素的窗口常驻寄存器：
    uint8_t win[3][3][MAXC];        // [行][列][输入通道]，MAXC = 32
    寄存器量 = 3*3*32 = 288 字节 = 2304 FF（预算 106400，可忽略）

循环顺序（关键）：
    for y                       // 逐输出行
      for x                     // 逐输出列
        1) 把窗口左移一列，只加载 1 个新列（每行 cin 个像素）
        2) for oc_group (cout/OC_PAR)      // 像素在外、通道组在内！
             for ic                        // 流水线放这里，1 ic/周期
               9 个 tap 全展开 x OC_PAR 路    // 操作数全在寄存器里
```

**为什么通道组要在像素内层**：窗口是三种卷积分共享的。
反过来的话，每换一个通道组就要重建一次窗口（4 倍以上的移位开销）。

### 预期代价（手算）

| 层 | 周期 | 说明 |
|---|---|---|
| conv1 | 8192 | (16/8)*4096*1 |
| conv2 | 65536 | (32/8)*1024*16 |
| conv3 | 32768 | (32/8)*256*32 |
| 窗口移位 | ~12300 | cin 次加载/像素 |
| 池化+FC | ~5000 | |
| **合计** | **≈ 0.8–1.0 ms** | 目标 ≤2 ms，且不需要 ic 展开 → LUT 应大幅下降 |

DSP 预算：OC_PAR(8) x 9 tap = 72 个乘法器并行 → **72/220**，仍在上限内。

### 实施顺序（不许跳步）

1. 改 `hls/src/ts_cnn.cpp` 的 `conv3x3`（**保持函数签名与契约不变**）
2. **先在主机侧 g++ 跑 `tb_cnn.exe`，必须仍是 200/200 bit-exact** —— 秒级，别跳过
3. 再 `TS_HLS_MODE=csynth` 前台跑综合，只看三个数：延迟 / LUT / DSP
4. 不达标就调 OC_PAR 与流水级，**每次只改一处**
5. 若三轮仍压不到 ≤2 ms，**按计划维持 PS 退路**（120.8 ms，满足 ≤200 ms 节拍），
   行缓存版转为后续项，不再占关键路径

### 风险

- 窗口寄存器阵列若被 HLS 放进 BRAM，移位会变成访存 → 白做。**必须确认
  `report` 里 win 是寄存器（看 FF 数量是否相应增长）**
- 边界补零：窗口预载与列移位都要处理 x=0/x=W-1 与 y 的上下边界
- 每像素的执行顺序不能用 `if (x==0)` 分支把流水线打断

### 依赖与前置（都已完成，可直接开工）

- 参数包与向量：`hls/data/params.bin`、`vectors.bin`（导出布局已验证）
- 主机测试台：`hls/tb/tb_cnn.cpp` + MinGW g++
- 综合入口：`run_hls_nopipe.bat -f run_hls.tcl`（**必须前台**）
- 已知坑：见第三节（tee/cat/sh 命名管道、后台进程被回收、别用 HLS_MODE 这个变量名）

## 八、行缓存版结果（2026-09-24 收尾）· PL 加速器退出关键路径

| 版本 | 结构性改动 | 延迟 | 资源 | 结论 |
|---|---|---|---|---|
| 1 | 朴素直接卷积 | 79.6 ms | LUT 35% | 每 MAC 1.6 周期 |
| 2 | +8 路输出通道展开 | 56.1 ms | LUT 111% | HLS 又展开 ic，组合爆炸 |
| 3 | 窗口寄存器 + 行缓存 | 56.8 ms | LUT 121% | 并行度未生效 |
| 4 | 3 改成加法树 | **逐位相同** | 相同 | 假设被否定（且差点被增量缓存骗过，见 T14） |
| 5 | **整层权重搬到片上** | **综合跑不完** | — | 停在 code transformations >29 min |

**版本 5 的主机验证是通过的**：`tb_cnn.exe` 仍然 200/200 bit-exact。
但综合在 `Starting code transformations` 阶段超过 29 分钟无输出（与前两次"展开过度"的失败形态相同）。

**瓶颈定位（有证据，未证实）**：`ic` 循环的 II≈72 ≈ 每次迭代需要的 72 个权重字节，
而权重走 8 位宽 AXI（约 1 字节/周期）→ 恰好等于实测的 1.09 周期/MAC。
即"**DSP 用了 185 个，吞吐却只有 1 MAC/周期**"这个矛盾指向数据通路。
版本 5 就是针对它的改动，但**综合规模失控，没拿到数字**。

**判定（按事先写好的规则：三轮不达标即维持退路）**

- **PL 加速器退出关键路径**，列为长期风险项
- **PS 定点路径为当前可用方案**：板上已验证与参考逐位一致，120.8 ms/帧，
  满足《项目定义》"每件 ≤200 ms"的节拍
- 界面侧不需要改动：判定链路走的是质量门 + 推理结果，与推理在哪执行无关

**若要再攻 PL（不在关键路径上）**，下一根杠杆按证据优先级：
1. 限制 `win` 的完全分区（288 个寄存器导致调度空间爆炸）→ 先试 `block factor=4`
2. 权重缓冲改为 `ARRAY_RESHAPE` 或按 `dim` 部分分区，避免 9216 元素全展开
3. 把 `OC_PAR` 从 8 降到 4，用综合时间换可行性
4. 或直接换思路：**降输入分辨率/通道数**（模型层面），而不是继续压硬件
