# 诊断工具本身的陷阱

> 这一份和其他踩坑清单不同：它讲的是**你用来判断"板子/程序有没有问题"的那个脚本**，
> 本身可能是错的，而且错得"看起来很有说服力"。
>
> 每一条都来自本队真实经历，附带当时被骗了多久、怎么发现的。

---

## D1 **读值函数拿不到值**：`catch` 里没有赋值

- **触发条件**：写 Tcl/脚本包装 `mrd`、`Get-FileHash`、`subprocess.run` 之类的取值调用，
  用 `catch { ... }` 包住，但**没有把返回值赋给变量**。
- **现象**：整轮测试每个读数都一样（都是初始值 `-1`），而脚本"跑完了、没报错"。
  本队因此宣布过"两路相机全部冻结"，并浪费了一轮现场取证时间。
- **根因**：
  ```tcl
  set r -1
  if {[catch { mrd -force -value $a } e]} { return -1 }   ;# 结果被丢掉了
  ```
  `catch` 只捕获错误，**不会**把命令的输出存起来；`r` 永远是 `-1`。
- **排查步骤**：
  1. 先单独跑一次读值，把**原始字符串**打出来（本队实测 `mrd` 返回的是十进制整数）；
  2. 再跑你的包装函数，对比两者；
  3. 若不一致，看赋值有没有丢。
- **修复**：
  ```tcl
  if {[catch { set r [mrd -force -value $a] } e]} { return -1 }
  ```
- **失效条件**：不适用于已经用返回值赋值的写法；也不适用于返回对象而非值的 API。
- **来源**：2026-10-18 夜，10 分钟 soak 第一次运行，30 次采样全是 `-1`，
  被误读成"两路都冻结"。**判据：整轮读数完全相同**——物理量极少如此。

## D2 **永远返回"通过"的检查器**

- **触发条件**：写一个"检查内存布局/资源冲突/文件完整性"的脚本，只做正向判断。
- **现象**：无论输入怎么改，脚本都打印 `CLEAN`。本队的 DDR 布局检查器第一版就是这样：
  它只在**同一个窗口分组内**比较区间，两个不同窗口的区域即使重叠也不会被比较。
- **根因**：检查器没有**反向用例**——从来没有一个"必须失败"的输入。
- **排查步骤**：人为构造一个已知错误（例如把两个区域故意重叠 4 KB），跑检查器，
  **它必须报错**。不报错就说明检查器无效。
- **修复**：检查器内置自检：
  ```python
  bad_case = REGIONS + [("injected overlap", 0x10000000 + 0x1000, ...)]
  if check(bad_case, quiet=True) == 0:
      print("SELF-TEST FAILED: the checker did not notice an injected overlap")
      return 1
  ```
  并且比较必须是**全局两两比较**，不能按分组跳过。
- **失效条件**：不适用于"只报信息、不做判断"的工具（它们本来就没有通过/失败）。
- **来源**：2026-10-18，队友审查用一个"故意重叠"的反例把第一版检查器推翻了；
  第二版加入自检后才可信。

## D3 **探针的分辨率比被测现象还粗**

- **触发条件**：用读总线/读文件的方式去测一个**时间上很窄**的现象
  （例如"这块缓冲现在是否正在被 DMA 写"）。
- **现象**：测出来"两块都在变"或"全都一样"，与物理直觉矛盾。
- **根因**：单次读取耗时（经 JTAG 读 3.8 KB × 8 次）**超过了现象本身的周期**
  （帧周期 121 ms），两次快照相隔远超一帧，于是任何结论都成立。
- **排查步骤**：动手前先估"一次采样要多久"，与现象周期比较。
  若采样间隔 > 现象周期，这个探针**不可能**分辨它。
- **修复**：改由**被测端自己测**（固件在内存速度下采样并发布结果），
  或把探针缩小到单字、把采样点放到能一次读完的粒度。
- **失效条件**：现象本身是稳态（例如"寄存器值对不对"）时，分辨率不成问题。
- **来源**：2026-10-18，用 JTAG 逐行读两块缓冲判断"谁在被写"，结果两块都"在变"，
  实际是采样间隔约 200 ms > 帧周期 121 ms。

## D4 **用相邻字节判断图像异常**

- **触发条件**：判断一块相机缓冲"是不是有效图像"，用的是"相邻字节差值超过阈值就报警"。
- **现象**：一整行**纯红**像素被判成 66% 乱码。
- **根因**：存储格式是 BGR 三字节一像素，相邻字节可能是**同一像素的 B 与 G**，
  也可能是**相邻像素的 R 与 B**——它根本不是同一个通道的相邻采样。
- **排查步骤**：先用一张**已知纯色图**跑检查器；纯色图必须是"正常"。
- **修复**：按像素解码，比较**同一通道**的相邻像素；或先转灰度再算梯度。
- **失效条件**：缓冲区确实是单通道（灰度/二值）时，原做法成立。
- **来源**：2026-10-18，队友审查给出纯红行反例；本队的
  `ps_cam1_data.tcl` 因此改成按像素比较。

## D5 **读取失败被当成"很亮/很大/正常"**

- **触发条件**：读值失败返回 `-1`，随后被 `& 0xFFFFFFFF`、`abs()`、`max(0, x)` 之类"修正"成正数。
- **现象**：一个**已断开的通道**在统计里表现为"非常亮"（255）或"计数很大"。
- **根因**：错误值参与了算术，而算术把它变成了合法值。
- **排查步骤**：把读值函数单独拿出来，**故意读一个不存在的地址**，看返回值能否与
  "读到 0" 区分开。
- **修复**：读值函数用一个**不可能出现的哨兵**（例如 `0x8000_0000` 或字符串 `ERR`），
  调用方必须先判哨兵再参与计算；统计里要单独计"读取失败次数"。
- **失效条件**：不适用于返回结构体/异常的语言（那里的失败不会被算术吞掉）。
- **来源**：2026-10-18，`ps_cam1_four.tcl` 里 `-1 & 0xFFFFFFFF` 被当作 4294967295，
  进而被统计成 255；队友审查指出后修正。

## D6 **一个永远通不过的闸门** —— 它读的那个字根本不在读取集合里

- **触发条件**：一个"闸门/门禁"函数先读一批字，再判断是否放行；而**读哪些字**是一份
  手写的名单（`READ_WORDS` / 列名表 / 字段表）。闸门是后来加的，名单是早先写的。
- **现象**：参考面明明是干净的（工位自己的字说 `REFQ_STATE = 0`），闸门每次都拒绝，
  报"参考面不干净"。换板、擦参考面、重启、重设阈值全部无效。**而"板子真的脏了"在外部
  看起来完全一样** —— 于是人去擦一块本来干净的板子，一遍又一遍。
- **根因**：闸门读 `d.value("refq_state")`，而这个字**不在 dump 实际读取的名单里**，
  返回 `None`；`None != 0` → 永远"不干净"。
  **闸门读到的不是板子的状态，是"我没读"这件事被翻译成了"状态是坏的"。**
- **排查步骤**（不用板子）：
  1. 让工具把**每个闸门的输入原样打印**出来，与它的期望值同一行；
  2. 只要某个输入是 `None` / UNREAD，就报 **PLUMBING FAULT（管路故障）**，
     明确写"检查这个字是否在本工具的读取名单里，**不要查板子**"；
  3. 判据：板子自己的字说 PASS 而闸门说 FAIL ⇒ 一定是闸门/管路，不是被测对象。
- **修复**：
  1. 把该字加进读取集合（**一处**，不要复制第二份偏移表）；
  2. `--check` 这类只读模式永远先打印"闸门的输入是什么"，再给结论；
  3. 加一条**离线**静态守卫：把"闸门用到的字段名"与"读取集合"做集合差，
     "用到了但没声明"必须让自测失败（`skill/scripts/readset_lint.py` 就是这条守卫）。
- **早期检出**：`readset_lint.py` 在提交前跑一次；它不需要板子、不需要固件，
  只读工具源码，代价是几毫秒 —— 而它拦下的那次代价是一整轮验收的第一块板。
- **适用 / 失效条件**：
  - 适用：任何"读取集合与判据分离"的工具 —— 邮箱/寄存器映射、日志字段解析、
    CSV 列、CI 门禁、监控指标名单。
  - 失效：按需读取（"要什么读什么"，没有名单）时不会踩这条，但会踩它的镜像问题
    （漏读一个字段）；此时同样要靠"打印每个闸门的输入"来抓。
- **来源**：2026-10-27。修复 commit `897b390`（"the reference gate could never pass
  (refq_state was not read)"），随后 `f77ea4e` 把这一类故障命名为 PLUMBING FAULT
  并加了守卫（`dl/host_qc/accept_range_selftest.py` 断言 `refq_state` 必须在
  `ROW_WORDS` 里）。

## 一条总结

> **一个不能失败的工具，和一个总是失败的工具，给你的信息量是一样的：零。**
>
> 所以每个诊断脚本至少要有一个"已知答案"用例：
> 纯色图、故意重叠、不存在的地址、已知的冻结场景。
> 如果它在那个用例上**没有**给出预期结果，先怀疑工具，不要怀疑板子。
