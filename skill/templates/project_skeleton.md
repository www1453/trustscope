# 模板 · 仓库骨架（含命名规则）

> **适用场景**：作品提交前的最后一周，或者一个新人接手仓库的第一天。
> 竞赛指南 `3.3.5.4` 给了推荐目录结构，并规定
> **"仓库内所有目录名与文件名须使用纯英文（小写字母、数字、下划线或连字符），
> 不得出现中文、空格或特殊字符"** —— **中文只出现在文件内容里**。
>
> **这份模板不是"建议的审美"**。它解决的是一个具体的失败：评审打开压缩包，
> 看到的第一眼是目录树；一个 `数据/` 或 `报告 最终版.docx` 会让人先怀疑整包。
> 而改名这件事，**越晚做越贵** —— 每个硬编码路径、每个脚本里的相对路径、
> 每份文档里的引用都要跟着改。

---

## 一、骨架

```
<project>/
├── README.md            一眼看懂：这是什么、怎么跑、证据在哪
├── src/                 源码（固件 / PS 程序 / RTL / HLS）
├── sim/                 仿真与离线回放（不需要硬件的部分）
├── build/               构建脚本与约束（XDC / lscript.ld / Makefile / .tcl）
├── board/               上板脚本与板上测量（xsdb / 上电时序 / 引脚核查）
├── data/                测出来的数据（csv / 采样 / 图像），带生成命令
├── skill/               可复用技能包（提示词 / 模板 / 校验脚本 / 踩坑清单）
├── report/              设计报告与图表（源码形式的 .md + 导出的 .docx/.pdf）
└── .gitignore           大体积产物不进版本库
```

**每个目录一条判据**（放不进去就说明它属于别处）：

| 目录 | 只放 | 判据 |
|---|---|---|
| `src/` | 会被编译的东西 | "删掉它，构建就失败" |
| `sim/` | **不需要硬件**就能跑的验证 | "在一台干净机器上能不能跑出结论" |
| `build/` | 约束、链接脚本、构建入口 | "别人拿它能重建出同样的产物吗" |
| `board/` | 只有接上板子才有意义的脚本 | "它会不会动硬件/写寄存器" |
| `data/` | **测出来的**数字与采样 | "这个数是怎么产生的、能不能重跑" |
| `skill/` | 换一个题目仍然能用的经验 | "陌生队伍能不能直接拿去用" |
| `report/` | 人读的文档 | "每个数字有没有指向它的来源" |

## 二、命名规则（机械执行，不靠自觉）

允许：`a-z` `0-9` `_` `-` `.`；不允许：中文、空格、括号、`#`、`&`、大写（大小写混用会导致
跨平台大小写不敏感文件系统的合并事故，所以统一小写）。

```bash
# 列出违规的路径（在任何 POSIX shell 里都能跑）
find . -path ./.git -prune -o -print | grep -nP '[^\x00-\x7F]| ' | head -50
```

**为什么不能只靠"提交前改一遍"**：

1. 路径会出现在**文件内容**里（脚本、文档、报告）。改名之后这些引用全部指向不存在的文件，
   而它们**不会报错** —— 只是一次 `open()` 失败，被上层 `except` 吞掉，看起来"没有数据"。
2. 路径会出现在**构建产物**里（调试符号、map 文件）。改名会让"逐字节重建"的判据失效。
3. 中文路径在**中文 Windows + Python + UTF-8 源文件**的组合下能工作，
   在**别人的英文 Windows / CI / 评审的 Linux** 上不一定 —— 而你只有一次提交机会。

**做法**：从第一天就用英文名；如果已经晚了，**先改名、再全仓扫一遍引用**，
用 `skill/scripts/leak_scan.py` 的路径扫描确认没有残留的个人绝对路径。

## 三、README.md 该写什么（五段，缺一段都不行）

```markdown
# <项目名>

## 这是什么
一句话 + 一张图/一张表。不要从背景讲起。

## 怎么跑
三条命令以内。每条都写出预期输出（"打印 RMS 0.137 px"比"运行脚本"强一百倍）。

## 证据在哪
| 结论 | 证据文件 | 怎么重跑 |
|---|---|---|
| 立体 RMS 0.137 px | data/calib_20261023.csv | python sim/calib_check.py <csv> |

## 已知的边界
不支持的场景、未验证的部分、被推翻过的结论（**保留撤回记录，不要删**）。

## 许可与致谢
```

**"已知的边界"这一节是本项目最强的一段**：一份写清了"什么没验证"的 README，
比一份什么都说"已完成"的 README 可信得多。评审读得出来区别。

## 四、常见错误（都真实发生过）

| 错误 | 后果 | 正确做法 |
|---|---|---|
| `报告/最终版/` | 打包工具、脚本、评审的解压工具各踩一次 | 全英文；版本用 `report/technical_report_20261027.docx` |
| `data/` 里放**生成脚本的输出**但不放脚本 | 数字无法复现，"数据"变成"断言" | 同目录放 `README.md` 写明生成命令，或直接放脚本 |
| `.gitignore` 漏了大体积产物 | 仓库变成 GB 级，clone 一次十分钟 | 按扩展名忽略（`*.bin` `*.dcp` `*.jou`），**并在 README 写明怎么重新生成** |
| 中文文件名"只是我自己看" | 它一定会进压缩包 | 见上 |
| 报告与仓库分家 | 报告里说 91 页、仓库里是旧版 | 报告源文件放 `report/`，导出件同目录，**用哈希核对两份一致** |
