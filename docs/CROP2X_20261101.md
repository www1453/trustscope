# 裁剪切换 2×（1:1 窗口）第三次尝试 · 2026-11-01 —— 负结果

> 一句话：**把裁剪做进模式表这条路也失败了**——640×360 与 1280×720 两种 1:1 几何从复位起
> **都不出流**，寄存器回读逐位正确，而同一次会话里原件表的控制组完全 live。至此 2× 放大
> 这条路线三次尝试（10-31 两次运行时改写 + 今天一次表内配置）**都没有拿到可用的流**，
> 应写进报告作为"未来工作"，不能宣称放大有效。

## 1. 做了什么

- 由 `ps_fft_dual\ov5640_table.txt`（303 条）生成变体 `ps_fft_dual\ov5640_table_crop2x.txt`：
  **303 条里 29 个值不同**，把最后一个窗口块（0-based 256..290）改成 **640×360、1:1、无抽取**。
  原件**未改动**（md5 `78EAF7111B9287698A492074F4AA4F2E`）。生成器 `dl\_crop2x_work\gen_table_crop2x.py`
  逐条断言旧值，防止改错行。
- 配套 bring-up `ps_fft_dual\bringup_crop2x_20261101.tcl`：照抄已验证的 `bringup_now_20261029.tcl`
  的顺序（ps7_init+post_config → FCLK_CLK0=50 MHz → 烧 PL → v_tc → 放复位 → 读 chip id →
  写表 → **回读断言** → arm 两个采集 VDMA → 64 s 存活性判定）。唯一实质改动：**VDMA 用
  360 行 × 1920 字节**（S2MM 按 H_SIZE 字节完成一行、按 TLAST 换行，行长度不对就永远完不成一行，
  这是 10-31 那次"停摆"的机制）。

## 2. 寄存器：29 个值及出处（没有一个数是猜的）

| 寄存器 | 原值 → 新值 | 出处 |
|---|---|---|
| 0x3820 / 0x3821 | 0x47/0x00 → **0x41/0x26** | Sonix 应用手册 p66-68「13.3.1 1080P」，仓库里唯一的 1:1 模式（0x3821 bit0=0 即不抽取） |
| 0x3814 / 0x3815 | 0x31/0x31 → **0x11/0x11** | 同上（X/Y 增量 1:1） |
| 0x3800/01, 0x3802/03 | 0x0000,0x00FA → **0x03D0(976), 0x0318(792)** | 窗口 = 输出 + 2×ISP 偏移，居中于 2624×1952；偏移取自 p67 的 0x3810/11=0x0010、0x3812/13=0x0004 |
| 0x3804/05, 0x3806/07 | 0x0A3F,0x06A9 → **0x066F(1647), 0x0487(1159)** | 同上（672×368 窗口） |
| 0x3808/09, 0x380A/0B | 0x0500,0x02D0 → **0x0280(640), 0x0168(360)** | 目标输出；p63 zoom 算式给出 (672-32)/640 = **1.0000**、 (368-8)/360 = **1.0000**，即精确 1:1 |
| 0x380C/0D (HTS) | 0x0764 → **0x04C4(1220)** | = 窗口宽 672 + 548（p67：2500 = 1952 + 548）；仓库自证的 1280×720 1:1 也是 1828 = 1280 + 548（`dl\MAGNIFY_PROBE_20261031.md`） |
| 0x380E/0F (VTS) | 0x02E4 → **0x04B0(1200)** | 本机既有值（固件 `SENSOR_VTS_TARGET`、10-31 那次 1:1 改写用的也是 1200）；帧期 1220×1200/25.6 MHz = 57 ms |
| 0x3618/0x3612/0x3709/0x370C | 00/29/52/03 → **04/2B/12/00** | p67（1080P 1:1 的模拟/时序配套）；与 10-31 的 1:1 改写同值 |
| 0x3A02/03, 0x3A14/15 | 0x02E0 → **0x04B0** | AEC 长曝光顶棚 = VTS（p67 同规则） |
| 0x4004 | 0x02 → **0x06** | p67 |

不动：0x3035/0x3036/0x3037/0x4837/0x460B/0x460C/0x3824/0x4001/0x3810..0x3813（沿用表内 720p 块；
10-31 的运行时 1:1 改写也没动它们）。

## 3. 上板实测（同一把尺子，三次）

| 次 | 传感器表 | 回读几何 | VDMA | 结果 |
|---|---|---|---|---|
| **控制组** | 原件（720p，2:1 抽取） | 窗口 x0..2623 y250..1705，out 1280×720，HTS 1892，VTS 740 | 720 × 3840 | **live**：303/303 两路写入，帧存 28/32、29/32 字在变，两次 dump 差 **53.94%**(cam0)/**45.51%**(cam1) |
| A | crop2x（640×360 1:1） | 窗口 x976..1647 y792..1159，out 640×360，HTS 1220，VTS 1200，0x3820/21=41/26，0x3814/15=11/11 **全部与写入一致** | 360 × 1920 | **无帧**：SR=0x00010000（无 IOC），arm 后 1.5 s 内两个帧存 **0/32** 字变化，探针 160 次采样 **0 次**帧指针跳变 |
| B | t1（**1280×720 1:1**，即 10-31 运行时裁剪的同一几何） | 窗口 x672..1951 y616..1335，out 1280×720，HTS 1828，VTS 1200，0x3820/21=41/26，inc 11/11 | 720 × 3840（**与 10-31 成功时相同**） | **同样无帧**：16 s 窗口内 0 次帧指针跳变、0/32 变化 |

→ **B 否掉了"窗口太小"这个解释**：不是尺寸问题，是"从复位起进入 1:1 模式"这件事本身不出流。

## 5. 采集是否保持 live（验收第一条）

- 控制组：**是**（上表，两条独立判据：帧存字节在变 + 帧指针在跳）。
- 裁剪组：**否**——从 arm 起就没有一帧完成，16 s 与 64 s 窗口都一样；**未出现"先 live 后停摆"**，
  是"从未开始"。
- 旁证：0x41200008 探针字在 crop 态只有 bit0/1/2/8 在变（高速计数器活着，PL 有时钟），
  **bit4（cam0 帧指针）与 bits[14:9]（cam1 帧指针）恒定**——所以不是 PL 死了，是没有数据。

## 6. 视野（验收第三条）

- **设计值**：640 个物理列 × 0.0244 mm/px = **15.6 mm** 横跨
  （0.0244 = 0.05 mm/px ÷ 2.05，即本机既有 0.05 mm/px 标尺与 2624 列阵列的关系）。
- **实测值：没有测到**，因为没有帧、没有图像，任何"视野"都只是寄存器算术，不是测量。**不得写成已验收。**
- 能做的旁证（用控制组图像量）：那块 PCB 在控制帧里 **538 px 宽 = 26.9 mm**（0.05 mm/px 标尺）；
  在 640 px 的 1:1 视场里它需要 **1102 px** → **装不下**，与验收预期"板子不再装得下"一致。
  另一个副作用：板心在控制帧 (572, 549)，而裁剪视场中心在 (640, 360)——**视场比板子高约 189 行**，
  即使出图，板子也大半在画面外；下次应把窗口整体下移（只改 0x3802/0x3803、0x3806/0x3807，其余不动）。

## 7. 今天被否证的假设（都留了证据）

1. **"窗口太小/ISP 不接受小窗口"** —— B 组用 1280×720（10-31 出过干净图的同一几何）同样无帧。
2. **"0x3816/0x3817 没写"**（10-31 的运行时脚本显式写过 0x11）——实测复位后读到 **0x00**，
   运行时写成 0x11 后**仍然 0 次帧指针跳变**。
3. **"表写失败/被静默忽略"** —— 40 个寄存器回读（含 0x3800..0x3817、0x3612/0x3618/0x3709/0x370C、
   0x3A02/0x3A14、0x4004、0x3035/0x3036/0x3037、0x4837、0x4300、0x5000/0x5001）逐位等于写入值。
4. **"VDMA 几何不匹配"** —— A 组已按传感器自报几何 arm（360×1920），仍无数据。

**仍然开放的一条**（唯一没来得及跑的一分钟实验）：把 S2MM 的 H_SIZE 缩到 192 B 再 arm，
若帧存开始变化，就说明"流其实在来，只是行长不是 1920/3840"。这条在交接时**没跑**（操作员在现场，
台面要被第二个实验用），所以"传感器到底有没有驱动 DVP"目前**没有直接证据**。

## 8. 对交付最重要的一句

**唯一曾在 2× 采样下出过干净图的条件，是 2026-10-31 在"传感器已经在出厂商模式的流"之后
用 29 个运行时写把它改成 1280×720 1:1**（`dl\MAGNIFY_PROBE_20261031.md` §4：行均值差 0.56、
无条带无重影）；而那次配置**随后把采集弄停了**，靠 `bringup_now_20261029.tcl` 救回。
今天证明：同样的寄存器值**从复位写进去就不出流**。也就是说这条路线缺的不是寄存器值，
而是**复位/出流顺序**（OV5640 内部从 1:1 配置起来需要一次 stream off/on 或等价的重新锁定）。
这是硬件通路的发现，可以诚实写进报告；**2× 放大目前不可用，应列为未来工作**。

## 9. 恢复（已执行，并验证）

顺序与结果（10:50:35–10:53:06）：
1. `ps_fft_dual\bringup_now_20261029.tcl` → 两路 303/303、帧存 28/32 与 30/32 在变、`=== DONE ===`
2. `ps_fft_dual\disp_fix_20261023.tcl` → CR=0x00010001、VSIZE 480、HSIZE/STRD 2400、ADDR1/2 正确
3. `ps_fft_dual\strict_load_cores.tcl` → 镜像下载并运行
4. 复核：0x41200008 bit4 **69 次跳变 / 400 次采样**、cam0 S2MM SR=0x00015810、邮箱 +40 帧计数 84→91/2 s。
   **台面已恢复为可用状态，锁已释放（10:53:06）。**
