# 硬件安全清单 · 来自 AN5642（双目相机模块）损毁事故

> 2026-09-24 整理。事故本身：AN5642 模块的 **PCB 上 +5V 走线烧断**，
> 代价 = 模块报废 + 返修往返 + 数天调试时间（误判为软件/时序问题）。
> 本文的目的只有一个：**下次接任何外部模块之前，先过一遍这张表。**

---

## 一、事故现象与推断（区分"已知"与"推断"）

**已知（实测）**
- 模块内部 **2.8V 轨测不到**
- 芯片 ID 读回 `0x00`（应为 `0x56/0x40`），302 条初始化寄存器写入全部失败
- `cmos_pclk` 完全不跳变
- 同一块板、同一根 I2C 总线上，**备用 OV2640 模块工作正常** → 板侧完好

**推断（未证实，标注清楚）**
> **烧断 +5V 走线 = 5V 轨过流**，典型原因是**短路**：
> 模块内部故障、焊接桥连、**反插**（J10 是 PIN1=GND / PIN2=+5V，反向插会把 +5V 直接接到 GND）、
> 或 ESD 打坏器件后形成短路。

**为什么不太可能是"IO 方向冲突"**
- J10/J11 每个 IO 都串了 **33Ω**，方向冲突通常先烧串阻或 IO，**不会烧电源走线**
- 电源走线上的电流由模块整体功耗决定，与 IO 方向无关

**教训**：把"烧电源线"和"烧 IO"当成两类不同的事故去查，不要混。

### 📌 2026-09-26 修订：官方引脚表到手后，对"上次怎么坏的"的更正

原记录把 **反插** 与"模块内部故障 / 焊接桥连 / ESD"并列，**没有给优先级**；
而我一度把"反插"当成**最可能**的机制 —— **那个说法证据不足，此处更正。**

**新到手的证据**：官方 `an5642.xdc` 完整引脚表（展开见 `dl/CAMERA_BRINGUP.md` §0.3）；
以及故障报告 §四第 9 条 —— "相机在**任何重新插拔之前**就已无法工作"。

**更正后：两个并列假设，暂不能定案。**

| 假设 | 内容 | 与证据的吻合度 |
|---|---|---|
| **H1** 模块内部电源树故障 | 模块从 **J10 PIN2** 取 5V，板载 LDO 链短路/失效 → 5V 过流烧走线 → 2.8V 轨死 → 无 PCLK、无 I2C 应答、SCCB 被拉到 1.7V | **一个机制解释全部现象**（含"板侧完好"） |
| **H2** 第一次插入时反插 / 错位 | 反插时：模块 PIN2(+5V)→J10 PIN1(GND) **纯短路**；模块 PIN40(+3.3V)→J10 PIN1(GND) **3.3V 直接对地**；模块 PIN39(+3.3V)→J10 PIN2(+5V) **5V 灌进 3.3V 轨** | **能解释烧 +5V 走线**；但解释不了"为何 3.3V 侧没一起坏" |

> **"排除重新插拔" ≠ "排除第一次就插反"**。如果第一次就是反的，它当然"从未工作过"。
> 所以 **H2 仍然活着**，不能划掉。

**判别测量（几分钟，能定案 —— 前提是坏模块还在手上）**：
- 坏模块的**物理损伤范围**：只有 +5V 路径受损 → 指向 **H1**；
  +5V 与 +3.3V 两侧都有损伤 → 指向 **H2**
- 坏模块**单独**（不插板）量 **模块 PIN2(+5V) ↔ 模块 PIN1(GND)**：
  ≈0Ω 且不回升 → 5V 入口死短

**不变的部分**：无论定案哪个，`dl/CAMERA_BRINGUP.md` §2 的六道闸门都要全过 ——
两套闸门本来就是为两个假设**各挡一半**。

## 二、接线前必须过的四项检查

| # | 检查 | 怎么做 | 不看会怎样 |
|---|---|---|---|
| **1** | **方向不能冲突** | 列出这条网上**所有**驱动源。任一时刻只能有一个输出。核心板配成输出的脚，底板上必须是被动/输入 | 两个输出对顶 → 大电流 → 烧 IO 或串阻 |
| **2** | **电压域一致** | 确认 BANK 电压（J10/J11 = **BANK35 = 3.3V**）与 XDC 里的 `LVCMOS33` 一致；模块的供电脚接的是 +5V 还是 +3.3V | 3.3V IO 接 5V 信号 → **打坏 FPGA 引脚**（LVCMOS33 不耐 5V） |
| **3** | **静态电流先量后接** | 用**限流电源**或串一个自恢复保险丝/限流电阻，先量模块静态电流 | 模块有缺陷时，烧的是板子 |
| **4** | **断电插拔 + 防静电** | 插拔先断电；接手腕带；不直接碰管脚 | ESD 打坏器件 → 短路 → 下次上电烧电源轨 |

## 三、本项目的具体隐患（2026-09-24 实际状态）

### ⚠️ 隐患 1：B20 ↔ V12 跳线在相机在位时必须拔掉

- 我们的应用**主动驱动 B20**（J10 PIN35），而且**即使"源关闭"也会把它拉低**
- 跳线把它连到 **V12 = J10 PIN28 = `cmos_d_0[0]`**，这是**相机的输出脚**、PL 的输入脚
- **相机一旦插上，PIN28 由相机驱动；此时我们的应用仍在驱动 B20 → 两个输出顶在同一根网上**

**动作**：相机到货后，第一步就是**拔掉这根跳线**。相机在位时那个引脚属于相机。
**当前状态（2026-09-25 实测）：该跳线已拔出，未插。**
- 未插 -> B20 上只有 PL 一个驱动源 -> **现在驱动它是安全的**
- **但隐患是条件性的**：现在没插 != 以后不会插；一旦有人插上且相机在位，立刻恢复为"两个输出对顶"
- **未插是唯一在有相机 / 无相机两种配置下都正确的状态** -> 不要为任何用途把它插回去
- 此前跳线在位期间**数据未被污染**（相机一直不在位 -> 单驱动源），已归档数据不需要作废
- 附带更正：不用 B20 当观测 LED 的真正理由是"**B20 是相机复位脚，不是板载 LED**"
  （当灯用 = 每切换一次就复位相机），不是"跳线导致双驱动"

### ⚠️ 隐患 2：LVCMOS33 引脚不耐 5V

之前讨论过用 USB-TTL 适配器接 J10/J11 引脚测串口。
**若该适配器是 5V 电平，直接接上去会打坏 FPGA IO。**
必须用 **3.3V 适配器**，或加电平转换。

### ⚠️ 隐患 3：相机由 J10 PIN2 的 +5V 供电

双目模块功耗可能不小。**建议先限流测量，再直接接板。**

### 2026-10-03（第四场）· AEC 瞄准点扫描：一个**被测量推翻的假设**

**问题**：画面里一出现亮窗就整幅过曝、发蓝。

**先读寄存器**（`ps_camsense.tcl`，先确认 I2C 能复现已知 chip ID `0x56 0x40`）：
```
0x3503 = 0x00         AEC/AGC 自动——一直是开着的
0x3500..02 = 10656    = 666 行；0x3A02/03 = 0x02E0 = 736 行（50Hz 防闪上限）
0x3400..05            AWB 工作增益，两次读数之间就变了 => 在持续自适应
```
**翻 303 条表发现更重要的事**：表里配了 **23 条 AEC/AGC 算法寄存器（0x3A00..0x3A1F）**，
而**从未写过曝光或增益的手动值**（`0x3500..0x350B` 只有 `0x3503=0x00`）。
所以**传感器自己的 AEC 一直在跑** —— 上次"传感器 AEC 不驱动曝光"的结论
是**在天花板上测出来的假象**（一个正常工作的 AEC 在极限处看起来也是不动的）。

**假设**：AEC 按**帧平均**优化，所以它会牺牲高光。那就把它的**瞄准点**压低。
机制听起来很硬，于是做了一次**受控扫描**（`ps_aec_sweep.tcl`）：
先验 chip ID，**断言采集在出帧**（否则 dump 是死图），5 个瞄准点各等 3 秒收敛、
读回曝光寄存器、dump 原始帧，**末尾再测一次基线**证明场景没漂。

```
  瞄准点            曝光寄存器        黑削顶    白削顶
  0x30/0x28(默认)   10656 (666行)     7.5%     12.6%
  0x28/0x20         10656 (666行)    19.2%      9.4%
  0x20/0x18          5328 (333行)    33.4%      8.1%
  0x18/0x10          1776 (111行)    50.2%      4.6%
  0x38/0x30         10656 (666行)     2.4%     14.1%
  恢复默认           10656           7.8%     12.3%   <- 场景没漂，实验有效
```

**"瞄准点是有效控制"这一半完美成立**（曝光从 666 行一路降到 111 行，6 倍）。
**但按它去调，画面明显变差**：白削顶是降了，代价是**1/3 到 1/2 的画面被压成黑**，
而且那个窗口**依然是过曝的** —— 因为它是**物理上超出传感器**，不是瞄准点不对。
把图调出来看，`0x20/0x18` 那张里主体几乎看不见。

**结论（与最初的假设相反）**：**默认瞄准点已经接近最优**；过曝是动态范围问题
（阳光窗 vs 室内约 1000:1），不是自动曝光瞄歪了。**没有可调的余地了。**

**留下的工具**：`ps_aeaim.tcl` 可以把瞄准点显式设为 `default | hl | shadow`
（默认值 = 厂商表值），让"曝光响应"成为**每台机器的显式记录**而不是厂商表的偶然。
实测值已写进脚本注释，避免下次又靠"机制听起来合理"去猜。

**对"手机那样"的诚实回答**：手机好看是因为**多帧 HDR**，这颗传感器没有。
唯一能做到的路线是**时间维 bracketing**（长短曝光交替 + 融合），代价是帧率减半。
真正有效且便宜的仍然是**视野里不要有强光源**（遮光罩 / 换朝向 / 受控照明）。

**隐患 1 检查结论**：本场没有任何物理操作（全部 JTAG + I2C）。跳线状态与上场相同，
**本场同样没有、也无法目视确认**。

**厂商设计是否已恢复**：未改 BD、未重新综合。**相机寄存器已恢复厂商表默认值**
（`0x3A0F/0x3A10 = 0x30/0x28`、`0x3A1B/0x3A1E = 0x30/0x26`、`0x3503 = 0x00`、曝光 10656，
由 `ps_aeaim.tcl default` 读取确认）。


### 2026-10-03（第三场）· 画面"发灰"的根因：**把相邻字节当成相邻像素去平均**

**起因**：用户对比"屏幕上的画面"和"手机拍的同一场景"，问能不能做成手机那样。

**先做的事：把两件事分开。**
用户给的两张图**都是照片**。拿"拍屏幕的照片"去和"手机照片"比，
比的是两次拍照，不是我们的链路 —— 拍 LCD 本身会加色偏和丢对比度。
所以直接 dump **我们真正写进帧缓冲的像素**（经 JTAG），和手机照片比统计量。
`ps_ui/compare_looks.py` 就是干这个的。

第一次的结论**是错的**，而且错法值得记：
- 帧缓冲 R/G 0.943、B/G 0.942（中性），拍屏幕的照片 R/G 0.601、B/G 1.224（很蓝）
  → 蓝色不在我们的数据里，是 LCD 白点 + 拍照。**这一条是对的。**
- "我们的采集把室内暖光中和掉了" → **这一条是错的**：
  两次测量隔了几分钟，**房间光照变了**，场景本身移动的幅度比色调曲线还大。

**改用受控实验**：`ps_rawcam.tcl` 把**原始采集缓冲**整块 dump 下来（2764800 字节），
之后所有候选曲线都在**同一帧**上离线算（`ps_ui/tune_tone.py`）。
这才叫实验。

**受控实验立刻推翻了自己的结论**：原始采集 R/G 1.130、B/G 1.095，
手机拍同房间 1.115 / 0.931 —— **采集本来就是暖的**，没有"中和掉暖光"这回事。

**然后用逐字节判据找到了真根因。**
`ps_lutcheck.tcl` 停掉采集让 PS 反复渲染同一帧，同时 dump
**原始缓冲**和**渲染后的 UI**，在主机上按正确算式重算并**逐字节比对**：
```
  按正确算式：输出字节应为 136
  PS 实际写入：123          <- 不一致
  修好后：691200 字节，0 处不符
```
根因：`draw_camera()` 的 2×2 均值滤波写成了对**线性字节数组里相邻的两个字节**
求平均 —— 也就是**两个不同的颜色通道**（B 和 G、R 和 B…），
而不是同一通道的两个像素：
```
  错： o[c]   = avg(s[c*2],   s[c*2+1])
  对： o[P*3+ch] = avg(s[6P+ch], s[6P+3+ch])
```
于是每个输出字节都是两个通道的混合，整幅画面被拉向局部平均 ——
**结构完全正确、只是去饱和、发灰**。这正是"看着还行但就是不对"的样子，
也解释了为什么它能活这么久：**它没有任何视觉上的荒谬**。

**实测改善**（同一冻结帧）：
```
  修复前  luma sd 41.0    修复后  sd 64.0    手机拍同房间 sd 68.0
  色相    R/G 1.130  B/G 1.095  ->  加 0.92 蓝增益后 B/G 0.999
  削顶    0.00% / 0.00%
```
**并且：之前为了"发灰"调出来的色调曲线（levels + S 曲线）修完后全部不需要了** ——
那一帧本身已经占满 9.8..250.3，再拉伸只会压黑 3.4%、过曝 6.7%。
**修了根因，辅助手段要跟着撤掉**，否则它会把真正的问题掩盖得更深。
现在只保留一条极小的蓝通道校正。

**性能**：顺带把内层循环展开，渲染 **21.6 ~ 22.0 fps**（之前 19.6），
`faultcode = 0`。相机区域两张 dump 变化 88.3%（实时）。

**自己踩的坑（已记入案例卷 T26）**：`ps_lutcheck.tcl` 为了冻结采集先停掉它，
dump 完**只写了一次 `CR = RUNSTOP`** 去恢复 —— 又是那条 VDMA 顺序规则，
**通道报告正常但一个像素都不再更新**。之后 PS 一直在渲染同一张冻结帧。
暴露它的是那条**独立判据**："两张相隔 1.5 秒的 dump 相机区域应变化约 88%"，实测 0.0%。
**副作用是诊断脚本自己造成的，而且不报错。** 已修成按完整序列重新 arm。

**隐患 1 检查结论**：本场同样**没有任何物理操作**（全部 JTAG 脚本）。
跳线状态与上场相同，**本场同样没有、也无法目视确认**。

**厂商设计是否已恢复**：未改动 BD、未重新综合。板上仍是 `design_1_wrapper_cdcfix_50m.bit`。


### 2026-10-03（下半场）· 渲染 2.87 → **19.6 fps**、CDC 违规清零、显示翻转第一次真正生效

**这次做了什么**：三件用户指定的/发现的事，都在板上验证过。

**（1）开 MMU + D-cache：渲染 2.87 fps → 19.60 fps（6.8×）**

之前 MMU 与 D-cache 全关，每次访问都是强序、各自一次 AXI 事务。
`draw_camera()` 每帧读 2.76 MB 采集帧、写 1.15 MB 显示帧，全是一个 32 位访问一次。

先测清楚再写代码（这一步很关键）：
```
  L2C-310 @0xF8F02000  Cache ID = 0x410000C8（控制器在）
                       Control  = 0x00000000 -> bit0=0，**L2 是关的**
```
所以只有 L1 会开，**L1 的维护就够**（`DCIMVAC`/`DCCMVAC` 能到内存）。
如果 L2 是开的，L1 操作只到 L2 为止，还必须额外编程 L2C-310 寄存器 —— 那是完全不同的实现。
**这个测量决定了整个方案，猜错就是"画面冻住"。**

一致性义务（VDMA 走中央互联，**不侦听 CPU 缓存**）：

| 区域 | 谁写谁读 | 处理 |
|---|---|---|
| 采集帧存 | VDMA 写 / CPU 读 | 读前 `dcache_invalidate` —— 否则**画面冻住** |
| 显示帧存 | CPU 写 / VDMA 读 | 翻转前 `dcache_clean` —— 否则面板显示上一帧 |
| mailbox | 主机经 JTAG 写 / CPU 读 | 该 1 MB **映射为不可缓存**（缓存维护对它无效） |

`mmu.c` 用 1 MB 段描述符建表（16 KB 表放在 OCM `0x20000`，链接脚本已预留并做重叠断言）。
**未映射的地址就是转换故障** —— 报错点名地址，比静默读垃圾好。

实测：`SCTLR = 0x08C5107D`（bit0 M / bit2 C / bit12 I 全置），
**帧率 8 秒窗口 19.60 fps**；相机区域两张 dump 变化 **92.4%**（实时，没冻住）。

**（2）CDC"违规"其实全是 ILA 探针 —— 没有用 `set_clock_groups` 抹掉**

先读报告，不先改约束。100 MHz 那份 `timing_summary_routed.rpt`：

```
clk_fpga_1 -> clk_fpga_0   WNS -3.792  TNS -29.155   9 个端点失败
clk_fpga_0 -> clk_fpga_1   WNS  8.835  TNS   0.000   0 个失败
Requirement: 0.010ns  (clk_fpga_0 rise@550.000 - clk_fpga_1 rise@549.990)
```

**9 条全部终止于 `capture_ram_0/inst/mem_reg_*/DIADI[*]` —— 调试捕获 RAM 的数据输入**，
源信号正是当初查显示链路时在探的那些（`v_tc_0` 的 hsync/vsync/active_video、
`v_axi4s_vid_out_0/locked`、`rst_33M`、`axi_vdma_1` 内部）。
那一对时钟里**唯一不是探针**的路径在 `v_tc_0` 内部（`SYNC2PROCCLK_I/data_sync_reg`），**它是满足时序的**。
而且这条失败的组要求是 **0.010 ns** —— 两时钟同周期、偏斜 10 ps，**结构上就不可能满足**。

**为什么不用 `set_clock_groups -asynchronous`**：那会把两个时钟对**整个设计**声明为无关，
连带把 42 条**当前满足时序**的 `clk_fpga_0 -> clk_fpga_1` 实用路径和上面那个 v_tc 同步器一起丢掉 ——
那些是真的、同源（同一个 PS PLL）、它们的时序裕量是有意义的证据。
所以改成**只对调试探针的数据输入加 `set_false_path`**，精确到 `capture_ram_0` 的 `DIADI/DIBDI`。

重综合（50 MHz，`cdcfix_build.tcl`）实测：
```
  clk_fpga_0 period=20.000ns 50.000MHz | clk_fpga_1 period=30.555ns 32.728MHz
  violated paths: 0   ->  TIMING CLOSED: no violated paths at all
  bitstream -> design_1_wrapper_cdcfix_50m.bit
  ps7_init -> ps7_init_cdcfix_50m.tcl
```
**WNS 从 −4.08 变成全满足，0 条违规。**（脚本会自己读回报告并断言，不是只看 "Complete!"。）

**（3）显示"翻转"从来就没生效过 —— 面板其实一直停在帧存 0**

`ps_crbit.tcl` 直接测：
```
  wrote bit8 SET (0x00010103) -> read 0x00010003  bit8=0
  wrote bit8 CLEAR(0x00010003) -> read 0x00010003  bit8=0
  => bit 8 根本不存储
```
PS 每帧写的 `0x00010003 | (target << 8)` 是**空操作**。
而 `DIS CR = 0x00010003` 的 **bit1 = Circular_Park = 1 是 park 模式**，配合
`PARK_PTR = 0` —— **面板一直停在帧存 0**：
渲染器有一半时间在写正在被扫描的缓冲（撕裂），另一半工作从来没显示过。

**"推断自可用代码"这个说法在这里是骗人的**：那条映射从来没被单独测过。
正确机制是 park 模式 + `PARK_PTR`（实测可写：写 `0x107` 读回 `0x07`，写 `0x01` 读回 `0x01`）。
改成每帧 `PARK_PTR = target`（park 切换在帧边界生效，正好是干净的翻转，
而且 `axi_vdma_1` **没有** `frame_ptr_out` 接到任何地方，所以这是唯一不需要改 BD 的办法）。

实测验证（`ps_parkwatch.tcl`）：
```
  120 次采样/4.36 秒；park index 见到 0 和 1；翻转 84 次
  PS frames 900 -> 985（窗口内 19.51 fps）
  => 翻转是真的，而且和渲染帧率同步
```
并且 `ps_shot.tcl` 现在按 `PARK_PTR` dump **正在被扫描**的那一块，**两次采样都是完整帧**（面板 6 色 / 底栏 5 色），
从来没有抓到画到一半的缓冲。

**（4）顺带挖出一个"只会在重新下载时才出现"的坑：开缓存后程序不能靠 JTAG 重启**

改完之后出现**非确定性**的数据中止：同一份镜像，每次跑死在不同的 PC，
寄存器里还出现反汇编上**不可能存在**的值
（`r5 = 0x08C5107E`，而 `movt r3, #0` 保证 r3 < 0x10000）。

排查方式（都是先量再下结论）：
- dump OCM 里的代码，**逐字和 ELF 比对 —— 完全一致**，所以不是镜像被改坏；
- 逐个反汇编所有被调用的函数，**没有一个破坏 r4-r11**；
- 于是只剩一个解释：**CPU 执行的不是内存里的指令**。

根因：**`dow -data` + `con` 不会复位 Cortex-A9**。缓存和 MMU 完全保持**上一次运行**留下的状态。
一旦本程序开过 D-cache，上次就留下了**脏行**，而且 I-cache 里是**上一版镜像的指令**：
- 脏行迟早被替换写回，盖在新下载的镜像上；
- 取指命中陈旧的 I-cache 行，CPU 执行的不是刚加载的代码。

修法：`startup.S` 的 `_start` **第一件事**就是把状态复位到上电无异 ——
关 C/I、按 set/way 作废整个 D-cache（**丢弃脏行而不是写回**）、作废 I-cache/TLB、关 MMU。
之后 `dow` + `con` 重新变得可靠。修完实测 `faultcode = 0`、`fault_row = 0`。

**隐患 1（B20 ↔ V12 跳线）检查结论**：本次会话仍然**没有任何物理操作**，
全部是 JTAG 脚本（`xsdb` + 一次 Vivado batch 重综合，两者都不碰板子的电源和跳线）。
`rst -system` 是 SoC 复位，不等于物理断电。跳线状态与上次会话结束时相同，
**这次同样没有、也无法目视确认**，下次有人上板时应重新确认。

**厂商设计是否已恢复**：**没有改 BD**。这次唯一的硬件侧改动是在 `two_fft.xdc`（仓库内文件，
工程直接引用它）追加了一段 `set_false_path`，然后重综合了一次。
板上现在跑的是 `design_1_wrapper_cdcfix_50m.bit`（新版），
旧的 `design_1_wrapper_bitpair_50m.bit` 完整保留，`GOOD_20260927_bitpair/` 仍是回退点。

**尚未做 / 未验证**：
- 相机仍是 RGB565（65536 色），RGB888 转换仍未做（优先级最低）。
- 采集 ~16 fps，PS 渲染 19.6 fps，两者无同步关系（渲染快于采集，会重复读同一帧，无害）。
- 本次**没有**用 `ps7_init_cdcfix_50m.tcl` 跑过完整冷启动流程；`live14_bitpair.tcl` 仍指向
  旧比特流。要换成新比特流需要同步更新 `live14_bitpair.tcl` 与 `RESTORE.md` 的引用。


### 2026-10-03 · ⛔ **OCM 不是 256 KB，是 192 KB** —— 一个链接脚本里的内存假设，让 PS 程序一条自己的指令都没跑

**这次做了什么**：把 `ps_ui/`（裸机 PS 状态屏：左边 DISP 里的相机画面，
右边一列状态）编出来，用新写的 `ps_fft_dual/ps_run.tcl` 通过 JTAG 加载到 OCM
并运行。用的是当时板子上已经在跑的 `design_1_wrapper_bitpair_50m.bit`，
**没有重新配置 PL**（只做了 `dow -data` + `con`）。捕获通道被停掉
（`CAP SR = 0x00015811`，Halted 位在），显示通道指向 UI_A/UI_B。

**结果：程序数据中止（data abort），而且是在它自己的第一行代码上。**
判据来自程序自己写进 mailbox 的寄存器快照：

```
faultcode   = 0x11111104      数据中止
DFSR        = 0x00001808      同步外部中止（external abort）、且是写
DFAR        = 0x0003FFDC      出错地址
faulting_PC = 0x000004A8      = `push {r4-r9, sl, fp, lr}`
fault_row   = 1               处理器只跑了一次
SPSR        = 0x600000D3      被中断的是 SVC 模式
```

反汇编确认 `0x4A8` 就是 `main_loop` 的第一条指令：
`push {r4-r9,sl,fp,lr}` 把 SP 从 `__stack_top = 0x00040000` 往下压 36 字节，
第一个写入正好落在 **0x0003FFDC**，和 DFAR 完全对上。
也就是说程序**还没执行到任何一行自己的逻辑就已经死了**，
而表现出来的现象只是"帧计数器不动"。

**根因：`lscript.ld` 把 OCM 当成 256 KB（`0x00000000..0x0003FFFF`），
实际可用只有 192 KB。** 用 `ps_fft_dual/ps_ocm.tcl` 写一个图样再读回来，
逐点量出来的边界（不是查手册，是自己测的）：

| 地址范围 | 实测结果 |
|---|---|
| `0x00000000 .. 0x0002FFFF` | 写进去读得回来 —— **192 KB 可用** |
| `0x00030000 .. 0x0003FFFF` | 读回 `0xFFFFFFFF` —— **根本没有译码** |
| `0xFFFF0000 .. 0xFFFFFFFF` | 写进去读得回来 —— 另有 **64 KB** |

边界是精确的：`0x0002FFF0` 正常，`0x00030000` 就没了。
`ps_ocm2.tcl` 又验了一次：写在 `0x00008000` 的内容**不会**出现在
`0xFFFF8000`，所以 `0xFFFF0000` 那 64 KB 跟低 192 KB 是两块独立的内存，
总数仍然是 256 KB，只是**不在文档暗示的位置上**。
（补充：`ps7_init_50m.tcl` 里没有任何 OCM 相关配置写入，所以不是初始化改的。）

**修法**：`lscript.ld` 的 `ocm` 改成 `ORIGIN = 0x00000000, LENGTH = 0x0002F000`，
栈区改成 `0x0002F000..0x0002FFFF`，`__stack_top = 0x00030000`。
现在第一次压栈写 `0x0002FFFC`，落在可用区内。
（这个修法**还没有在板上验证过** —— 见下面"本次会话的结局"。）

**这次一并修掉的另外两个真问题**（都不是猜的，是量出来的）：

1. **板上跑的是过期二进制。** `build.ps1` 只产出 `.elf`，
   真正被 `dow -data` 送进去的 `ps_ui.bin` 是**手工生成的**，已经旧了两版
   （8064 字节，而当时的 `.text + .data` 早就是 8199 字节了）。
   也就是说：板子执行的代码和我正在读的源码**根本不是同一份**。
   这正是前面两轮 `DFSR/DFAR` 读出垃圾值的原因 —— 那个 handler 是旧版的。
   修法：`build.ps1` 现在自己跑 `objcopy`，并且**独立校验**
   `.bin` 长度必须等于最后一个可加载段的结束地址，不等就直接报错。
2. **加载校验本身烂掉了。** 老脚本 `run_ps_ui.tcl` 拿三个**写死的机器码**
   （`0xE59FD020` 等）去比对内存，那是某一次构建的值，之后每次构建都是错的。
   现在改成**拿刚生成的 `.bin` 逐字和内存比对**，永远不会过期 ——
   本次会话实测 `verified 8200 bytes against the file: 0 mismatching words`。

**会话中途板子失去响应 —— 但 `rst -system` 就救回来了，不需要人动手。**
中途读到：

```
TARGETS:   1  DAP (AHB AP transaction error, DAP status 0x30000021)
JTAG:      1  Digilent JTAG-HS1 210512180081
```

JTAG 线还在，但**只剩下 DAP，Cortex-A9 两个核都不见了**，且 AHB-AP 报事务错误；
再读 OCM / DDR / PL 全部是 `0xFFFFFFFF`。

**注意这里差点下错结论。** 当时判断是"PS 没有时钟 / 处于复位，需要人断电重新上电"——
但按纪律先试了一次脚本（`ps_fft_dual/ps_recover.tcl`）：`disconnect` → `connect`
→ `rst -system`，第一次就恢复了，目标树重新出现 `1 APU / 2 Cortex-A9 #0 / 3 #1`，
`0xF8006078`（DDR 控制器）也能读了。
之后 `live14_bitpair.tcl` 一次跑通（`chip id = 0x56`、`table ok=303`）。
**"需要人断电"这个结论是错的** —— 代价只是多写了一个脚本，
而如果直接叫人过来断电，就永远不知道 `rst -system` 就够了。
（第一次 `live14_bitpair.tcl` 里的 `ps7_init` 确实在同一地址失败过一次，
原因是复位后 DAP 还没稳定；隔一次重跑就好了 —— 所以这种失败**值得重试一次再下结论**。）

**修法验证通过（这次是真的在板上跑通了）：**

```
  DIS CR = 0x00010003                                  <- PL 在
  verified 8200 bytes against the file: 0 mismatching words
  t=600ms prog=2 frames=1 ... t=6000ms prog=2 frames=19  <- 帧计数器在涨
  faultcode = 0x00000000  fault_row = 0x00000000        <- 没有任何异常
```

进度信标一直停在 `prog=2`（= 正在画相机），说明**这一帧的时间全花在 `draw_camera`** 上，
和后面实测的 3.0 fps 对得上。把缓冲区 dump 出来渲染成 PNG，
画面正确：左边实时相机（颜色自然），右边状态栏
判定/不合格（红条）、总数 000137、合格率 095.60、报警、成像质量（曝光 064 / 对比度 081），
底部"实时 相机 / CAM_BUF / SEQ"。

**实测渲染帧率 = 3.00 fps**（主机时钟测：101 → 125 帧 / 8.01 s），
由 `ps_fft_dual/ps_fps.tcl` 写回 mailbox +28，面板随即显示"帧率 03.0" ——
**"主机测量 → 写 mailbox → PS 读取 → 显示"这条回路是通的**。
（限制：这 3 fps 是**未开 D-cache、强序访问 DDR** 的结果，
瓶颈在 `draw_camera` 逐字读相机缓冲，不在面板。）

**期间又抓到一个真 bug（肉眼看不见的那种）：面板背景不是纯色，是四种等量颜色。**
`fillrect_fast()` 拿一个 32 位字去填 3 字节/像素的帧缓冲。
`gcd(3,4)=1`，所以每个字都比上一个**多走一个字节的像素相位**，
于是"纯色"填充产出四种颜色，只有一种是对的（76800 像素里
16992/16392/16386/16318）。实测某一行：
`x=644 1e160a | x=645 001e16 | x=646 0a001e | x=647 160a00 | x=648 1e160a`。
**一个常量字永远填不出均匀颜色。**
修法：改用 **12 字节（4 像素 = 3 个字）循环图案**，12 同时是 3 和 4 的倍数。
修完背景从"四色各约 16.4k"变成"**单色 66088**"。
（顺带：渲染图里那条"斜线"在内存里**根本不存在**，是 4 像素周期竖条纹
被缩放显示时的摩尔纹 —— 先量像素再去"修"它，否则会去修一个不存在的东西。）

**又把"VDMA 顺序规则"踩了一次 —— 而且这次的症状是"通道一切正常，就是不产出"。**

要让面板显示**实时**画面（而不是冻结的一帧），采集通道必须真的在跑。
实测发现：`CAP CR = 0x00010003`（running）、`SR = 0x00015810`（看起来什么都在），
但**两个帧存 4.8 秒内逐字节完全相同，`axi_gpio_0` bit4（`s2mm_frame_ptr_out[0]`）从不翻转** ——
也就是说采集通道**一个像素都没写**。

根因：之前的 `ps_run.tcl` 曾经把采集停掉（那时是故意的，为了让 PS 复制一帧静止画面），
后来改成"只写一次 `CR = RUNSTOP`"把它启起来。
**只写 CR 就是那条规则里的禁区**：

```
几何 / 地址  ->  CR = RUNSTOP  ->  VSIZE 最后
```

`ps_capture.tcl` 用 `live14_bitpair.tcl` 里**已经验证过的那一段原样重发**
（注意采集通道用 `0xA0-0xB0` 寄存器块，显示通道用 `0x50-0x60`，这个不对称是实测的、不是笔误），
重发后实测：

```
  frame pointer values seen: 0 1   transitions: 32 over 2 s
  CAPTURE IS LIVE: ~16.0 frames/s
```

**这个坑的教训在于"怎么判定它没在跑"**：光看 CR/SR 永远看不出来，
光看渲染出来的画面也看不出来（静物场景和冻结帧长得一样）。
唯一可靠的是**数帧指针的翻转次数** —— 所以 `ps_capture.tcl` 自带这个测量，
`ps_cam.tcl` 则直接对比两个帧存的像素。
同理，`ps_shot.tcl` 现在会**隔 1.5 秒 dump 两次**：单张快照无法区分"静止"和"冻结"，
两张一比就可以（实测相机区域 **88.2% 像素发生变化**，面板/底栏 0.0%，符合预期）。

**面板全黑 —— 根因是"一直在量我能量的那一端"（本次最贵的一条）**

用户反馈"板子上什么也没看到"。而那一刻我手上握着一整套**证明缓冲区正确**的证据：
dump 出来的帧、PNG、颜色统计、填充图案检查、88% 像素变化率 ——
**每一条都是对的，画面也确实是"正确的一帧"，但面板上什么都没有。**
因为我从头到尾**没有量过显示通道**，只量了它读的那块内存。

根因有两条，都属于"看起来没问题的失败"：

**（1）显示通道的寄存器块写错了地址。** 用 `ps_regs.tcl` 把两个 VDMA 的整个寄存器块
（`0x00`–`0xBF`）dump 出来，拿已知值去认领，结果一目了然：

| | MM2S（memory→stream，**显示**） | S2MM（stream→memory，**采集**） |
|---|---|---|
| CR | `0x00` ✅ | `0x30` |
| SR | `0x04` ✅ | `0x34` |
| VSIZE | `0x50` ✅ | `0xA0` |
| HSIZE / STRIDE | `0x54` / `0x58` ✅ | `0xA4` / `0xA8` |
| ADDR1 / ADDR2 | `0x5C` / `0x60` ✅ | `0xAC` / `0xB0` |

`axi_vdma_1`（显示）只实现了 MM2S，而 `run_ps_ui.tcl` 把 `CR` 写到 `0x30`、
`VSIZE` 写到 `0xA0` —— 那两个地址对 `axi_vdma_1` **读回来全是 0x00000000**，
写入石沉大海，**不报错、不置位、不影响任何状态位**。

**（2）VDMA 顺序规则，第二次踩（这次是显示侧）。** 老的 `ps_run.tcl` 先把显示通道
**停掉**（写 `CR = 0`），之后唯一把它启起来的是 PS 程序每帧写的 `CR = RUNSTOP` ——
**一个寄存器、没有 VSIZE**。于是通道报告 `Halted = 0`（"没停机"）却**一个拍都不出**。
**"没有停机"和"正在出拍"是两件事。**

修法与判据：
```
  重新按 MM2S 地址 arm：几何/地址 -> CR=RUNSTOP -> VSIZE(0x50) 最后
  修前：DIS SR = 0x00010000
  修后：DIS SR = 0x00011000   <- bit12(IOC_Irq) 在清过状态之后又置起来了
```
**bit12 是新证据**：清过 SR 之后它又出现，说明**真的完成了一次传输**；
而 `Halted=0` 只能说明"没停"。现在 `ps_run.tcl` 会在 `SR` bit0 为 1（停机）时
直接打印 `*** DIS reports HALTED`，不再让人靠"缓冲区是对的"去推断面板。

**（3）引擎的数字接到面板上了。** 之前面板上的"总数 000137 / 合格率 095.60"
是**种子数据** —— 种子数据和真数据在屏幕上一模一样，所以演示很容易变成谎言。
现在通了整条回路：

```
  引擎(app/server.py, :8099) -> HTTP /api/state -> app/board_push.py
    -> ps_fft_dual/mailbox.txt -> ps_fft_dual/board_push.tcl(JTAG 常驻转发)
    -> DDR mailbox(0x10F00000) -> PS 每帧读取 -> 面板
```
两条跳的原因：PC 不能直接写 DDR（只有 JTAG 能），而每次调用一次 xsdb 要好几秒，
所以慢的那一段（JTAG）做成常驻循环，快的那一段（HTTP）放在 Python 里。
`board_push.tcl` **只写主机拥有的偏移（0..36）**，绝不写 +40/+44
（PS 自己的帧计数和进度信标）—— 否则 PS 就再也无法自证在运行了。

#### 同日最终 · ⭐ **根因找到：不是硬件故障，是 `sensor_init()` 漏了延时**

**我上一条关于"供电轨缺失 / 晶振"的判断被推翻了。** 相机供电正常、晶振正常、模块完好。

**证据链**
1. 在 XSCT 里用 PS I2C0（复用应用配好的除数）实现寄存器级读写，
   确认 **`0x300A/0x300B = 0x56/0x40`** —— OV5640 确实在，且应答正常。
2. 把传感器当前寄存器**逐条与厂商 `ov5640.c` 的表对比** —— **配置只应用了一半**：

   | 寄存器 | 厂商表 | 实测 | 说明 |
   |---|---|---|---|
   | 0x3008 | 0x02 | 0x02 | ✓ |
   | 0x3034 | 0x1A | 0x1A | ✓ |
   | 0x3036 | 0x69 | 0x69 | ✓ |
   | **0x3035** | **0x21** | **0x11** | ✗ **PLL 控制** |
   | **0x3037** | **0x13** | **0x03** | ✗ **PLL 分频** |
   | **0x3808** | **0x05** (1280) | **0x0A** | ✗ 上电默认值 |
   | **0x380A** | **0x02** (720) | **0x07** | ✗ 上电默认值 |
   | **0x4300** | **0x60** (RGB565) | **0xF8** | ✗ |

   **`0x3035/0x3037` 正是 PLL 配置寄存器** —— 所以 PLL 没被正确配置，
   传感器自然不产生有效的像素时钟。

3. **机制**：厂商 `sensor_init()` 不检查任何写入状态（其自身注释即写明"永远返回 0"），

   → 配置半应用 → 无有效视频输出。**这不是硬件缺陷，是厂商驱动的缺陷。**

**修正与验证（XSCT 闭环）**

  （0x3035→0x21、0x3037→0x13、0x3808→0x05、0x380A→0x02、0x4300→0x60 …）

**⭐ 结果：相机出图了**

- 转成 PNG：**`ps_fft_dual\cam_frame.png` / `cam_frame_bright.png` / `cam_frame_swap.png`**

#### 缺陷 4：ALINX IP **内部自己延时 3 亿个 PCLK** 才让数据出 FIFO（**已实测证实**）

源码 `23_ov5640_dual/Vivado/two FFT/two FFT.gen/sources_1/bd/design_1/ipshared/59bb/src/alinx_ov5640.v`：

```verilog
always@(posedge cmos_pclk)                       // 第 54-65 行
  if(reset_cnt < 32'd200_000_000) begin reset_cnt<=reset_cnt+1; cmos_aresetn<=1'b0; end
  else                                  cmos_aresetn<=1'b1;
always@(posedge cmos_pclk)                       // 第 67-83 行
  ... fifo_ready_cnt < 32'd100_000_000 ... fifo_ready <= 1'b1;
wire s_axis_tvalid = cmos_href_16bit_d1 & cmos_hblank_d1 & s_axis_tready;   // 第 41 行
wr_en = s_axis_tvalid & fifo_ready;                                          // 第 188 行
assign m_axis_video_tvalid = ~empty & m_axis_video_tready;                   // 第 162 行
```

- `cmos_aresetn` 由 **PCLK 自己**计数 2 亿拍才释放，之后还要再数 1 亿拍 `fifo_ready` 才置起；
  合计 **3 亿拍 ≈ 4 s（74.25 MHz）**。**比特流加载后必须让 PCLK 自己跑满这段时间。**
- 之前每次测试都在推表后 1–3 s 就读 probe → `tvalid=0` → 被我当成"相机没出流"，
  还去怀疑位数/线长/tready。**真正的解释是"太早"。**
- **实测**（`ps_fft_dual/probe_live.tcl`，先起 S2MM 再每 2 s 轮询）：
  `t=10s raw=0x00000048 tvalid=0 tready=1` → `t=12s raw=0x00000078` **`tvalid=1`**。
- 厂商应用能出图，正是因为它启动后本来就要跑好几秒才开始显示。

#### 缺陷 5：抓取 **32 bpp** 与显示 **24 bpp** 不一致 + S2MM 行缓冲 512 拍装不下 1280 拍的一行

- `axis_subset_converter_0`：S=2 字节 → **M=4 字节**（`TDATA_REMAP = 16'b0000000000000000,tdata[15:0]`，高位零填充），
  而显示侧 `axi_vdma_1` 的 `c_m_axis_mm2s_tdata_width = 24` → 字节流错位 → 花屏。
- `axi_vdma_0`：`c_s2mm_linebuffer_depth = 512`，而一行 1280 拍 > 512 拍
  → `SR = 0x00014810` 中的 **`0x800` = `XAXIVDMA_SR_ERR_FSZ_MORE_MASK`（FSize More Mismatch）**，
  外加 `0x10` = `XAXIVDMA_SR_ERR_INTERNAL_MASK`。（掩码取自 `axivdma_v6_11/src/xaxivdma_hw.h`；**不是** SlvErr。）
- **官方可用设计（`22_ov5640_single`）的对照值 —— 这就是"正确配置"的答案**：

| 位置 | 官方值 |
|---|---|
| `axis_subset_converter_0` | S=2、**M=3**、`TDATA_REMAP = tdata[4:0],3'b000,tdata[10:5],2'b00,tdata[15:11],3'b000` |
| 抓取 VDMA 的 S2MM | `c_s_axis_s2mm_tdata_width=24`、`c_s2mm_linebuffer_depth=4096` |
| 应用 `display_demo.c:128` | `vdma_write_init(..., 1280*3, 720, 1280*3, dispCtrl.framePtr[dispCtrl.curFrame])` |

→ 抓取几何 **VSIZE 720 / HSIZE 3840 / STRIDE 3840**（24 bpp）；
显示 800×480 裁剪 **VSIZE 480 / HSIZE 2400 / STRIDE 3840**；**两块 VDMA 用同一个基地址**（官方就是共用帧缓冲）。

修复脚本：`ps_fft_dual/fix_24bpp.tcl`（只改 BD 参数，逐项打印 before/after，`validate` 后再 `save_bd_design`）。

**接着读 `16_1_lcd7/auto_create_project/src/design/color_bar.v` 的 `VIDEO_800_480` 段：**

| | ALINX 可用值 | 我们原来的 v_tc |
|---|---|---|
| H_ACTIVE / H_FP / H_SYNC / H_BP | 800 / 40 / 128 / 88 → HTotal **1056** | 同样的 1056 ✓ |
| V_ACTIVE / V_FP / V_SYNC / V_BP | 480 / **1** / 3 / **21** → VTotal **505** | VTotal **525**、V_FP 10、V_BP 32 ✗ |

**而且还有一个更前置的问题：v_tc 的发生器从来没被软件使能过。**
读 `+0x00 CTL = 0x00000000`；厂商应用 `display_ctrl.c DisplayStart()` 做的是
`XVtc_RegUpdateEnable + SetGeneratorTiming + SetSource + EnableGenerator`，
即 `CTL = ALLSS(0x03FDEF00) | GE(0x04) | RU(0x02) = 0x03FDEF06`。
**没有应用，这一位就没人写** —— 之前 probe 里 av/hs/vs 全 0 就是这个原因（我当时读的

`GASIZE=0x01E00320`(H 800｜V 480<<16)、`GHSIZE=0x00000420`(1056)、`GVSIZE=0x02EE020D`(525｜F1 750<<16)、
`GHSYNC=0x03C80348`(840｜968<<16)、`GVBHOFF=0x02800280`、`GVSYNC=0x01ED01EA`(490｜493<<16)、
`GVSHOFF=0x02B70280`、`GPOL=0x7F`。

**改正后写入的值**（按 `XVtc_ConvTiming2Signal` 的公式算）：
```
GASIZE  = 0x01E00320   HActive 800 | VActive 480<<16
GHSIZE  = 0x00000420   HTotal 1056
GVSIZE  = 0x01F901F9   VTotal 505  (F0 | F1<<16)
GHSYNC  = 0x03C80348   HSyncStart 840 | HSyncEnd 968<<16
GVBHOFF = 0x03200320   BlankHoriStart/End = HFrontPorchStart = 800
GVSYNC  = 0x01E301E0   VSyncStart 480 | VSyncEnd 483<<16
GVSHOFF = 0x03480348   SyncHoriStart/End = HSyncStart = 840
GPOL    = 0x00000070   (ACP|AVP|FIP = 正；行/场同步与消隐 = 负)
CTL     = 0x03FDEF06   ALLSS | GE | RU
```
**实测结果：AN970 上出现竖条，显示链路打通。**（脚本 `ps_fft_dual/fix_vtc.tcl` / `fix_vtc2.tcl`）

#### 缺陷 7：**抓取侧 —— S2MM 缺少 DRE（数据重对齐引擎）**（当时的判断）

**判据必须先立起来：先给缓冲清零，再看 DMA 有没有写。**
两个关键工具事实（都是踩出来的）：
- **`mwr -bin -file` 在这个 xsdb 里不存在**（`wrong # of args: should be "mwr [options] address values [num]"`）；
  能用的**批量写内存**通路是 **`dow -data <file> <addr>`**（512 KB 约 2 s；**2.7 MB 一次会把 FTDI 写挂**，
  报 `FT_Write failed: io error` → 要分块，每块 ≤ ~450 KB）。
- **0x10000000 里一直是 DDR 残留**，所以"缓冲非零"根本不能证明 DMA 写了东西。
  清零（`dow -data zeros512k.bin 0x10000000`）之后：**capture 跑 70 s、tvalid 一直在跳，前 4096 个字始终是 0
  → S2MM 一个字节都没写。**（脚本 `ps_fft_dual/live3.tcl`）

**然后拿官方可用设计的 VDMA 参数做逐项对照**（`c_*` 参数级 diff，这是最有效的一招）：

| 参数 | ps_fft_dual `axi_vdma_0`（抓取） | 官方 `axi_vdma_1`（抓取，已验证可用） |
|---|---|---|
| `c_include_s2mm_dre` | **0** ← 缺 DRE | **1** |
| `c_s2mm_genlock_mode` | **2** | **0** |
| 其余（tdata 24、linebuffer 4096、sf 1、fsync 1、tkeep/tlast） | 一致 | 一致 |

**DRE = Data Realignment Engine**：没有它，S2MM 的 datamover 无法把**每拍 24 bit（3 字节）**的流写进
**32 bit 对齐**的 DDR。官方设计**正是因为流是 24 bpp 才开着 DRE**。
另外 `genlock_mode=2` 加在一个"只有 S2MM"的实例上也是错的（官方是 0）。
修复：`ps_fft_dual/fix_dre_build.tcl`（`c_include_s2mm_dre` 0→1、`c_s2mm_genlock_mode` 2→0，然后重综合）。

#### 2026-09-27 深夜 · **抓取真正通了：VSIZE 必须在 RUNSTOP 之后写**（附"面板测试"的教训）

**这一条是整个链路真正的堵点，而且和硬件无关，是寄存器写序。**

读 `axivdma_v6_11/src/xaxivdma_channel.c` 才看清驱动的真实写序：

```c
XAxiVdma_ChannelConfig()   /* 写 HSIZE、STRIDE_FRMDLY、CR */
XAxiVdma_ChannelStart()    /* CR |= RUNSTOP                                */
    /* 直接寄存器模式（非 SG）：
     *   Update vsize to start the channel                            */
    XAxiVdma_WriteReg(StartAddrBase, VSIZE_OFFSET, Channel->Vsize);
```

**在直接寄存器模式下，VDMA 只在"通道已经在跑"的时候写 VSIZE 才真正启动一帧。**
我此前所有脚本都是「先写 VSIZE → 再置 RS」，**传输从未启动过** —— 这才解释了两件事：
1. 无论怎么改几何/线长/DRE/TUSER，`S2MM SR` 都是**一模一样**的 `0x00014810`；
2. 缓冲清零后跑 70 s 一个字节都没写进去。

**改成正确写序后（`ps_fft_dual/captest6.tcl`）：立刻写出完整一帧**
`SR=0x00015831 nz(4096w)=4096`，dump 出来 1280×720 是**真实相机图像**（`cap6.png`）。

**同一条规则也适用于显示 MM2S，但顺序相反**（实测）：显示侧必须 **先写 VSIZE 再置 RS**，
反过来写（"驱动顺序"）会让 MM2S 立刻 halt 并报 SlvErr。→ **抓取 VSIZE 最后写，显示 VSIZE 先写。**

**此时整条链已打通到"显存里是实时相机画面"**（`live8a/live8b` 两次 dump 差异 **83%**）。

**⚠️ 面板测试的教训（这条代价很大，必须记下来）**
中途我上过 ALINX 自己的 `16_1_lcd7` 彩条例程比特流，屏上出现 8 条彩条，于是判定"面板 + J11 + 800×480 正常"。
**这个推断一直没被真正验证过**：那个例程的图案和屏"无信号回退"都可能长成 8 条彩条，**光看"有没有彩条"根本区分不了**。
后来我关掉 v_tc、停掉显示通道，彩条**依旧不动** → 我一度判定"彩条是屏自己生成的"。

**最终做对的做法**：把 ALINX 例程的源码拿来，**只改颜色**（8 条全改成纯蓝），
用它们自己的脚位/时序/时钟重新综合一个比特流（`ps_fft_dual/lcdsolid/` + `build_lcdsolid.tcl`）：
`xsdb → fpga -file lcdsolid/proj/lcdsolid.runs/impl_1/top.bit`
→ **屏变纯蓝**。
**这才真正证明了：AN970 + J11 + 800×480 + 33 MHz(MMCM) 这条通路是好的。**
（教训：要证明"显示通路通"，必须**改变画面内容**，而不是看它"有没有显示东西"。）

#### ✅ 2026-09-27 17:5x · **目标达成：AN5642 的实时图像已经在 AN970 上**

**最终判决（就是这一个）：直接寄存器模式下，VDMA 的 `VSIZE` 必须写在 `RUNSTOP` 之后 —— 两个通道都是。**

`xaxivdma_v6_11/src/xaxivdma_channel.c`：
`XAxiVdma_ChannelConfig()` 写 HSIZE / STRIDE_FRMDLY / CR；`XAxiVdma_ChannelStart()` 先 `CR |= RUNSTOP`，
**只有在通道被判定为 running 且非 SG 时，才写 `VSIZE`（注释就写着 "Update vsize to start the channel"）**。
写序错的时候通道**看起来完全健康**：`SR` 干净、`not halted`、`tready` 常高 —— 但**一个 beat 都不发**。
这就是为什么之前所有参数级修复（DRE / burst / fstores / TUSER / 线长 / 时钟 / 地址）全部“没反应”。

**硬判据（用 `ps_fft_dual/rtl/capture_ram.v` 自己当逻辑分析仪，`dispprobe_read3.tcl`）**：

| 写序 | `mm2s_tvalid` | `locked` |
|---|---|---|
| 先写 VSIZE → 再置 RS | **0 / 1024** | 0 |
| 先置 RS → 再写 VSIZE | **1024 / 1024** | 1 |

同一个采样器的正常读数（`dispprobe2.log`）：`vtc_av` 高 1281/2048、`vtc_hs` 2 个上升沿、`rst33n`=1 —— v_tc 一直在正常发生时序，
**只有 MM2S 的 `tvalid` 恒为 0**，这才是真正的病灶。

**由此确立的两条可复现流程**
```
抓取：  HSIZE/STRIDE/ADDR → CR=0x3(RUNSTOP) → VSIZE=720 最后写
显示：  HSIZE/STRIDE/ADDR → CR=0x10003      → VSIZE=480 最后写
```
脚本：`ps_fft_dual/live9.tcl`（完整链路）、`ps_fft_dual/center_crop.tcl`（显示窗口垂直居中）。

**实测结果**：AN970 上出现**实时的相机画面**（用户拍照确认），`mm2s_tvalid` 与 `locked` 全时有效，
`DIS SR=0x00011000` 无错误，抓取两次 dump 差异 39.5%。

**已知遗留（都不是故障，按优先级）**
1. **R/B 两字节接反**：厂商重映射把 R 放在最低字节，而 AN970 的 `lcd_rgb[23:16]` 才是 R
   （ALINX 彩条例程就是 `rgb_r → lcd_rgb[23:16]`）。要改需对调 `TDATA_REMAP` 的两个位段后重综合。
2. **撕裂**：采集与显示共用同一块缓冲。要消除需双缓冲 + 按帧切换。
3. **逆光/曝光**：当前相机对着窗户，中间过曝；属场景与 AEC 问题。

**方法论教训（这一晚最贵的两条）**
- **"屏上有彩条"不能证明显示通路正常**（官方例程的图案和其它状态都可能长成彩条）。要证明必须**改变画面内容**
  —— 把例程源码只改颜色（8 条全改纯蓝）重编（`ps_fft_dual/lcdsolid/` + `build_lcdsolid.tcl`），加载后屏变纯蓝，才算证据。
- **寄存器"看起来对"完全不代表流在动**。本项目两次栽在这上面。只要怀疑数据通不通，
  **先造一个能读到"有没有 beat"的观测通道**（这里就是复用 `capture_ram` 当逻辑分析仪），不要继续猜参数。

**已达成并保持**：AN970 上**实时**相机画面，**颜色顺序用厂商原版**，**无撕裂**（软件按硬件帧号逐帧纠正）。

> **方法**：依次跑两份 ps7_init，各自把整个 SLCR 块（`0xF8000000`，1024 字）dump 下来，

> 68 个不同的字里，**唯一落在 I2C0 引脚上的**是：

> | 地址 | 寄存器 | ps_fft_dual 自己 | 官方 |
> |---|---|---|---|
> | `0xF80007C8` | **MIO_PIN_50** | `0x00001201` | `0x00001200` |
> | `0xF80007CC` | **MIO_PIN_51** | `0x00001201` | `0x00001200` |
>

> ```tcl
> mwr -force 0xF8000008 0x0000DF0D          ;# SLCR unlock
> mask_write 0xF80007C8 0x00000001 0x00000000   ;# MIO_PIN_50: L0_SEL=0 -> I2C0 to EMIO
> mask_write 0xF80007CC 0x00000001 0x00000000   ;# MIO_PIN_51
> mwr -force 0xF8000004 0x0000767B          ;# SLCR lock
> ```
>
> **⚠️ 不能整份换成 `ps7_init_official.tcl`**：对比显示两份初始化还差着
> **ARM PLL(`0xF8000100`) / DDR PLL(`0xF8000110`) / IO PLL(`0xF8000118`) 和 FCLK0/1(`0xF8000170/0x180`)**
> —— 也就是 **DDR 与所有 PS 时钟频率都不同**。ps_fft_dual 的 LCD 像素时钟正是 `FCLK_CLK1`，
> 整份照搬会直接把屏的时序改掉。**用自己那份 + 上面三行补丁**。

### 2026-09-27 深夜 · 100 MHz 时钟、帧率 +60%、以及"画质到顶"的结论

#### ⚠️ 隐患 1 在本设计里是**结构性存在**的（必须每次上板确认）

之前几轮的 `w6f` 比特流"结构上安全"，因为它**一个对外引脚都没有**。**现在不再成立**：

`ps_fft_dual/vivado/two_fft.xdc` 同时把隐患 1 的那两个脚都用上了：

| 行 | 约束 | 含义 |
|---|---|---|
| 126-128 | `GPIO_0_tri_o[0]` → **B20** | FPGA **输出**（相机复位 `cmos_rstn`） |
| 42 | `cmos_d_0[0]` → **V12** | FPGA **输入**（相机 D0） |

**这两个脚就是 J10 PIN35 ↔ PIN28 那根跳线。** 相机在位、跳线插上时，
B20（FPGA 输出）+ V12（相机模块输出）会**在同一条网上对顶**。

**用户 2026-09-27 明确说明：那根跳线（J10 PIN35 B20 ↔ PIN28 V12）和相机不可能同时插上 —— 结构上互斥。**

因此本设计的隐患 1 是**"不可达"**，而不是"我小心了"：相机只要在位（现在是，
`chip id 0x56/0x40`、画面实时正常），跳线就**装不上去**，B20 与 V12 就不可能对顶。

- [ ] 唯一的残余条件：**相机必须确实插在 J10 上**。相机被拔掉时，
      这条"互斥"论证随之失效，此时不得插入跳线。
- 依据分类：**用户陈述的物理互斥**（用户能直接看到机械结构，我不能）。
  这与 `w6f` 那几轮的"接口里没有那根线"是同一类**结构性**论证，而不是"每次都小心检查"。

#### 1. `100 MHz` 时钟：先算、再测，结论是"没收益，还有代价"

官方 `22_ov5640_single` 用 FCLK0=100 MHz / FCLK1=150 MHz；本工程 `ps_fft_dual` 是 FCLK0=50 MHz / FCLK1=33 MHz。
关键区分：**屏幕像素时钟走 FCLK_CLK1（33 MHz），相机像素时钟来自 OV5640 自己的 PLL**，
两者都不由 FCLK0 决定。

带宽算术（改之前就写下）：1280×720×24bit = **691200 个 AXI beat/帧**，50 MHz → 13.8 ms/帧 → **理论上限 72 fps**；
实测 15–18 fps，只用了 ~22%。**所以 FCLK0 不是瓶颈。**

仍然改了并重新综合布线（`ps_fft_dual/fclk100_build.tcl`），实测对比（同一相机配置、同一探针）：

| FCLK0 | 实测 fps |
|---|---|
| 50 MHz | 18.17 |
| 100 MHz | 15.83 / 18.33 / 18.50 |

**统计上无差别 —— 预测被证实。**

**但 100 MHz 带来了真实代价**：post-route **时序未收敛**，
`WNS = −3.796 ns`、`TNS = −29.289 ns`、**9 个失败端点**，
全部落在 `clk_fpga_1 → clk_fpga_0`（32.728 → 100 MHz）这条**跨时钟路径**上；
intra-clock 全部为正（`clk_fpga_0` WNS **+3.851**、`clk_fpga_1` WNS +20.502）。
50 MHz 时同一路径裕量约 **+6 ns（推算，非实测）** → 即这是 100 MHz 引入的回归。

**处置：退回 50 MHz**（`ps_fft_dual/live14_50m.tcl` + 备份比特流 `design_1_wrapper_50m_live14.bit`）。
理由：**零收益 + 吃掉时序裕量**。

**顺带暴露的一个真实缺口**：`clk_fpga_1 ↔ clk_fpga_0` 这条 CDC 没有 `set_clock_groups -asynchronous`

#### ⭐ 画质问题的真正根因：整条链路是 **RGB565**，不是 RGB888

**现象**：面板上的实时画面上有**绿斑、品红描边、黄色色块**，白衬衫最明显。眼睛直接看也有（不只是照片伪影）。

**排查路径（每一步都用已知答案的判据）**

| 步骤 | 测试 | 结论 |
|---|---|---|
| 1 | dump 帧缓冲、按正确字节序渲染 | **内容是干净的**一张自然照片 → 不是采集数据坏 |
| 2 | 写入**纯灰阶**图案（每像素三字节相同）到帧存并冻结采集 | 面板显示**纯黑白无颜色** → **显示链路完好**，没有字节相位错位 |
| 3 | 写入色带（byte0/1/2 分别为 255）| 面板显示 **蓝/绿/红** → 字节序是 **B,G,R**，映射正确 |
| 4 | 统计帧缓冲里每个通道的**不同取值个数** | **决定性** |

**第 4 步的结果**（`mf_1.bin`，921600 像素）：

```
byte0:  只有 32 个取值，全部是 8 的倍数   → 5 bit
byte1:  只有 64 个取值，全部是 4 的倍数   → 6 bit
byte2:  只有 32 个取值，全部是 8 的倍数   → 5 bit
整帧不同颜色总数只有约 7000 个（正常 8bit 自然图像是 10 万级）
```

**这是 RGB565。有效色深 5:6:5 = 65536 色。**

**根因在 BD 里，而且是从骨子里带进来的**（`design_1.bd`）：

```
axis_subset_converter_0:
    S_TDATA_NUM_BYTES = 2      <- 输入 16 bit
    M_TDATA_NUM_BYTES = 3      <- 输出 24 bit
    TDATA_REMAP = tdata[4:0],3'b000, tdata[10:5],2'b00, tdata[15:11],3'b000
                  └─ 5 bit ─┘          └─ 6 bit ─┘          └─ 5 bit ─┘
```

子集转换器**只是把 16 位 RGB565 补零扩成 24 位**，没有任何精度恢复。
16 位从哪来：`my_ip/ov5640_ip/src/cmos_8_16bit.v` ——
它把 PCLK 上的 8 位数据**每两个字节拼成一个 16 位字**（`pdata_o <= {pdata_i_d0, pdata_i}`）。
ALINX IP（`www.alinx.com.cn:user:alinx_ov5640:5.4`，BD 里**没有任何可配参数**）输出固定 16 位。

**为什么这解释了全部现象**
- **绿斑/品红斑**：色度 = R−G、B−G，而 R/B 只有 5 bit。白衬衫这类低色度区域，
  1 个 LSB 的色度误差就是一块**肉眼可见**的色斑。背景里只要有噪声在"抖动"量化，
  色斑就会不断翻动 —— 正是照片里的样子。
- **显示链路与色带测试都通过**：显示链路忠实还原了 565 数据，它没错。
- **dump 缩略图"看起来正常"**：565 的色带在缩略图上不明显，一上屏就暴露。

**因此"颜色怪"不是调参能解决的** —— 需要把采集链路改成真正的 RGB888：
1. 传感器 `0x4300` 设为 RGB888（厂商表现为 `0x60`，需确认其真实含义，**不能猜**）；
2. 改 `cmos_8_16bit.v` / 换掉它，按 **3 字节/像素**输出 24 位；
3. BD 里把 `axis_subset_converter_0` 改成 S=3 / M=3（或直接去掉）；
4. 重新综合布线 + 重新上板。

**在改之前可以做的低成本缓解**：565 的色带之所以"翻动"是因为叠加了噪声。
**把噪声压下去，色斑就静止、就不刺眼了** —— 也就是"给场景加光"这条老结论。
它治不了 565，但能让画面从"很怪"变成"能看"。

**方法论**：第 1 步（dump 干净）差点让我得出"采集没问题"的错误结论 ——
**缩略图看不出来的量化误差，必须用"每个通道有多少个不同取值"这种逐位统计去查**，
不能靠肉眼看渲染图。这与前面"用最亮 3% 当色彩判据"是同一类错误：
**判据选错了，工具再好也没用。**

#### ⭐⭐ 真正的根因：LCD 数据位在接插件上**每两位内部颠倒**

拿到了 `C:\Users\wzh\Documents\zynq 文献\AN970_UG.pdf`（Rev 1.00，用户 2026-09-27 下载）。
手册第 6–7 页给出了 40 针排母 P4 的完整定义：

| 针 | 信号 | 针 | 信号 |
|---|---|---|---|
| 11 | **LCD_B6** | 12 | **LCD_B7** |
| 13 | **LCD_B4** | 14 | **LCD_B5** |
| 15 | **LCD_B2** | 16 | **LCD_B3** |
| 17 | **LCD_B0** | 18 | **LCD_B1** |
| 19–26 | LCD_G6,G7,G4,G5,G2,G3,G0,G1 | 27–34 | LCD_R6,R7,R4,R5,R2,R3,R0,R1 |

**每个颜色的数据位在接插件上都是"每相邻两位内部颠倒"的**（B6,B7,B4,B5,B2,B3,B0,B1），
不是顺序的 B7..B0。

而我们的 `two_fft.xdc` —— **与厂商 `16_1_lcd7/.../lcd_test.xdc` 逐脚完全相同**
（R: E19,E18,G18,G17,H17,H16,G15,H15；G: H20,J20,L17,L16,M18,M17,D20,D19；
B: L20,L19,M20,M19,K18,K17,J19,K19）—— 是按**顺序**分配到这些针上的。
于是每一位都落到了相邻位上：**进去的时候成对交换了。**

**实测证据**（写单比特色块到帧存，拍屏定量测光，`make_bittest2.py` + `measure_bars.py`）：

| 写入 | 面板实测亮度 | 成对交换的预测 |
|---|---|---|
| 0x40 (64) | **220** | 交换后 →128，应比 0x80 亮 ✓ |
| 0x80 (128) | **135** | 交换后 →64 ✓ |
| 0x10 (16) | **135** | 交换后 →32，应比 0x20 亮 ✓ |
| 0x20 (32) | **47** | 交换后 →16 ✓ |

**两条独立的顺序关系都精确吻合。**

**为什么这个缺陷能一直躲过所有测试**（这是本轮最重要的方法论教训）：
成对交换**只影响低位**，而下面这些图案**对"低位是否被交换"完全免疫**：

| 用过的判据 | 为什么免疫 |
|---|---|
| 纯色（byte=0xFF / 0x00） | 所有位置位或全不清零，交换后不变 |
| 纯灰阶（R=G=B） | 三个通道同样变换，仍然是灰 |
| 厂商彩条例程 | 彩条是**饱和色**，同样免疫 |
| `lcdsolid`（纯蓝） | 饱和色 |
| 色带 byte0/1/2 分别置 255 | 饱和色 |
| 我写的 3 条灰阶带（F0/0F, AA/55, C3/3C） | 值里面**配对的两位总是相同**，交换后不变 |

**所有我选来"验证颜色"的图案，恰好都是对这类失真免疫的图案。**
判据必须选**能暴露缺陷**的那种：**单价置 1 的块** —— 只有它能把"低位被接到高位"直接变成肉眼可见的亮度差。

**修法（只改约束，不动 RTL / BD）**：把 `vid_io_out_0_data[2k]` 与 `[2k+1]` 的 `PACKAGE_PIN`
成对对调（每个颜色 4 对，共 12 对 / 24 条）。脚本 `ps_fft_dual/fix_lcd_bitpairs.py`，
原文件备份在 `ps_fft_dual/rgb888_backup_20260927/two_fft.xdc.orig`。
构建脚本 `bitpair_build.tcl`（只重跑实现，综合可复用，因为 PACKAGE_PIN 不影响综合）。

**顺带确认的两件事（都来自这本手册）**
- **AN970 是 24 位色 / 16.7M 色**（第 3 页）→ 我们 24 位的接口宽度是对的，
  所以 **RGB565 截断完全发生在我们自己的采集侧**（ALINX IP 固定 16 位输出 +
  `axis_subset_converter_0` 的 565 补零扩展），与面板无关。这是**两个独立缺陷**。
- 面板型号 **TM070RDH13**，触摸 **GT911**，时序为 DE 模式、DCLK 上升沿采样。

**方法论（这一轮最贵的一条）**
> **测试图案必须选"能暴露目标缺陷"的那一类。**
> 我连续用了六种对"低位交换"完全免疫的图案（饱和色、灰阶、对称值），
> 于是六次都"通过"，却一直在盯着一个明显坏掉的画面找原因。
> 每写一个新判据，先问一句：**"如果缺陷正是我怀疑的那个，这个图案看得出来吗？"**

**✅ 验证结果：修好之后用户确认"很完美"。**

改动落地内容（`ps_fft_dual/fix_lcd_bitpairs.py` 生成，只改约束）：
`vid_io_out_0_data[2k]` 与 `[2k+1]` 的 `PACKAGE_PIN` 成对对调，12 对 / 24 条
（R: E19↔E18, G18↔G17, H17↔H16, G15↔H15；G 与 B 同理）。

**重新构建时踩到的一个坑（值得记）**：`reset_run impl_1` **只重跑实现、复用综合**，
而当时工程里的综合来自 **100 MHz 那次实验**（BD 里 `PCW_FPGA0_PERIPHERAL_FREQMHZ` 已被改成 100）。
于是"50 MHz 修正版"实际产出的是 **100 MHz 的比特流**，还带着那条 CDC 违规。
→ **改完 BD 频率后必须确认综合也重跑**；只 reset impl 会静默复用旧综合。

**顺带查清的一条既有问题（不是本轮引入的）**：
`clk_fpga_1 → clk_fpga_0` 这条跨时钟路径**在 50 MHz 下同样不收敛**
（`WNS = -4.075 ns`、9 个端点；100 MHz 下是 -3.79）。也就是说：
- 这条违规**从设计一开始就存在**，不是我把 FCLK0 提到 100 MHz 才有的
  （我先前"50 MHz 时裕量约 +6 ns"的判断是**错的**，已作废）；
- 而该设计已连续稳定运行数小时，说明这 9 个端点在实际工作条件下不构成故障。
- 正确做法是给这条 CDC 加 `set_clock_groups -asynchronous clk_fpga_0 -group clk_fpga_1`
  （或补真正的同步器），属于**独立的清理项**。

**仍然存在的第二个独立缺陷：采集链路是 RGB565（见上一节）。**
位序修好后画面颜色已经"很完美"，但**有效色深仍是 5:6:5 = 65536 色**，
而 AN970 手册明确写着面板是 **24 位色 / 16.7M 色**。所以色深这条**仍然卡在我们自己这边**：

```
cmos_8_16bit.v            : 每 2 个字节拼成 16 位
axis_subset_converter_0   : S=2 byte -> M=3 byte，TDATA_REMAP 只是把 5:6:5 补零扩成 24 位
```

要真正做到 24 位需要：改/换 `cmos_8_16bit.v` 打成 **3 字节 24 位**、ALINX IP 的端口宽度
从 16 改到 24（要重新打包 IP）、BD 里把子集转换器改成 S=3/M=3（或去掉）。
**这是独立的一次改造**，且会改变传感器每像素字节数（2→3），帧率可能随之下降，需要实测。

#### 60 fps 的尝试：**PLL 这条路是死路**（2026-09-27 深夜）

**背景算术**：`fps = PCLK / (HTS × VTS)`。当前 PCLK ≈ 21 MHz、HTS 1892、VTS 740 → ~18 fps。
60 fps 需要 PCLK ≈ 84 MHz（约 4 倍）。两个可能的来源：传感器 PLL、以及 FPGA 侧带宽。

**FPGA 侧先做好了**：`fclk100_bitpair_build.tcl` —— FCLK0 = 100 MHz **且带位序修正**，
上板验证画面正常（面板窗口 B=83.7 G=80.5 R=83.8，接近中性），帧率与 50 MHz 版一致（**17.33 fps**），
证明 **50 MHz 从来不是瓶颈**（与最早的带宽估算一致：720p 下 50 MHz 上限 54 fps）。

**传感器 PLL 扫描**（`pll_sweep.tcl`，100 MHz 版本上跑）：

| `0x3035` / `0x3036` | 含义 | 实测 |
|---|---|---|
| 0x21 / 0x80 | SDIV0=2, 倍频 128（当前最佳） | **17.33 fps** |
| 0x21 / 0x69 | SDIV0=2, 倍频 105（厂商原值） | 13.67 fps |
| **0x11** / 0x69 | **SDIV0=1**（想把 PCLK 翻倍） | **0.17 → 流死** |
| **0x11** / 0x60 | SDIV0=1 | **0.17 → 流死** |

**结论**：`0x3035` 的 SDIV0 从 2 降到 1 **即使在 100 MHz FCLK0 下也一定掉流**。
所以早先"50 MHz 带宽不够才掉流"的推测**不成立** —— 是传感器本身不接受这个分频。
**60 fps 靠这条 PLL 路线走不通**；要更高帧率只能换传感器模式（更小的 HTS/VTS）或换传感器。

**另一条重要教训：掉流之后传感器不会自己恢复。**
扫描脚本内置了"检测到掉流就回滚上一组好值"，但**回滚也救不回来** ——
`0x3035=0x11` 把传感器带进了需要**整表重配**（303 条）才能恢复的状态。
→ **以后任何可能掉流的传感器实验，恢复手段必须是"重跑整表"，而不是"写回旧寄存器值"。**

**由于这次扫描，板子当时处于掉流状态，已用 `live14_bitpair.tcl` 恢复。**
（`live14_bitpair.tcl` 会重推 303 条表，正是上面说的正确恢复手段。）

### 曝光包围 + 融合（PS I2C 时序 + 双缓冲）：**机制通了，收益是 0**（2026-10-03）

**做出来的东西**（`ps_ui/cam_i2c.c`、`ps_ui/main.c`）：
PS 自己通过 **`0xE0004000` 的 I2C0**（经 EMIO 到 PL 的 T16/T15）写 OV5640，
把 `0x3503=0x01`（关自动曝光）、长/短两档曝光（`10656` / `1640`，**比值恰好 6.5**）
逐帧轮流写给传感器，VDMA 的两个采集 store 各拿一档，渲染时按 `FUSE_CLIP=248`
在长曝光削顶处换成 `短曝光 × 6.5`，再做色调表。
**I2C 必须留 ~2 ms 沉降时间**（`periph` 每次读之前、每次写之后），
否则写寄存器会被传感器**静默忽略**（`0x3503` 读回还是 `0x00`、VTS 根本没变）；
不加沉降时间还会读回 `13621` / `0x053535` 这种不可能的值。

#### 收益：实测为 0，不是"接近 0"

渲染器**自己**输出两个计数（邮箱 216/220/224），所以这组数字不是事后用 Python 反推的：

| 模式 | 帧内被计数通道 | 长曝光 ≥ clip | 融合真正拉回满量程 | 帧率 |
|---|---|---|---|---|
| bracket | 691200 | **41157（5.95%）** | **35（0.09%）** | **4.7 fps** |
| single | 691200 | 70285（10.17%） | 0（无短曝光） | **19.3 fps** |

**原因是结构性的，不是调参能解决的**：某通道落在 `≥248` 处，等价于"该点场景已达满量程"，
于是 `6.5 × 短曝光` 必然 **> 255**，被 clamp 回 255 —— 和只用长曝光渲染**一模一样**。
唯一能被融合改变的，是"长曝光刚好擦到 clip 点"（真实值 248~255）的通道，
那正是上表那个 35/691200。**6.5 档 8-bit 素材换不回一个太阳照的窗户。**

#### 顺手抓到的两个测量错误（都差点变成"结论"）

1. **"白削顶 12.6% → 0.4%"是假的，两条曲线根本不在同一级。**
   12.6% 来自 `tune_tone.py` 的定义 `min(B,G,R) ≥ 251` 作用在**原始帧**；
   0.4% 是同一个定义作用在**过完色调表的帧**上。而色调表里
   **B 增益 = 235/256**，满白 `(255,255,255)` 出来是 `(234,255,255)`，
   `min = 234` —— **这个探测器在渲染级上恒为 0，它测的是蓝增益，不是融合。**
   附带查清：本采集链路里 **`min(B,G,R)` 最大只有 248**，
   所以 `min ≥ 251` 在**任何**原始帧上都是 0.00%。
   复现脚本：`ps_ui/clip_stage_check.py`、`ps_ui/clip_find.py`
   （后者能在存档帧上反查出 12.6% 最接近的定义其实是 `green ≥ 248`）。
   → **教训：报"改善"之前先确认前后两次测量在同一个 stage、同一套定义、同一批像素上。**

2. **我造的"融合后仍然削顶"计数器是个恒等式。**
   第一版用 `g_clip_fused` 数"救完之后仍 ≥248 的通道"，板上一跑给出
   **36738 / 36738** —— 一个**永远不可能变成别的数**的计数器。
   一个输出被自己定义锁死的仪器，什么都测不出来，包括它被造出来要找的那个改善。
   → 改成数"救完**真的低于 255**"的通道（`g_recovered`），它才可能是 0，也确实是 0。

#### 还抓到一个真 bug：长/短是**每帧轮换**的，不能只判一次

第一版在第一次判完 `g_long_buf` 后就**永远不再改**。板上证据：
两个 UI store 的相机区亮度分别是 **mean green 16.9 和 62.7** ——
其中一个把**短曝光帧当长曝光**渲染了（暗帧）。
曝光是写给"下一帧"的，而 VDMA 逐帧轮换 store，所以长短**每帧对调一次**，
固定答案只有一半的帧是对的。改成**每帧都测**（`cam_mean_green` ×2，
约 7200 次 load，相对 ~50 ms 的一帧可忽略）。

#### 剩下的问题（诚实记录，没解决）

- **渲染比采集一帧还慢，融合永远读不到两个完整帧。**
  实测 bracket 循环 **4.7 fps（≈213 ms）**，而 VTS 1450 的采集帧只有 **≈122 ms**。
  交接发生的瞬间 VDMA 已经开始**覆盖另一个 store**，所以
  "两个 store 都是完整帧"的窗口**为零**。`ps_brackwatch.tcl` 的逐帧采样直接看到了这点：
  状态在两档之间摆动 —— 要么两个 store 亮度几乎相同（都拿到长曝光，没配成对），
  要么一个暗一个中等（那个"中等"正被新帧覆盖，是一半旧一半新的混帧）。
  代码注释里"VTS 1450 → 渲染塞得下"依据的是**旧的 73 ms** 数字，与现在实测的 213 ms 不符，
  **这条注释已经把错误的依据写死了。**
- 要真正做成，需要让采集 VDMA 带 **≥4 个 frame store**（渲染期间 VDMA 不碰要融合的那两个），
  这是 **Block Design + 重新综合 + 新比特流**，不是 PS 端能修的。
- **但按上面的收益（0.09%）看，这些代价不值得投。**

#### 结论与当前默认

- **默认走单曝光（`MB_BRACKET`（邮箱 232）= 0）**：19.3 fps、自由跑、无撕裂，
  而且对一台**测量仪器**来说这才是可复现的那条路（校准后锁死的曝光）。
  包围+融合留作 boot 开关（邮箱 232 = 1），**只在"被摄目标是高光"的场景下用**。
- 模式是 **boot flag 而不是运行期开关**：模式会连带改 VTS，而"运行中重臂采集通道"
  正是本项目已经错三次的动作。
- **注意**：单曝光路径现在 19.3 fps，比加这套东西之前的 21.6–22.0 略低（约 −11%），
  代价是每帧多了两次 `cam_mean_green` + 两次亮样本计数（4×1800 次 load）。这是实测值，不是估计。

### CDC 修复版比特流的首次冷启动验证（2026-10-03 下午）

**背景**：9 条 `clk_fpga_1 → clk_fpga_0` 违规（WNS ≈ −3.79 ns）在 2026-10-03 早些时候修掉了
（全部落在调试探针输入 `capture_ram_0/inst/mem_reg_*/DIADI[*]`，用**精确 `false_path`**，
不是 `set_clock_groups`）。但产物 `design_1_wrapper_cdcfix_50m.bit` 一直**没上过板**，
而 `live14_bitpair.tcl` / `RESTORE.md` 指向的还是旧比特流。本次把它补上。

#### 验证链（每一环都留下可复现的判据）

| 环节 | 判据 | 结果 |
|---|---|---|
| 约束**输入** | `vivado/two_fft.xdc` 的前 8682 字节与 `GOOD_20260927_bitpair/two_fft.xdc.bitpair_fixed` **逐字节相同**，后接 2874 B 追加块 | 通过（字节比对，非肉眼） |
| 时序 | routed 报告 violated path 条数 | **0** |
| **构建产物** | `impl_1/design_1_wrapper_io_placed.rpt` 里 24 条 LCD 数据脚的**实际布局**，对比"期望"与"厂商"两份 XDC | **24/24 落在修正后的位置，0 条落在厂商位置** |
| 冷启动 | 系统复位 + 重配 PL + `ps7_init` + 303 条相机表 | 断言全过，采集帧指针 **19 次/s** |

**第三行是这次最有价值的一步**：验证"XDC 里写了什么"只证明**我们要了什么**，
不证明**工具做了什么**。从 `io_placed.rpt` 读出来的才是**真的载进板子的那个产物**的引脚位置。
新脚本 `ps_fft_dual/check_io_placement.py` 干这件事，可复用于以后每次构建。

#### 顺手修掉的三个真问题

1. **`ps_run.tcl` 里一句裸写 `CR=0x00010003` 是危险动作，已换成检查。**
   PL 重配之后 VDMA 没有任何 geometry，**只写 CR 启起来的通道会报 `Halted=0` 却一个拍都不出**
   （本项目已栽三次）。重配后再跑 `ps_run.tcl` 是**第一次**会撞上这个场景的机会，所以改成：
   先读回 `VSIZE/HSIZE/ADDR1`，不对就**拒绝继续**并指明"先跑 live14"；确实 Halted 才按
   geometry → CR → **VSIZE 最后** 的顺序重臂。
2. **`ps_run.tcl` 里"SR 的 0x1000 位表示 Halted"是错的，已改。**
   实测 `CAP SR = 0x00015810`：bit12 **是置位**的，而采集**明显在跑**（帧指针在动），
   所以 bit12 不可能是 Halted。VDMA `DMASR`：bit0 = Halted，bit12 = IOC_Irq。
   这句错话此前被当事实抄了好几处。
3. **断言第一版自己写错了，被自己的好板子打了一次脸。**
   新加的启动断言用 `CR & 1` 同时判采集和显示两个通道。但 **CR 与 SR 极性相反**：
   `DMACR bit0 = RS`（1 = 运行），`DMASR bit0 = Halted`（1 = 停止）。
   健康的板子上显示 `CR = 0x00010003` → 读出 1 → **对自己的好板子报了假失败**并拒绝报告成功。
   教训照旧：**判据的"期望值"必须先在一个已知好系统上对过**，否则它不是守卫，是噪声源。

#### "面板颜色对不对"这件事：说清楚验到了哪一级

`ps_bootcheck.tcl` + `bootcheck_compare.py` 在**一次 JTAG 会话**里同时 dump
原始采集帧与正在扫描的 UI store，再按渲染器自己的管线
（2×2 盒平均 → 色调表 B×235/256、G/R 恒等）预测三通道均值比。

**它自报 INCONCLUSIVE，这个结论是对的。** 本场景接近中性
（原始 B/G/R 均值 114.4 / 98.1 / 111.9）：把**两个整通道对调**之后三个比值是
0.893 / 1.000 / 1.023，**仍然落在 ±6% 容差内**。
所以这个检验**通过也说明不了任何事** —— 脚本现在会先算"如果通道被对调，我这组数据能不能看出来"，
看不出来就报 INCONCLUSIVE 而不是 OK（`--selftest` 会演示这一点）。
单通道内的**位对交换**（b6↔b7、b4↔b5…）是 256 级的**置换**，均值几乎不变，
任何均值判据都看不见 —— 那需要面板上放已知色块拍照（`make_bars.py` / `measure_bars.py`）。

**所以颜色这一级是靠"引脚级验证"（上表第三行）关掉的，不是靠画面统计量。**

#### 一条明确没做的：不是物理断电冷启动

本次是 `rst -system` + JTAG 重配，**不是拔电重上**。
脚本幂等，真要物理冷启动，拔电重上后再跑同样两条命令即可。

### 场景控制：把"逆光救不了"变成可施工的数字 + 让仪器拒绝在饱和区下结论（2026-10-03）

前两轮已经证明软件救不了过曝（AEC 瞄准点扫描、双曝光融合 0.09% 回收）。
所以这一轮做两件软件该做的事：**把问题量到能施工的程度**，以及
**让仪器在信息已丢失的地方说"无法判定"，而不是照判**。

#### 一、量化：过曝区是**两层**，不是一层

从存档的同场景长/短曝光对（曝光比恰好 6.5）直接量：

| 量 | 数值 |
|---|---|
| 长曝光下 `green >= 248` 的像素 | 37 697 px = **4.09%**（另一帧量为 2.25%） |
| 其中**即使曝光再降 6.5 倍仍然饱和**的 | 5 057 px = 该区的 **13.4%** |
| 这些"硬核"像素的隐含辐亮度 | ≥ **6.5 × 满量程 ≈ 2.7 stops** |
| 其余 86.6% 的隐含辐亮度均值 | 480 = 1.9 × 满量程 ≈ **0.9 stops** |
| 硬核的位置（短曝光帧里的 bbox） | x 18..408 / 1280、y 0..222 / 720 → **左上约 1/3 × 1/3** |
| 按"让高光不过曝"去压曝光的代价 | 中位数 100 → 39（砍 2.5 倍）；硬核要再砍 6.5 倍 → 中位数个位数 |

**结论（可以直接拿去施工）**：
- 过曝**分两层**：一层只超出满量程不到 1 stop（约 1 stop 的衰减就能压住），
  另一层超出 **≥2.7 stops**，任何"还能看见房间"的曝光都救不回来。
- 硬核**集中在左上角约 1/3 × 1/3 的视场**，所以**遮光罩/改瞄准是有明确目标的**，
  不需要遮住整个视场。
- 要衰减而不是遮住的话，**至少 3 stops**。
- "全局压曝光"这条路被数字否掉：为了那个角，整幅中位数掉到个位数。

#### 二、仪器侧：饱和闸门（这是"可信成像"该有的行为）

**三态本来就为这种情况存在** —— 判不了就说判不了。软件做不了两件事之外的事：
把"哪里丢了信息"指出来，以及**拒绝在丢了信息的地方下结论**。

| 层 | 改动 | 验证 |
|---|---|---|
| 判定引擎 `app/engine.py` | `Inspect.inspect` **第 0 关**：`_saturated_fraction` 超限直接返回 `UNSURE`（"画面饱和，该区域信息已丢失"） | `test_engine.py` 自检三项全过 |
| PS 渲染器 `ps_ui/main.c` | 每帧统计削顶通道千分比 + **饱和区 bbox** + 闸门，发布到邮箱 244..272 | 板上实测 |
| 面板 | 闸门触发时在饱和区画 **2px 红框**（只描边不填充，填充会把要看的地方挡住） | 数值验证 + 反例 |

**引擎自检三项**（`test_engine.py`，不通过就不跑后面的混淆矩阵）：
1. **合成工件数据从不触发闸门**（实测最大码值 217 < 250）—— 否则它就在悄悄改那张混淆矩阵；
2. 含 2.3% 纯白的图 → `UNSURE`，且理由里写的是饱和；
3. **饱和帧不得进入参考图历史**（连喂 5 帧饱和图后历史长度 6 → 6）。
   —— 被烧掉的背景会污染之后每一件，宁可少一帧历史。

**"加上去没改结论"是单独证明的**：改前/改后同一组数据跑 `test_engine.py`，
逐行数值差异**只有新增的 5 行自检输出**，混淆矩阵、三态计数、逐批次数字**逐字节相同**。

**红框也是量出来的**（`check_clipbox.py`）：3384 个纯红像素，
**全部落在包围框的描边上、内部 0 个**；用加框之前 dump 的帧做**反例**，
同一个 bbox 下报 "NO outline pixels found" 并失败 —— 检查不是瞎过的。

#### 三、这一轮自己踩的坑：闸门**失效方向是开**的

第一次上板：`CLIP_PM = 4.40%` 而 `GATE = 0`。原因是我把限值做成**主机写**的字（字节 268），
而 `ps_run.tcl` **从没种过它** → PS 读到 DDR 垃圾 `0x91C8D0B2` → 被 clamp 到 1000 →
"永不触发"。**"永不触发"和"一切正常"在读数上分不开。**

两处都改了：
- PS：**超出范围回落到默认值**（而不是回落到"禁用"）。测量设备必须往"我判不了"的方向失效，
  **绝不能往"看着挺好"的方向失效**；
- 主机：`ps_run.tcl` 显式种入限值，并把"主机要求的限值"（268）和"PS 实际用的限值"（272）
  **两个都打出来**，否则这种事故永远不可见。

#### 四、顺手记账：邮箱数字是**逐字 JTAG 读**，不是一个快照

报告里 `CLIP_PM = 13.00%` 与 `CLIPLONG = 8.64%` 曾经对不上，看着像 PS 把同一个量算了两遍。
实际是**两次读之间隔了若干帧**（一帧 52 ms，一次 `mrd` 要毫秒级）。
现在报告里做了**交叉核对**：连着读"通道数"和"千分比"两个量并比较，一致就说明落在同一帧上，
不一致就明说是**读数跨帧**而不是代码矛盾，并给出**区分办法**（重跑：差值在变=跨帧；差值稳定=真 bug）。
实测 87‰ vs 84‰（差 0.3%）—— 落在同一帧附近。

### 帧率去哪了：相位计时（2026-10-03 晚）

"比之前慢了"不是一个结论。这一轮给 PS 装了**相位计时**，把一帧拆成
sync / class / qual / cam / panel / tail / pub 七段，于是"慢"有了地址。

#### 先造仪器，再造仪器：这台仪器自己错了三次

三次都会给出**看起来很确定**的错答案，而且每次的"症状"都像是**被测对象**的问题：

| # | 症状 | 真因 |
|---|---|---|
| 1 | 七段只占"总计"的 **40%**，推导出的时钟 **786 MHz** | 总计写成 `tG − 上一轮的 tA`，等于**一轮半**；786 MHz ≈ 2.36 × 333 MHz，正是"量了 2.36 轮"的样子 |
| 2 | 七段占"总计"的 **136.8%** | 九个计时字是**九次独立 JTAG 读**，跨了不同帧；而 `draw_camera` 的耗时确实逐帧变化，幅度足以把加法学反过来 |
| 3 | 同一个二进制连跑两次，`draw_camera` 一次 **67%**、一次 **94.6%**，`tail` 反向移动几乎同样的量 | **单帧采样 vs 平均帧率**：一帧的偶发变慢（首次访问、JTAG 快照后的冷缓存）被当成常态 |

修法（三处都改）：
1. 总计改成 **上一个循环末尾 → 这一个循环末尾**，每一段正好覆盖一次；
2. 邮箱改成 **一次 `mrd` 取整块**（`MBSNAP`），并**校验解析器**：拿固定字 SCTLR 与
   直接 `mrd` 对比，不一致就拒绝输出（避免把大小端猜错变成"看起来合理的数"）；
3. 上板发布的是 **32 轮累加和 + 轮数**，除法放在主机（PS 上除法要 libgcc 调用），
   并且**溢出保护写在值上**（`sum_total > 3e9` 就提前发布重置），不写在期望上。

**最后一点是这台仪器的自我确认**：修好之后
- 七段之和 = **100.0%**（缺 79 ticks，纯读噪声）；
- 由 `(每轮 ticks) × (实测 fps)` 反推的时钟 = **330.8 / 333.0 / 330.0 MHz**。

Cortex-A9 global timer 时钟是 CPU_3x2x，本设计应为 ~333 MHz ——
**这个值程序里从没写死过，它是被量出来的，而且落在本该在的地方**。
（顺带：计时器复位后是**关闭**的。程序先写 `GTIMER_CTL` bit0，再**确认它在动**，
把这次确认作为 `TIMER_OK` 发布；全 0 且 `TIMER_OK=0` 只表示"没测到"，不表示"每段都很快"。）

#### 答案

单曝光模式，平均 32 轮，整环 **61.0 ms（16.4 fps）**：

| 段 | 占环 | 时间 |
|---|---|---|
| **cam（draw_camera）** | **90.3%** | **55.0 ms** |
| class（失效 + 分类） | 5.1% | 3.1 ms |
| tail（底栏 + `dcache_clean` + park 翻转） | 2.7% | 1.6 ms |
| panel / qual / sync / pub | 1.3 / 0.7 / 0.0 / 0.0 % | 0.8 / 0.4 / 0 / 0 ms |

**一帧的 90% 就是那个逐像素渲染循环本身。** 其余全部加在一起不到 10%，
所以想再快只能动渲染器，动管道没有意义。

#### 据此修了什么

- **单曝光只失效它真正要读的那一个采集 store。** 融合路径必须失效两个（读两帧），
  单曝光只读一个，另外 2.7 MB 的失效是**没有任何东西会去看的工作**。已删。
- **测量了饱和红框的代价**：同一个二进制、同一场景，只改限值让红框画/不画 ——
  `draw_camera` 55.01 ms vs 54.88 ms，**差 0.13 ms = 0.2%**，等于免费。
  所以"加了饱和闸门把帧率拖慢了"这个怀疑被证伪。

#### 两条必须更正的旧数字

1. **之前的 18.7–19.3 fps 偏高了。** 那个算法用**标称**采样间隔（`i*600 ms`）做分母，
   而每次采样还要两次 JTAG 读、真实墙钟更长，帧计数却仍在增长 —— 分母偏小、分子不变，
   于是高估约 10%。现在用 `clock milliseconds` 量**真实**经过时间，得 **16.3–16.4 fps**。
2. **"比加这套东西之前慢 11%"这个说法不能再引用**。它建立在上面那个偏高数字上；
   而红框的 A/B 已经把新增代价的上界压到 **0.2 ms**。
   旧版（加闸门之前）的相位分解**没有测过**，所以那个差值我**不再给归因** ——
   想知道就得把旧版编一份上来量，这是待办，不是结论。

### "像手机一样不怕光源"：三种方法在同一条辐射度图上对比（2026-10-03）

**问题**：手机拍同一个逆光场景好看，这台相机拍出来是"过曝的窗 + 发暗的房间"。
三轮已经证明换曝光、两帧**线性**融合都救不了。那就把"手机到底做了什么"拆开量。

**方法**：先用已有的长/短曝光对（比值 6.5）重建**辐射度图**，再让三种映射跑在
**同一张辐射度图**上 —— A 线性（今天板子的做法）、B 全局对数曲线、
C 局部（base/detail，手机做的事）。脚本 `ps_ui/phone_like.py`，产物
`phone_A_linear.png` / `phone_B_global.png` / `phone_C_local.png`。

#### 结论 1：物理要的曝光数，是量出来的

重建出的辐射度图：中位 82、p99 **1089**、最大 **1627** = **满量程之上 2.7 stops**，
而 **1.62% 的像素即使加上短曝光仍然超量程**（两档全饱和 = 没有任何测量）。
→ **还需要约 2.7 stops**，也就是再要一档比最长曝光**短约 6 倍**的曝光。

#### 结论 2：今天这套 A 是三者里最差的，而且"缺陷灵敏度"随背景变 3.7 倍

对**同一个物理缺陷**（+12% 辐射度的圆斑）在三种背景亮度下量输出对比度：

| 背景辐射度 | A 线性（今天） | B 全局对数 | C 局部（手机） | C/A |
|---|---|---|---|---|
| 40（暗） | 4.43 | 4.48 | 5.05 | 1.14 |
| 140（中） | 16.59 | 4.99 | 16.04 | 0.97 |
| 250（亮） | 7.55 | 4.58 | 12.67 | **1.68** |
| **离散度** | **3.7×** | **±6%** | 1.7× | 0.71 |

- **A 今天就有 3.7 倍的不均匀**，真因是**削顶**（亮背景下缺陷被截平）。
  也就是说：**"缺陷灵敏度随位置变化"不是引入局部映射才会有的问题，现在就有，而且更严重。**
- **B（全局单调曲线）最均匀（±6%）**，同时把亮度均值 85 → 115、削顶 1.82% → 1.42%。
  代价是细节变软（高通 sd 17.15 → 10.69）。
- **C（局部）保住了细节（19.01）**，但灵敏度随背景变 1.68 倍（离散 0.71）——
  **它对"看得好看"有帮助，对"当仪器用"有害**。
- 三者**都不会**在"没有任何曝光测到"的区域**编造**纹理（该区输出 sd = 0.00 / 1.97 / 0.00）——
  这一条很重要：它说明这些算子没有无中生有。

#### 结论 3：手机的样子，主要不是靠色调映射算子换来的

C 的画面（`phone_C_local.png`）和 A 相比**只是略亮略软**，并没有变成手机那样。
原因是量出来的：这张辐射度图**只比满量程高 2.7 stops**，
"压缩高光"这一步几乎没有东西可压。**要像手机，先要有手机的动态范围数据。**

#### 因此这个"新方法"是：静态工件的**多帧曝光堆叠**，而不是更花哨的色调映射

工件在夹具上是**静止**的 —— 这正是手机做不到而我们能做到的地方：手机必须**去鬼影**，
我们不必。所以：

1. 采集侧连续取 **N 档曝光**（本例 N=3 就够：1× / 6.5× / ~39×，覆盖到 5 stops 以上；
   留余量取 4–8 档）；
2. 叠成一张真正的辐射度图（每像素取"未饱和且最亮"的那一档，重叠区加权融合）；
3. **测量通道**用 **B：全局单调曲线**（实测最均匀，且单调 ⇒ 可反解回辐射度，可标定）；
4. **显示通道**才叠加 C 的局部增强，**只给人看，绝不参与判定**。

**代价**：takt 时间。16 fps 下 8 档 = 0.5 s/件。**这是用节拍换动态范围，不是免费的。**

**这一点必须说清楚**：N 档也救不了"所有档都饱和"的像素 —— 上表的 1.62% 就是这种。
它们唯一的解仍然是**场景控制**（遮光/改瞄准），仪器能做的只是**拒判 + 指出位置**（已实现）。

#### 本轮自己的两个测量错误（都在同一个脚本里，都先给出了"结论"）

1. **拿圆斑外的一圈当参考** —— 而那一圈在场景亮度梯度上，于是同一个物理缺陷
   在某些位置量出**负**对比度（亮的圆斑量出负值）。真因是**参考里含梯度**，
   不是缺陷。改法：与**同一像素在未注入缺陷的那张图**相减，梯度被精确抵消。
2. **"没有数据"的掩膜写成 `R > 255`** —— 那只是"比满量程亮"，
   而重建时乘了 6.5，几乎每个过曝像素都满足。于是把**测到过**的像素标成"没测到"，
   在辐射度**常数**的区域报出很大的方差。**数字与算术矛盾时，是掩膜错了，不是发现。**
