# STM32 传送带接口协议（PC ⇄ STM32，2026-10-24）

> 面向：STM32 侧固件负责人。
> 目标：让 PC 能命令传送带**停 / 走 / 询问状态**，并且在**通信失联时自动停**。
> 本文件是**建议规范**，实现前请一起确认；改动请回写本文件的版本号。
> **版本 v1.1（2026-10-25）**：补上 XOR 的范围与算例（§4，这一点曾让 PC
> 与固件互不理解）、增加诊断命令 0x05/0x06（§5）、补 FAULT 粘滞规则（§6）、
> 补实测时序（§7）。

---

## 1. 为什么是 PC 做桥，而不是 FPGA 直接连 STM32

已核实的硬件事实：AX7020 的 **UART1（MIO48/49，3.3V 电平）已经接到板载 CP2102**，
插 Micro USB 就在 PC 上是一个 COM 口。所以：

```
Zynq ──(已存在) USB → CP2102 → PC 的 COM_A
STM32 ──(需加一个 USB-TTL 模块) → PC 的 COM_B
PC：读 A 侧的判定，向 B 侧发命令
```

**好处**：FPGA 侧一根线都不用加、不用改引脚、不用重建位流；你那边只要接 PA9/PA10/GND。

---

## 2. 物理接线（STM32 侧）

| STM32 引脚 | 接到 | 说明 |
|---|---|---|
| **PA9 (USART1_TX)** | USB-TTL 模块的 **RXD** | 交叉接 |
| **PA10 (USART1_RX)** | USB-TTL 模块的 **TXD** | 交叉接 |
| **GND** | USB-TTL 的 **GND** | 必须共地 |
| — | USB-TTL 的 VCC **不接**（除非模块需要供电） | STM32 自己由 USB 供电 |

**电平必须是 3.3V TTL**，不能接 RS-232，不能接 5V 信号。
**上电顺序**：先上 STM32（此时电机必须处于停止），再开 PC 端脚本。

## 3. 串口参数

```
115200 bps，8 数据位，无校验，1 停止位（8N1），无流控
```

## 4. 帧格式（PC → STM32 与 STM32 → PC 相同）

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0 | `0xA5` | 帧头 |
| 1 | `CMD` | 命令码 |
| 2 | `SEQ` | 序号 0–255，PC 递增；STM32 回显 |
| 3 | `DATA0` | 参数 / 状态 |
| 4 | `DATA1` | 参数 / 结果码 |
| 5 | `XOR` | **第 1..4 字节（CMD、SEQ、DATA0、DATA1）逐字节异或；不含帧头 `0xA5`** |

固定 6 字节。**接收方必须处理分包、粘包、错帧、断帧**：找不到帧头就丢弃；
一帧超过 **50 ms** 未收齐 → 丢弃并重新找帧头。

> **⚠ XOR 范围（2026-10-25 踩过的坑，务必照抄）**：XOR **不包含** `0xA5`。
> 例：`GET_STATUS` 应答 `CMD=0x84, SEQ=0x01, DATA0=0x00, DATA1=0x00`，
> 则 `XOR = 0x84 ^ 0x01 ^ 0x00 ^ 0x00 = 0x85`，整帧为
> **`a5 84 01 00 00 85`**。旧固件曾把 `0xA5` 也算进 XOR（那会得到 `0x20`），
> 于是 `dl/host_qc/stm32_link.py` 一个应答也解析不出来——现象是"板子明明在回
> 字节，PC 却说超时"。不要重新推导成 5 字节版本。
> 判定方法：抓到一帧应答，若末字节 == 前 5 字节的异或，就是错的。

## 5. 命令

| CMD | 名称 | DATA0 | DATA1 | 说明 |
|---|---|---|---|---|
| `0x01` | STOP | 0 | 0 | 立即停，关闭 PWM/输出拉低；**同时清除 FAULT** |
| `0x02` | RUN | 占空比 1–100 | 0 | 正转；0 或 >100 视为参数错误；**夹到当前上限**（出厂 100 %，诊断旋钮 3 可临时改）；FAULT 中拒收（结果码 2） |
| `0x03` | HEARTBEAT | 0 | 0 | PC 每 **200 ms** 发一次 |
| `0x04` | GET_STATUS | 0 | 0 | 查询，不改变状态 |
| `0x05` | WORD（诊断） | 字索引 | 0=低 16 位 / 1=高 16 位 | 回 `DATA0/DATA1` = 该字那一半（小端） |
| `0x06` | KNOB（诊断） | 旋钮号 | 值 | 0=输出方式(0 定时器AF/1 软件PWM)，1=旧语义复现，2=软复位，3=占空比上限（0–100，不保存，复位回 50） |

**应答**：`CMD = 请求 CMD | 0x80`，`SEQ` 回显，
`DATA0` = 状态（**0 停止 / 1 运行 / 2 故障**），
`DATA1` = 结果码（**0 接受 / 1 参数错误 / 2 状态不允许**）。
例外：`0x05` 的应答里 `DATA0/DATA1` 是诊断数据，不是状态/结果码；
`0x85` 的帧长仍是 6 字节，老主机照样能解析这一帧。

诊断字（`0x05` 的索引）见 `dl/stm32_conveyor_main.c` 的 `DW_*` 定义与
`dl/host_qc/stm32_link.py` 的 `DW` 表；`DW_RUN_CMDS`、`DW_STOP_CMDS`、
`DW_STOP_WHY_*`、`DW_LAST_STOP_CAUSE`、`DW_HB_GAP_MS` 就是回答
"谁叫的停" 与 "失联判定了多久" 的那几个。**这几个命令是本次加的**，老固件
对它们回结果码 2，不影响原有 0x01–0x04。

## 6. 状态机与安全规则（这几条比协议本身重要）

1. **上电默认停止**：初始化后立刻 `INA=0, INB=0`，不要沿用旧固件那种"上电跑 10 秒"。
2. **失联停止**：**500 ms 没收到心跳就停**。这是唯一的自动保护，必须实现。
3. **主循环不许被 `delay_ms` 阻塞**：现在的 `delay_ms()` 会卡住一切，
   UART 必须用**中断 + 环形缓冲**，主循环解析。
4. **非法参数不执行**：`RUN` 的占空比非法 → 回结果码 1，保持当前状态（若在运行，允许继续）。
5. **序号幂等**：同一 `SEQ` 的重复命令不得导致重复启动动作。
6. **超时停机后清空接收队列**：不能把缓存里的旧 `RUN` 当成新的启动授权。
7. **STOP 优先级最高**：任何时刻收到的 `STOP` 必须在一个主循环周期内生效。
8. **FAULT 是粘滞的（v1.1 新增，实测过的坑）**：失联停机置 **2** 之后，
   **心跳不许把 2 改回 0**。心跳只证明 PC 还活着，不证明故障已排除。
   只有 `STOP` 能把 FAULT 清成 0；FAULT 中收到 `RUN` → 结果码 **2**，不动电机。
   旧固件在心跳里做了 `if (state == FAULT) state = STOPPED`，于是"失联停机"
   在日志里表现成 **state 0**（不是 2），查了很久才发现是心跳把故障抹掉了。
9. **RUN 自带宽限（v1.1 新增）**：一条 `RUN` 本身就是"PC 刚说过话"的证据，
   所以 `RUN` 要把心跳时间戳打在当前时刻，给 500 ms 的宽限。旧固件没打这个
   时间戳，复位后时间戳还是 0，`RUN` 之后主循环第一圈就判超时 → 电机 0 ms
   都转不了，而 `RUN` 的应答已经回了 state 1。这就是"RUN 之后一秒变 0"的根因。

## 7. 时序

| 项 | 值 |
|---|---|
| PC 心跳周期 | 200 ms |
| STM32 失联判定 | 500 ms 无心跳 → 停止 |
| 单帧超时 | 50 ms |
| **实测失联判定（2026-10-25，STM32F103C6）** | **501 ms**（`DW_HB_GAP_MS`，两次独立测量都是 501；PC 侧括号 494–506 ms） |
| **实测 1 ms 时基** | 板载 `g_ms` 与 PC 单调钟比 **1.0006**（2006 ms vs 2005.7 ms），确认跑在 72 MHz 而不是 HSI |
| **实测：皮带开始动的最小占空比** | **100 %**（40 % 与 70 % 只嗡不转；软件与硬件通路在 100 % 都能带动皮带） |
| **出厂默认：输出通路 / 占空比** | `TIM3_CH1` 复用 20 kHz / **100 %**（软启动约 0.8 s） |
| 命令应答超时（PC 侧） | 200 ms，超时重发 2 次 |

## 8. 建议的第一阶段实现范围

先只做：**上电停止 + 解析 STOP/RUN/HEARTBEAT/GET_STATUS + 心跳超时停止**。
**PWM 调速、反转、加减速曲线都放到第二阶段** —— 现在 `PA6/PA7` 是普通 GPIO，
改成 `TIM3_CH1` PWM 需要重新配置复用和定时器，且频率/最低启动占空比必须实测。

> **2026-10-25 更新：两条输出通路都做完了，默认是 `TIM3_CH1` 复用 20 kHz、100 %。**
>
> 台架实测（`dl/host_qc/stm32_hold.py`，时间窗事先公布）：
> - 软件 PWM 40 %：电机发出 250 Hz 可闻嗡声，**皮带不动**；
> - 软件 PWM 70 %：**皮带不动**；软件 PWM 100 %：**皮带动**；
> - 硬件 PWM（复用 20 kHz）40 %：**听不到任何声音、皮带不动**；
>   硬件 PWM **100 %：皮带动**。
>
> 100 % 那一段是关键：两条通路在 100 % 都是**直流**、没有开关动作，所以在
> 这个占空比上"软件能动、硬件不能动"才是复用通路坏了的证据。实测两条都能动，
> 于是之前"复用通路是死的"这个结论**被推翻**——它来自 20 kHz 在听觉之外这一
> 混淆（堵转电机在 20 kHz 上是静音的，在 250 Hz 上会嗡）。**"没声音"不是
> 证据；示波器或 100 % 直流段才是。** 复用通路因此成为默认（不占 CPU），软件
> 通路保留为可切换的退路（`0x06` 旋钮 0）。
>
> **占空比上限从 50 % 提到 100 %，这是按实测改的，不是放宽着玩**：在 5 V 经
> L9110S 驱动这台电机/减速箱时，40 % 与 70 % 都克服不了皮带的摩擦，只有接近
> 满占空比才动。也就是说**这台传送带没有可用的调速区间，实质是开/关**。对
> "检出即停"的产线逻辑这够用，但这是**硬件余量不足**的结论，必须写进局限：
> 想调速/提力，要换更高电压或更大扭矩的电机，不是改固件。8 ms/1 % 的软启动
> 仍在（限制浪涌），500 ms 失联保护仍在，这两条没有因为提高上限而放松。
>
> **粘包（两帧连写）目前不支持，这是实测的已知限制**：主循环一次只取一个字节，
> 而回一帧要占用约 520 µs（6 字节 @115200），这期间第二帧的字节把只有 1 字节
> 的 RX 寄存器冲掉。实测两帧连写时只回了第一帧，`overrun +1`、`resync +2`，
> 第二帧丢失——**丢失，但不会被伪造成命令**。主机是一问一答（等应答再发下一
> 帧），所以正常联调不会触发；真要支持粘包，得做 §6 第 3 条说的
> "中断 + 环形缓冲"，本次未做。

## 9. 联调验收顺序（每步都能独立失败）

| 步 | 做什么 | 通过判据 |
|---|---|---|
| A | 不接电机，只做串口 | PC 发 `GET_STATUS`，STM32 回 `0x84` + 合法 SEQ + 状态 |
| B | 接电机但空载 | `STOP` 立即停；`RUN` 转；再 `STOP` 停 |
| C | 拔掉串口线 | **500 ms 内电机停**（失联保护） |
| D | 重复发同一 `SEQ` 的 `RUN` | 只启动一次，不重复动作 |
| E | 故意发错帧（错 XOR、缺字节） | 不执行、不崩、继续找帧头 |

## 10. PC 侧已实现（本仓库）

- `dl/host_qc/stm32_link.py`：
  - `stop()` / `run(duty)` / `status()` / `heartbeat_loop()`；
  - `--dry-run` 用内置模拟器跑完整协议，**不需要硬件也不需要 pyserial**；
  - `--selftest` 验证组帧、XOR、超时重发、非法应答处理；
  - `read_word()` / `knob()`：读诊断字、设诊断旋钮（v1.1 新增）。
- `dl/host_qc/stm32_conveyor_probe.py`（v1.1 新增）：**实测验收工具**。
  一条命令跑完"复现旧故障并读出谁叫的停 → 40 % 跑 8 s → 断心跳量 500 ms →
  FAULT 粘滞 → 软件 PWM 窗口 → 复位查上电停止"，把每次的计数器写进
  `dl/host_qc/logs/stm32_probe_*.log`：
  `python dl/host_qc/stm32_conveyor_probe.py --port COM7 --motor --duty 100 --seconds 8 --pause 2`
  （`--motor` 是安全闸：不给它，脚本绝不转电机。）
- `dl/host_qc/stm32_hold.py`（v1.1 新增）：**给万用表/人眼用的定时窗口**。
  按事先公布的墙钟时间跑三段（硬件 PWM 40 % / 软件 PWM 40 % / 软件 PWM 50 %），
  每段打印起止时间，段间有停车：
  `python dl/host_qc/stm32_hold.py --port COM7 --start-at 19:12:30`
  只用于"把表的读数绑定到某一时刻"；结论仍然要人看。
- 用 `--port COM7` 指到你的 USB-TTL 模块。

**你的固件一就绪，我们可以用 A–E 五步联调，每步都是分钟级。**

> **2026-10-25 实测结论**：A–E 五步全部通过（`dl/host_qc/logs/
> stm32_probe_20261025_190242.log` 与 `..._190916.log`，各 34/34 项自动判据）。
> 失联判定实测 **501 ms**（两次独立测量，PC 侧括号 493–506 ms），FAULT 粘滞、
> `RUN` 在 FAULT 中被拒、`STOP` 清故障、上电停止都已验证。**电机确实转了，但
> "转"这个结论来自操作员的眼睛，不是来自任何计数器**，所以脚本里它永远不作为
> PASS 项。
>
> **万用表读数的教训（值得单独记一笔）**：在同一时间窗里先后读到 PA6 = 0.0 V
> 和 INA = 0.0 V，结论一度写成"引脚没在驱动"；随后操作员看到轴在转，把这两个
> 读数推翻了。直流表接在开关输出上、探头点不对、或者窗口已经结束，都会给出
> 0.0 V。同一时期"PA6 稳态 3.3 V 说明引脚正常"也不成立：`stm32_pin_test.c`
> 的 1 Hz 翻转依赖 TIM4，而当时 TIM4 的 UIF 根本不触发，引脚只是被第一圈循环
> 拉高后再没动过——3.3 V 是**卡住的高电平**，既不是翻转，也不能证明 TIM3 复用
> 通路。**开关输出上的直流表读数不能当证据**：要么用示波器，要么用人眼配合
> 明确的时间窗（`dl/host_qc/stm32_hold.py` 就是为后者写的）。
