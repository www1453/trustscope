## B1 · 脚本打印 "done"，但设计什么都没改（**最危险的一条**）

**触发条件**
用 Tcl 脚本遍历 BD 对象做"查找 → 修改"，尤其是**拿 `get_property NAME` 的结果当路径**。

**现象**
脚本顺利跑完、打印 `done`、没有报错。**但设计完全没变。**

**根因**
**BD pin 的 `get_property NAME` 返回的是"局部名"，不是完整路径。**
例如 pin 的完整路径是 `ila_0/probe3`，而 `NAME` 返回 `probe3`。
把这个局部名当路径去 `get_bd_nets` 查，**查不到任何东西** ——
而"查不到"不会报错，于是匹配全部落空，修改一个都没做。

最要命的是：**脚本不会告诉你它匹配到 0 个对象。**

**排查步骤**
1. 检查所有 `get_*` 的返回值，看**数量**对不对：
   ```tcl
   set pins [get_bd_pins -quiet ...]
   puts "found: [llength $pins]"
   if {[llength $pins] == 0} { puts "NOT FOUND -- CHECK THIS" }
   ```
2. **问自己一句话**：*"如果这一步什么都没找到，我的输出会告诉我吗？"*
   如果答案是"不会"，这就是静默失败。

**修复**
- 查 net **必须传 pin 对象**，不要传名字：
  ```tcl
  set net [get_bd_nets -quiet -of_objects $pinobj]   ;# 正确
  ```
- 每个查找都打印结果；**空结果必须显式打印 `NOT FOUND`**
- 循环结束打印**实际处理了几个对象**
- 关键步骤后加断言，不满足就 `error` 中止

**适用 / 失效条件**
- 适用：所有 Vivado BD Tcl 脚本
- 失效：—

**来源**
本队真实踩坑：一个"自动修复 ILA probe 冲突"的脚本打印了
`ILA probe/clock conflict check done`，看起来完全成功。
实际上每个 probe 的 net 都查成了空字符串，**一个都没匹配上，什么都没修**。

## B2 · 改完 BD 后报 `[BD 41-758] 时钟引脚没有有效时钟源`

**触发条件**
想"重新连接"某个已有信号，于是写了这样的辅助函数：
```tcl
proc reconnect {a b} { disconnect $a; disconnect $b; connect $a $b }
```

**现象**
```
ERROR: [BD 41-758] The following clock pins are not connected to a valid clock source
```
**整条时钟网络被切断了。**

**根因**
这个辅助函数**看起来是幂等的，实际不是**。
当 `a` 是一个**已经在驱动很多负载的源引脚**（如系统时钟）时，
`disconnect $a` 会把**整条 net 撕掉** —— 所有负载同时失去时钟。

**排查步骤**
1. 确认你 disconnect 的是**源**还是**汇**：
   - 源引脚（`DIR == O`）：**绝对不能随便 disconnect**
   - 汇引脚（`DIR == I`）：安全
2. 报 `[BD 41-758]` 时，直接查那几个时钟引脚的 net 是否为空

**修复**
**要分接一个已有信号，只 ADD 新引脚，不要动已有的：**
```tcl
connect_bd_net [get_bd_pins <已经存在的源>] [get_bd_pins <新汇>]
```
**不要**先断开再连。

**保存前加护栏（guard）**，确认共享基础设施还在：
```tcl
foreach g {processing_system7_0/FCLK_CLK0 processing_system7_0/FCLK_CLK1} {
    set n [get_bd_nets -quiet -of_objects [get_bd_pins -quiet $g]]
    if {[llength $n] == 0} { error "GUARD FAILED: $g has no net. NOT saving." }
}
```

**适用 / 失效条件**
- 适用：所有 BD Tcl 编辑
- 失效：—

**来源**
本队真实踩坑：BD 修补脚本一度把视频时钟网切断，综合才暴露问题。
护栏机制加入后未再复发。

## B3 · 综合报某个标识符"语法错误"，但代码看起来没问题

**触发条件**
给 Verilog 模块内部的变量命名时**没有避开保留字**。

**现象**
```
ERROR: [Synth 8-27] syntax error near 'buf'
```
而 `buf` 这个词看起来完全正常。

**根因**
`buf` 是 **Verilog 的门级原语关键字**（三态缓冲器）。
它是保留字，**不能用作信号名、变量名或存储器名。**

**排查步骤**
1. 语法错误指向一个"看起来正常"的标识符时，**先查它是不是保留字**
2. 常见容易撞的：`buf` `not` `and` `or` `xor` `nand` `nor` `xnor`
   `wire` `reg` `input` `output` `inout` `bufif0` `bufif1`

**修复**
换名（如 `buf` → `mem`、`sample_mem` 等），**不要试图用转义**。

**适用 / 失效条件**
- 适用：Verilog / SystemVerilog
- 失效：—

**来源**
本队真实踩坑：采样器的存储器命名为 `buf`，
`create_bd_cell` 直接失败；改名 `mem` 后通过。

## B4 · 脚本第一次跑成功，第二次报"已经连接"

**触发条件**
增量修改脚本被**重复执行**（协作、重跑、恢复现场）。

**现象**
第二次运行报错中断，或者反向把已经正确的连接又改坏了。

**根因**
脚本没有做**幂等性**设计：创建对象前不检查是否存在，连接前不检查是否已连。

**修复**
三个标准范式：
```tcl
# 1) 创建前检查
if {[get_bd_cells -quiet $name] eq ""} { create_bd_cell ... }

# 2) 连接前检查目标引脚是否已连
set existing [get_bd_nets -quiet -of_objects $dpin]
if {[llength $existing] > 0} { puts "  already connected"; return 0 }

# 3) 断开前检查是否已断
```

**适用 / 失效条件**
- 适用：所有自动化修改脚本
- 失效：—

**来源**
本队真实踩坑。修复后，`templates/bd_patch_template.tcl` 在同一个 BD 上
**重复执行 3 次以上，结果一致且无报错**。

## B5 · 改了 BD，但改动没生效（忘了保存）

**触发条件**
脚本编辑 BD 后**校验失败**，或脚本中途出错退出。

**现象**
重新综合出来的比特流和改之前一样。

**根因**
`validate_bd_design` 失败时，**`save_bd_design` 不会执行**，
于是改动只存在于内存中，**磁盘上的设计还是旧的**。

**排查步骤**
1. 确认脚本最后的输出里有没有 **`DONE: BD validated and saved`**
2. 检查 BD 文件（`.bd`）的**修改时间戳**是否晚于你运行脚本的时间

**修复**
- 脚本末尾必须**显式打印终态**：`DONE` 或 `FAILED: <原因>`
- **绝不要在校验失败时强行保存** —— 失败即中止，磁盘设计保持完好

**适用 / 失效条件**
- 适用：所有 BD 编辑流程
- 失效：—

**来源**
本队真实踩坑。**这也是"校验失败反而保护了你"这个设计原则的来源。**

## B6 · CPU 轮询 PL 的一个"完成"标志，永远读不到

**触发条件**
PL 侧产生一个完成标志供 CPU 轮询（`while(!(reg & DONE))`），
而该标志**只在满足条件的那一拍为 1**。

**现象**
CPU 轮询了几百万次，**一次都没看到标志置位** —— 而 PL 逻辑本身是对的。
实测代价：每帧空转满 500 万次轮询预算，**每帧约 1.9 秒**，帧率掉到 0.5 fps；
屏幕上的帧率读数显示"1"。

**根因（两层，叠加在一起）**
1. **PL 侧**：FSM 在缓冲区填满的那一拍置 `done`，
   但**下一拍就自己重新启动**并把 `done` 清零 ——
   因为 CPU 写进去的"重启位"**一直保持为 1**（CPU 之后只读不写）。
   → `done` 只维持**一个 50 MHz 周期 = 20 ns**。
2. **CPU 侧**：轮询一次约 380 ns。
   **20 ns ÷ 380 ns ≈ 5%** —— 几乎必然错过。

**为什么"以前是好的"**
原来的触发条件**还要求另一个信号的上升沿**，重启要等到那个边沿（31.7 µs 后），
`done` 因此能维持 31.7 µs，CPU 轻松抓到。
触发条件一改，重启变成"立即"，**这个一直支撑着系统工作的隐式延迟就消失了**。

**排查步骤**
1. 算两个数并比较：**标志的高电平持续时间** vs **CPU 的轮询间隔**
2. 查 PL 侧：标志置位后**什么条件会让它清零**？那个条件是不是一直成立？
3. 查"以前能用"的原因里，有没有**一个已经消失的隐式延迟**
   —— 这类依赖是隐形的，改别的地方时会一起崩

**修复（两侧都要做）**
- **PL 侧**：让 `done` **锁存**，直到下一次明确的重启请求才清零
- **CPU 侧**：重启脉冲要**保持足够长再释放**
  ```c
  Xil_Out32(CTRL, REARM);     /* 置位                            */
  delay_us(10);               /* 保持 10 us，保证 50 MHz 侧一定采到 */
  Xil_Out32(CTRL, 0);         /* 释放，让 done 能锁存             */
  ```
  ⚠️ **两次写只隔几个 CPU 周期时，可能跨不过 PL 的一个时钟沿**
  —— 置位与释放之间**必须有明确的延时**，不能靠"写两次"。

**适用 / 失效条件**
- 适用：跨时钟域 / 跨处理器的标志轮询（PL↔PS、双核、外设状态位）
- 失效：用中断、或 PL 侧锁存 + CPU 明确应答，可彻底避免

**来源**
本队真实踩坑。**这条的核心教训是：**
> **"CPU 一定能抓到 PL 的标志"这个效率假设，从来没有人验证过。**
> 它一直靠另一个偶然存在的延迟在维持；那个延迟一消失，系统就静默地慢了 4000 倍。

它和 M10（把返回值丢掉）叠加在一起，让故障拖了很多轮 ——
**标志读不到**（B6）和**没人记录"读不到"这件事**（M10）同时发生，
缓冲区读回来全是 0，于是"采集没启动"和"输入恒为 0"看起来一模一样。

## B7 · 缓存了 BD 对象引用，中间一改设计它就失效了

**触发条件**
用 Tcl 脚本改 BD 时，把 `get_bd_nets` / `get_bd_pins` 的结果**存进变量**，
中间又做了 `create_bd_cell` 之类**修改设计**的动作，之后再拿那些变量去用。

**现象**
```
ERROR: [BD 41-701] connect_bd_net requires at least two pins/ports,
                   or one pin/port and a net
```
而那个 net **上一行刚刚打印出来、明明是非空的**。

**根因**
**修改 block design 会让之前取到的 BD 对象句柄失效。**
变量里存的**不是"名字"，而是对象引用**；设计一变，引用就指向不存在的对象，
于是 `connect_bd_net` 收到的参数形同虚设 ——
报出来的是"参数个数不够"，**和真实原因毫无关系**。

**排查步骤**
1. 报错说"参数不对"，但你能确认参数确实存在 → **优先怀疑对象引用失效**
2. 在报错的那一行**现场重新 get 一次**，看是否立刻恢复正常

**修复**
**永远不要跨"修改设计"这个动作缓存 BD 对象。** 每次用之前重新解析：
```tcl
proc NetOf {pinpath} {
    set p [get_bd_pins -quiet $pinpath]
    if {$p eq ""} { return "" }
    return [get_bd_nets -quiet -of_objects $p]
}
# 连接尽量 pin 对 pin，不要 pin 对"缓存的 net"
connect_bd_net [get_bd_pins capture_ram_0/aclk] [get_bd_pins spi_gen_0/aclk]
```

**适用 / 失效条件**
- 适用：所有修改 BD 的 Tcl 脚本
- 失效：只读脚本（连续 get 不修改设计）不会碰到

**来源**
本队真实踩坑。注意这次**没有任何东西被破坏** ——
脚本没走到 `save_bd_design`，BD 文件的**时间戳和大小前后完全一致**。
这正是"校验失败绝不保存"（B5）这条设计在兜底。

## B8 · 自相矛盾的前置条件，让脚本在成功前一刻中止

**触发条件**
脚本里写"如果 X 不成立就中止"，而 **X 恰恰是这段代码自己要去建立的东西**。

**现象**
脚本把前面**所有步骤都做完了**，却在最后一步中止，
报一个看起来像"环境不对/没接好"的错误。

**真实例子**
```tcl
set want [NetOf xlconcat_probe/dout]
if {$want eq ""} { error "concat not wired" }          ;# 要求输出已经有网表
...
connect_bd_net [get_bd_pins xlconcat_probe/dout] $probe_pin   ;# 正是它来建这个网表
```
`xlconcat_probe/dout` 在**还没接下游时本来就没有网表** ——
Vivado 里**没有负载的输出引脚不产生 net**，
所以 `get_bd_nets -of_objects` 返回空是**正常状态，不是错误**。

这个检查等于在说：**"你必须先连上，我才允许你连。"**

**排查步骤**
1. 看中止的那一步，**是不是本来就要建立那个条件**
2. 对**输出引脚**特别小心：没有负载时不产生 net 是正常的

**修复**
- 前置条件只检查**输入端**（源端存在、必填参数非空）
- **输出端**该做的是"直接接"，而不是"先检查它有没有被接"
- 幂等判断改用**名字匹配**，而不是"有没有网表"：
```tcl
if {[string match "*xlconcat_probe*" $have]} { puts "already connected" }
```

**适用 / 失效条件**
- 适用：所有带前置检查的自动化脚本（不只是 Vivado）
- 失效：—

**来源**
本队真实踩坑。**"防御性检查"本身也会成为故障源** ——
写检查的时候要问一句：*"这个条件，是这段代码执行前就应该成立的吗？"*

## B9 · 给 interface 引脚加负载，等于把接口绑定**换掉**（**只报 WARNING**）

**触发条件**
想观测一个属于 **interface**（接口）的信号 —— 例如把某根总线接进 ILA / concat / GPIO
—— 于是用 `connect_bd_net` 把它连到自己的网络上。

**现象**
```
WARNING: [BD 41-1306] The connection to interface pin </processing_system7_0/I2C1_SCL_I>
         is being overridden by the user with net <Net>.
         This pin will not be connected as a part of interface connection <IIC_1>.
CRITICAL WARNING: [BD 41-759] The input pins ... are either not connected or do not
                  have a source port ... These pins are tied-off to all 0's
```
**`validate_bd_design` 通过了**（只有警告），BD **保存成功**，脚本打印 DONE。
但那个网络里**两端都是输入、没有任何驱动源**。

**根因**
**interface 连接不是网络（net）。**
接口引脚在接口内部被绑定到源信号；一旦对它做**显式**连接，
Vivado 会**把它从接口绑定里摘出来**（"overridden by the user"）—— **原来的源就没了**。

| 目标引脚类型 | 显式连接的含义 |
|---|---|
| **普通 pin** | **追加负载** ✓（一个源可以驱动任意多个消费者）|
| **interface pin** | **替换绑定** ✗（源被摘掉）|

**最容易骗人的地方：它只报 WARNING，不报 ERROR。**
脚本的 `validate_bd_design` 会"通过"，然后你心安理得地保存了它。

**排查步骤**
1. 接信号之前先问：**这个引脚是普通 pin 还是 interface pin？**
   ```tcl
   get_bd_intf_pins -quiet -of_objects [get_bd_cells <cell>]
   ```
2. **接之前先记下它的 net**：如果 `NetOf <pin>` 返回**空**，
   往往意味着**它由接口驱动**，而不是"没接"。
   —— 这个"空"是**警告信号**，不是"可以随便接"。
3. 接完**认真读 validate 的 WARNING**，不要只看它有没有通过
4. 特别警惕 `41-1306` + `41-759` **成对出现**

**正确做法（按代价从低到高）**
- **首选：不要碰接口引脚。** 去找那个信号的**普通网络**版本，
  或从接口的**外部端口侧**取
- 次选：把接口**显式展开**成 O/T/I 三态 + 一个 IOBUF，
  把线上的实际电平引出来当普通网络用
  （这是"从接口内部取真实电平"的标准做法，但会改动接口本身，风险高）
- **最后才考虑**：为了可观测性去改一个**已经工作**的接口

**适用 / 失效条件**
- 适用：Vivado 所有带 interface 的 BD 修改脚本
- 失效：目标引脚确实不属于任何 interface

**来源**
本队真实踩坑。本意是"给 I2C 总线加一个观测负载"，实际把 PS7 的 I2C 输入引脚
从接口绑定里摘了出来，**I2C 回读被摘空了**，而我看到 `validate ok` + `saved` 就以为成功了。
（硬件因该改动从未被综合而幸免 —— 见 B10。）

## B10 · BD 被改坏之后：先判断"坏在哪一层"，再决定恢复到哪一层

**触发条件**
一次失败的 BD 修改**已经被保存**，而后续的修复又因为别的原因失败。

**现象**
修不下去：`validate` 和 `generate_target` 都失败，错误还是别的东西
（本例是 `[Common 17-233] Error initializing slave interpreter` / `[IP_Flow 19-3428]`）。

**根因与恢复顺序**
**同一个"失败"可能来自完全不同的层，必须逐层排除：**

| 层 | 判据 | 本例结论 |
|---|---|---|
| **工具/环境** | 建一个**全新空工程**做同类操作 | **正常** → 排除环境 |
| **工程文件** | BD 引用的 `xci` 是否存在 | `auto_pc_1/2` 的 xci **不见了** |
| **BD 内容** | 我这次改动加了什么、能不能精确还原 | 能：2 个网络 + 2 个参数 |

**关键认识：BD 文件是 JSON，改动可以被精确还原。**
不必依赖 Vivado 去"撤销"，可以直接对文件做**外科手术**：

1. **先备份**坏掉的 BD
2. **逐行断言**要删的内容确实是自己加的那些（缩进、标点都要对）
   —— 断言不通过就中止，绝不在"看起来差不多"的情况下动刀
3. 删除自己加的网络 / 恢复被改的参数
4. **检查大括号是否配平**
5. 再让 Vivado 跑一次 `generate_target`，观察产物大小是否回到出事前的值

**本例的验证链**
```
BD 治好前 94502 字节（坏的）
JSON 手术后 91100 字节（行尾被改成 LF，少 3140 字节）
generate_target 后 94469 字节  ← 与出事前的良好版本【完全一致】
validate_bd_design → PASS，无 41-2576 / 41-759 / 41-1306
```

**⚠️ 一个必须分开确认的问题：硬件有没有受影响？**
**"工程文件坏了" ≠ "板子上的东西坏了"。**
本例中：坏的 BD 保存于 19:39，而板上的比特流构建于 19:19
—— **那次改动从未被综合**，所以硬件完全正常。
**判断依据是时间戳：比特流的构建时间 vs 坏改动的保存时间。**

**适用 / 失效条件**
- 适用：BD/工程文件被改坏、而 Vivado 自身的撤销路径也失效时
- 失效：改动无法精确还原（例如大面积手工编辑）时，不要动刀，去找备份

**来源**
本队真实踩坑。**两条经验：**
1. **失败信息可能来自别的层** —— 修 A 的时候撞上 B 的错误，
   先做**隔离实验**（空工程）判断是不是环境问题
2. **"改坏了"和"已经造成后果"是两件事**，时间戳能把它们分开

## B11 · Tcl 的 `else` 不能换行写

**触发条件**
写 Tcl 时把 `if {...} {...}` 和 `else {...}` 分成两行。

**现象**
```
invalid command name "else"
```

**根因**
**Tcl 用换行来结束命令。**
`if {...} {...}` 在 `}` 后面的那个换行处**就已经结束了**，
下一行的 `else` 被当成**一条新命令** —— 而并不存在叫 `else` 的命令。

**这与 C / Java / Python 的直觉相反**，写惯了别的语言非常容易犯。

**修复**
```tcl
# 错误
if {$x} { do_a }
else { do_b }

# 正确（1）：} 和 else 同一行
if {$x} { do_a } else { do_b }

# 正确（2）：大括号跨行写（推荐，可读性最好）
if {$x} {
    do_a
} else {
    do_b
}
```

**排查步骤**
1. 看到 `invalid command name "else"` 或 `"elseif"` —— 直接就是这个
2. 搜脚本里所有**单独成行**的 `else` / `elseif`

**适用 / 失效条件**
- 适用：所有 Tcl（Vivado / Vitis / XSCT / OpenROAD …）
- 失效：—

**来源**
本队真实踩坑。一个**已经跑完最关键步骤**（`generate_target` 成功）的恢复脚本，
因为这个换行问题在**最后一步**中止。
**值得注意的正是这一点：它中止在成功之后** ——
所以看到"失败"时，还要确认**失败之前已经做到了哪一步**。

## B12 · 引脚"顺序分配"到接插件，而接插件的数据位是**成对颠倒**的

**触发条件**
把一个多 bit 总线（RGB 数据、地址、并口）按 `bit0..bitN` **顺序**分配到接插件的连续引脚上，
而**接插件的引脚定义不是你假设的那个顺序**（这一步通常没人去核对）。

**现象（真实经过，排查了一整晚）**
- 画面**结构还在**，但**数值对不上**：写 `0x40` 比写 `0x80` 还亮。
- **纯色测试全部通过**（全 0 / 全 1 在任何逐位排列下不变）
- **灰阶测试全部通过**（R=G=B 在三通道受同样变换时仍是灰）
- **厂商自带的例程也是好的** —— 因为它的测试图是**饱和彩条**
- 结果：**所有测试都通过**，人却一直盯着一个明显坏掉的画面找原因

**根因**
AN970（TM070RDH13）40 针排母的数据位是
**B6,B7,B4,B5,B2,B3,B0,B1** —— **每相邻两位内部颠倒**（R、G 同样）。
而 XDC（与厂商 `lcd_test.xdc` **逐脚完全相同**）按顺序分配 → **每一对都交换了**。
成对交换**只影响低位**，所以饱和色 / 灰阶 / 对称值**全部免疫**。

**排查步骤**
1. **先去拿引脚定义**（模块手册里的排针表 / 接插件定义）。**不要假设顺序。**
2. 写**单价置 1** 的图案：8 块，值 `0x01,0x02,0x04,0x08,0x10,0x20,0x40,0x80`。
   - 忠实：只有 `0x10/0x20/0x40/0x80` 看得见，从左到右渐亮
   - 成对交换：**`0x40` 比 `0x80` 亮、`0x10` 比 `0x20` 亮**（这是它的签名）
3. 用**定量测光**（拍屏 + 每块取均值），不要靠"深灰/浅灰"的口头描述（见 M26）

**修复**
**只改约束**：把 `data[2k]` 与 `data[2k+1]` 的 `PACKAGE_PIN` 成对对调。
不动 RTL、不动 BD。参考实现：`ps_fft_dual/fix_lcd_bitpairs.py`。

**规律**
> **"纯色 + 灰阶测试通过"根本不代表数值通路正确** ——
> 这两类测试对**任何逐位排列**都免疫。
> 要验数值通路，必须用**能暴露目标缺陷的图案**（这里是"单价置 1"）。

**适用 / 失效条件**
- 适用：任何把 FPGA 引脚映射到外部接插件 / 排针 / 软排线的场合
- 失效：接插件定义本身就是顺序的（那就没有这个风险）

## B12b · `make_bd_intf_pins_external` 会**静默地不连线**

**症状**：想给一个 AXI GPIO 的输出加外部端口。脚本报"成功"，
后续约束也加了，**构建一路成功到 `write_bitstream Complete!`，
时序 0 违规** —— 但**那 4 个引脚一个都没接上**。

**真因有两层**：

1. `make_bd_intf_pins_external` 把端口**自动命名**成了别的名字（我们要 `GPIO_1`，它建了 `GPIO_2`）
2. 更要紧的：**端口建出来了，但没有连到引脚网络上**。
   查网络可见 `axi_gpio_1_gpio_io_o` **仍然只碰 `axi_gpio_1/gpio_io_o` 一个对象**。
   未连接的端口**不进 wrapper**，所以 `design_1_wrapper.v` 里根本没有它。

**为什么极难发现**：
- 端口创建**没有报错**
- 约束匹配到零个对象，**只产生 WARNING**（`Vivado 12-584 No ports matched`）
- 构建**成功**、时序**0 违规**、比特流**正常产出**

**如果没有"从 `io_placed.rpt` 反查这几个位落在哪个引脚"这条断言，
我会拿着一个"看起来完全成功"的比特流上板，然后发现灯不亮。**

**正确做法（不要依赖自动命名）**：

```tcl
set p [create_bd_intf_port -mode Master \
       -vlnv xilinx.com:interface:gpio_rtl:1.0 GPIO_LIGHTS]
connect_bd_intf_net [get_bd_intf_pins axi_gpio_1/GPIO] $p
# 断言连线真的存在
if {[get_bd_intf_nets -quiet -of_objects $p] eq ""} { error "端口没连上" }
# 断言端口真的进了 wrapper
make_wrapper -files [get_files design_1.bd] -top -force
if {[string first "GPIO_LIGHTS_tri_o" [read [open $wrapper r]]] < 0} { error "wrapper 里没有" }
```

**关键**：**"命令没报错"和"设计真的变了"是两件事**，必须各自断言一次。

**代价**：一次完整构建（约 10 分钟）+ 一轮排查。
但**真正的代价是它差点让一个空操作被当成成果交付**。

## B13 · AXI VDMA 的 **MM2S 与 S2MM 是两套完全不同的寄存器块** —— 写错地址**静默无效**

**触发条件**
一个设计里有**两个** VDMA 实例：一个采集（stream→memory）、一个显示（memory→stream）。
给它们配寄存器时，凭"两个都是 VDMA，偏移应该一样"去写。

**现象**
另一个通道一切正常，而显示通道**面板全黑** ——
但 `CR` 读回来是 `0x00010003`、`SR` 读回来也正常、`Halted = 0`。
**寄存器看起来完全健康，写进去的值却什么都没发生。**

**根因**
AXI VDMA 的 MM2S 和 S2MM 是两个**不同的地址块**，不是同一个块的复用：

| | MM2S（memory→stream，显示） | S2MM（stream→memory，采集） |
|---|---|---|
| CR | `0x00` | `0x30` |
| SR | `0x04` | `0x34` |
| VSIZE | `0x50` | `0xA0` |
| HSIZE | `0x54` | `0xA4` |
| STRIDE | `0x58` | `0xA8` |
| ADDR1 / ADDR2 | `0x5C` / `0x60` | `0xAC` / `0xB0` |

本例：显示脚本把 `CR` 写到 `0x30`、`VSIZE` 写到 `0xA0`（都是 S2MM 的地址），
而 `axi_vdma_1` 只实现了 MM2S —— 那两个地址**读回来全是 0**，
写入石沉大海，**不报错、不置位、不影响任何状态位**。

**排查步骤**
1. **把整个寄存器块 dump 出来**（`0x00`–`0xBF` **两个** VDMA 都 dump），
   然后**拿已知值去认领寄存器**：本例的已知值是
   `VSIZE 720/480`、`HSIZE/STRIDE 3840/2400`、`ADDR 0x10000000/0x10400000/0x10800000/0x10A00000`。
   值出现在哪个偏移，**那个偏移就是真的** —— 这比查手册可靠，因为可以直接对上号。
2. 顺带就能看出哪几个地址"是 0"，也就是**这个实例根本没实现**的方向。
   本例：`DIS +0x30` 和 `DIS +0xA0` 全是 0。
3. **别把"两个通道偏移一样"当成常识**。采集和显示的脚本是分开写的，
   非常容易一个抄对、一个抄错。

**规律**
> **往一个不存在的寄存器写，是嵌入式里最安静的一种失败。**
> 它不报错、不置位，甚至连"值没写进去"都要靠**读回来比对**才发现 ——
> 而如果那个寄存器本来就该被写两次（例如 CR），
> 读回来的值还可能来自**另一次**写入，于是看起来"明明写进去了"。

**适用 / 失效条件**
- 适用：VDMA / DMA / 任何"多通道、每通道一套寄存器"的 IP；
  以及任何"两个实例，配置脚本互相抄"的场合
- 失效：只有一个方向、或配置由厂商驱动完成

## B14 · VDMA 的"选哪个帧存"**不在 CR 里** —— 一个从未被测过的 bit，和真正的机制

**触发条件**
双缓冲：一块内存给显示、一块给渲染，**每帧切换显示哪一块**。

**现象**
代码一行不改、逻辑看着完全正确（"渲染到没显示的那一块，然后翻转"），
但画面**撕裂**，而且**有一半的渲染工作从来没显示出来**。
最要命的是：**寄存器读回来一切正常**，没有任何一位在报错。

**根因（两层）**
1. 用的那个 bit **根本不存储**。本例 `DIS MM2S CR` 的 bit8：
   ```
   写 0x00010103 -> 读回 0x00010003   bit8=0
   写 0x00010003 -> 读回 0x00010003   bit8=0
   ```
   所以每帧的"翻转"是**空操作**，通道按自己的节奏走，软件完全不知道现在扫的是哪一块。
2. 而 `CR` 的 **bit1 (`Circular_Park`) = 1 是 park 模式**，配合 `PARK_PTR = 0`
   —— 通道**一直停在帧存 0**。于是软件每帧轮流写 0 和 1：
   写 0 时在改**正在被扫描**的缓冲（**撕裂**），写 1 时那份工作**永远不会显示**。

**排查步骤**
1. **先测那个 bit 存不存**：写进去、读回来。
   只读"状态位都正常"是没用的 —— 不存在的位不报错。
2. 弄清楚通道**当前扫的是哪一块**。这一个信号是双缓冲的全部前提。
   本例查 BD 才发现：`axi_vdma_0`（采集）的 `s2mm_frame_ptr_out` 接到了 GPIO，
   而 `axi_vdma_1`（显示）**什么都没接** —— 软件根本无从知道。
3. 找**不需要改 BD 的替代机制**：`PARK_PTR`（偏移 `0x28`）实测**是可写的**
   （写 `0x107` 读回 `0x07`）。park 模式下通道停在 `PARK_PTR[4:0]` 指定的帧存，
   而且**切换发生在帧边界**，正好就是干净的翻转。

**修复与验证**
```c
R32(DIS + 0x00) = 0x00010003;   /* RS=1 | Circular_Park=1，只设一次 */
/* 每帧：渲染到 target -> 清缓存 -> 把显示 park 到它 */
R32(DIS + 0x28) = target;
```
验证不是"看着不撕了"，而是**数翻转次数**：
```
  120 次采样 / 4.36 秒；park index 见到 0 和 1；翻转 84 次
  同一窗口 PS 帧率 19.51 fps   => 翻转与渲染帧率同步
```
再加一条硬判据：**dump 正在被扫描的那一块**，它必须**永远是完整帧**
（本例两次采样面板都是完整 6 色，永远抓不到画到一半的缓冲）。

**规律**
> **双缓冲的前提是"知道现在显示哪一块"。这个信号必须存在、可读、且被测过。**
> **"寄存器写进去了"和"这一位存在"是两件事**；
> **"状态位正常"更不能证明你没在写一个不存在的字段。**
> 凡是注释里写"从可用代码推断"的映射，都是**从未被单独验证**的假设。

**适用 / 失效条件**
- 适用：任何双缓冲/多缓冲的显示、音频、DMA 通道
- 失效：硬件提供可读的当前缓冲指针（那也必须测一次它真的会翻转）

- 失败的那 9 条**全部**终止于 `capture_ram_0/inst/mem_reg_*/DIADI[*]`
  —— **调试捕获 RAM 的数据输入**，源信号是当初查显示链路时探的那些
  （`v_tc_0` 的 hsync/vsync/active_video、`v_axi4s_vid_out_0/locked`、`rst_33M`、VDMA 内部）。
- 那一对时钟里**唯一不是探针**的路径在 `v_tc_0` 内部
  （`SYNC2PROCCLK_I/data_sync_reg`，一个两级同步器），**它满足时序**。
- 而且这条失败组的要求是 **0.010 ns**：两时钟同周期、10 ps 偏斜，**结构上就不可能满足**。

**为什么不能 `set_clock_groups -asynchronous`**
那会把这两个时钟对整个设计声明为无关，**连带丢掉**：
- 42 条**当前满足时序**的 `clk_fpga_0 -> clk_fpga_1` 实用路径（同源同 PLL，是真路径，
  它们的正裕量是有意义的证据）；
- 上面那个 v_tc 同步器的时序检查；
- 以及**将来**任何真正跨这两个域的路径——约束会把将来的 bug 一起藏起来。

**修复**
**只对调试探针的数据输入加 `set_false_path`**，精确到实例名：
```tcl
set_false_path -to [get_pins -hierarchical -filter {NAME =~ "*capture_ram_0/inst/mem_reg_*/DIADI*"}]
set_false_path -to [get_pins -hierarchical -filter {NAME =~ "*capture_ram_0/inst/mem_reg_*/DIBDI*"}]
```
并且**从报告里核实结果**，不是只看 `Complete!`：
```
  violated paths: 0   ->  TIMING CLOSED: no violated paths at all
```
（注意 `capture_ram` 是 **OOC 的 module_ref**：顶层综合时这些单元**还不存在**，
匹配为空是正常的 —— 所以约束里**不要 `error`**，把"必须有非零匹配"的强校验放到实现之后、
从报告里断言。否则综合阶段会被自己的检查卡死。）

**规律**
> **先看违规路径是谁，再决定加什么约束。**
> **`set_clock_groups` 是"这两个时钟没有关系"的断言，不是"让时序过"的开关** ——
> 它同时抹掉真路径和将来出问题的能力。
> **调试逻辑造成的时序违规，应当精确地约束调试逻辑本身。**

**适用 / 失效条件**
- 适用：任何"带 ILA/调试核 + 多时钟域"的设计，尤其是跨域探针
- 失效：确实全部是异步跨域且没有同步器时，那时该加的是**同步器**，不是约束

## B15b · 参考设计里的一个部件**不是装饰** —— 去掉它可能一条警告都不报

**症状**：把自研 CNN 集成进 BD。集成、综合、实现、出比特流**全部成功**，
`validate_bd_design` 通过，**CRITICAL WARNING 0 条**，时序收敛（WNS +2.373 ns）。

**但上板一跑，硬件输出是垃圾**（与 csim 的 200/200 逐位期望完全不符）。

**一步步排除**：
1. DDR 里的权重/表/测试图 **与文件逐字一致**（排除"数据没写对"）
2. 6 个 AXI-Lite 地址寄存器写入**回读一致**（排除"控制不通"）
3. `ap_done` 22 ms 内到达、`AP_CTRL` 回读 `0x4`（排除"内核没跑"）
4. **把 logits 预填成魔术值 `DEADBEEF`，跑完再看 —— 一个字节都没变**

第 4 步是决定性的：**CNN 根本没有写输出。**
之前读到的那些数值是 DDR 里的**陈旧数据**，不是计算结果。

**根因**：查 master 的数据位宽

```
m_axi_gmem0  DATA_WIDTH = 32
m_axi_gmem1  DATA_WIDTH = 32
m_axi_gmem2  DATA_WIDTH = 64      <- 只有它是 64 位
```

而参考设计（`dl/w6/w6f`）**恰好只在 gmem0 和 gmem1 上放了 `axi_dwidth_converter`，
gmem2 直连**。数字与结构完全对上 —— **那两个转换器不是可选的装饰，
它们把 32 位 master 接到 64 位互连上。**

**我当初为什么去掉它们**：探不到 dwc 的时钟引脚名
（`get_bd_pins dwc/aclk` 匹配零个对象），于是改成三个 master 全直连，
并且**用"综合 0 条 CRITICAL WARNING"当作它没事的证据**。

**教训有三层**：

1. **"参考设计多放了一个部件"通常有原因，不要在没弄清原因之前删掉它。**
   正确做法是**先问它为什么在那儿**（这里是查位宽），而不是"删掉试试、没报错就留下"。

2. **`validate` 通过 + 综合 0 CRITICAL WARNING + 时序收敛 ≠ 功能正确。**
   位宽不匹配在这种接法下**竟然不产生 CRITICAL WARNING**，
   于是设计"看着完美"地坏掉了。**工具不报的错，只能靠"跑一遍看结果"来发现。**

3. **"预填一个魔术值、跑完看它变没变"是判别"到底有没有写"的最便宜手段。**
   在这一步之前，我花了很久怀疑算法、权重、地址。
   真正的分界线是"它一个字都没写"。

**代价**：一次完整构建 + 一轮上板调试。
**但如果没有那个自检，这件事会在演示现场才暴露。**

## B16 悬空网 ≠ 已连接：`get_bd_intf_nets` 非空不能当作"接好了"

- **触发条件**：删掉一个 BD cell 后再连接它留下的 master 端口；脚本用
  `if {[llength [get_bd_intf_nets -of_objects $pin]] == 0}` 判断"是否已连"。
- **现象**：脚本打印"already connected"并跳过连接，保存成功、`validate_bd_design` **0 条 ERROR**，
  但构建时出现：
  ```
  WARNING [BD 41-2671] The dangling interface net <ps7_0_axi_periph_M10_AXI> will not be written out
  WARNING [BD 41-2670] Found an incomplete address path from /processing_system7_0/Data ...
  WARNING [BD 5-699]   No address segments matched ...
  ```
  且地址段 `offset=` 为空。
- **根因**：删 cell 后它的网可能留在对端成为 **dangling net**。有网对象 ≠ 有对端。
- **排查**：`get_bd_intf_pins -of_objects <net>`，数**两头**的 pin；只有 1 个就是悬空。
- **修复**：
  ```tcl
  foreach n [get_bd_intf_nets -quiet -of_objects $m10] { catch { delete_bd_objs $n } }
  connect_bd_intf_net $m10 $slv
  ```
  并且**把"地址段 offset 为空"当成失败**，而不是当成打印里的一行。
- **失效条件**：全新搭建、没有删除过 cell 时不会遇到。
- **来源**：2026-10-17。`validate_bd_design` 报 0 条 ERROR，问题只出现在 WARNING 和构建期。

## B16b · `catch` 吞掉了地址分配失败 —— 产出一个"全绿但功能为零"的设计

**症状**：CNN 集成后综合通过、时序收敛、**CRITICAL WARNING 0 条**、比特流正常产出。
上板自检时：
- DDR 里的权重/表/图与文件**逐字一致**
- 6 个 AXI-Lite 地址寄存器写入**回读一致**
- `ap_done` 20–33 ms 内到达，`AP_CTRL` 回读 `0x4`（idle）
- **但把 logits 预填成 `DEADBEEF`，跑完一个字没变** → CNN 根本没写输出

**根因**：CNN 的三个 M_AXI master **从来没有地址映射**。

```
Data_m_axi_gmem0 : 0 段      <- 一个段都没有
Data_m_axi_gmem1 : 0 段
Data_m_axi_gmem2 : 0 段
```

分配之后：

```
Data_m_axi_gmem0 : 1 段  ✓
```

**后果的形态特别坏**：AXI 事务无处可去 → 读写全部落空 →
但**控制状态机照样跑完并置 `ap_done`**。
于是所有"看起来对"的信号都在：构建成功、时序收敛、零警告、内核跑完 ——
**只有结果悄悄是错的。**

**为什么没被发现**：集成脚本里那段地址分配**包在 `catch` 里**：

```tcl
foreach m {m_axi_gmem0 m_axi_gmem1 m_axi_gmem2} {
    set sa [get_bd_addr_spaces -quiet ts_cnn_top_0/$m]     ;# <- 这里的查询也是坏的
    if {$sa ne ""} { catch { assign_bd_address ... } }
}
```

两个错叠在一起：
1. `get_bd_addr_spaces -quiet ts_cnn_top_0/$m` 用**路径字符串**，返回空 → `if` 直接跳过
2. 即使进去，`assign_bd_address` 也包在 `catch` 里

**所以我"分配过地址"了 —— 从执行路径看确实跑过那几行代码，只是什么都没有发生。**

**教训**：
1. **`catch` 只应该用来"把错误变成可读的信息"，不应该用来"让错误消失"。**
   凡是被 `catch` 包住的写操作，**必须在之后断言它的效果**，而不是只断言它没报错。
2. **"控制寄存器通了"不代表"数据通路通了"。** 这两个是**独立的** AXI 通路：
   控制走 `M_AXI_GP0 → ps7_0_axi_periph`，数据走 `M_AXI_HPx → mem_intercon`。
   前者通只证明 AXI-Lite 接对了。
3. **判别"到底有没有写"的最便宜手段**：预填一个魔术值，跑完看它变没变。
   在这一步之前我在怀疑算法、权重、地址；真正的分界线是"它一个字都没写"。

## B18 手写 AXI4-Lite 从口：地址可能根本没到，寄存器窗口每 4 个字重复

- **触发条件**：自己写一个 AXI4-Lite slave（端口名 `s_axi_awaddr/araddr/...`），用
  `create_bd_cell -type module -reference` 引入，再 `connect_bd_intf_net` 接到
  `ps7_0_axi_periph/Mxx_AXI`。
- **现象**：连接"成功"、`validate_bd_design` 0 条 ERROR、地址段也分配了；
  但 PS 读该窗口时**每 16 字节重复一次**同一组值：

  ```
  +0x00=3  +0x04=3  +0x08=0  +0x0C=FFFFFFFF
  +0x10=3  +0x14=3  +0x18=0  +0x1C=FFFFFFFF
  ...（一路重复到 0x70+）
  ```

  于是"某个寄存器读到 0、相邻的却读不到"看起来像两个独立怪现象，实际是**同一个窗口在回绕**。
- **根因**：推断出来的 AXI4-Lite interface 与手写端口之间的地址通道并未真正连通；
  从口只看到低 2 位地址。（把 `s_axi_araddr` 从 `[5:0]` 加宽到 `[31:0]` **没有改变现象**，
  说明不是位宽问题。）
- **排查**：
  1. **先扫窗口**：从基地址起读 64 个字并打印，**看周期**；周期 = 2^k 个字说明只看到 k 位；
  2. 再核对 BD 里该 interface 的**对端**（`get_bd_intf_pins -of_objects <net>`）。
- **修复**：**不要手写 AXI-Lite 从口**。把寄存器搬到标准 IP 后面：
  - `axi_bram_ctrl` + 一块小 BRAM（统计逻辑只写 6 个字，PS 直接读），或
  - `axi_gpio` 的只读输入通道。
  标准 IP 的接口连接由 Vivado 生成和验证，不需要人工证明"它连上了"。
- **失效条件**：用厂商模板（`axi_lite_ipif` / IP Integrator 的 Create Interface）时风险低。
- **来源**：2026-10-17。两次失败：一次是 M09 被 `touch_gpio` 占用导致孤儿从口，
  一次是地址没到导致窗口回绕。**"看起来连上了"在这件事上被骗过两次。**

## B18b · 验证闸门写成看返回值 —— 而它返回**空字符串**，于是"永远通过"

**事故经过**
我把"validate 通过才保存"写成：

```tcl
set vok 0
catch { set vok [validate_bd_design] }
L "  validate 返回 $vok"
save_bd_design          ;# <- 无条件保存
```

以及更"严谨"的一版：

```tcl
CHK {$vok == 1 || $vok eq ""} "validate 正常返回"
```

**两版都是坏的**：
* 第一版**根本没有条件**，只是打印。
* 第二版把 `""` 当成"正常" —— 而 **`validate_bd_design` 在成功和失败时都可能返回空串**，
  所以这个条件恒为真。**闸门形同虚设**，把删掉全局时钟的设计保存了。

**正确做法：查验证产生的错误消息数量，不看返回值**

```tcl
reset_msg_config -severity {ERROR} -quiet
set before [get_msg_config -count -severity {ERROR}]
catch { validate_bd_design }
set after [get_msg_config -count -severity {ERROR}]
if {$after > 0} { error "验证产生 $after 条 ERROR，拒绝保存" }
save_bd_design
```

**教训（与本项目反复出现的那一族一致）**：
* **"闸门"必须真的能拦住** —— 一个恒为真的条件不是闸门，是装饰。
* **判断依据要选对对象**：判断验证是否通过，要看**它报了什么错**，
  而不是看**它返回了什么**。返回值是 API 的表面，错误消息才是它的判断。
* **闸门要能自证有效**：故意造一个错误设计跑一次，确认闸门真的拦住 ——
  否则你只是在"以为"它有保护。

## B19 · 备份工具在**含空格的路径**上静默失效

**事故经过**
恢复 BD 时执行 `python dl/backup.py restore <备份名>`，输出：

```
*** 源不存在，跳过: C:\...\trustscope\D_/BaiduNetdiskDownload/Vivado/two
完成。
```

**"完成"了，但文件的 MD5 一点没变 —— 它什么都没恢复。**

**根因**：MANIFEST 的格式是 `<路径> <字节数> <sha256>`，**路径在最前面**，
而**路径里有空格**（本项目的 BD 就在 `two FFT.gen` 下）。
解析时 `line.split()` 把路径切成了好几段，取 `parts[0]` 只得到
`D_/BaiduNetdiskDownload/Vivado/two`，拼出来的源文件当然不存在。

**更坏的地方**：`restore` 对"源文件不存在"只打印一行提示就继续，
**最后照样打印"完成"**。所以调用方以为恢复了，其实没有。

**修法（两处）**
1. **格式改成路径放最后**：`<sha256> <字节数> <路径>`，用 `split(None, 2)` 解析 ——
   这样路径里的空格不会把字段切碎。
2. **回写后立刻校验哈希**，并把结果打出来：

```python
got = sha256(dst)
print("  恢复 %s  %s" % (r, "OK" if got == h else "*** 校验不符 ***"))
```

**教训**
* **"完成"这个词必须被证据支撑。** 工具打印"完成"之前，
  要确认它真的做成了它该做的事（这里是：文件真的被回写了）。
* **文件路径是含空格自由的**，任何"空白分列"的格式都要把路径放在最后一列。
* **这个 bug 与 B16/B18 同族**：一个环节"没报错"，于是上游以为它成功了。

## B20 `v_tc` 的 CONTROL 常量（06 vs 07）—— **本条原先写反了极性，已用实测更正**

> **更正（2026-10-18，由受控 A/B 得出）**：本条最初断言"写 `0x03F7EF07` 等于把发生器按在
> 复位里"。用同一块板做单变量对照（冻结 CPU、以显示通道 `SR` 的 bit12 `IOC` 为判据、
> 每个值两轮）后，结论相反：**`0x03F7EF06` 与 `0x03F7EF07` 都能出帧（IOC 全为 1）**。
> 这个常量**不是**屏幕更新与否的区分因素。真正造成"黑/白/冻"的是**板子被留在半初始化
> 状态**（一次失败的重建/烧录之后），而不是这个值。
> **纪律**：在没有一次能证明 `IOC` 不同的 A/B 之前，**不要再改这个常量** —— 24 小时内它
> 被来回改了至少两次，每次翻面都让屏幕换一种表现，而改动本身并没有修好任何东西。

以下保留原来的分析，作为"为什么会误判"的记录：


> 编号说明：本条最初误写成 B19，与"备份工具在含空格路径上静默失效"那条撞号。
> 撞号的后果正是 B19 描述的同一类问题——按 ID 检索时会静默丢一条。改为 B20。

- **触发条件**：为了让 v_tc 输出时序，写 `CONTROL` 寄存器。看到"使能"字样就想 `|= 0x3`
  或直接写 `0x03F7EF07`。
- **现象**：
  - 面板**永远不更新**（黑 / 白 / 冻在最后一帧，取决于它最后收到过什么）；
  - 而 `v_tc CTRL` 读回 `0x03F7EF07`，看起来"已使能"；
  - 显示 VDMA `CR=0x00010003`、`SR` 有 SOF，看起来"在跑"；
  - DDR 里的画面**完全正确**，dump 出来是一张完美的截图。
- **根因**：`0x03F7EF06` 的 bit1/bit2 是使能，**bit0 是软复位**。写 `...07` 把发生器按在复位里
  ⇒ 没有行场同步 ⇒ `v_axi4s_vid_out` 不锁定 ⇒ 没人消费 VDMA 的流 ⇒ 面板收不到任何新像素。
- **排查（只认寄存器，不认截图）**：

  | 判据 | 坏 | 好 |
  |---|---|---|
  | `v_tc CTRL` @ `0x43C00000` | `...07` 或 `0` | **`0x03F7EF06`** |
  | 显示通道 `SR` @ `0x43010004` 的 **bit12 (IOC)** | 0 | **1** |
  | `HORIZ` @ `0x43C00070` | 默认值 | **`0x00000420` (1056)** |
  | `VB` @ `0x43C00074` | 默认值 | **`0x01F901F9`** |

- **修复**：写引导脚本用的那个值 —— `0x03F7EF06`。**写后立刻读回并发布到邮箱**，
  这样"写了没生效"会变成可见的失败，而不是一个绿色的假象。
- **失效条件**：用 XIlinx 官方 `v_tc` 例程时它的值是对的；换分辨率时 `HORIZ/VB` 要重算。
- **来源**：2026-10-17/18。**一个常量错，赔掉一整晚**；期间"寄存器都对 ⇒ 屏坏了"的错误结论
  出现四次（见 M40）。

## B21 module_ref 的 GPIO 引脚可能已经归属别的外设 —— 一驱动就是 100% 崩溃

- **触发条件**：BD 里有一个自己写的 GPIO（本例 `touch_gpio`），软件通过它位翻转驱动外部器件的
  两根线；而同期**同一对引脚被改配给了另一个外设**（本例 PS 的 I2C1 从触屏改到了相机 1）。
- **现象**：
  - 只要调用那段驱动代码，程序**每次**都在同一处 `data abort`（`faultcode=0x11111104`、
    `DFAR=0`），**0/10 存活**；
  - 把调用去掉 ⇒ **20/20 存活**；
  - 而**看代码看不出问题**：位翻转本身完全正确，它只是驱动了一对不再属于它的引脚。
- **根因**：引脚复用是**全局**的，`touch_gpio` 的位翻转与相机 1 的 I2C 争同一对脚。软件无从分辨
  "我驱动的这根线现在被谁拥有"。
- **排查**：
  1. **先数存活的次数**，不要看单次：同一固件跑 10 次，记 `fault==0 且 帧数递增` 的次数。
     0/10 与 20/20 是两句话，一次成功或一次失败什么也说明不了；
  2. **再查引脚归属**：BD 里该 GPIO 的端口约束 + XDC 的 `PACKAGE_PIN`，与相机/其它外设逐一对照。
     （本次我先去找 XDC 却找错了路径，于是根因只能标"推断"——这一步必须做对。）
- **修复**：这**不是**改驱动能解决的，是**二选一**：
  - 放弃该外设（本例：触屏不可用，靠别的输入方式）；
  - 或把另一个外设的引脚挪走（本例：给相机 1 换一对空闲脚做 I2C），代价是那个外设要重新验证。
- **失效条件**：引脚未被复用时不存在此问题；但"曾经没冲突"不等于"现在没冲突"。
- **来源**：2026-10-18。开启 0/10、关闭 20/20，两次十次测量才把"偶发"这个错误印象纠正为
  **确定性碰撞**。

## B22 · Block Design 不在仓库里 —— `git revert` 撤不掉一次 BD 修改

- **触发条件**：要改 BD（Vivado Block Design）。仓库里有 `ps_fft_dual/` 一整套 BD 相关 Tcl、
  `backups/`、XDC、bring-up 脚本，于是"这个设计在仓库里，改坏了 `git checkout` 回来"看起来是成立的。
- **现象**：
  - 改完 BD 后 `git status` **一个 `.bd` / `.xpr` 都不显示**，干净得像什么都没做过；
  - `git revert` 或 `git checkout -- .` 之后重开工程，**改动还在**；
  - 仓库里能找到的 `.xpr` 只有 `ps_fft_dual/lcdsolid/proj/lcdsolid.xpr` 和
    `ps_fft_dual/vivado/LED/LED.xpr` —— **两个都不是主设计**；
  - 连"这次构建的日志"也不在版本库里（`*.log` 被 `.gitignore` 忽略）。
- **根因**：主设计的 Vivado 工程在**仓库之外**：

  ```
  D:/BaiduNetdiskDownload/23_ov5640_dual/Vivado/two FFT/two FFT.xpr
      BD: two FFT.srcs/sources_1/bd/design_1/design_1.bd
  ```

  git 只跟踪仓库内的路径，所以工程、BD、`.runs/`、布线报告**全部不受版本控制**。
  "`git status` 干净"只说明**仓库里**没变，与设计有没有被改过无关。
- **排查**（三步，动手前做完）：
  1. **不要猜工程在哪**：`grep open_project` 所有构建脚本，看真正被打开的是哪一条路径。
     本次是 `ps_fft_dual/rebuild_fp1_1024.tcl` 里那个外部路径，**不是**仓库里的任何 `.xpr`。
  2. **确认 BD 路径并从磁盘核对**：`<proj>.srcs/sources_1/bd/<design>/<design>.bd`。
     用时间戳交叉确认它就是产出当前比特流的那份 —— 本次实测：

     ```
     design_1.bd                          2026-10-24 12:50:13   <- 先改 BD
     two FFT.xpr                          2026-10-24 13:09:56   <- 再存工程
     impl_1/design_1_wrapper.bit          2026-10-24 13:10:23   <- 再出比特流
     safe_bitstreams/BIT_20261024_fp1.bit 2026-10-24 13:10:23   <- 与它同一秒
     ```

     三者按"改 BD -> 存工程 -> 构建"单调递增，且产物与 `safe_bitstreams/` 里那份**同一秒**，
     才敢认定是同一次构建。两个陷阱：
     * **BD 不是最新那个时间戳。** 我最初把 `.xpr` 的 13:09 当成了 `.bd` 的时间，
       差一点就把一个**没核对过**的数字写进证据。`.bd` 是 12:50，比比特流旧 20 分钟 ——
       BD 比 bit 旧是正常的，不要因为"BD 比 bit 旧"就以为拿错了文件。
  3. **证明它确实不受版本控制**：`git ls-files --error-unmatch "<bd 路径>"`。本次的失败信息是

     ```
     fatal: D:/.../design_1.bd: 'D:/...' is outside repository at 'C:/Users/<user>/Documents/trustscope'
     ```
     退出码 128。这比"未被跟踪"更强：**这个路径根本不在仓库里**，所以 `git` 连"跟踪与否"
     都无从谈起 —— `git status` 干净与它无关。`git check-ignore -v` 同样报不在仓库内。
     这一步的结论要写进当天记录。
- **修复**：
  - **第一次改动之前**备份，且**必须同时包含 `.bd` 与 `.xpr`**：

    ```
    python dl\backup.py save <名字> "<...>/design_1.bd" "<...>/two FFT.xpr"
    ```

  - 恢复用 `python dl\backup.py restore <名字>`，它会回写并校验哈希。
    **但这条路径里有空格**（`two FFT`），正是 **B19**"备份工具在含空格路径上静默失效"的
    同一条路径 —— 所以恢复后要**独立**再确认一次：把 `.bd` 读出来看改动确实没了，
    不能只看工具打印"完成"。
  - 换个说法记：**在这个项目里，"备份"是 BD 唯一的撤销键**，不是"更保险的做法"。
- **失效条件**：若哪天把工程搬进仓库并纳入跟踪，本条不再适用。
  但在那一天到来之前，**"仓库干净"永远不能用来证明"设计没被改过"**。
- **来源**：2026-10-28。由 `rebuild_fp1_1024.tcl` 的 `open_project` 行、以及对外部
  `design_1.bd` 的实际 JSON 解析得出（`PCW_USE_S_AXI_HP2/3` 是从这个外部文件里读的，
  不是从任何注释里抄的）。同一个检查也直接决定了当天的动作：**因为 BD 不受版本控制，
  所以不开始一次无法收尾的 BD 修改。**
