## Stage 0: DONE, and the gate for everything after it

Before: on an untouched scene, 13 attempts published 5 different transforms (angle −0.15 ..
+4.00 deg, dx 0..+14 px, dy −20..+2 px, scale 0.90..1.06) with cells 0..27, and 2 refusals
each published an angle from one stage next to a shift from another.

Root cause, measured (`ps_ui/st6_warm_cal.py`, real part frame, same integer arithmetic):
0.1 deg costs 6..11 units of the search's error, 1 half-res px 54..92, 1/256 scale 25..35 —
while the SAME transform re-measured on consecutive frames reads 56..168. The frame-to-frame
term (the rolling-shutter row bar) is 10x the 0.1-degree step, so a global argmin over five
dimensions had no reason to stay put.

Fix (temporal, as the task specified): the last published transform is a candidate every
frame, a small window around it is searched first, adoption needs a measured gain (1 grey
level near, 2 far), a fresh reference seeds the answer with the identity, and a disagreement
that neither beats is published as new state 3 UNSTABLE (the comparison refuses). Two extra
defects fixed: refusals published a mix of numbers from different transforms, and the angular
search's saturation rule made the local window never answer (measured 0 of 24).

After: **3 runs, 3 fresh references, 84 comparisons, ONE transform value** — angle 0.00,
dx 0.00, dy 0.00, scale 1.0000, spread 0.00 deg / 0.00 px. Cells 0 in 80 of 84; the other 4
read 8..12 against an 8-cell limit. That tail is the row bar and is Stage 2/4's job.

## Stage 1: NOT SHIPPED, and why (read this before retrying it)

The 2026-10-24 bitstream was reported to route `s2mm_frame_ptr_out[1]` to probe bit 15 of
`0x41200008`. Implemented the Gray decode `writing = (g1<<1)|(g1^g0)`, the freshness gate,
the liveness check and six new evidence words. Then:

* the canary probe (MB_CMD = 6, **six** runs) shows bit 4 is a perfect function of the write
  store in all six (the Gray LSB), while bit 15 is the correct Gray MSB in two runs, its
  inverse in two, and unreproducible in two;
* the row detector (index-independent) puts bit 9 at 0.0% torn, bits 10-15 at 31-50%, and
  the edge wait at 0.0-0.6% — and then **bit 9 contradicted itself**: 0.4%/1.3% torn in one
  25 s run (9.2 fps) and 59.0%/59.9% in the next (8.9 fps), same code path, same writes;
* with the decode and no wait the loop reaches **11.3 fps** (so the wait is confirmed as the
  frame-rate cost), but the read window is ~65 ms and the decode's worst case leaves only
  54.4 ms, so it tears 36-39%.

Shipped instead: the edge wait (0.0% torn, 6.40 fps) plus ALL the instrumentation — the
runtime bit selector `MB_CAP_MSB` (178, default 0 = off, written at boot), `MB_CAP_G1`
(172), `MB_CAP_PAIRS` (173), `MB_CAP_DEC` (174), `MB_CAP_DECN` (175), `MB_CAP_WAITN` (176),
`MB_CAP_WORD` (177), and `MB_CAP_WRIDX` (372) publishing the decoded index again.

**The next attempt must not start from behaviour measurements.** Read the block design
(`vtc_probe_concat` NUM_PORTS, the net on `In<k>`, `dout` width) — `bd_inspect_1024.tcl` is
read-only but needs the Vivado project — and add an `MB_CMD` that polls `0x41200008` at
>=5 kHz from the CPU for ~120 ms recording every change. Host-side `mrd` sampling is two
orders of magnitude too slow for a 27.2 ms signal; that is why this stage's evidence
contradicts itself.

## Human-dependent experiments (exact wording for the operator)

1. **Move the part** 1-2 cm with a reference taken first (`MB_CMD = 9`): `MB_REG_MODE` (393)
   must become 4 or 1 with a new answer, `MB_REG_INCERR` (394) must be high before the move
   and low after, and `MB_DIFF_CELLS` must return to 0..8. If the answer does not follow the
   part, the margins are too large for this bench and must be re-derived with
   `ps_ui/st6_warm_cal.py` on a frame pair that really differs.
2. **Rotate the part** by 0.16 / 0.5 / 1.0 degrees with a protractor: `MB_REG_ANGLE100`
   (386) must track it and `MB_REG_MODE` must stay 4.
3. **Re-run the Stage 1 bit sweep on a still bench** (`st1_bit_sweep_20261024.tcl`), with
   nothing moving in the field of view, and then again with a hand moving. If bit 9 reads
   0% in both, it is a real index; if it moves, the signal is aliasing.
