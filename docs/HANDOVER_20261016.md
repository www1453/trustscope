## 五、必须遵守的纪律（血泪换来的）

### 硬件安全
- **J10 PIN35(B20) ↔ PIN28(V12) 的跳线必须保持不插**
- 相机数据脚**全部是 INPUT**，设计上从不驱动 → 对相机零风险
- **绝不修改冻结的 HLS 交付物**、`hls/data` 金标准、`w6d/w6e/history` 归档
- 工程必须保持 Tcl 可复现

### 测试纪律（今晚两条新教训）
- **没有对照组的"对比测试"不成立**（案例集 M25）：
  "两次都失败"在数值上表现为"两次都相同"。任何"X 没变"的结论，
  先说出**你凭什么相信这次读到了 X**。
- **判据必须有归零检查**：验证闸门要查**错误消息数**，不是看返回值
  （`validate_bd_design` 成功失败都返回空串 —— 案例集 B18）

### BD 改动（案例集 B17，今晚代价最大的一次）
- **`delete_bd_objs <net>` 删的是整条网络** —— 我用它删 `cam_switch` 的网络时，
  把 `FCLK_CLK0` 全局时钟网一起删了（45 个引脚悬空）
- **不删 cell；断线前先断言那条网只有 2 个端点；每步后断言全局时钟网引脚数只增不减**
- 正确参考：`ps_fft_dual/stereo_2vdma_v2.tcl`（这是"不加不减、纯增量"的范例）

### 工具陷阱
- **`mrd -bin -file` 的长度参数按"字"（32 位）计，不是字节**
- **`targets -set N` 的编号在不同状态下指向不同对象**（正常 1=APU/2=CPU；DAP 出错时 1=DAP/2=xc7z020）
- **I2C 只能在 `rst -system` + `ps7_init` + `ps7_post_config` 的同一会话里访问**；
  之后新起的会话里 `ISR` 读到 ARB_LOST、读值全 -1
- **`disconnect_bd_intf_net` 在这个 Vivado 版本里不工作** → 用"先断言 2 端点再删网"
- **脚本只用 ASCII**（中文 Windows 下 Tcl 按 GBK 读）
- **警惕 `$(...)`**（shell 语法，Tcl/Python 都不认）与**嵌套双引号** —— 今晚各犯了 3-4 次

## 十、2026-10-16（第三轮）：画中画显示已上板 + 抓到一个反了的判据

### 10.1 画中画已经出图（视觉已确认，逐字节校验待补）

`ps_ui/main.c` 新增 `draw_camera1_pip()`：读 `CAM1_BUF(0x11200000)`，窗口
`x420..632 / y236..355`（213x120，源取样步长 6 → 源码里没有除法），带 1px 边框。
调用点在 `draw_panel()` 之后。截图 `ps_ui/ui_pip.png`（`ui_pip_panel_zoom.png` 是面板放大）。

**实测代价**：panel 相位 `0.78 ms → 7.63 ms`（+6.85 ms/帧），整帧 `16.75 → 14.90 fps`。
原因是 `AT_NC` 的非缓存字节读：25560 像素 × 3 次 ~89 ns 的独立读。
**可优化**：把取样步长改成 8（源偏移永远是 24 字节的倍数 → 4 字节对齐），
每次读 1 个字而不是 3 个字节，预计降到 ~2 ms。**没做**，因为要动几何常量。

### 10.2 抓到的真问题：`ps_run.tcl` 的"是否已停"判据是反的

AXI VDMA `CR` bit0 = RS：**1 = 运行、0 = 停**（本项目自己的脚本用 `0x00010003` 启动、
`0x00000000` 停止）。而 `ps_run.tcl` 写的是 `if {$cr & 1} { 重新武装 }` ——
**在跑的时候才重新武装，停着的时候什么都不做**；随后又无条件打印 `capture running`
（一句永远不会为假的"检查"）。

后果：`stereo_both.tcl` 结尾会停掉两路采集（它要静止帧来 dump 立体图对），
自那以后 `ps_run.tcl` 的每一次运行都**没把采集重新打开**，
PS 一直在渲染一帧静止画面 —— 而日志写着 "capture running"。

**是 1c 段的对照检查把它揪出来的**：对照（相机0）采样 0/32 在变 → 测量判为 VOID，
没有据此得出"相机1 坏了"的结论（这正是 M25 想防的事）。

修好之后：`capture before: CR=0x00010000`（停的）→ 重新武装 →
`CR=0x00010003 / SR bit0=0`；1c 段 `对照 22/32、相机1 20/32` 都在变。
新增的是**断言而不是说明文字**：武装后必须 `CR bit0=1 且 SR bit0=0`，否则整轮判失败。

### 10.3 顺带查实的两件事

- **`axi_vdma_2` 没有帧指针可用**：BD 里只把 `axi_vdma_0/s2mm_frame_ptr_out[0]`
  引到了 `axi_gpio_0` ch2 bit4；`vdma2_frmptr_probe.tcl` 又测了 S2MM 块
  0x38/0x3C/0x40/0x44/0x48/0x4C，**没有一个寄存器跟着帧存变**（对照位在跳，测量有效）。
  **所以画中画读固定帧存，可能有横向撕裂**；要根治得改 BD 引一根线 + 重新综合。
- **画中画逐字节校验还没做完**：`dl/verify_pip.py` 比对窗口与相机1 帧存，
  当前最好结果是 `4936/25560 精确相同，平均差 13`，错位一像素的错误映射是 4278 ——
  **区分度太弱**。原因是判据设计错了：dump 与"渲染那一刻"相差若干帧，静止场景也有传感器噪声。
  正确顺序是**先冻采集 → 让 PS 再画一帧 → 再停核**（这样参考帧与窗口必然逐字节相同），
  `ps_pip_dump.tcl` 已按此改好，但**还没跑成功**（见 10.4）。

**这次能到 100% 的原因**：`ps_pip_dump.tcl` 的顺序是"**先冻采集 → 让 PS 再画一帧 → 再停核**"。
旧顺序（先停核）让参考帧差了若干帧，同场景也有传感器噪声，只能到 19%——
数字看着像"窗口不是相机1"，其实是**参考帧不对**。

### 11.2 这一轮真正的根因：**别用 APU 容器去读内存**

症状很误导：`ps_run.tcl` 报 `PL looks unprogrammed`（读回全 `0xFFFFFFFF`），紧接着
`ps_pip_dump.tcl` 又判自己 VOID（冻结证明失败），看起来像"板子坏了/PL 掉了"。
量出来是另一回事（`board_state_now.tcl`，**同一个会话**里）：

| 走 **A9（按名字选中）** | 结果 |
|---|---|
| OCM `0x00000000` | `EA000006` = PS 程序入口字，**程序还在** |
| DDR0 / DDR1 | `F8F8FCF8`（两路相机实时帧） |
| PL `DIS CR` / `VDMA2 CR` | `0x00010003` / `0x00010003` → 两路都在跑 |

而**走 `targets -set 1`（APU 容器）读同样这些地址，全是 `0xFFFFFFFF`**。

于是两处修复：
- `ps_run.tcl` 顶部与 `ps_pip_dump.tcl` 顶部：**先按名字选中 A9**（`targets -set -filter {name =~ "*Cortex-A9*#0"}`），
  再做任何读写；选不中就 `FATAL` 退出，不再 `catch` 成一句 WARN。
- `ps_pip_dump.tcl` 的写入（停采集）此前发生在选目标之前 → `WM` 吞掉错误 →
  采集没停 → 冻结证明失败。这就是它自判 VOID 的原因。

**为什么之前没暴露**：历史上 APU 容器这条路能读。它现在不一定能——同一块板子、
同一天，前后两个会话行为不同。**容器不是核**，不要拿它当读数通道。

### 11.3 T22 的极端形态：根本没有可用的编号

断电重启后链路是正常的（`1=APU,2=A9#0,3=A9#1,4=PL`）。`stereo_both.tcl` 的
`rst -system` 之后 DAP 进入 `AHB AP transaction error, DAP status 0x30000021`：
**新会话里只有 `1=DAP(带该错误)` 和 `2=xc7z020`**，A9 只在"发出 reset 的那个会话"里出现，
且**编号变成 3/4**。此时项目里所有 `targets -set 1/2/4` 全部指错对象
（`2` 是 PL 而不是 CPU）。

新增 `stereo_bringup_byname.tcl`：与 `stereo_both.tcl` 同样的步骤，
但**一律按名字选目标**、必要时先做一次恢复 reset，并且**最后不停采集、不 dump 图对**
（`stereo_both.tcl` 停采集是为了抓静止图对——而正是"停着没被重新打开"让
ps_run 测了几小时的静止画面）。`stereo_both.tcl` 原样保留作参考。

## 十二、2026-10-16（第五轮）：画中画开销降 3 倍；撕裂**量出上限后决定不改 BD**

### 12.1 优化：步长 6 → 8 + 每像素一次字读

理由不是"更快"，而是**对齐**：源行步长 8 像素 = 24 字节，使每个取样点的源地址都是
4 字节的倍数，于是每像素从 **3 次非缓存字节读**变成 **1 次非缓存字读**。
几何随之变成 160x90 @ (473,266)（仍是精确 1/8，源码里没有除法）。

| | 优化前 | 优化后 |
|---|---|---|
| panel 相位 | 7.94 ms | **3.07 ms** |
| 画中画净代价（减 0.78 ms 基线） | 7.16 ms | **2.29 ms** |
| 整帧 / 帧率 | 67.4 ms / 14.84 fps | **62.2 ms / 16.07 fps** |

预测（跑之前写下的）是 2~3 ms 与 ~16 fps，实测 3.07 ms / 16.07 fps。
**回归检查**：`verify_pip.py` 仍报 `exact 14400/14400 (100.00%)`，
错位映射 18.18% —— 优化没有改变内容。

### 12.2 撕裂：先量，再决定花不花那半小时

`ps_live_snap.tcl` 是**只停核、不停采集**的快照（与 `ps_pip_dump.tcl` 相反：
后者先冻采集，因此**在构造上不可能出现撕裂**，它只能证明"窗口是相机1"，不能证明不撕裂）。

撕裂带宽 = 读窗口这段时间里采集前进的行数，所以两个量都要实测：

- 窗口读时间：来自 PS 自己的相位计时（上面那张表）
- 采集行速率：`ps_capture_rate.tcl` 数 `0x41200008` bit4（= `axi_vdma_0/s2mm_frame_ptr_out[0]`）
  的翻转 —— 实测 **18.24 帧/秒**、54.8 ms/帧、**13.13 源行/ms**

| 窗口读时间 | 撕裂带 | 占窗口 90 行 |
|---|---|---|
| 旧 7.16 ms | 94 源行 | 11.8 行（13%） |
| 新 2.29 ms | 30 源行 | **3.8 行（4%）** |

即：优化顺带把撕裂带也缩小 3 倍；仅"读与写重叠"的帧里出现（约一半）。
并且**当前场景是静止的**，`ps_live_snap.tcl` 的快照放大后看不到接缝
（`ps_ui/ui_live_window_zoom.png`）。

**决定：不改 BD。** 代价是改图 + 重新综合（约半小时）且有 B17 那类风险，
收益是消除一个 ≤4 行、静止场景下看不见的带子。**如果以后要拍有运动的演示**，
这就是要修的东西，修法已写明：把 `axi_vdma_2/s2mm_frame_ptr_out` 引到一个空闲探针位。

### 12.3 本轮新增文件

| 文件 | 作用 |
|---|---|
| `ps_fft_dual/ps_capture_rate.tcl` | 只读：用帧指针探针位实测采集帧率/行速率，并据此算出撕裂带宽上限 |
| `ps_fft_dual/ps_live_snap.tcl` | 只停核的**实时**快照（保留撕裂），与 ps_pip_dump 的冻结快照互补 |

## 十三、2026-10-16（第六轮）：把画中画改成**触屏切换的纯左/纯右两视图**

### 13.1 已经做成并验证的

- **视图切换**：屏幕显示**相机0（质检画面）**或**相机1（整幅 640x360）**，二选一。
  `MB_VIEW`(344) 是双向字：PS 每帧发布"我现在显示哪个"，**主机写 0/1 可强制切换**
  （这就是没有手指也能验证切换的方式，也是脚本切视图的接口）。
- **视图1 逐像素验证通过**：`230400/230400 = 100.00%` 与相机1 帧存逐字节相同，

- **判定不受显示影响**：`measure()` 与裁剪切点统计直接遍历 DDR 帧，切视图不改变判定。

### 13.2 触屏：**改完了接线，但面板依然不应答——这是电学问题，不是驱动问题**

做过的（都已入库）：

1. 侦察出触屏在**当前比特流里根本没有控制器**：`iic1_emio.tcl` 当初为了把 IIC_1 让给相机1，
   删掉了 `lcd_touch_i2c` 端口，并让 PL 的 `axi_iic`(`cam_iic_1`) 主接口**悬空**。
   实测：GT911 在 PS I2C0、PS I2C1、PL axi_iic 上**全都不应答**，而两颗相机在同一会话里都答
   （控制组有效）→ 属于"接线事实"，不是"驱动事实"。
2. `bd_touch_on_axi_iic.tcl`：**只增不减**地把 `cam_iic_1/IIC` 接到新建的 `lcd_touch_i2c` 端口，
   全程断言时钟网引脚数(51→51)与两条相机总线不变，验证查 ERROR 条数(0)后才保存。
3. XDC 补回 F20/F19 约束；**全量重建**；构建后核验引脚表：
   `io_placed` 里 `lcd_touch_i2c_scl_io = F20`、`lcd_touch_i2c_sda_io = F19`，LVCMOS33+PULLUP ✓。
4. `ps_ui/touch.c`：AXI IIC + GT911 驱动（寄存器位义取自 `xiic_l.h`，配置表与坐标解析取自
   早先**验证可用**的 `dl/ts_inspect_ui.c`）。

**结果：GT911 仍然不应答。** `axiiic_trace.tcl` 逐步追踪一次事务：
CR/DTR 能写能读回、SR 恒为 `0xC0`（= RX_FIFO_EMPTY|TX_FIFO_EMPTY，正确空闲态），
但设了 `CR=MSMS` 之后 ISR 全置位（含 `TX_ERROR 0x02`）——即**地址被 NACK**。
PS 程序发布的诊断也一致：`MB_TOUCH_PID = 0xEEEEEEEE`（传输本身失败，无 ACK）。

**这与项目自己的历史一致**：当初第二路相机用 axi_iic 时也是"读不到任何器件"，后来换到 PS I2C1 才好。
**所以 axi_iic 这条路从来没有被证明能用过。**

**下一步（需要电学手段，不是改代码）**，按优先级：

1. 确认 GT911 的**复位是否被释放**、面板供电是否正常（ALINX `28_lcd7_touch` 例程里触摸复位是否由 FPGA 控制）；
2. 用示波器/逻辑分析仪看 F19/F20 在发起事务时**有没有波形**——有波形而 NACK，器件侧问题；没波形，IP/IOBUF 侧问题；
3. 项目曾用 `axi_gpio_0` ch2 的探针位把 I2C 总线引出来看过（`bd_add_i2c_tap.tcl`，后被 `bd_revert_i2c_tap.tcl` 撤掉）；
   若要走这条路，重新加回探针比猜寄存器快；
4. 另一种架构选择：**给触摸单独例化一个 AXI IIC**（现有一个从未验证过），或把触摸与某路相机**电气合并到一条 I2C**（需要改板/跳线）。

**注意**：`MB_TOUCH_*` 的语义是分开的，别把它们混成"触摸坏了"：
`MB_TOUCH_OK`=1 才是"面板报出了 id 911"；`PID=0xEEEEEEEE` 是"传输失败"；`PID=0` 是"传了但读到 0"。

### 13.3 其它改动

- `mmu.c`：相机1 帧存 `AT_NC → AT_WBWA`（**可缓存**）。理由：整幅 640x360 走非缓存读约 35 ms，

  （CPU 从不写这块，所以只需 invalidate）。忘了会**冻结**而不是报错——契约写在映射处与读者处两遍。
- `main.c`：5x7 字库**没有 W 和 Z**，所以按钮文案避开了这两个字母
  （第一版 `CAM1 VIEW` 渲染成 `CAM1 VIE`）。
- `ps_run.tcl`：把主机实测 fps 写进面板字（面板的帧率本来就是主机写的；不写就永远显示 00.0）。

## 十四、2026-10-16（第七轮）：缩略图不是"板子在显示"、网页实时画面、以及一次我自己做坏的 BD

### 14.1 屏幕全黑的真因：`v_tc` 从没被配置（**已在 13 之前修好，这里补记**）

重烧 PL 会把 `v_tc` 复位成**关闭**。引导脚本（照抄 `stereo_both.tcl`）只配相机与显示 VDMA，
**从没配 v_tc** → 没有时序输出 → 没人消费显示 VDMA 的流 → 通道报"运行中"而整帧永不完成 →
面板全黑。**而 DDR 里的画面一直完全正确**，所以那几张截图看起来完美。

| 判据 | 修前 | 修后 |
|---|---|---|
| 显示通道 `SR` 的 `IOC`（bit12） | **6 次读全 0** | **8/8 置位** |
| `v_tc` `CTRL` | `0`（关闭） | `0x03F7EF06` |
| `v_tc` `HORIZ`/`VB` | — | `0x420` / `0x01F901F9`（写入已核验） |

**教训**：截图是 DDR 的转储，它证明不了面板收到任何像素。
`display_check.tcl` 就是为这件事写的只读体检（CR/SR/几何/被扫描帧存内容/IOC）。

## 十六、2026-10-16（第九轮）：**触摸面板是好的；坏的是 PL 的 axi_iic 主机**

### 16.1 决定性实验做成了：GT911 活着，接线也对

断电重启后（这次**没有做 `rst -system`**，直接停核就读到了 OCM，DAP 没坏），
`vendor_touch_test.tcl` 烧**厂商自己的比特流 + 它 XSA 里提取的 ps7_init**（其触摸走 PS I2C0→EMIO→F20/F19），
从 JTAG 读：

| 探测 | 结果 | 含义 |
|---|---|---|
| `I2C0 @0x5D reg 0x8140` | **`0x39`（'9'）** | **GT911 产品 ID "911" 的第一个字符 → 面板与接线都好** |
| `I2C0 @0x14` | 无应答 | 符合预期（非该地址） |
| 控制：`I2C0 @0x3C`（相机地址） | 无应答 | 总线上确实没有相机 → 上一条不是幻觉 |
| 控制：`I2C1 @0x3C` | 无应答 | 厂商设计不用 I2C1 |

**结论**：面板、GT911、F20/F19 接线、以及我们用的协议与地址（与厂商同源）**全部正确**；
**唯一坏的是"让 PL 的 axi_iic 当 I2C 主机"这条路**。

### 16.2 交换实验：做了、测了、**不可行、已回退**

`bd_swap_touch_to_ps_i2c.tcl`（只动两条点对点网、每步断言时钟网与端点数、ERROR 0 才保存）：
触摸回到 **PS IIC_1**，相机1 改挂 **axi_iic**。重建后第一件事就是问 axi_iic 要**相机1 的已知 ID**：

```
0x300A -> tx_error IISR=0xFF        (want 0x56 0x40)
```

**axi_iic 连一个已知答案的器件都读不到。** 于是交换不可行（相机1 的 303 条配置表会永远写不进去），
已用 `bd_swap_touch_back.tcl` 回退并重建。

### 16.3 为什么 axi_iic 不工作：FIFO 与引擎是活的，**但总线从未真正被驱动**

一次只读的寄存器实验（`axi_iic_cam1_test.tcl` + FIFO 测试）：

- 写 DTR 后 **`TFO` 变成 1**（FIFO 收下了数据），随后被排空 → 引擎在跑、FIFO 没问题；
- 但 **`SR` 的 `BUS_BUSY` 恒为 0**：**总线从来没有忙碌过**；
- 器件侧从此收不到任何东西，IP 报 `TX_ERROR`（NACK/仲裁类）。

**这三条放在一起只支持一个解释：IP 没有真正把 SCL/SDA 驱动出去（引脚一直高阻）**，
于是它自己看到的是"线被上拉为高"→ 发不出 START → 报错；而相机/触摸什么都没看到。
BD 层面的接法（`cam_iic_1/IIC` **Master** ↔ `cam_iic_1_io` **Master**）与厂商
`lcd_i2c`↔`IIC_0` **完全同型**，接口网也是完整打包的，**所以从这个层面看不出 `_t`（三态控制）
是否接对**——再往下需要 **ILA 抓 `_o`/`_t`/引脚电平**或示波器。

### 16.4 触屏剩下的路（按性价比）

1. **ILA 抓 axi_iic 的 `scl_o`/`scl_t`/`sda_o`/`sda_t` 与端口电平**，发一次事务看它们动不动。
   设计里本来就有 ILA（`analyzer_fe`、`capture_ram`），加探针比猜快。这是**唯一还缺的一块证据**。
2. 若 `_t` 确实没接对 → 属于 BD 级修复（可能只需重连接口或换一种端口模式）。
3. **换一个新的 AXI IIC 实例**接到触摸（现有一个可能是某个配置坏掉，但我们没找出是哪一项）。
4. 极端方案：把**相机1 的 I2C 彻底去掉**（若不需要第二路画面）来腾出 PS I2C1 给触摸——

**在触摸解决之前，可交付的替代**：视图切换已可用且可脚本化（主机写 `MB_VIEW`；

## 十七、2026-10-16（第十轮）：屏幕"撕裂 / 帧率低 / 频闪"三条定位（**结论未全部验证**）

用户报告：画面变化时有撕裂、帧率很低、有频闪。先量了链路本身（都正常）：

- `v_tc`：`CTRL=0x03F7EF06`、`GASIZE=0x01E00320` ✓（时序在发）
- 显示通道：`CR=0x00010003`、`SR=0x00011000`，**`IOC` 连续 3 次读都置位**（整帧持续完成），
  无 Idle/Halted ✓
- 设计里**没有 dynclk**（`0x43C10000` 读回 `0xFFFFFFFF`），所以 `official_lcd_run.tcl`
  里"重编像素时钟到 33.33 MHz"那一步**在这个设计上不适用**，不是本症状的原因。

### 17.1 频闪：**最可能是"不合格"红底在按帧率闪**（高度怀疑，代码级可修）

`main.c` 里 `draw_panel()` 的 NG 分支：`if (g_alarm_blink & 1u) { 画红底 }`，
而 `g_alarm_blink` **每帧 +1**。当前渲染率 ~15 fps → 红底以 **~7.5 Hz** 闪烁。
而当前场景判定就是"不合格"（`GATE=1`，饱和告警）——所以操作员看到的就是**持续的频闪**。
**修法**（便宜、风险低）：把闪烁改成按时间（例如 0.5 s 翻转一次，约 1 Hz），或直接改成常亮色块；
对操作性屏幕来说，7.5 Hz 闪烁本身就是不合格的设计。

### 17.2 帧率低：**渲染 87% 的时间花在 `draw_camera`**（实测过）

相位计时实测：`draw_camera` ≈ **53–55 ms / 61–67 ms**（约 87%），整帧 15–16 fps。
其中**双曝光融合在当前场景是空转**：项目早先实测 `recovered under full scale = 0（0.00%）`
（6.5× 的短曝采样对每一个过曝通道都仍然过曝，钳位后与长曝一致）。
而 `g_bracket_on == 0`（单曝光）时融合本来就无意义，却仍在跑。
**修法方向**（需要实测确认收益）：单曝光模式下走"2×2 箱式 + 色调表"的直通路径，跳过短曝解包/融合；
或把渲染降到半分辨率。**改前先写下预测，改后看相位计时的 `cam` 分量。**

### 17.3 撕裂：**怀疑单曝光模式读的是"固定帧存"，而采集在两块之间交替**

`main.c` 在单曝光模式下把 `g_long_buf` 固定成 `CAM_BUF`（只有 bracket 模式才按帧指针切换）。
而采集 VDMA 在两块帧存之间交替 → **约一半时间 PS 读的正是正在被写的那块** → 图像顶部/中部错位
（撕裂）。**修法**：单曝光模式也用 `axi_gpio_0` ch2 bit4（`s2mm_frame_ptr_out[0]`，`CAP_FRPTR`）
选"当前完整的那块"，与 bracket 路径同一套逻辑。

**注意**：17.1 可以说是"已定位"；17.2/17.3 是**基于已有实测与代码阅读的推断，尚未验证**。
按项目纪律，改任何一条之前先写下预测（`cam` 相位毫秒数、撕裂是否消失），改完只对照那个量。

### 18.3 顺带量到的一条设计级事实（**不要盲改**）

`FPGA0_CLK_CTRL (0xF8000140)` 当前 = `0x00003C01`（分频 60、源 IO PLL 1000 MHz）⇒ **FCLK_CLK0 ≈ 16.7 MHz**；
而 BD 里 `cam_iic_1`（axi_iic）的配置写着 `AXI_ACLK_FREQ_MHZ = 50.0`。
我们的 `ps7_init_cdcfix_50m.tcl` **从不写这个寄存器**（厂商那份写 `0x00100801` ⇒ 125 MHz）。

⇒ PL 的 AXI 带宽可能是**整个显示/采集链路的瓶颈**（采集 1280×720 每帧 2.76 MB ≈ 33 MB/s，
显示再读 1.15 MB/帧；16.7 MHz 下 32 位 AXI 的理论上限约 66 MB/s，已经接近饱和）。
这**可能就是"帧率低/撕裂/频闪"在硬件层的根因**，但像素时钟由 FCLK0 经 MMCM 倍增而来，
**直接提高 FCLK0 会改掉 LCD 时序**，必须先弄清 MMCM/时钟树再动。

### 18.4 三条量具教训（都是这一轮踩的，代价是几小时的错误结论）

1. **CPU 运行时 `mrd` 会间歇失败并返回 -1。** 把 -1 当值读，就会看到"帧计数 185 → 14"、
   `frames: -1 -> 44 -> -1`，于是得出"程序在自我重启"的结论——**它根本没重启**。
   所有在跑的板上读数必须**重试**，并且**把重试/失败次数打印出来**（`ps_phase_measure.tcl`
   与 `ps_ab_lr.tcl` 现在都这么做，输出里的 `READ HEALTH` 就是它）。
2. **`MB_T_*` 是"每 32 次循环的窗口和"，必须除以同一窗口的 `MB_T_N`。** 把窗口和当累加和、
   或把两个时刻的值相除，会得出 53/120/391 ms 三个互相矛盾的"cam 相位"。
   `ps_phase_measure.tcl` 现在**先读 N、读和、再读 N，两次一致才采纳**。
3. **别用 JTAG 采样率不够的工具去量快信号。** `ps_capture_rate.tcl` 自己写着"必须远慢于 7/s，
   否则是混叠"，而它正是在 3 Hz 上用了 7 Hz 采样。要么提高采样率（PS 紧循环），
   要么承认这个数不可用——**不要**在它上面建结论。
4. 顺带：`ps_ui.bin` 未被 git 跟踪，我用 `git show ...:ps_ui/ps_ui.bin` 重定向得到**空文件**并覆盖了它；
   ELF 是跟踪的，A/B 应用 `dow` 装载 ELF（`ps_ab_lr.tcl` 即如此），不要靠拷贝 bin。

## 十九、2026-10-16（第十二轮）：**FCLK_CLK0 只有设计值的 1/3** —— 一个统一的候选根因

| | 值 |

| BD `PCW_FPGA_FCLK0_ENABLE` | 1 |
| BD `PCW_FPGA1_PERIPHERAL_FREQMHZ`（FCLK_CLK1） | 33 |
| **实测 `FPGA0_CLK_CTRL (0xF8000140)`** | **`0x00003C01`** = 分频 60、源 IO PLL 1000 MHz ⇒ **16.67 MHz** |

**为什么：我们那份 `ps7_init_cdcfix_50m.tcl` 从不写 `F8000140`。** 而 `rst -system`（以及断电）
会把时钟单元复位到默认值，`ps7_init` 不写它就等于放任。厂商那份 `ps7_init` 是写的
（`0x00100801` ⇒ 125 MHz）—— 也就是说，**触摸调查中跑厂商 `ps7_init` 的那次，
FCLK0 一度是 125 MHz**，之后的复位又把它打回 16.67 MHz。

### 19.2 这条时钟挂什么（BD 里逐个 consumer 查出来的）

- **FCLK_CLK0（应 50 MHz，实 16.67 MHz）**：`ps7_0_axi_periph` 全部 M00–M08、**三个 VDMA** 的
  `m_axi_*_aclk` 与 `s_axi_lite_aclk`、**两个 DDR HP 端口**、`v_tc_0/s_axi_aclk`、`axi_gpio_0/1`、
  **两个 `alinx_ov5640` 的 `m_axis_video_aclk`**、`ts_cnn_top_0/ap_clk`、**`cam_iic_1/s_axi_aclk`（那个 axi_iic）**、
  `mem_intercon_cap`/`mem_intercon_disp`、`capture_ram_0`、`proc_sys_reset_0`。
- **FCLK_CLK1（33 MHz）**：`v_axi4s_vid_out_0/aclk`、**`v_tc_0/clk`（时序发生）**、
  显示 VDMA 的 `m_axis_mm2s_aclk`、`rst_33M`、`inv_lcd_pclk`、`clk_probe_cnt` —— **LCD 时序只挂这条**。

⇒ **把 FCLK0 恢复成 50 MHz 不会碰 LCD 时序**，却能让整条 AXI 数据通路快 3 倍。

### 19.3 为什么这条值得优先试（统一解释多个现象）

若整条 AXI 通路真的只有 1/3 时钟，那么下面这些**一直是同一个原因**：

1. **帧率/撕裂/频闪**：采集 1280×720 每帧 2.76 MB（≈33 MB/s）＋显示读 1.15 MB/帧，
   在 16.7 MHz 的 32 位 AXI 上（理论上限 ≈66 MB/s）**已经接近饱和**；CPU 的 DDR 流量
   与 PL 的 HP 端口流量共享 DDR 控制器，因此被拖慢（实测 `draw_camera` 有时 391–565 ms）。
2. **axi_iic 从来没成功过**：该 IP 的配置写着 `AXI_ACLK_FREQ_MHZ = 50.0`，
   而它一直在 16.67 MHz 下跑 ⇒ SCL 实际 ≈33 kHz（而非 100 kHz），
   且 IP 内部状态机（TX_EMPTY 处理、启动延时）全部按 50 MHz 设计。
3. 采集通道偶发的 `DMAIntErr`。

**这条把"触摸"和"显示三症状"两件事合并成一个根因候选**，而且**修复只需一条寄存器写**。

## 二十、2026-10-16（第十三轮）：性能塌陷的排查、"量具先验证"的两处教训、以及把调试链路弄卡的那个形状

### 20.1 我犯的三个方法论错误（评审指出，我接受并已改）

1. **没有先问"16 → 1.4 fps 是哪一刻发生的"**，而是拿"今早 15.2 fps"当基准、从底部枚举原因。
   重建的时间线：**15.15 fps 出现在 ~13:37**（交换—回退重建后），**第一次变慢在 ~14:26**；

2. **把 1675 ns 这个 25 倍的异常直接当地基**去推硬件，而没先校正量具。补做之后（见 20.2）
   结论是"量具没问题、异常是真的"，**但流程本身当时是错的**：应先做已知答案对照。
3. **补上了更致命的一处**：`global timer` = CPU/2，**tick 是 CPU 派生的**，所以**任何 tick 计时的量

   我们 `ps7_init` 之后才是 40（334.8 MHz）。用固定值会在 A/B 之间**制造**出 1.5 倍假效应。

### 20.3 关键观察：**同一天同一套文件，不同上电给出快/慢两种状态**

|---|---|

| 第 2 次 | **慢**：引导+装程序后 **1.79 fps** |

⇒ 这**不是任何可编辑文件**造成的（已逐条排除：我的代码、比特流、`ps7_init` 内容、PS 时钟、
MMU/cache、看门狗、FCLK0、PL 流量、等帧、曝光、显示读带宽），而**指向"上电时 DDR/PS 初始化"本身**。
**尚未与另一条假说分开**：第 1 次与第 2 次之间跑过**厂商的 `ps7_init`**，而 Zynq 的 DDR **只在上电时

### 20.4 **把调试链路弄卡的那个形状**（两次都是它）

**在 CPU 正在运行程序时执行 `fpga -file`（重配 PL）。** 引导脚本一直是
`halt → fpga → ps7_init → dow → con`，从未出问题；而我写的冷启动脚本把 `fpga` 放在了停核**之前**，
两次都把 PS 的 APB 访问打成 `0xFFFFFFFF`（只能断电恢复）。**规则：烧 PL 之前必须先停核。**
另外：**停不住核就地放弃，不要重试**（重试是第二次卡死的直接动作）。

### 20.5 断电后的执行顺序（两条路，各要一次上电）

- **上电 #1（量"冷态"）**：`ps_boot_probe.tcl`（只读）→ `ps_cold_state.tcl`

## 二十二、2026-10-16（第十五轮）：**触屏做通了** —— GPIO 软件位翻转

### 22.1 结论

**GT911 现在正常工作**：启动时报出产品 ID **"911"**（`MB_TOUCH_PID = 0x39313100`），
每帧轮询 10 秒 **零 I2C 错误**，184 字节配置表写入成功，无触摸时状态寄存器 `0x814E = 0x00` ✓。

### 22.2 为什么是位翻转（一条把 IP 判死的证据）

PL 的 `axi_iic` 被逐项检查后**否证**：
- 它**确实在驱动总线**（能报 NACK 就意味着它驱动并观察了总线）；
- 它的 **IOBUF 三态接对了**（综合后网表：`T <- scl_t/sda_t`）；
- 它的引脚就是厂商验证过的 F20/F19，地址 `0xBA` 与寄存器指针 `0x81 0x40` 与厂商驱动一致；
- 却在 **100 / 50 / 32 kHz** 三档、对 **GT911、相机1 的已知 ID、以及一个总线上根本不存在的地址**
  给出**同一个结果：NACK**。

> **对"存在的"和"不存在的"都给 NACK ⇒ 是它的应答检测坏了，不是器件不答。** 这不在 IP 外面能修。

⇒ 把这两根引脚交给**一个 2 位双向 AXI GPIO，由 PS 软件位翻转**：每一次边沿、每一个 ACK 都是我们自己的代码。

### 22.5 这一轮的两条新教训

1. **读"活着的"寄存器会得到撕裂值。** `PARK_PTR` 在 0x00000001 与 0x00010001 之间交替（bit16 跟着 bit0），
   而我第一版 `ps_view_dump.tcl` 拿整字去比 0/1 ⇒ 报出 `PARK_PTR=65537 is neither store`，
   **看起来像硬件故障，其实是我的判据太严**。已改为掩码 `& 0x1F`（两个转储脚本都改了）。
2. **脚本在 dump 前 FATAL 时，旧文件会被当成结果。** 那次 `verify_view.py` 报 6.09% 与 5.94%，
   是它读了**上一轮的 `ui_view.bin`**。判据要能区分"这次真的转储了"——转储脚本的
   `dumped N bytes` 行必须出现，否则结论无效。
