## 2. 三个真病灶（全部有测量支撑）

### ① arm 太慢 ⇒ 根本没有配对
`i2c_gap()` 原为 1.4M 次循环（注释写 2 ms，实测 15–20 ms），一次 arm = 6 次 gap
≈ 100–120 ms，而捕获周期 103 ms ⇒ 每 3 帧才换一次曝光 ⇒ 两个 store 永远同曝光。
证据：融合开启时 12 次相干快照 ratio = 1.00–1.25，并随相位一起在 17 与 4–5 之间翻。
旧记录"融合输出 MEAN=5"= 采样正落在两 store 都是短档的相位。
修：`i2c_gap()` 改为 GTIMER 计时 2.5 ms。

### ② 多字节 I2C 写会污染别的寄存器
为提速把曝光写成 5 字节单事务、VTS 写成 4 字节单事务。**回读是对的**，但随后
相机 0 的 VTS 变成 `0x3501`、相机 1 的 VTS 变成 `0x3500`——正是这两个写事务的
**指针字节**。说明这套手写轮询 I2C 不能保证每次都以 STOP 结束传输，传感器会
沿旧指针继续写。
后果：VTS 13569 行 ⇒ 捕获掉到 ~1 fps，且相机 0 卡死（软复位/重写表都救不回，
最后靠完整引导里**脉冲相机复位线**才恢复）。
修：**所有写回到 3 字节**（曝光 2–3 次写 + 0x3500 不变则不写；VTS 两次 `cam_write`）。

### ③ arm 在帧内的位置漂移 ⇒ 有些帧拿到上一档曝光
arm 原来放在渲染之后，位置随渲染耗时在 82–116 ms 之间移动（帧长 105 ms）。落到
下一帧起点之后就等于"这一帧还是上一档"⇒ 两 store 相同 ⇒ 渲染落到短档。
证据：`MB_MEAN_RENDER`（新增）显示屏上亮度在 23 与 77 之间跳，12 次采样离散 **54**；
约 40% 的帧 ratio=1.0。
修：arm 固定在**交班后 25 ms**（`wait_ticks`，占帧内 25 ms，由 sync 的等待吸收）。
结果：ARM_DT 稳定 106.7 ms、配对 12/12、屏上亮度离散 **1**。

## 3. 仍未解决：高光救援

- 当前 `CLIPLONG = 6.4%`、`RECOVER = 0`：短档把被截顶的通道乘 6.5 后仍 >255，被钳回。
- 原因：**两档的有效亮度比只有 3.3**，而按曝光比 6.5 设计要求 ~6.5。
  候选原因（**未验证**）：
  - `0x3503` 只置了 bit0/bit1（AEC+AGC 手动），传感器可能仍有部分自动增益；
  - 长档 10000 行可能受帧长限制（VTS 1450）而被钳，短档 1538 也接近该上限；
  - 当前场景本身偏亮（MEAN 79、CLIP 6.4%），两档都挤在高光端。
- **下一步判定实验**：单变量扫短档（1538 → 800/400/200），看 `RECOVER` 与
  `CLIPLONG` 是否随之变化；若比例升到 ~6，则 1538 只是"太接近长档"；若不变，
  说明增益/钳位仍在起作用，需要读 `0x350B` 在两种相位下的值。

## 5. 方法学备忘（本轮踩到、值得写进案例集的）

- **"值回读正确"不等于"这一次写没有伤到别处"**：多字节写回读全对，别的寄存器却被写串。
- **手写 I2C 轮询不能假设 STOP 一定发出**；能写 3 字节不代表能写 4/5 字节。
- **屏幕亮度要用快采样测**：一次 `ps_live_dump.tcl` 要 7 秒，对 5–10 Hz 的摆动完全是
  混叠；改为让程序发布 `MB_MEAN_RENDER`，250 ms 一次相干采样。
- **一个计数器读数是焦点值**：`MB_ARM_N` 曾与 `MB_FOCUS` 撞在 135 号字。
